# CLAUDE.md

corrallm is a cross-platform Electron desktop app (Electron Forge + Vite + React + TypeScript). It will become an agent orchestrator that spawns and manages the Claude Code and Codex CLIs as child processes. Today it has a canvas of agents in the renderer (`src/renderer/graph/`), each opening into a Claude Code-style session (`src/renderer/agent/`); canvases saved as `.corral` files over the `canvas:*` IPC channels, with a project folder their agents work in. A Claude agent runs the real `claude` CLI, in a Terminal or through the Agent SDK (see Connected sessions): a Terminal agent runs Claude Code's own interactive CLI in a node-pty pseudo-terminal, shown in its agent view with xterm.js (`src/main/sessions/claude-code/`, on the toolkit in `sessions/terminal/`); an Agent SDK agent runs a Claude Code session through the Agent SDK, shown in corrallm's own transcript and composer (`src/main/sessions/claude-code/sdk/`). A Codex agent runs the real `codex` CLI (`src/main/sessions/codex/`, see Codex): in a Terminal, Codex's own interactive CLI on the same terminal plumbing (`src/main/sessions/codex/terminal/`), or through its app server, shown in corrallm's transcript (`src/main/sessions/codex/app-server/`).

## Commands

Requires Node 24.21.0 (`.nvmrc`) and pnpm 12.11.2 (`packageManager`).

| Command            | Purpose                                                                                                                                           |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm dev`         | `electron-forge start`: Vite dev server + HMR; press `r` in its terminal UI after main-process changes                                            |
| `pnpm typecheck`   | `tsc -b` over the solution (node, web, tooling projects)                                                                                          |
| `pnpm lint`        | ESLint, type-aware, zero warnings allowed (`lint:fix` to autofix)                                                                                 |
| `pnpm format`      | Prettier write (`format:check` to verify)                                                                                                         |
| `pnpm test`        | Vitest: `main`, `preload` (Node) and `renderer` (jsdom) projects                                                                                  |
| `pnpm test:e2e`    | Playwright; its global setup first builds the app unsigned (`electron-forge package`) and the CLI                                                 |
| `pnpm package`     | Packaged app for the current OS in `out/`                                                                                                         |
| `pnpm make`        | Installers for the current OS in `out/make/`                                                                                                      |
| `pnpm build:cli`   | The `corrallm` CLI for plain Node (`vite.cli.config.mts`) in `dist-cli/corrallm.cjs`                                                              |
| `pnpm corrallm`    | Runs the CLI bundle: `serve`, `wait` (see Headless) or the self-test (`scripts/corrallm.mjs`; it says to run `pnpm build:cli` when it is missing) |
| `pnpm api:surface` | Writes `src/shared/api/surface.snap.json`, every party's surface, after the registry changes                                                      |

- Run one Vitest project with `pnpm exec vitest run --project main`.
- `E2E_SKIP_BUILD=1 pnpm test:e2e` reuses the existing production build in `.vite/` and the CLI bundle in `dist-cli/` (note `pnpm dev` overwrites `.vite/`). Headless Linux: `xvfb-run -a pnpm test:e2e`.
- `CORRALLM_CLAUDE_PATH=/path/to/claude` makes connected agents run that `claude` instead of the user's own, and only that one: the core looks nowhere else, even if nothing can run there (the e2e tests point it at a fake: `e2e/fake-claude.mjs` for Terminal agents, `src/main/sessions/claude-code/sdk/fake-claude.mjs` for the Agent SDK). `CORRALLM_CODEX_PATH` does the same for `codex`. Set empty, the user's own are found as usual.
- `CORRALLM_DISTRIBUTION=commercial` (or `hosted`) when building (`pnpm package`, `pnpm make`) makes a build for a commercial or hosted product, whose App Server connection refuses a ChatGPT login (see Codex); the default is `local`.
- Packaged-app native check: after `pnpm package`, run the app binary with `CORRALLM_NATIVE_SELFTEST=1` (e.g. `CORRALLM_NATIVE_SELFTEST=1 out/corrallm-darwin-arm64/corrallm.app/Contents/MacOS/corrallm`). `runNativeSelfTest` (`src/main/native-selftest.ts`) runs `src/main/core/selftest.ts`'s checks in main, then forks the core process (`core.cjs`, an Electron utility process: `host/core-process.ts`) and asks it over CoreLink to run them there too, printing how soon it was ready after the fork and its memory. The checks (Electron-free): a shell that exits in a node-pty pseudo-terminal (through `spawnPty`, as Terminal agents run); a terminal screen copy (@xterm/headless and its addons) reads a status report and snapshots; the bundled Agent SDK (its `import.meta.url` define, its spawning) runs a query against `src/main/sessions/claude-code/selftest-claude.mjs`, a tiny fake `claude` bundled as text (`?raw`, typed in `src/main/raw.d.ts`) only for this, written to a temporary folder and run with the `node` on the PATH (no login); the core's database (`core/store/`, through Node's built-in `node:sqlite`) opens in a temporary profile as the core opens it, and reports SQLite's version, WAL, `synchronous=NORMAL`, on macOS `fullfsync`, its other pragmas as it sets them (naming one that isn't), a write through its lane (its log flushed on Node's thread pool) read back by a read-only connection, a checkpoint on its checkpointer's worker thread, which begins the log anew there, a snapshot (SQLite's backup, on Node's thread pool) read back, and (but on Windows) `core.db`, `-wal` and `-shm` at 0600, then the profile is removed; a loopback HTTP server is called; a shell is spawned; and, packaged, `child_process.fork` throws (the RunAsNode fuse). It exits 0 on success, 2 if a check fails (saying which) or the core process does, 3 on a timeout, 4 on an uncaught error. CI runs this on all three OSes; `scripts/check-linux.sh` runs it (and the launch-switch checks, and the CLI's) for Linux arm64 in Docker; `src/main/core/selftest.test.ts` runs the checks in the unit tests, and `e2e/selftest.e2e.ts` runs the unpackaged build's in main and its core process. `CORRALLM_NATIVE_SELFTEST=1 pnpm corrallm` runs them under plain Node, in the CLI bundle (built by `pnpm build:cli`), exiting the same way.

## Testing

- Test-driven by default. For a bug, first write a test that reproduces it and fails, then fix it, then confirm the test passes. For new behaviour, write the tests with (or before) the code.
- The test suite is the regression guard, not ad-hoc review. Keep tests robust and meaningful: assert behaviour users or callers rely on, not incidental details. Prefer unit tests for logic, and add Playwright e2e only for what needs the real app (pointer interactions, CSP, packaging).
- Tests never run the real Claude or Codex. `launchApp` (e2e/launch.ts) points `CORRALLM_CLAUDE_PATH` and `CORRALLM_CODEX_PATH` at nothing unless the test gives a fake, so the app finds neither CLI (nor offers them as installed, `catalog.installed`) by accident. Main's session tests use the fake connector (`src/main/sessions/fake.ts`, one per CLI), and so do the core's engine and message tests (`core/engines.test.ts`, `core/messages.test.ts`); the engine's and the renderer's tests a fake backend (`src/shared/engine/test-backend.ts`), and e2e runs the app with `CORRALLM_FAKE_SESSIONS=1` (`launchApp({ env })`; honoured only by unpackaged builds), which gives each CLI's connections a fake connector. A connector's own tests drive a fake CLI that prints the real one's formats.
- The Agent SDK connector's tests replay what the real CLI did (`src/main/sessions/claude-code/sdk/fixtures/`, recorded with Haiku in a scratch folder, its paths and the user's own skills and servers taken out) and drive the real SDK against `sessions/claude-code/sdk/fake-claude.mjs`; e2e (`e2e/sdk.e2e.ts`) points the built app at it with `CORRALLM_CLAUDE_PATH`. With `CLAUDE_CONFIG_DIR` set (only then, so it never writes into the user's own `~/.claude`), the SDK fake keeps its conversations' transcripts there as the CLI does, so the SDK's session functions (listSessions, getSessionMessages, forkSession) read them: `sdk/cli.test.ts` and `e2e/sdk.e2e.ts` point it, and main, at a throwaway folder. It takes the SDK's flags as the SDK passes them (`--flag=value`), really edits the project's notes.txt ("edit"), and with file checkpointing on keeps it as it was before each message, for `rewind_files`. Both fakes answer `claude auth status --json` as the real CLI does: a Claude subscription unless their environment has an API key (the SDK one also takes a cloud provider, or an apiKeyHelper in the project's settings), so tests of a working SDK session give the agents a fake ANTHROPIC_API_KEY. On a machine logged in only with claude.ai, the real Agent SDK connection refuses to start: check it live that way, with no prompt, and use Terminal for live checks. To record new fixtures, run a few tiny prompts through the SDK in a throwaway folder, never a real repository, and keep the same sanitizing.
- The Terminal connector's unit tests run `sessions/claude-code/fake-claude.ts` behind a fake pty, and `e2e/terminal.e2e.ts` runs the real connector with `CORRALLM_CLAUDE_PATH` pointing at `e2e/fake-claude.mjs` in a real pty (it logs what it gets in the project folder, since the terminal draws its text on a canvas; its `--help` lists `--effort`), and with `CLAUDE_CONFIG_DIR` a throwaway folder, so the user's own settings are never read.
- Codex: what the real CLI did is recorded in `sessions/codex/app-server/fixtures/` (its app server's JSON-RPC, both ways, with timestamps: the handshake, models and limits; three turns with a command, an approval, plan mode, `thread/read`; and, recorded through corrallm's own App Server session, a patch and a command with /diff, /status, /mcp and /skills, an interrupt, a pasted image, a resume with its history and /compact; and, as asked for an agent's settings, config/read and model/list, `options`: the connector's tests replay these through `replay.ts`, which fails on any request the recording did not make) and `sessions/codex/terminal/fixtures/` (its TUI in a pty: everything it printed, its window titles, the hooks it posted, the keys sent; two sessions of prompts, one of them corrallm's own (`turns`: an approval and an interrupt, with no view, so its composer is unshaded), a resume, and a resume of a missing session; `recorded.ts` reads them). They were recorded with Codex CLI 0.160.1 and GPT-6-Luna (low effort) in a scratch folder, paths, names, account and the user's own MCP servers replaced with stand-ins of the same length. `sessions/codex/fake-codex.mjs` is a fake `codex` (`--version`, `app-server`: what a message starts with makes it run a command, patch, ask, plan, fail or crash; it keeps threads in `FAKE_CODEX_STATE` to resume them, and is logged in as `FAKE_CODEX_LOGIN` says: an API key, ChatGPT or none) in the same shapes; tests run it with node, and `e2e/app-server.e2e.ts` runs the built app against it (`CORRALLM_CODEX_PATH`).
- The Codex Terminal connector's tests replay those recordings into a real Terminal session (`codex/terminal/session.test.ts`: each pty plays one back, in order, waiting wherever keys were sent until the session sends the same), and `e2e/codex-terminal.e2e.ts` runs the real connector with `CORRALLM_CODEX_PATH` pointing at `e2e/fake-codex-tui.mjs` (Codex's TUI in its real formats, running its `-c` hooks as Codex does, only if trusted as Codex trusts them; its app server answers hooks/list, account/rateLimits/read, model/list and config/read) in a real pty.
- Renderer and engine tests read the catalog the core builds (see The catalog) from `src/shared/test-catalog.json`: `src/renderer/test-setup.ts` loads it as the app does before it mounts, and the engine's tests read it, with the lookups the app gives the engine, from `src/shared/engine/test-engine.ts` (shared code, tests included, never imports the renderer). It is a copy, never edited by hand: `src/main/sessions/adapters.test.ts` keeps it equal to main's catalog (a vitest file snapshot), and rewrites it with `pnpm exec vitest run --project main -u src/main/sessions/adapters.test.ts` when a descriptor changes (prettier leaves it alone). What reads the catalog it is given (the engine: the run, the sessions, the words they share) is also tested over `src/shared/test-made-up.ts`, a catalog of an adapter no build has, which the loaded one lacks.
- Every test file that makes a run makes it with `liveRun` and checks, after each test, that it restores from its checkpoint as it was (`afterEach(expectRestorable)`, `src/shared/engine/run/test-restore.ts`): whatever a run holds, its checkpoint keeps, since the core journals it. The run's tests share a harness (`run/test-run.ts`: a run with its clock and its agents' turns under the test's control), and so do the built-in templates' run tests, which stay with the templates (`src/renderer/graph/templates-run.test.ts`).
- jsdom cannot draw xterm.js: renderer tests that show a Terminal agent mock `src/renderer/terminal/screen.ts` with `fakeScreens` (`src/renderer/terminal/test-screen.ts`), which also fakes main's terminals (`fakeTerminals`).
- `src/main/cli/serve.test.ts` runs the CLI bundle (`corrallm serve` and `corrallm wait`), which the vitest `main` project's global setup builds first (`src/main/cli/global-setup.ts`), in child processes on a profile of its own: its database keeps a canvas and its project folder, as the app would (seeded through the store's API, `keepCanvases`), its tokens.json known tokens' hashes, and its agents run `fake-codex.mjs` (which reads what it is asked after corrallm's frame line); an MCP client (the SDK's `Client`) calls as an outside orchestrator, and `--new-token` runs under `script(1)`, a terminal. `src/main/cli/wait.test.ts` checks how `corrallm wait` exits on each refusal, against a stand-in server. The core database's gates (Core Database §8): `src/main/cli/crash.test.ts` (G3) kills `corrallm serve` with SIGKILL seven times while two outside orchestrators send three agents messages (every third a turn that goes on until interrupted) and wait for replies, and checks across every crash that no message reaches an agent twice (the fake codex logs each turn it starts), none acknowledged is lost, no read position goes back, and each in flight as it was killed is unresolved; `e2e/load.e2e.ts` (G2, B11's load test built in B9.0) runs `corrallm serve` (the app's core process serves no messages, waits or pauses until B11) with `e2e/loop-delay.mjs` loaded into it (`node --import`), which measures its event loop from inside between two SIGUSR2s, while four orchestrators send six agents about 2,600 messages over 35 s, wait for every reply and pause and release an agent ten times a second, and holds it to p99 under 25 ms and max under 100 ms, on a quiet drive (while another program writes heavily to the same drive, a commit's own writes into the log can stall the loop past 100 ms, as 2 of 8 runs did with `dd` writing alongside: only the core's connection on a thread of its own would hold G2 then); `e2e/damaged-store.e2e.ts` (G4) gives the built app a `core.db` that isn't a database, and it runs on, restored or empty, saying so in its window (serve.test.ts checks `serve` does the same). e2e specs may import the store's test helpers (`src/main/core/store/test-store.ts`). `e2e/lock.e2e.ts` checks `core.lock` with the built app (whose core process holds it, found through `app.getAppMetrics()`), and `e2e/core-crash.e2e.ts` kills that process: the window reconnects to the new core, the canvas restored paused, and a core that keeps stopping is given up on.
- Before calling a change done: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm test:e2e`.

## Layout

```
src/main/       Main's entry is index.ts; security.ts, app-protocol.ts, csp.ts and url-policy.ts
                hold the security baseline. ipc.ts checks the preload's core:connect handshake; main
                owns windows and native UI, and hosts the core process. The Electron-free services
                here are composed only by core/core.ts: canvas.ts opens and saves canvas files,
                project.ts keeps project folders, memory.ts remembers each canvas's file, folder and
                agents' conversations and run-journal.ts journals runs and where each party has read
                to (both in the core's database, core/store/), settings.ts keeps app consents and
                api.port, usage.ts keeps readings, exhaustion and spending rules in usage.json, and
                whole-file.ts writes and reads the files written whole (canvases, api.json and the
                JSON stores that stay files). Their state reaches the GUI through operations,
                topics, and the remaining hand-written channels served by core/channels.ts.
src/main/core/  The core: corrallm's one server, owning profile stores, messages and sessions
                (the app's canvas and run still live in the renderer until B9/B11), in an
                Electron utility process in the app and under plain Node headless.
                Electron-free: it never imports Electron or src/main/host/ (ESLint's
                app/boundaries-core); what differs between hosts is passed in. host.ts is
                HostServices, what it asks of the app that hosts it (dialogs, links, file reveal
                and run-save acknowledgements), and TrustedPath, the only paths a canvas is opened
                from or saved to and
                the only project folders; entry.ts, the core process's entry (core.cjs): main asks it
                `init` for the app (it takes core.lock first, and while `serve` holds the profile
                answers who does), then hands it each trusted window's port beside the link, which
                gui.ts serves over createCore(config, appHost(link)); main passes the profile,
                distribution, locale and unpackaged fake-session setting. In the native
                self-test it only runs the checks; protocol.ts, what main and the core process ask
                and tell each other (`init`, `selftest`, HostServices, `windowGone`; a window's port
                crosses beside the link, WindowMessage); gui.ts, windows' ports (WindowPorts: every
                call on one is yours, at that window, `asHuman`, through core.call; an op outside
                GUI_OPS is refused before dispatch; remaining hand-written channels are parsed
                and handled by channels.ts); selftest.ts (and selftest-claude.mjs), the native self-test's
                checks, run by main, the core process and the CLI; host/app.ts, the core's host in
                the app (main, asked over the link, its dialogs' picks branded TrustedPaths on
                the core's side); host/node.ts, the core's host under plain Node (`corrallm
                serve`: no dialogs, so what needs one is human-only; `appProfile`, the app's own
                profile folder); lock.ts, core.lock, one owner per profile (the app's core
                process, from `init`, or `corrallm serve`; a lock whose process is gone, or whose
                pid was reused, is taken over, by
                one process at a time holding core.lock.taking; `stillRuns` also tells whether
                api.json's server runs); tokens.ts, the outside tokens (TokenStore: tokens.json,
                hashes only, a new token of a live one's name replacing it). The core's operations
                (see The registry): call.ts is core.call, the one dispatcher every transport calls
                (audience, limits per token, the canvas, filled in for a caller with one, or the
                one holding a message it names (`withdraw` takes none), and asked of one with
                several otherwise, schema, reach, self, rules, repeated requests, scopes; failures
                as values); caller.ts its callers (you, an agent's session, an outside token) and
                their parties (no token is ever you; only gui.ts makes you); scopes.ts the order
                ops run in (one at a time per scope; a preempting op aborts what runs beneath it
                first, never another preempting op, and those that overlap run in turn, ahead of
                the queue);
                throttle.ts the limits per token (calls in flight and writes a second; a long
                poll, `waits`, counts against the waits in flight instead of the calls);
                requests.ts the repeated requests (each caller's own; a result kept only when its
                op came to it by itself, so a cancelled call's retry runs again); reach.ts
                resolves the ids a token names against its reach (`resolvers`: a canvas it has, an
                agent or a group it reaches there, a message it sent or received there; a caller
                with one canvas may leave it out; `holder`, which of a caller's canvases holds a
                message it sent or got); rules.ts checks each rule an op carries on a token's
                arguments (shell-text, sticky); parties.ts words parties and the pauses they set,
                for refusals and notices; ops/ is each op's implementation, by area (open.ts: the
                open canvas a call names, and pages of a list within MAX_PAGE_BYTES; wait.ts:
                `wait`, see Headless); core.ts is createCore, the operations composed over the
                Electron-free services, kept in a profile folder (in the app and under
                `corrallm serve`; tests may say which agents are leads, none being until
                B24, and give the limits per token a clock), with its tokens, `keptCanvas` (the

                Engine, its agents' sessions run by the core's own SessionManager in this process (a

                per 250 ms and before every message the run sends, and its messages (see Messages),
                its run and its messages one record: every write of either holds what the other has
                changed and hasn't on disk yet (`writeWith`, `#journalWithin`), and `advance` moves
                every read position a `wait` moves in one write with them. delivery/messages.ts is
                the message store (MessageStore, a canvas's, over MessageTable, every canvas's rows
                of `message`); delivery/delivery.ts delivers them, framed, and brings replies back;
                delivery/withdrawals.ts carries durable withdrawal notes into the next CLI message
                without opening a run for a renderer-owned canvas; delivery/reads.ts each party's
                `wait` read position, moved only once it is on disk (the journal's read_position).
                `Engines.watch`'s watchers hear each message added (what closing a canvas cuts off
                included) and what newly waits for an answer. test-registry.ts is a registry for the
                core's tests, with an op for every check core.call makes, fixtures for every op, and
                what each party doesn't reach (from which T3b generates its reach calls);
                test-world.ts the core the registry's generated tests run on (a canvas of the test
                callers' agents, messages waiting, nothing ever running a turn); test-worker.corral
                the canvas the engines' test runs.
src/main/core/store/  The core's database (B9.0, Core Database §5): <profile>/core.db, through
                Node's SQLite, which sqlite.ts alone reaches, lazily (`process.getBuiltinModule`,
                never a static import, which the bundler would hoist above the CLI's check of Node's
                version; a test keeps it so). open.ts is openStore, which never rejects: core.db
                made 0600 before SQLite opens it (so its -wal and -shm are too); one that was there
                checked read-only first (a transaction a crash left in its rollback journal, as
                while it is set up, rolled back first; corrallm's application id, meta.min_reader,
                quick_check: faults.ts); then incremental vacuuming on a new one, WAL, synchronous
                NORMAL (no sync as SQLite commits: the store flushes its log itself) and F_FULLFSYNC
                on macOS for each sync SQLite does make (checkpoints), foreign keys, an untrusted
                schema, a 4 MiB journal size limit, no automatic checkpoints, no busy timeout (the
                core is the only writer), and migrations.ts' forward-only migrations (each with its
                user_version and meta.min_reader in one transaction, run with foreign keys off, so
                one may rebuild a table others refer to, and refused if it leaves a reference to
                nothing; schema 1: canvas, conversation, run, run_workflow, message,
                read_position, open_canvas, meta, STRICT). One a newer corrallm made that this one can't read is refused, left
                untouched; a damaged one is set aside (core.rejected-<uuid>.db, its -wal first, then
                -shm and -journal) and the newest snapshot passing the same checks restored, else it
                starts empty, saying so; a profile with snapshots but no core.db (a restore cut
                short) is restored the same way, saying so. Every open numbers each never-reused
                sequence (migrations.ts' SEQUENCES: message's seq) on from the clock in ms, past
                every place given before, those whose rows a crash cut off and those a database a
                restore replaced gave included, so a cursor from before reads what comes next; a
                restore, or an empty start in place of a database, then settles in the same
                transaction what waited in the snapshot (restored.ts: a message pending there may
                have gone since, so it is unresolved, never sent, and its sender told by a notice).
                What opening wrote is checkpointed (TRUNCATE) before the store is used, so it is on
                the drive, and the log begun anew (checkpointer.ts' `beginLog`: a write that changes
                nothing, since SQLite syncs a new log's header on the connection that begins it).
                store.ts is the open Store: `prepare` (cached), `tx` (transaction.ts: BEGIN
                IMMEDIATE, a synchronous function, COMMIT, a savepoint within one, rolled back only
                if SQLite hasn't, as on a full disk; its log flushed on the loop: tests only),
                `write` (the lane: writes queued in one turn of the loop share one commit, each in a
                savepoint, each resolving only once that commit returned and its log was flushed to
                the drive, off the loop: Node's fsync on its thread pool, F_FULLFSYNC on macOS, one
                flush at a time for every commit made before it began: "on disk before it is sent").
                A failed flush fails the store closed: every write and read refused from then on,
                saying why (once on stderr), until the core opens it again; what it committed since
                its last flush that worked taken back best effort (the log cut back to where those
                commits began, as `wal_checkpoint(NOOP)` said before each, and closed while a connection that only
                reads holds the database, so SQLite checkpoints none of it, and the next open
                recovers the log up to there alone; every snapshot published since removed, including
                one whose rename succeeded but publication rejected). Limit: if cutting the log or
                syncing that cut itself fails, a write whose flush failed may come back after a
                restart, in doubt as in PostgreSQL and SQLite. The store says so on stderr. No
                recovery marker is written or checked at open. Successful writes cost only their
                WAL flush; normal opens and writes create only core.db, -wal and -shm (snapshots
                are taken separately, as it closes or once due).
                `checkpoint` (checkpointer.ts: PASSIVE, once every commit made is flushed, on a
                worker thread with a connection of its own, whose code is a string run as CommonJS,
                since the bundles are one file each; sqlite.ts gives the expression it connects
                with; once it copied all of the log it begins it anew there, cutting it back to
                JOURNAL_SIZE_LIMIT, and the lane commits nothing meanwhile, so the two connections
                never write at once), run once idle a second (at most 30 s after the first
                unchecked commit), so no drive flush waits on the core's loop while it serves (only
                opening and closing sync on it). A commit's own writes into the log do run on the
                loop, into the system's cache, which the system holds back while other programs
                write heavily to the drive: G2 holds on a quiet drive, and only the connection on a
                thread of its own (Core Database §4's fallback, not built) would hold it under such
                writing. `snapshot` (snapshots.ts: SQLite's backup
                into backups/core-<time>.db, read through a connection of its own in one step,
                quick-checked and forced to disk before it is named, never kept with a fault, the
                newest three kept, what one cut short left removed by the next; taken as it closes
                and every four hours) and `close` (writes, and transactions outside one, refused
                from its start; the lane drained and flushed, the checkpointer's thread ended, a
                TRUNCATE checkpoint, a snapshot; once). `Database` is what the stores kept in it
```

## Run recovery and persistence

- Per-agent controls live in the right-click menu on canvas cards, All queues headings and session headers (also Context Menu / Shift+F10). `RunStore.pauseAgent` finishes current work then holds dispatch; `killAgent` cancels owned/received work immediately, holds the queue and leaves its native console open. `resumeAgent` releases only that hold. `AgentRun.paused` persists in the checkpoint, separately from whole-run pause; it is runtime state, never part of a saved `.corral` workflow. `RunIO.hold` keeps SessionStore's queued sends held too, while a fresh manual prompt can still intervene. Release drains in a microtask so same-stack canvas resets cannot send stale work.
- Group controls use the same menu on frames; an agent containing children keeps its individual controls and adds a Group section. `RunStore.pauseGroup/killGroup/resumeGroup` include every descendant agent and the parent agent itself, when present. Individual and group pause causes are kept separately, each stamped with the party that set it (`PauseCause`: you from the GUI, a token's party through the core): Resume releases only its own cause (a party's release only that party's, yours every party's), including across checkpoint restore, global Resume and Run again. New members inherit an active group hold; moving out, ungrouping or deleting a group releases that group's cause. Group Kill holds all members before withdrawing any work, so cancellation callbacks cannot start another member. Manual console correction remains available while held.
- Every session `end` carries its required `result` (`TurnResult`), live and in replayed history; there are no `end.interrupted` or `end.failed` flags or compatibility fallback. It keeps native completion, cancellation and failure reasons separate (a usage limit, a login, the API, the model declining, a start or connection that failed). A tool's task verdict is independent of that native result. Neither cancellation nor a native failure (a usage limit, a login, an API error, a start that failed) triggers an If failed branch, starts a repeat's next round or satisfies an expected failure: they hold for the user.
- `AgentRun.problem` holds the original queue item in Needs you. Retry, Mark resolved, Continue with failure/cancellation and Stop here are explicit decisions. Corrective composer messages include the original objective, keep the human note as a visible Message row, and create another attempt. A direct Terminal submission is correlated by its native message ID when exactly one held task owns that console; observation never sends it again. Slash commands stay commands. Attempt metadata stores timestamps, concise reasons and corrective notes.
- `engine/run/checkpoint.ts` validates the whole versioned runner snapshot before applying it. It includes cursor/outcomes, repeat rounds, held condition decisions, deadlines and minimal reply evidence for downstream conditions. `engine/delivery/submission-state.ts` stores manual Message metadata, never an executable queue of messages. Restored running/queued submissions are unresolved and are never automatically sent.
- `run/persistence.ts` serializes writes and holds dispatch across canvas identity changes (a transition, or a rebind after the project folder changes): a flush asked for meanwhile, as main's RunShutdown asks as it quits, waits for the change and saves under the new token, and only a disposed store refuses it. Every automated dispatch waits for its in-flight checkpoint to reach the core. The core owns paths and generation tokens: `main/run-journal.ts` journals each canvas by its id in the core's database (Core Database §5: its run's state in `run`, and the workflow it runs in a row of its own, `run_workflow`, written only when its hash on disk differs, decided within the write, so a save that changes only the state never writes the workflow again, nor JSON-reads it; each party's `wait` position in `read_position`), reading its file back from canvas memory's row (one source of truth: memory keeps it, and nothing keeps a copy), and remembers the last active canvas (`open_canvas`, one row). Its writes go through the store's write lane, each on the drive once it resolves (its commit returned and the log flushed); the core journals a canvas's run within a write that holds its messages too (`core/engines.ts`' `#journalWithin`, and `MessageStore.writeWith`), so a canvas's run and its messages commit together. A run it can't restore (a state it can't parse, another checkpoint version) is discarded, saying so in the window's warning, as the store's own sentences are (set aside, restored from a snapshot) with the first canvas a window restores. Save As keeps the canvas's id, so its run, folder and conversations stay with it; a canvas a window opens or begins anew gets a new token, so stale generations cannot overwrite another canvas. Unsaved workflow edits survive too. A canvas whose file went missing restores as the same canvas, unsaved, with a warning.
- The core journals each headless canvas it runs from its engine's own state (`core/engines.ts`): at most one write per 250 ms, and one before every message the run sends, so a sent message's record is always on disk first (a party's message too, its row in `message`: see Messages), and one before a `wait` that moved a party's read position returns (`read_position`, which every other save, as the app's, keeps as they were; the position moves only once its commit returned). A canvas's run and its messages are one record: each write of either holds every change to the other not yet on disk (the run's only if it changed since it last was), so what changes together lands together or not at all (a kill's hold and the withdrawals it makes, a turn's reply and what its end changed in the run), and a `wait` moves every position it moves in one write, or none. Each write is on the drive before it resolves (its commit returned and the log flushed, off the loop), so no crash loses a sent message's record or a position a `wait` returned past; closing the core holds each run where it is (what was going on is uncertain until inspected), journals it, then closes its sessions, writes out its stores and closes its database last, all of it even if a run can't be journaled (then `close` rejects, saying so, once everything has closed). A database that can't be opened (`unopened`) fails every read and write of the journal and canvas memory, saying why: no canvas restores or opens, so nothing is journaled and the run sends nothing.
- Reopen/reload restores paused. Resume is explicit; an interrupted in-flight task stays uncertain until inspected/resolved or explicitly retried. Native session reconnection uses each connection's existing restart/resume and exact conversation ID. Main's `RunShutdown` asks the renderer to freeze/save and waits for acknowledgement. The core then flushes fallible saves while sessions and dispatch remain usable: a failed save surfaces the reason and Keep corrallm open cancels closing. Only an approved quit stops supervision and irreversibly closes the core and its sessions. Hidden unpackaged apps report save failures on stderr and exit without a native dialog.

## Canvas identity

- Every canvas has a stable id, a UUID (`CanvasId`, `src/shared/canvas.ts`): in its `.corral` file (`{ "format": "corrallm", "version": 2, "id", … }`; another version is refused), or a draft's journal record. The core keeps everything of a canvas by it: its file, project folder and agents' conversations (`memory.ts`), its run (`run-journal.ts`), both in the core's database, its sessions (`sessions/manager.ts`) and folder (`project.ts`). `core/windows.ts` maps each window to the canvas it shows, and IPC handlers look the canvas up there first.
- New and a template give a draft with a fresh id (`canvas:forget` resolves with it); Save As keeps the id; a save of text whose id is another canvas's is refused. Opening a file makes it that canvas, unless the canvas is kept in another file that still holds its id (the original after Save As, or a copy made in the Finder): it opens as a copy with an id of its own (kept the next time it opens), and says so. A moved or renamed file keeps its canvas. A file belongs to one canvas.
- Stores are version 2, with no migration: a version-1 `.corral` is refused; `settings.json` (consents by adapter, the API server's port) and `tokens.json` of version 1 read as empty, and a run whose checkpoint isn't version 2 is discarded with the journal's warning. The core's database (`core.db`) keeps its own schema version (`core/store/migrations.ts`), and started empty (B9.0, no import): `canvases.json` and the `runs/<id>/record.json`, `runs/<id>/messages.jsonl` and `runs/last.json` of before are left as they were and never read, so each canvas's folder is picked again in the app, and its messages start anew. The JSON stores (`settings.json`, `tokens.json`, `usage.json`, `links.json`: `readWhole` in `whole-file.ts`) read as empty only when the file is missing: one of another version (version 1 included), or not JSON, also reads as empty, but is first set aside as `<name>.rejected-<uuid>.json` and said on stderr, so nothing it held is written over; one that is there but can't be read (its permissions, the disk, too many files open) is never read as empty nor written over: what needs it fails, saying why, and it is read again next time (`tokens.json` and `usage.json`, read once as the core starts, keep it from starting). Until milestone 1 settles them, a phase may change a version-2 shape (B6: a run checkpoint's pause causes became `{ id, by }`, so a B5b-era record is set aside once; a `.corral` file's node ids are at most `MAX_NODE_ID` characters); after that, phases only add optional fields, which a version-2 reader accepts when absent. `settings.json`, `usage.json`, `tokens.json` and `links.json` also write back what they hold that the running corrallm doesn't know (`unknownFields` in `whole-file.ts`): a newer one's fields, of the file and of each entry it rewrites as it read it (a reading, rule or hard limit replaced is the writer's own), and `usage.json`'s entries for backends this build lacks, so an older corrallm sharing the profile never erases them; a token this build can't read is still dropped, never carried unchecked.

## Security rules (do not regress)

- Never enable `nodeIntegration`, and never disable `contextIsolation`, `sandbox` or `webSecurity`. No `<webview>`.
- The preload exposes one typed function per IPC channel through `contextBridge`, and one per registry operation in `GUI_OPS`, generated from that fixed list in `src/shared/api/surface.ts`, each posting its own operation over the window's port to the core. Never expose `ipcRenderer`, the port, a generic `invoke`/`send` or a function that takes an operation or channel name, or Electron event objects to the renderer.
- Main registers only `core:connect` in `src/main/ipc.ts`, checking its sender frame (top-level frame of our own origin) and empty arguments. Keep `ipcMain.handle`/`ipcMain.on` there. This handshake is the preload's own, never exposed to the page: through it main hands a trusted window a `MessagePort` to the core (`host/ports.ts`), tagged with that window, which the preload keeps inside a CoreLink. The core makes every call on it yours, at that window (`core/gui.ts`), and validates it with the op's schema in `core.call`; identity comes from the port, never from a message. Remaining hand-written channels are declared in `src/shared/ipc.ts`, and parsed and handled in `core/channels.ts` for that same window.
- Production renderer is served from `app://main_window/` by `src/main/app-protocol.ts` (not `file://`, not `loadFile`). The CSP is a response header from `src/main/csp.ts`: never add `'unsafe-inline'` or `'unsafe-eval'` to `PROD_CSP`. Dev-only relaxations go in `DEV_CSP`. The only inline styles allowed are the two exact ones xterm.js writes for its scrollbar, by hash (`TERMINAL_STYLES`); xterm.js draws only with its WebGL renderer, loaded before the terminal opens (its DOM renderer's inline styles are blocked).
- Dev vs production is decided by `MAIN_WINDOW_VITE_DEV_SERVER_URL` (defined only under `pnpm dev`), not `app.isPackaged`. e2e runs the production build unpackaged.
- Navigation and redirects away from the app origin, and renderer-created windows, are blocked (`security.ts`; one to an allowlisted site, `allowedExternalUrl`, opens in the browser instead). Links the user clicks (Markdown links in a transcript, links Cmd-clicked in a terminal, OSC 8 or found by xterm.js's web-links addon) go to the core over `link.open` with only their URL (`OpenLinkContext` in the renderer), never through `window.open` or `target="_blank"`. The core decides, never on the renderer's say-so (`links.ts`): the URL is validated and length-capped (`MAX_LINK_LENGTH`) and normalized by `linkTarget` (`url-policy.ts`: https, or http to localhost or 127.0.0.1 only; no credentials); a site on `EXTERNAL_URL_ALLOWLIST` (https, default port) opens at once; any other asks in a native dialog ("Open docs.example.com in your browser?", with "Always for this site"), one question per window at a time, and a site allowed always is remembered by origin in user data (`links.json`). Always open the normalized URL, never the raw input. A file:// link Cmd-clicked in a terminal (Claude Code prints the files it names as OSC 8 links; xterm.js's `allowNonHttpProtocols` is on only for these, and the renderer drops every scheme but http, https and file, `linkAction` in `open-link.ts`) goes to the core over `link.reveal` with only its URL. The core (`reveal.ts`) asks main to show it in the OS file manager, selected in its folder (`shell.showItemInFolder`), only if the URL is length-capped, a file:// URL on this machine (no host; `localhost` counts as none) with no credentials, naming a file or folder that exists, whose real path (symlinks resolved, `fs.realpath`) is the real path of the canvas's project folder (`ProjectFolders.of` for the canvas the sender's window shows) or inside it. Anything else stays inert: no project folder, outside it (a symlink in it that leads out included), another host, missing. It never opens the file (no `shell.openPath`, no `openExternal` for file:// URLs), so no executable or document is ever run from a link.
- All permission requests and checks are denied (`ALLOWED_PERMISSIONS` in `security.ts`). Add entries deliberately.
- A canvas's text never acts as the user, nor does a token's. The run never sends canvas text (a queue's message or step, which a shared file may hold, or a hand-off) that starts with its recipient connection's `shellPrefix` (the catalog's: "!" for both Terminals), checked as the run sends it and again as its session starts it (`shellRefusal` in `src/shared/engine/catalog.ts`, worded from the catalog), each time against the connection the recipient runs then, since a message kept in a session's queue (behind a turn, or by a session that refused to start) may go after the agent switches: it holds in Needs you, unsent. A connection that declares no `shellPrefix` (the App Server, the Agent SDK) runs no text as a shell command, so the hold never applies to it. A token's `message` whose body starts with its recipient's prefix is refused at once (rule `shell-text`, R1). Only what the user typed may (an Agent SDK agent's bash mode, continued in Terminal); a correction you type that starts with any connection's prefix (`EngineCatalog.shellPrefixes`) is sent alone, never with the canvas's text, since its agent may run in a Terminal by the time it goes. Only your sends go past holds; every other party's waits on them (see Messages). Every message from another party (a token's, an agent's, a delivered reply) reaches its agent framed with who sent it (`core/delivery/delivery.ts`), and a CLI that takes who sent a message (the Agent SDK's `origin`) is told it too, so its CLI never takes it for its user's. And no message takes Codex's App Server out of its sandbox: `/permissions full-access` is refused, since Full access is the mode menu's, which asks first.
- No token is ever you. Only a window's port, made by main, or main's own native UI gives a human caller (`asHuman`, defined and called only in `core/gui.ts`, which only the core process's entry loads, for a port main posted on its parentPort). A token's lookup can't name you (`clientOf`'s type), and the MCP server refuses one that would. Operations only you may call are never listed on the agents' server, and are refused there if called (`human-only`).
- Which canvases and agents a caller reaches, and the rules that narrow what tokens may do, are enforced in `core.call` (and, once canvas edits reach the core, at commit), never left to an operation's implementation. Every transport calls `core.call`, which checks the caller's audience on every call, not only when listing tools.
- Both local servers (MCP, `api/mcp.ts`; hooks, `sessions/terminal/hooks.ts`) listen only on 127.0.0.1 and refuse a foreign Host or any Origin header before checking the token (`loopback.ts`). MCP takes only an `application/json` body, of at most `MAX_REQUEST_BYTES`, read before a body too large is answered 413.
- Session ids are UUIDs (`sessions/id.ts`), checked in hook signals, resume IPC arguments, remembered sessions loaded from disk, and both Terminal CLIs' argv builders. Claude resume uses `--resume=<id>`; an id must never be read as a CLI flag.
- Only one app instance may use a profile (`requestSingleInstanceLock` in index.ts), and `<profile>/core.lock` (`core/lock.ts`) admits one owner, so the app and `corrallm serve` never own one profile at once (a lock left behind is taken over by one process at a time): the app's core process takes it as main asks it up (`init` in `core/entry.ts`, before it composes the core; let go once the core closes, and a crashed core's is taken over by the next) and, while `serve` holds it, answers who does, composing nothing, so main refuses to start, saying so in a native dialog; `serve` refuses while the app holds it. A window that crashes ends its canvas's sessions as one that reloads or is destroyed does (`core/windows.ts`).
- Paths the core opens, saves to or works in (canvases opened from and saved to, the folders agents run in) are `TrustedPath`s (`core/host.ts`): from a dialog you completed (`host/dialogs.ts` returns an unbranded path; `core/host/app.ts` brands its answer in the core process), or from canvas memory reading back a path it wrote, as the journal does with a canvas's run. No command line mints one, so `corrallm serve` runs a canvas only from the file and in the folder canvas memory keeps for it, picked in the app (`Core.keptCanvas`; it has no `--project`).
- Outside tokens are made by a person (`corrallm serve --new-token`, only with stderr on a terminal), named (the name is the party, `outside:<name>`; a new token of a live one's name replaces it at once), reach only the canvases named when made, by their stable ids, read-only or read-write, expire within 12 hours (1 by default), and are kept only as a SHA-256 hash (`tokens.json`, 0600), a new token forced to disk (`writeWhole`'s `durable`) before it is printed, so no power loss brings back the one it replaced. A new one is printed once, on that terminal, and no log, result, store or child process's arguments ever hold it; orchestrators register corrallm by the variable that holds it (`CORRALLM_OUTSIDE_TOKEN`, under the server name `corrallm-outside`), and `corrallm wait` reads it only from its environment and sends it only to http on 127.0.0.1 or localhost, with no credentials, query or fragment (`loopbackUrl` in `url-policy.ts`). No operation a token can call creates or widens a token.
- Read-only Git commands share `SAFE_GIT_OPTIONS` (`main/git.ts`), disabling fsmonitor and implicit bare repositories. The App Server's `/diff` also disables external diff, textconv and filter drivers; file suggestions must never run a repository's fsmonitor.
- Packaged builds exit if launched with a switch in `FORBIDDEN_SWITCHES` (`src/main/index.ts`): remote debugging, or launcher prefixes such as `--gpu-launcher` that would make the app run an arbitrary executable. CI asserts this.
- Fuses (`forge.config.mts`) must stay as configured: RunAsNode, `NODE_OPTIONS` and Node inspect flags disabled; ASAR integrity and OnlyLoadAppFromAsar enabled (integrity is enforced on macOS and Windows only). Consequences: `child_process.fork` throws in packaged builds (use `utilityProcess.fork`, as the core process is forked, or `spawn`; the packaged self-test checks it throws), and Playwright cannot drive the packaged app.
- Credentials only come from environment variables (see `.env.example`). Never commit `.env` or key files; `pnpm dev` strips the signing variables before launching the app. Agents use the `claude` and `codex` CLIs' own logins; corrallm never reads, stores or passes credentials (the Agent SDK connection asks `claude auth status` only what kind of login it has, the App Server connection asks Codex's `account/read` the same).
- Agents run only in the project folder the user picked in main's folder dialog (`project.ts`, through `HostServices.pickFolder`): that choice is the trust gate (SDK sessions skip Claude Code's own trust dialog, Codex is told the folder is trusted for its session alone). The renderer never passes a path, a command line or an environment, and names a session to resume only by picking one the core listed for the canvas's project folder (`session:list`, then `session:resume`): the core resolves `claude` (`sessions/claude-code/claude.ts`) and `codex` (`sessions/codex/codex.ts`), the environment and the folder, and remembers session ids itself. The one path that crosses is a file dropped on a terminal: the page passes the dropped `File` objects, the preload reads their paths with `webUtils.getPathForFile` (a file the page made has none), and the core checks them (`terminal.drop`: absolute, length-capped, no control characters; then that they exist) before pasting them, quoted, into that terminal, never using them otherwise. Connectors use an agent's id only to route events, never in a path or a command line. What an agent is set to run with goes on its CLI's command line only as checked values, from the renderer and from `.corral` files alike: a model's name (`MODEL_PATTERN`: never with a dash first, which would read as a flag), an effort (`EFFORT_PATTERN`; Claude Code's only one of its levels) and a mode its connection starts in (the catalog's `startModes`, each one that asks: neither a file nor `session:start` sets one that never asks). Every session's process is closed before the app quits. A Terminal view sends only keystrokes, its size and dropped files; its CLI's hooks post to a server on 127.0.0.1 that needs the session's own token (from its environment), and corrallm only listens to them (it never answers with a decision, and never answers what the CLI asks in its terminal). corrallm only reads Claude Code's settings files (the user's, the project's and the organization's managed ones) to tell whether they turn its hooks off (`hooks-off.ts`), and never overrides them (its `--settings` never set `disableAllHooks` or the hook allowlists). Codex's hooks are given and trusted for its session alone, on its command line: corrallm never writes the user's config.toml, and never runs Codex with `--dangerously-bypass-hook-trust` (which would also run the user's and the project's untrusted hooks). Claude Code's status line posts to that server too, with the token read from a file only the user can read (never on a command line), and never puts what Claude Code gives it into a command line; Codex's are read from its app server (a Codex · Terminal session asks a private one nothing but `account/rateLimits/read`). Usage readings keep only shares and times.

## The registry

Every operation of corrallm's one API is defined once (`src/shared/api/`, Core Server §3), and both surfaces are generated from it: MCP for agents and outside orchestrators (`api/mcp.ts`), and a window's port for the GUI (`core/gui.ts`), which serves `GUI_OPS` (`surface.ts`: every op you may call that isn't in `UNHOSTED`; the app keeps its hand-written channels for the rest until they move). An op's audience (`access` in `surface.ts`: `you` for the GUI, any other party for MCP) is the only thing that decides where it appears, and `core.call` checks it on every call. Results are always objects; failures are values (`OpError`: `invalid`, `forbidden`, `human-only`, `not-found`, `conflict`, `refused`, `unavailable`, with one sentence), on MCP `isError` with the sentence first and `{ error }` as JSON second, never in `structuredContent`.

- By default an op is on both surfaces. One on a surface alone needs a `DEVIATIONS` row (`deviations.ts`) of one of the closed `REASONS`, or, until B11, an op the app doesn't host yet a line in `UNHOSTED` (`unhosted.ts`) naming the phase that will. A rule an op carries needs its row in `RULES` (`rules.ts`) and its check in the core.
- The GUI’s global topics (`core/topics.ts`, `shared/api/topics.ts`) are `usage` and `settings` from B8: `topics.subscribe` returns `{ epoch, rev, state }`, then the port’s `topic(changes)` carries replacements in 16 ms batches, with topic revisions, a shared sequence, actor and time. `topics.unsubscribe` stops them; a port going forgets its subscriptions. Each read is dispatched through the op whose surface declares `reads` for that topic, so its audience and reach remain the one authorization path. Tokens get neither subscription op (D5, `transport`). The core announces its own UUID `epoch` on each port; `renderer/api/topics.ts` mirrors the latest immutable state for `useSyncExternalStore`, shares one subscription per observed topic, re-subscribes on a new epoch or a revision gap, and keeps changes that arrive ahead of a snapshot’s reply. T3c (`core/topics.test.ts`) checks the two topics against their reads, subscribed windows, unsubscribe and token refusal.
- The renderer's B9 mirror also accepts `canvases`, `canvas:<id>` and `needs:<id>` (subscribed as `{ topic: 'canvas' | 'needs', canvas }`). Keyed `set`/`remove` changes preserve unchanged entities' objects; `replace` takes a whole topic's state. `whenAt(topic, rev)` holds a subscription until that revision arrives, even without a view listening. A GUI write resolves only after all its returned `revs` reach the mirror. Waiting writes fail on a core restart, rather than mistaking a new epoch's revisions for the old one's. The mirror's transport bypasses the client’s draft and revision barriers so subscriptions cannot deadlock a commit waiting for its change.
- T6 (`main/gestures.test.ts`) scans production renderer calls: every GUI op without `reads` needs a call site or a reason in `renderer/api/gestures.ts`'s `NO_GESTURE`. `renderer/test-api.ts` records operations separately from transport subscriptions, feeds snapshots and changes, and supplies `expectOneOp` for each gesture's intent.
- The tests that make 1:1 the default (Core Server §3.7): T1 and T2 (`shared/api/surface.test.ts`: the surface's rules, each also shown to catch a registry made wrong; `surface.snap.json` up to date), T3a (`core/transport.test.ts`: every op's fixtures through MCP's dispatch half and over HTTP answer byte for byte as `core.call` does, for the same caller, and every GUI op's through a window's port, for you), T3b (`core/callers.test.ts`: audience and tool lists agree, results alike but for `varies`, rules per party, and reach generated per op and party: each id in an op's valid arguments swapped for each one its `OutOfReach` world says a token party doesn't reach, which must be not-found; it fails an op taking a kind of id no valid argument names, or that the world says nothing of for a party in its audience), T7 and T8 (`boundaries.test.ts`, ESLint). Each runs on the registry and on the core's test registry.

To add an operation:

1. Add its surface to `SURFACE` in `src/shared/api/surface.ts`: its audience (who may call it, and how far each reaches), kind, scope, and any rules, `self` (required when a token may call it naming an agent), `destructive`, `preempt` (it aborts what runs beneath it in its scope first), `waits` (a long poll: only a read on MCP alone, the transport deviation, which T1 checks; it counts against a token's `TOKEN_WAITS` waits in flight, not its calls), `varies` and `reads`.
2. Define it in `src/shared/api/ops/<area>.ts` with `define(name, { summary, input, output })`: the summary is its MCP description; the input a `z.strictObject`, every string and list bounded, every id a branded one (`ids.ts`), never put through a pipe (a transform after it, a preprocess before it) nor in a union with a transform, which T1 refuses: core.call reads the id the op gets for reach, and finds nothing in reach where it can't; the output an object. Add a new area's ops to `OPS` in `registry.ts`.
3. Implement it in `src/main/core/ops/<area>.ts` (the `Implementations` type refuses a missing one), over the services `createCore` composes.
4. List it in `UNHOSTED` until the app serves it, or give it a deviation; give it fixtures in `REAL_FIXTURES` (`core/test-world.ts`): valid arguments (naming between them every kind of id it takes; `by`, those only some parties may pass, as a message they sent; `fresh`, the result's fields each call mints anew), invalid ones and arguments meeting each of its rules; for a kind of id no op took before, say in `REAL_OUT_OF_REACH` which ids of it each token party doesn't reach, as far as each reach goes. A write's fixtures carry a `request` id, so a call repeated through another transport dedupes.
5. Run `pnpm api:surface` and review the snapshot's diff.

## Messages

What parties send a canvas's agents (API Spec §5, Core Server §5.9), served by the core from B6 (headless; the app from B11, whose composer keeps its own submissions until then). A party is you, `corrallm`, `agent:<id>` or `outside:<name>` (`PartyId`, `src/shared/model/messages.ts`); no token is ever you. An agent's id is its node's: any text (line breaks too) of at most `MAX_NODE_ID` characters (`model/canvas.ts`), which a canvas file, the API's ids and a party id all hold to.

- **The store** (`core/delivery/messages.ts`): each canvas's messages in order, in memory and in the core's database, a row of `message` each (with the key of what a notice told, `told`, and the note its recipient must still be told of a withdrawal, `withdrawal`, in the same row), written with the database's next commit, and on disk once `durable()` resolves. The order is one every canvas's messages share (`MessageTable`): the core gives each place past the last the table's AUTOINCREMENT sequence gave, which every open raises past every place given before (from the clock: `store/open.ts`), so a cursor survives pruning, restarts and restores, and one naming a place whose row a crash cut off never skips the message given that place next (`end()` is the last place given, in any canvas). It keeps the newest `STORE_SETTLED_PER_PARTY` settled messages of each party within `STORE_BYTES`, and every pending and unresolved one (a party may have at most `MAX_WAITING` messages waiting for an agent: `message` refuses another), deleting the rows of those it drops. Each row is written as the message is in memory when its write runs, each column by name (so a newer corrallm's stay), and marked on disk only if it hasn't changed since; a write that fails leaves its rows to the next. It never throws: what it can't write it says on the console, but `durable` rejects then. Rows it doesn't read (a newer corrallm's kind) are left as they are. A store whose rows can't be read (the database couldn't be opened) starts empty, says why, and journals nothing (`durable` rejects once anything has changed), so nothing is sent without its record. What waited in a snapshot a damaged database was restored from may have gone since: the restore makes it unresolved and tells its sender (`store/restored.ts`).
- **Delivery** (`core/delivery/delivery.ts`): a message to an agent is delivered once the agent is idle (no turn, nothing asked, nothing queued in its session, nor on its way there from the run: `RunStore.sending`, a message whose record is on its way to disk first) and nothing holds it: its own or its group's pause (a kill too), a session that won't start (it stays first in line), a session that would act on a party's text unchecked (`#asking`: yours still go; you see it in Needs, `unasking/<agent>`, and its sender is told why): one that runs in a mode its adapter says never asks (`EngineCatalog.neverAsks`), or, on settings of its user's that are none of its modes (Codex's App Server on a custom policy), whose `started` event says they never ask (`asks: false`; `asksOf` reads Codex's: approvals `never`, or no sandbox with `on-failure`; `on-request` still asks about dangerous commands); one that says neither holds messages until permissions are reported, even if a startup mode was requested; one yet to start starts in its saved start mode if its connection starts in it (each asks), else in its CLI's own default: a session given no mode starts in the user's own default, which may never ask, so delivery reads it (`defaultAsks`: `session:options`' reader, in the canvas's project folder, its `defaults.asks`) once a session, again once that session ends, or with the next message sent RETRY_AFTER or more after a read that held its messages, and holds a party's message while it reads, while that default never asks, and while corrallm can't tell (a custom Codex policy it doesn't know, settings it couldn't read). A mode switched in either CLI’s terminal is seen only once the next hook fires. Codex’s permission_mode tells whether it asks, without distinguishing every sandbox preset; until that hook its last report stays in force. Claude Code’s managed (policy) settings are not read by `session:options`. Other holds are an exhausted usage backend (a turn hit its hard limit, held until its reset even without a rule), or its backend's usage rule (headless, a rule that asks waits for the reset, and one whose window's reset isn't known only warns, since nothing would read its usage again while messages waited; a usage hold the run set, `AgentRun.usage`, is that rule read now, so one a stopped run left, or whose window has reset, holds nothing), whether or not a run is going. A whole-run Stop, and the paused state a run restores in, hold only the run's own sends. A session that refused to start is tried again by the next message sent to its agent a minute or more after the refusal (`RETRY_AFTER`), which delivers the first in line; the sender's notice and the Needs item say so. A message goes only once its own record is on disk; one whose record can't reach it fails its `message` call and is unresolved, never sent; one whose delivering record can't reach it was never sent either, so it waits again, first in line, and nothing on its canvas is delivered until delivery tries again (`RECORD_RETRY`, a second on). Each is journaled delivering, with the id its session is sent it under (`delivery.as`), committed and flushed, then sent; the session's echo marks it delivered. Yours go past the run's holds into the session's queue, as typed; everything else is framed. A message's turn ending makes the agent's reply a message to its sender with the turn's `TurnResult`: a turn for an agent (its frame saying how the turn ended, when it didn't complete), a record for you or an outside party, and never answered by another reply. Each sender is told once (a `notice` from corrallm, keeping the key of what it told, so once across restarts too) when its message waits on a pause (naming who set it, and that only they or you can release it), a session that won't start, a mode that never asks, an exhausted backend or a usage window (every party whose messages wait, not only the first; told again once the agent holds again after it was released: a pause let go, a session that started, after a restart too, a mode that asks), when its turn waits for you (on its session's own prompt, or what its CLI asks in its terminal: never a hold of the run's, which holds no party's message), and when it ends withdrawn by someone else or cut off. A notice quotes a prompt's title and an agent's name on one line, cut after 120 characters, and a reason after 1000: never a whole command. Closing the core, or a crash, leaves what was delivering, or delivered with no turn end, unresolved, never sent again. What waits for an agent no longer on the canvas (or from one) is withdrawn by corrallm, its sender told. Before its first party message, delivery starts the session without sending and rechecks the native started mode or asks; an unasking or unknown report holds the message, while yours still go. A session that has not reported permissions waits for a report, even if an asking startup mode was requested. Codex on-request can still ask about dangerous commands without a sandbox; on-failure without a sandbox and never remain unasking.
- **Withdrawal after receipt:** `withdraw` returns `{ reached, interrupted }`, based on the session's receipt and how the turn ended, rather than a delivering record (which may still be on disk or in the session's queue). The CLI's history keeps a message it received, and work already done stays. With the next message delivered to that agent, from any party or the user, corrallm includes a note inside the same `[corrallm]` frame: the message's id and sender, that its sender withdrew it after it reached the agent and its turn was interrupted, not to carry out what it asked unless someone asks again, and that anything already done is left as it is. A kill (`run.kill`, of an agent or a group) leaves the same note for each message it takes back after its recipient received it, whichever end was killed: in place of its sender's withdrawal, whom the kill killed (the recipient, or else its sender) and who killed it, named as `core/parties.ts`' `quotedParty` names a party (the user, or anyone else's name in quotes; "at your own request" where the agent killed itself). A note quotes nothing of the canvas but parties' names, capped as notices cap them: never a body, a group's name or a queue's text. The run's own sends (queue steps and messages) leave none: they are no messages of the store, the run holds each task a kill interrupted in Needs you, cancelled, for the user to inspect, resolve or retry, and a note could name such a task only by its canvas text. Untold notes are kept with the withdrawn messages, across restarts and log pruning, until the CLI echoes the message carrying them. Several withdrawals are named together; one taken off the queue before receipt adds no note. A note never starts a turn by itself, except before a message the user typed that starts with any catalog shell prefix: then a separate framed note goes first and the shell-prefixed message goes alone. The transcript shows the text echoed by the CLI, including these notes; a separate note appears before the shell-prefixed message, and resumed history keeps what the agent was told. The note asks the agent not to act; it cannot force it or undo work.
- **Operations** (`core/ops/conversation.ts`, `session.ts`, `run.ts`, `wait.ts`): `wait` (outside tokens only: see Headless), `message` (to an agent, at most `MAX_MESSAGE_BYTES` of UTF-8), `withdraw` (your own message: off the queue, or its turn interrupted; you may take back anyone's still waiting; no canvas needed, the message says which), `messages` (the caller's own, after a cursor; you: all), `needs` (yours with their choices; a token sees yours on the agents it reaches without them or their forms, an MCP server's link among them, and an agent its team's prompts too; each item's id is unique on its canvas: `hold/<agent>/<item>`, `start/<agent>` for a session that won't start, `unasking/<agent>` for one that would act without asking (its mode never asks, its CLI's default never does, or corrallm can't tell), `limited/<agent>` for an exhausted usage backend, `prompt/<agent>/<prompt>`, the agent's id escaped), `agents`, `status`, `session.get`, `session.transcript` (paged by entry; an MCP server's link left out for a token, as in `needs`; it and `messages` end a page early rather than pass `MAX_PAGE_BYTES` of JSON; a transcript's first entry, of whatever kind, is cut to fit and marked `cut` when it alone wouldn't (a diff's last lines first, then its texts, then its lists), while `messages` gives whole messages, each at most `MAX_MESSAGE_BYTES` of text), `session.interrupt`, and `run.pause`, `run.kill` (which takes back what was sent to or from the agent, its recipient told of what had reached it: see Withdrawal after receipt) and `run.unpause`, on an agent or a group, each taking effect at once and returning once it is on disk (the canvas's run committed, and for a kill, in the same commit, what it took back at once, one being delivered once its interrupted turn ends; one that can't be fails `unavailable`, saying the change is in place but may not survive a restart), each pause stamped with the party that set it: a token releases only its own (rule `sticky`, R9: one whose release would let go of no pause that holds its target is refused, naming who set those), you any; `run.unpause` returns the pauses that still hold its target (another party's on it, or any on a group it is in: `RunStore.holding`), worded by `core/parties.ts`.

## Headless

`corrallm` is one Node CLI on the core's code (`src/main/cli/`; API Spec §8.6, Core Server §7.6), built by `pnpm build:cli` and run as `pnpm corrallm`, from a checkout kept for it rather than one being changed.

- It runs only on the Node package.json's `engines` names (24.21.0 or later, `NEEDED_NODE` in `cli/node.ts`): on an older one (`pnpm corrallm` runs whatever `node` is on the PATH) it says so in one sentence naming both, on stderr (for `wait`, as its one JSON line too), and exits 64, as a command line that can never work does, before anything else of it loads. Its entry (`cli/index.ts`) imports the CLI (`cli/main.ts`) only once its Node will do, and the build inlines that import to run only then (`codeSplitting: false`); Node's own modules are required as the bundle loads, before the check, so the CLI's code imports one an older Node lacks (`node:sqlite`) only where it uses it, never at the top (`cli/node.test.ts` runs the bundle as Node 22.18 without it).
- `corrallm serve --canvas <file> [--canvas <file>…] [--profile <dir>] [--port <n>] [--new-token [--name <name>] [--hours <1-12>] [--read-only]]` runs the core under plain Node, on the app's profile (`appProfile`) or `--profile`, with the Node host (`core/host/node.ts`: no dialogs). It makes a profile it lacks 0700, takes the profile's `core.lock`, opens its database, opens each `--canvas` only if canvas memory names that very file (by real path) for the canvas it holds and keeps a project folder for it that is still there (`Core.keptCanvas`; otherwise it says, naming the file, to open the canvas and pick its folder in the app), restores each run paused (which holds only the run's own sends, so parties' messages still reach idle agents), starts MCP (`api/mcp.ts`, its callers named by `TokenStore.clientOf`) on `--port` (kept as the profile's port), else `settings.json`'s `api.port` (chosen free once and kept), exiting with a sentence naming a port that is taken, writes `api.json` (0600: `{ url, port, pid, started }`), and logs a line to stderr per message, reply, notice and need (`Core.watch`, heard from before the canvases open, each named before it opens, so that what one has waiting as it opens is said by its name), every control character in it escaped (`\x1b`), since the names and titles it quotes come from canvases, agents and MCP servers. Canvases open held: nothing is delivered until every check that may refuse the start has passed (`Core.deliver`), so a refused start sends nothing; one told to stop as it starts (while it reads the login shell for `--new-token`, say) makes no token, delivers nothing and stops. It names each canvas by its file and id; on a profile other than the app's, it says to export `CORRALLM_URL`. SIGINT, SIGTERM or SIGHUP close the server, hold each run where it is, journal, end the sessions, write out the stores, close the database, remove `api.json` and release the lock; told again meanwhile, it says it is stopping already, and a stderr that went away (its terminal closed) never stops it short. Then it exits, its terminal gone or not: as the CLI exits (`cli/main.ts`' `exit`), it waits only for the streams its command printed on (`serve` never prints on stdout, which Node would open as it is first asked for, and on macOS opening a terminal that hung up never returns), and on a terminal at most a second. It exits 1 when it refuses to start.
- `--new-token` makes an outside token for the canvases named, called `--name` (`orchestrator` by default), read-write unless `--read-only`, for `--hours`, and prints it once, with the URL and each installed adapter's `registerMcp` filled in (`{server}` `corrallm-outside`, `{url}`, `{var}` `CORRALLM_OUTSIDE_TOKEN`), so the platform holds no CLI's syntax. Claude Code expands `${CORRALLM_OUTSIDE_TOKEN}` in a header `claude mcp add` saved (checked with 2.1.303: Build Plan Q23).
- `corrallm wait [--for <id>] [--after <cursor>] [--timeout <s>]` makes one `tools/call` POST of `wait` to `CORRALLM_URL`, else to the app profile's `api.json` while its process lives, with the token only from `CORRALLM_OUTSIDE_TOKEN`, and prints one JSON line (the result, or `{ error }`), exiting 0 (something came), 1 (the time limit passed), 2 (its token refused: none, a wrong one, one expired or replaced, the last told by `TOKEN_REPLACED`), 3 (no server answered, or a URL that isn't corrallm's on this machine, or none that can take the wait now: one that can't wait now, or the token's waits at their limit, told by `TOO_MANY_WAITS`; it may try again later) or 5 (the wait refused for what it asked: a cursor or message id the server doesn't know); a command line that can never work exits 64, with an `invalid` error line. It sends its token only to http on 127.0.0.1 or localhost (`loopbackUrl`), and finds a server in `api.json` only while a process with its pid and start time runs (`stillRuns`). `--timeout` is at most `MAX_WAIT_SECONDS`, an hour, and that by default.
- `wait` (`core/ops/wait.ts`; MCP only, deviation `transport`; a long poll, `waits` in its surface, which the limit on calls in flight leaves out, counting it against `TOKEN_WAITS` waits in flight instead) returns the messages addressed to the caller's party on its canvases after its starting point, oldest first, a page at most, or waits for the next until `timeoutSeconds` pass, its caller gives up, or its token is replaced or expires (then it is refused, `TOKEN_REPLACED`). The starting point is `after`'s place in each canvas's store (0 in one the cursor doesn't name), else the party's read position; `for` keeps what concerns one message, and moves nothing. Cursors say which op gave them: `wait` takes only its own and `status`'s (a `messages` cursor names one canvas), and none past what a store holds. Waits that read on from the read position (no `after`, no `for`) take turns, each reading it afresh, so one message wakes only one of them with it. It never consumes. One without `for` moves the party's read position forward (`core/delivery/reads.ts`), only once it is committed (`read_position`), before it returns: the party's, not the token's, so a renewed token reads on from it. Every canvas's position moves in one write (`Engines.advance`), with what each canvas has to journal, or none: a wait whose positions can't be written fails, so no message is skipped. `status`'s cursor is at the end of every canvas the caller has.

Exiting waits for every pipe to drain fully. Each terminal stream has its own one-second cap, so a terminal on stderr never cuts off wait’s piped JSON line.

## Adding an IPC channel

1. Declare it in `IpcContract` in `src/shared/ipc.ts`: `'domain:action': { args: [path: string]; result: Thing }`. Add the matching method to `InvokeApi` (part of `AppApi`) and its channel to `API_CHANNELS`.
2. Add an entry to `createHandlers` in `src/main/core/channels.ts`: `'domain:action': { parseArgs, handler }`. `parseArgs` receives `unknown[]` from an untrusted renderer and must validate every argument (type, length, allowed values) or throw. Use `noArgs` for channels without arguments.
3. Expose it in `src/preload/index.ts`: `action: (path) => invoke(API_CHANNELS.action, path)`.
4. Call it from the renderer as `window.api.action(...)`.
5. Extend `src/main/core/channels.test.ts` (argument validation and window identity) and `src/preload/index.test.ts`. If the UI uses it, stub it in `src/renderer/App.test.tsx` via `stubApi`.

The compiler enforces that main, preload and renderer agree on argument and result types, and that no contract channel is missing a core handler or an `AppApi` method.

Core-to-renderer events: declare the event in `IpcEvents` in `src/shared/ipc.ts` (`'domain:event': [agentId: string, thing: Thing]`), add a function to `EventApi` and its event to `API_EVENTS` (the compiler checks none is missing), expose it in the preload with `core.listen` (returning a function that stops listening), and send it with `Channels.emit` over the window's port to the canvas's windows only. `run:stopping` alone stays main-to-window through `sendEvent` and `ipcRenderer`; topic state uses the port's `topic(change)` contract instead.

## The catalog

What every adapter declares about the agent it runs is plain data, the catalog (`src/shared/adapter.ts`: `Catalog`, `AdapterDescriptor`, `ConnectionDescriptor`, `ModeDescriptor`, `UsageBackendDescriptor`, `AgentAction`; every id has `ID_PATTERN`'s shape; a step's job is one of `JOBS`). Each adapter fills in its own descriptor in its folder (`sessions/claude-code/adapter.ts`, `sessions/codex/adapter.ts`), and the registry (`sessions/adapters.ts`, the only file meant to import adapters' folders; ESLint's `app/adapters` allowlist names the platform files that still do, each to go: see Layout) builds the catalog from them (`CATALOG`: adapters sorted by name, and the usage backends they spend). The shared types name no CLI, and their comments give no CLI's examples.

- The ids: adapters `claude-code` and `codex`; connections `<adapter>.<name>`, in their adapter's order, the first its default (`claude-code.terminal`, `claude-code.sdk`; `codex.terminal`, `codex.app-server`); usage backends `claude-code` (Claude Code's Terminal spends it) and `codex` (both of Codex's), each with the windows `fiveHour` and `weekly`. They name everything stored (`.corral` files, the database's conversations, `settings.json`'s consents, `usage.json`, run checkpoints) and every IPC argument.
- Each adapter's contract test (`<its folder>/adapter.test.ts`) pins its descriptor: its ids and connection order, each mode's `asks` and `rank`, each connection's `startModes`, `shellPrefix` and `usage`, its `logo` and `registerMcp`, and that each connection's `live` and `panels` match the methods of the LiveSession its connector starts. `adapters.test.ts` checks what holds for every adapter (unique ids of the right shape, start modes that ask, declared backends, a connector and an options reader for each) and keeps the renderer tests' copy (see Testing).
- The core reads it in args.ts (a connection, an adapter, a mode a connection starts in, a usage backend), the manager (a connection's adapter and its modes) and usage.ts (the backends it keeps, in the app and in `createCore`; `usage.get`'s schema takes a backend by `ID_PATTERN`'s shape, since the registry names no adapter). The renderer gets it through `api.catalogGet()` (`catalog.get`) before it mounts (boot.ts) and reads it in usage.ts and catalog.ts's lookups, and reads files against it (`src/shared/model/file.ts`, as the core does); the engine (the run and the sessions) reads it through the `EngineCatalog` it is given (`src/shared/engine/catalog.ts`: an agent's adapter and connection, the adapter an agent naming none runs, its actions, the usage backend it spends, whether a connection starts in a mode, whether a mode never asks, a connection's label and a usage backend's name; `runCatalog` in agents.ts makes the renderer's, which its views also pass to the words they share with the run; the core makes its own, its default adapter the registry's `DEFAULT_ADAPTER`), never a table of its own nor the loaded catalog. ## Connected sessions

The core’s CLIs belong to its profile (`core/children.ts`, B8 Design §6): before opening any canvas it reads `<profile>/sessions/pids.json`, verifies each stale leader’s actual start time and private process group, and sends that group SIGTERM, then SIGKILL to the whole group after a three-second grace if it still runs. A missing or reused pid is never signalled. Failed cleanup never prevents startup: inspection or signalling failures, or a group surviving SIGKILL, warn with the pid and reason and keep its record for the next start, including across new children’s spawns and exits. Reading or updating the registry failing also warns and lets startup continue. Each new pty and stdio CLI, the Agent SDK’s custom-spawned process included, is recorded atomically and forced to disk before its spawner returns, and removed on exit. `sessions/process.ts` carries the profile’s owner through asynchronous operations, channels and engine backends with AsyncLocalStorage, so helper app servers, auth/version/help commands, the login shell and git are covered too; tests and self-test calls outside a composed core have no profile owner. Stdio processes use `detached` on POSIX; node-pty’s `forkpty` already creates its session and group. Windows keeps `useConptyDll: true`, records children and forgets exits, but creates no detached console and does no stale-group signalling: Windows process identity and group cleanup remain deferred until before launch. The registry holds only pid and start time, never arguments, environment or tokens.

An agent names its adapter (`adapter`: `claude-code` or `codex`, the catalog's ids) and its connection (`AgentConnection` in agents.ts: one its adapter offers; its adapter's first when it names none; `unavailable`, Not connected, when its adapter or the connection it names is one this build lacks, which is kept and saved back as it was, its work held with an actionable hold). Claude Code's connections are `claude-code.terminal` (its default) and `claude-code.sdk`; Codex's `codex.terminal` (its default) and `codex.app-server`. A connection names what runs it, so it implies its adapter and its view (the catalog's `view`: the CLI's own terminal, or corrallm's transcript; `adapterOf` and `isTerminal` in the renderer's catalog.ts). Modes are the adapter's (each classified in its descriptor with `asks` and `rank`: Claude Code's permission modes; Codex's presets, Read only, Default ('auto'), Full access, and Plan), validated against the connection's adapter in args.ts and the manager; a session starts only in a mode its connection's `startModes` names (args.ts). The composer offers an agent's own (`modesOf` in agent/modes.ts), and shows Your default until a native mode is reported (`Session.mode` and `session.get`'s `mode` are null meanwhile). There is no platform default mode. All runnable sessions use real native connections in main, over the `session:*` channels and the `session:event` event, in the protocol of `src/shared/session.ts`:

- The engine's connected driver (`src/shared/engine/transcript/receive.ts`, in the renderer in the app; its backend's calls reject in words fit to show: App.tsx's unwrap what IPC adds, `ipc-error.ts` fromMain) starts an agent's session only when its view opens (or its connection changes while it is open) or a message is sent (`session:start`: connection, and what the agent is set to run with in its CLI, its settings (see Agent settings: the store has them from the canvas, `SessionStore.sync`, and the driver reads them as it starts, `DriverIO.settings`); null for a model or mode not set, no effort for an effort not set; `Session.running` keeps what the session that runs started with), sends one message at a time (it keeps its own editable queue; the runner hears each turn's end through `SessionStore.send`'s `onDone`, with what the agent replied in it, and takes a message back with the function `send` returns: off the queue, or interrupting its turn), passes on answers to prompts, interrupts, mode, model and effort changes, and closes the session when the agent goes or runs another way. Session events from main are routed to the agent's driver only if they come from its current connection. A start that fails after a `notice` offering another connection (`switchTo`) is a refusal, not a failed turn: the message that started it goes back to the head of the queue, unsent (never a turn in the transcript; the refusal is said once), its sender hears through `send`'s `onRefused` (as do those of every message queued behind it), and it goes once the agent runs another way, or once the session starts after all (when its view opens again, or another message tries it again). main's `user` echo of a message marks it as the CLI's (`reached`), the only messages a rewind offers. Each message (and /clear's mark) is marked with the conversation it is of (`conversation`: its adapter's, which every connection of that adapter resumes, or `unavailable` for an adapter this build lacks), since an agent that runs another way keeps its transcript: the queue's Chat row and a rewind take only the conversation the agent is on now.
- The core (`sessions/manager.ts`) starts the session with the connection's `Connector` in the canvas's project folder (it refuses without one), with the agents' environment (the user's login shell's, cleaned of what corrallm was started from: `environment.ts`), resuming the agent's last conversation (remembered per canvas id in `memory.ts`, a `conversation` row, so sessions survive a restart: one per CLI, under `conversations` by adapter, each `{ id, role? }`, read back only if its id is a session id: Claude Code's session, Codex's thread; the same id is resumed whichever of its CLI's connections the agent switches to). It starts it with what the renderer gives (the agent's settings), nothing of its own: what is not given goes to the connector as null, meaning the user's own default model, mode and effort, else the CLI's. A mode that never asks (`UNASKING_MODES`, the catalog's modes with `asks: false`: bypassing permissions, Codex's Full access) is never an agent's setting or an explicit startup override: `session:start` takes only a mode its connection's `startModes` names, none of which is one (args.ts), and choosing one in the composer unsets the agent's mode. corrallm enters one only live, in a running session: from the composer's mode menu, which asks first (the composer keeps them out of Shift+Tab), or where a Terminal agent's CLI offers one in its terminal. But a session given no mode starts in the user's own default, which may be one (Claude Code's `permissions.defaultMode`, Codex's config.toml), so delivery holds parties' messages to an agent that would start in it (see Messages). A window that opens or begins another canvas, or reloads, crashes or closes (`core/windows.ts`: `SessionManager.closeCanvas`, keeping the canvas's conversations), choosing another project folder (which forgets them), and quitting (`before-quit` in index.ts) close sessions.
- A connector emits `SessionEvent`s through its `SessionHost`: `started` (model, mode, the models it offers, which the composer's model picker lists; a model may offer reasoning `efforts` (`EffortChoice`s: Claude Code's /effort levels, Codex's reasoning efforts, each labelled in its adapter's folder (`claude-code/efforts.ts`, `codex/efforts.ts`); the platform owns no effort names) and its `defaultEffort` where its CLI says it, which the composer's one effort picker lists, and then `started` says the `effort` it runs at (null: the model's default); and `modes` when it can't switch to every mode: bypassing permissions turned off by the CLI's settings, so the mode menu leaves it out; and `asks` where its mode is null because it runs on settings of the user's that are none of its modes, saying whether those ask before acting, `Session.asks`), then per turn: `user` (with the renderer's message id, or a new one for a message typed in a terminal), `status` (working, or waiting on the user) and entries by id (`text`/`thinking` stream in, `tool`/`todos` replace; `parent` nests a subagent's entries; a `tool`'s `progress`: how long it has run, what a subagent is doing and has used), prompts (`permission` with what "always" allows, `question` for AskUserQuestion with its header, its answers' meanings and whether several may be picked, `plan` for ExitPlanMode, `elicitation` for an MCP server's form or link; `withdrawn` when no longer asked), `notice` (compaction, retries, usage limits with their reset time, login problems, hooks that failed or blocked; `switchTo` offers another connection, shown as a button that switches the agent: a connector that refuses to start says why this way, before `start` rejects with the same words), `cleared` (/clear: the transcript marks it), `usage`, `mode`, `model`, `effort`, and exactly one `end` naming the messages it answered and carrying its required `result` (completed, cancelled or failed, with its native reason). `status` is never sent outside a turn: only `end` makes a session idle. In a turn or not: `tasks` (the work it runs in the background now, the whole list each time; the composer lists them with a Stop, as does each one's tool line), `suggestion` (what the user might send next, after a turn: the composer's empty box offers it, Tab takes it) and, from a Terminal session, `asking` (what its CLI asks the user in its terminal now, `TerminalAsk`s, the whole list each time, none once it goes on: listed in the canvas's Needs you sidebar, never answered from corrallm; a `trust` ask is its folder trust dialog, which comes before any turn) and `unheard` (once, as a Terminal session starts: corrallm can't hear its replies, because the user's or their organization's settings turn off its hooks, in a sentence that says what won't work; a warning in its session, and `Session.unheard` for the queues' Run). `closed` if the session stops by itself; it calls `remember(sessionId)` whenever its CLI's session id is known or changes (as after /clear).
- Restarting (`SessionStore.restart`, a Terminal agent's "Restart with these"): the renderer ends the session (`session:close`) and starts it again with the agent's settings now; the core resumes its conversation as for any start.
- Manual submissions are visible by default as read-only Message rows everywhere the queue is shown (`Session.submissions`, `queues/submissions.ts`). `SessionStore.send` defaults to user origin; the RunIO adapter explicitly marks automated sends as queue origin, while typed OK/repeat replies remain user origin. Live Terminal `user` events are recorded by message ID, with `end.messages` correlating their native turn outcomes; CLI echoes and restored history create no extra rows. Locally handled SDK slash commands use `recordSubmission` without sending a CLI turn. The UI reads projected nodes; save/edit/run operations read the original graph, so submitted messages never replay or become authored wait targets. Records survive conversation clearing within the current canvas session; durable run metadata belongs to 7d. Full transcript/screen snapshots are deferred to V2.
- Besides the turn, the renderer may answer a permission with a no and `feedback` (what to do instead: Claude's; Codex's No stops the turn), set the effort (`session:effort`, one its model offers or null for the model's default, for the session only; a session that starts again starts at the effort chosen, which the start carries) and stop a background task by the id `tasks` gave (`session:stopTask`). A connection that does neither leaves `LiveSession.setEffort`/`stopTask` out, and the manager refuses them (a Terminal agent sets them in its terminal).
- To build a connection: write its `Connector` in its own folder (`src/main/sessions/claude-code/sdk/`, `src/main/sessions/terminal/`, `src/main/sessions/codex/app-server/`), find the CLI with `requireClaude(spec.env)` (or `requireCodex`), declare it in its adapter's descriptor (`<adapter folder>/adapter.ts`: its id, `<adapter>.<name>`, and what it does, which the adapter's contract test pins), and register it in `connectors.ts` (`Connectors`: each connection's connector by its id, typed with its adapter's modes; `adapters.test.ts` checks every catalog connection has one). Its tests drive a fake CLI; the manager, IPC, renderer and UI need no change unless the protocol grows (then extend `session.ts`'s types, the engine's `transcript/receive.ts`, and their tests).
- Rewind: a `LiveSession` may restore its files to before a message (`rewindFiles`, with a dry run to preview: an Agent SDK session's, Claude Code's file checkpoints, `enableFileCheckpointing`; never while a turn goes on), over `session:rewind-preview` and `session:rewind` (`code`, `conversation` or `both`). Main rewinds a conversation by forking it (`sdk/conversations.ts`: a copy up to the entry before the message, `forkSession`), so either connection resumes the copy, across restarts too: the copy becomes the agent's own and its session ends, to resume it when it starts again (rewound to its first message, the agent starts afresh); the original stays, for /resume. It checks the message is in the conversation, and restores the files, before it forks or ends anything, so a failure changes nothing. A copy has no file checkpoints from before it (the SDK copies none), so its earlier files can no longer be restored, as the preview then says. A Terminal session rewinds in its terminal (Esc twice there).
- /mcp: a `LiveSession` may show its MCP servers itself (`mcpServers`, `changeMcpServer`: an Agent SDK session's, from the CLI's `mcpServerStatus`, `reconnectMcpServer`, `toggleMcpServer`), over `session:mcp` and `session:mcp-change`; a Terminal session's are its terminal's own /mcp, and Codex's App Server answers /mcp itself.
- /resume: `session:list` lists the conversations Claude Code kept for the canvas's project folder (`sdk/conversations.ts`: the SDK's `listSessions` for the folder's real path, not its worktrees', most recent first), saying which is the agent's own; `session:resume` makes one the agent's own (its session ends; it resumes that one when it starts again). Main opens only a conversation it listed for that renderer and the folder it has now: the renderer names one, never a path.
- Beyond turns, a session can send `commands` (the slash commands the composer completes; again when they change) and `history` (a resumed session's past turns, as events: the renderer puts them ahead of its transcript unless it shows them already, matching entries by id). A message may carry pasted `images` (validated in args.ts: kinds Claude reads, base64, at most 5 MB each). The composer's @-mentions search the project folder over `project.files` (`src/main/files.ts`); the renderer sends the canvas from `window.get` and what was typed, and the core reads only its chosen folder through `ProjectFolders.of`. At most `MAX_FILE_MATCHES` paths are returned, folders ending in `/`; without a project folder the list is empty.

### Agent settings

What an agent runs with by an adapter (`AgentSettings` in `src/shared/session.ts`: its model, reasoning effort and the mode its sessions start in, each only if set) is the agent's, in its node's data (`settings`, by adapter: `{ 'claude-code'?, codex? }`, so switching between Claude and Codex loses neither), saved in its `.corral` file (file.ts checks it: a model by `MODEL_PATTERN`, which never starts with a dash, an effort by `EFFORT_PATTERN`, a mode the catalog lists for that adapter with `asks: true` that its connection names in `startModes` (for its own adapter, the connection it runs; for another, any of that adapter's), and nothing else; an adapter the catalog lacks has its settings checked for shape only) and copied to an agent spawned from it. Switching an agent's connection or adapter drops a saved mode the connection it then runs does not start in (graph.ts), so what the app saves always reads back. Both of an adapter's connections start with them (`session:start`, which refuses a mode outside the connection's `startModes`); the core keeps none of its own. They are set in the shared Agent settings sheet (`AgentSettings.tsx`), opened from the session-header summary, the summary in All queues, or Settings… in an agent's context menu. It contains Name, CLI/connection, Role, and native startup Model/Effort/Mode. Claude and Codex default to real Terminal connections. An adapter or connection this build lacks says Not connected; missing CLIs fail visibly. No agent simulation or fabricated replies remain. The quick agent chip and a structured session's live composer controls remain shortcuts.

- **Role** is CLI-independent standing instruction text (`data.role`, top-level `role` on a file's agent node), separate from the per-CLI model/effort/mode settings. `shared/role.ts` trims it, removes blank values, rejects non-text/control characters and caps it at 16,000 characters. Templates discover/fill role blanks; changing CLI, inserting a template, and spawning an agent preserve it. A role never becomes a user prompt or Message row.
- **Changes and native conversations.** Editing the role or startup choices saves them without interrupting the session. `Session.running` captures what it started with. Main remembers a SHA-256 role fingerprint (or `none`), never its text, beside each CLI's conversation ID; it is forgotten with that ID. A resume with no fingerprint counts as a changed role once. For Claude, the sheet offers an idle-only restart that resumes the same native conversation; the SDK preserves its claude_code preset and appends the role, while Terminal uses --append-system-prompt. Both disable saved system-prompt snapshots only when the resumed role changed or was removed. Terminal reads --help only for a role, an effort or a changed role.
- **Codex limitation.** Current Codex 0.162.1 retains plain developer instructions in resumed history (upstream issue #19045), so a same-ID restart cannot guarantee a changed role. The sheet explains this and offers an explicit idle-only new conversation. `session:fresh` closes the agent, durably clears only the selected CLI's remembered ID and role fingerprint, then opens its current settings; the old native conversation remains available in the CLI's history. Ordinary restart keeps exact-ID resume. Both connections read effective native developer_instructions only for a current role (appended on every launch) or a changed role (restoring native instructions when removed).
- **Startup choices.** Model and Effort use native options/defaults. Claude Terminal's Mode is limited to --permission-mode values, Codex Terminal to Read only (Default uses its config, Plan is chosen in the terminal). Structured connections offer their supported modes. Modes that never ask are chosen live, not persisted as startup settings. The structured composer's model/effort/mode controls still change its live session and the saved settings; bypassing permissions or Full access unsets the saved mode.

What a CLI's agents can be set to, and the user's own defaults, come over `session:options` (one CLI; main reads in the canvas's project folder, else the home folder, with the agents' environment, never changing anything; the renderer asks once per CLI and project folder, `SessionStore.settingsOptions`):

- Claude Code (`claude-settings.ts`): no prompt, no session, and never the Agent SDK on a subscription, so no model list from the CLI. The models are the aliases `claude --model` takes (opus, fable, sonnet, haiku: Claude Code's descriptions from 2.1.296's list), only those in the user's `availableModels` where set, plus their own model if it is none of them, each with Claude Code's effort levels. The defaults are read as Claude Code reads its settings (project local, project, user in CLAUDE_CONFIG_DIR or ~/.claude: `model`, `effortLevel`, `permissions.defaultMode`), with ANTHROPIC_MODEL and CLAUDE_CODE_EFFORT_LEVEL (environment, or a settings file's `env`) over them; managed settings are not read.
- Codex (`codex/options.ts`): a private `codex app-server` (the folder trusted for it alone, as a Terminal session trusts it) asked only `model/list` and `config/read` (no thread, no model asked, so no usage and no consent on a ChatGPT plan), then closed: Codex's models with their efforts and default effort, and the config's model (else model/list's `isDefault`), `model_reasoning_effort` and the preset its sandbox and approvals make (recorded in `app-server/fixtures/options.jsonl`).

The Agent SDK connection likewise shows what will be used before the first turn: get_settings' `effective.model` (by alias, else its id) or `applied.model` (ANTHROPIC_MODEL…, unless it is just the account's default) is `started`'s model, and the user's effort (`applied.effort`, else `effortLevel`) each model's `defaultEffort` where it has that level (`sdk/settings.ts`, `startingModel` in `sdk/connector.ts`).

### Agent SDK

`src/main/sessions/claude-code/sdk/` runs a Claude agent through `@anthropic-ai/claude-agent-sdk` (bundled into main: devDependency, root entry only; its per-platform CLI copies are skipped in `pnpm-workspace.yaml`, `ignoredOptionalDependencies`). Rules it keeps:

- One streaming `query()` per session, fed by an `Inbox`, so the CLI runs between turns (interrupts, mode and model changes need it). It runs the user's own `claude` (`pathToClaudeCodeExecutable`), never a JS CLI, with Claude Code's own system prompt (`systemPrompt: { type: 'preset', preset: 'claude_code' }`; without it the agent is bare), the user, project and local settings, `permissionMode` only when the agent was given a mode (Manual is the SDK's `default`; otherwise the user's own default mode applies, and `started` reports it from the CLI's settings: `settings.ts` asks the running CLI with `get_settings`, which the SDK's Query has at runtime though its types leave it out; the first turn's `init` corrects it if the CLI says otherwise), `allowDangerouslySkipPermissions` (so the mode menu can switch to bypassing permissions once the user confirms it there; as in Claude Code, Shift+Tab never cycles into it, and where the CLI's settings turn it off, `permissions.disableBypassPermissionsMode`, read with `get_settings`, it is not offered), partial messages (streaming), summarized thinking (`--thinking-display`), `perTaskStopAffordance` (interrupting stops the turn, not background work), file checkpoints (`enableFileCheckpointing`, which rewinds restore) and `onElicitation` (MCP servers' requests).
- Each message is sent with the renderer's id as its uuid and `origin: { kind: 'human' }`, but another party's (one the core delivers for an agent or an outside orchestrator, `UserMessage.from`: the renderer can name no sender) as a peer's, `{ kind: 'peer', from: <its party>, name }` with no `fromMode`, so its trust gates never take it for the user's. A peer's message the CLI would hold for its user's review (nowhere corrallm shows it) or refuse, which no result would ever end, is never sent: where the settings' `crossSessionInbound` (read with `get_settings`) holds or refuses messages from other sessions, or, unless it accepts them, while the session bypasses permissions, the send rejects saying why, and the turn fails with those words, which its sender's reply carries (Delivery holds a party's message while a session runs in a mode that never asks anyway, so the latter only meets a mode switched as it was sent). The fake CLI holds such a message, never answering it, as the CLI does; a turn ends on the `result` whose `user_message_uuids` name it. A result naming none of the messages waiting (a background task's follow-up) ends none of them. Interrupt asks the CLI to cancel what it queued too, and ends what it cancelled.
- Its session id is remembered once a turn has run (the CLI writes the transcript from the first message), and again after /clear. An id with no conversation (one a Terminal session of the agent was given before its first message: the connections share the agent's id; or one whose transcript is gone) starts afresh quietly, as a Terminal session does; a session that cannot be resumed otherwise starts afresh, with a warning. A resumed session's history comes from `getSessionMessages` (history.ts).
- Entry ids are stable between live and history: text and thinking are `<API message id>:<block index>`, tool calls their `tool_use` id, user messages their uuid.
- Prompts are canUseTool calls: permissions offer "always" only where the CLI suggests a rule to keep (its suggestions, worded as Claude Code words them); No denies and stops the turn, as the CLI's No does; No with what to do instead denies with Claude Code's own message and those words, and the turn goes on. An approved plan is carried out in the mode chosen once the CLI has left plan mode (it reports the mode it goes back to). An MCP server's request (`onElicitation`) is a prompt too: a form, in the flat JSON Schema the protocol allows (`mcp.ts`; one corrallm can't show is declined, and the user told), whose answer main checks against the form before it goes back (one that does not fit is refused and the form still waits), or a link the user opens through `link.open`.
- Live progress and the background (translate.ts): `tool_progress` and `task_progress` become a tool's `progress`; `task_started` ties a task to the call that started it, and `background_tasks_changed` (a level: each one replaces the list; housekeeping tasks left out) becomes `tasks`. `stopTask` stops only a task in that list (query.stopTask; its notification ends its line). Hook events (`includeHookEvents`) show only what Claude Code shows: a hook that failed ("… hook error: …") or blocked ("… hook returned blocking error: …"; a Stop hook's "… hook feedback: …"), never what hooks print when they work. Predictions of the next message (`promptSuggestions`) arrive after a turn's result. The effort is set for the session only (`applyFlagSettings({ effortLevel })`, as /effort does without saving; null goes back to the model's default; only one of Claude Code's levels), and set as the session starts when it was given one its model takes (`started` says it). Each model's levels are offered with Claude Code's own words for them (`CLAUDE_EFFORTS`).
- History (history.ts): a turn lasts until its own last work (never the next message, nor what the CLI noted later); a slash command's output shows even when the transcript keeps it as meta (as /context's is). The SDK keeps no live result records: replay uses saved completion, refusal and interruption markers, and emits no `end` for an unknown outcome. An App Server turn still in progress likewise has no historical `end`.
- Logins ("Terminal for subscriptions"): Anthropic doesn't allow other products to offer claude.ai logins or subscription rate limits through the Agent SDK without its approval. So wherever corrallm offers a Claude connection, Terminal comes first (Claude Code's descriptor lists it first, and its contract test pins that; new agents default to an adapter's first connection, and spawned agents keep their source's connection), and the Agent SDK connection starts only with an API key (ANTHROPIC_API_KEY, an apiKeyHelper, ANTHROPIC_AUTH_TOKEN) or a cloud provider (Bedrock, Vertex, Foundry, a gateway). Before `query()`, `login.ts` asks the CLI how it is logged in: `claude auth status --json`, run by main with the agents' environment in the project folder (so a project's apiKeyHelper counts). That is the check, not the SDK's own `account`/`apiKeySource` reports, which come only once the CLI runs under the SDK. A claude.ai login (`authMethod: "claude.ai"`), a `claude setup-token` token (`"oauth_token"`), or a status it can't read refuses the start: a `notice` (one sentence, offering Terminal) and a rejection. Not being logged in at all starts, and the CLI says so. corrallm reads only what kind of login the CLI reports, and whether ANTHROPIC_AUTH_TOKEN is set, never a credential's value; it passes none. The Terminal connection runs the CLI itself, with any login.

### Terminal

- A Terminal session (`sessions/terminal/session.ts`) runs whatever CLI its TerminalCli describes (`cli.ts`): how to start and resume it (in the user's own default mode unless given one; unknown until its reports say), what its screen reports (Program Status, or its window title), what its hooks mean (`TerminalSignal`s: its session id, prompts it took, its reply, a failure, its state when its screen does not say, its mode and model, what it is about to ask the user, what its notifications say it needs), how to read its prompt's draft and type into it, and its words (`words`: what it waits on, by its report's kind). Turns, waiting on the user, what it asks listed outside its terminal (`asking`), typing the queue's messages once the prompt is ready, files dropped on it pasted in, views and closing are the same for every CLI. A CLI that picks its own session ids (`newId()` is null) is remembered once its hooks tell it. A CLI whose reports leave out some dialogs (`waitsForPrompt`) is typed into only while its prompt is drawn, one that holds a message while it gets ready (`holds()`) is waited for rather than given up on, and one that reads keys late (`waitsForEcho`: Claude Code) gets Enter once its prompt shows the end of what was typed (at most `TerminalTiming.echo`).
- The Terminal connection (`sessions/claude-code/connector.ts`, on the toolkit in `sessions/terminal/`) runs Claude Code's own interactive CLI, so the user has all of Claude Code in the agent view (`TerminalPane.tsx` in place of the transcript and composer): its prompts, modes, models, slash commands and dialogs are answered there. It is started with `--settings` (a file in the temp folder: corrallm's HTTP hooks, merged with the user's, and corrallm's status line: see Usage readings and rules), `--session-id` (new) or `--resume` (one with no transcript starts afresh under the same id), and `--model`/`--effort`/`--permission-mode` only when the agent is set to them (an explicit Manual too, as `manual`, one of the flag's choices; `default` as a model is left out; `--effort` only with one of Claude Code's levels, and only where its `claude --help` lists the flag, asked once per executable: `claudeFlags` in claude.ts, since an older CLI would not start with it): otherwise the user's own defaults apply. corrallm follows it to orchestrate it: Claude Code's Program Status reports (OSC 7501, answered and read in main's copy of the screen) say when it works, waits on the user, is done, was interrupted (idle) or failed; its hooks (`hooks.ts`) tell the session id (it changes with /clear), prompts typed in the terminal, the last reply, failures (StopFailure names its error, which the turn's end carries as its reason, mapped as the Agent SDK's are: `claude-errors.ts`), mode and model. A message corrallm sends is typed in (a few characters at a time, Ctrl+J for line breaks, then Enter: never a paste, which Claude Code collapses and treats as untrusted) once the prompt is ready: Claude Code idle or done, and nothing the user typed in it; Enter goes once the prompt shows what was typed (keys that pile up while Claude Code is busy, as right after the folder trust dialog or as a turn ends, are read in one go as a paste, where 2.1.296 keeps an Enter as an invisible character, not a submit). Meanwhile, a dialog (the folder trust prompt) or the user's draft makes the turn wait on the user. A turn ends once Claude Code has taken every message sent in it and stopped working; one the user started in the terminal is a turn too. Answers, modes and models are refused over the session channels: they belong to the terminal.
- Folder trust: Claude Code asks whether to trust a folder the first time it runs there ("Quick safety check…", default "No, exit"), before it reports anything or runs a hook, so the session reads it from the screen (TerminalCli's `trusting`): while it shows, `asking` lists a `trust` ask, turn or not, and a message waiting for the prompt waits on the user at once. The CLI is past its first-run dialogs once it reports its state, a hook posts, or its prompt shows. Every Claude Code started before the user answers would ask again, so Claude's Terminal connector has its sessions in a folder (by real path) take turns (`first-run.ts`): one starts first; the others wait (held: `started` is sent, their screen says why, a message for them is `working`) until it is past them (then all start, and so does every later one) or it ends without (the next one goes, and asks). Codex is told the folder is trusted on its command line, and never asks (checked with 0.160.1 in a fresh folder).
- What Claude Code asks in its terminal (`asking`, from its TerminalCli's hook signals, `claude-code.ts`): its PermissionRequest hook tells a permission prompt's tool and input (worded by `sdk/tools.ts`: its summary, and what the prompt shows, `proposedDetail`, cut to 12 lines by `preview` in transcript.ts), PreToolUse (only for AskUserQuestion and ExitPlanMode) its questions and plan (PermissionRequest tells them too, without a call id: told once), Notification what it needs when nothing else says (an MCP server's question). Recorded from 2.1.296: the hooks come just before its Program Status says `blocked` (with `kind` permission, question or auth, and `msg`, as "approve Bash: git init" or "answer: Pick a color (Red · Blue)"). The session lists what the hooks told within a few seconds before a wait began, or else the wait's `msg` (or the notification's words, or the CLI's own for the wait's kind), while it waits; once it goes on (the user answered in the terminal), the turn ends or the CLI exits, it lists nothing. Without status reports, what the hooks told is listed until the turn ends. Every hook is answered with no decision. Codex tells nothing ahead: while its title says Action Required, its wait is listed in its own words.
- Hooks turned off: corrallm hears Claude Code's replies, prompts, session ids and asks only through its hooks. When a session starts, `hooks-off.ts` reads the settings Claude Code reads (never writing them): the organization's managed settings (`managed-settings.json` and `managed-settings.d/*.json` in the OS's folder: `/Library/Application Support/ClaudeCode`, `/etc/claude-code`, `C:\Program Files\ClaudeCode`), then the project's `.claude/settings.local.json` and `.claude/settings.json`, then the user's (`CLAUDE_CONFIG_DIR` or `~/.claude`). They turn corrallm's hooks off with `disableAllHooks` (the most particular that sets it wins; the status line goes too, so no usage readings), `allowManagedHooksOnly` or `strictPluginOnlyCustomization` locking hooks (managed only), `allowedHttpHookUrls` without a pattern matching its server on 127.0.0.1, or `httpHookAllowedEnvVars` without its token's variable (both lists merged across files). Then the session says so once, as it starts (`unheard`: which setting, where, and that the run can't read its replies). Not read: managed settings from a server or an OS policy.
- The view, for every Terminal agent: files dropped on it are pasted as their paths (the preload reads them from the files with `webUtils.getPathForFile`; `terminal.drop` checks them; the core pastes those that exist, quoted for a shell, `drop.ts`, bracketed when the CLI asked, so Claude Code takes an image's path as the image). On a Mac, Option works as Meta only on a US-like keyboard layout (`navigator.keyboard.getLayoutMap`; elsewhere Option types characters, as @ on a German layout), unless the user chose otherwise with the switch in the bar (kept in localStorage). When the screen is reset (a snapshot, as for a new CLI process), the view fits it and draws it afresh (`Screen.redraw`). Links Cmd-clicked in it go to main (`link.open`; a file:// link to `link.reveal`).
- Terminal views: `terminal.attach` asks the core to show an agent's terminal; the core sends the port's `event('terminal', [agent, TerminalEvent])`, heard through the typed client's `terminalOnEvent` (`src/shared/terminal.ts`): the screen as it is (a snapshot of its headless copy, now or once the session starts, and again for each new process), then the CLI's output, then its exit. The view (`link.ts`) writes the snapshot from scratch, drops what its terminal answers while doing so, then passes keystrokes (`terminal.input`) and its size (`terminal.resize`) on. The pty lives in the core: closing the view (`terminal.detach`) leaves the session running. While no view is shown, the core's copy answers the terminal queries a pty needs answered (DA1, which Windows' ConPTY waits on).

### Codex

- `codex.ts` finds the user's `codex` (CORRALLM_CODEX_PATH, the standalone installer's ~/.local/bin, the login shell's PATH; on Windows npm's native `codex.exe`, never its `.cmd`) and checks its version against `MIN_CODEX_VERSION` (0.160.0: what the fixtures and protocol were read from). Codex keeps its own home (~/.codex: config.toml, AGENTS.md, skills, MCP servers, sessions), so corrallm's threads are the user's (`codex resume` sees them, and corrallm can resume theirs).
- `rpc.ts` runs a private `codex app-server` per session over stdio (never the shared daemon a desktop app runs, never `--listen`: its sockets are unauthenticated), says hello (`initialize` with the experimental API, then `initialized`), always sends params (Codex refuses a request without them), answers every request the server makes (an unanswered approval stalls the turn; unhandled methods get -32601), drains stderr, and closes by ending its input, then SIGTERM, never SIGKILL (that orphans what it runs). The renderer never gets raw JSON-RPC or a generic channel: each action gets a typed `session:*` channel.
- Logins: corrallm never reads, stores or passes credentials; Codex uses its own (`codex login`), and corrallm asks its app server only which kind it is (`account/read`, `login.ts`). The App Server connection runs on any login, a ChatGPT plan included, because OpenAI allows it for local apps (learn.chatgpt.com/docs/app-server, Auth endpoints: "If you’ve built a local or open-source application using Codex app-server authentication, you can continue using it… App-server authentication has never been permitted for commercial or hosted services."). So on a ChatGPT login a session's first turn that would use the plan (a message, /review, /compact, /init) first asks (`planPrompt`, quoting that): Yes allows it for the session, "don't ask again" for good (the `codex` consent `plan` in `settings.ts`, through `Consent` in sessions/adapter.ts), No sends nothing; interrupting withdraws it. A build made as a commercial or hosted product (`CORRALLM_DISTRIBUTION=commercial` or `hosted` when building: vite.main.config.mts defines `CORRALLM_DISTRIBUTION`, 'local' by default) refuses a ChatGPT login instead (`appServerRefusal`), leaving the plan to Codex · Terminal, which is Codex's own CLI. Sign in with ChatGPT (developers.openai.com/siwc), which OpenAI recommends instead, is not built: it would have corrallm keep and refresh the user's OAuth tokens.
- The App Server connection (`codex/app-server/`) runs a Codex thread in corrallm's transcript. Rules it keeps:
  - One private app server per session, closed with it. Its thread starts (`thread/start`) in the project folder with the approval policy and sandbox of the mode it was given; with none, it passes no permission overrides and reports Codex's actual policy. Modes are Codex's /permissions presets (Read only: read-only sandbox, on-request; Default: workspace-write, on-request; Full access: no sandbox, never) and Plan (Codex's plan collaboration mode, with Default's permissions). Every `turn/start` carries the model and effort; only a chosen mode adds approval policy, sandbox policy (the one Codex reported for the thread when of the same kind: it carries the user's own config.toml settings) and collaboration mode, which Codex keeps, so a mode switched mid-turn applies from the next turn. `clientUserMessageId` is the renderer's message id, so a resumed thread's history (`thread/resume`'s `initialTurnsPage`, its last 30 turns) matches what was shown live. A thread is remembered once it has a turn (Codex keeps none without), and one that cannot be found starts afresh quietly.
  - A turn ends with `turn/completed`. A plan proposed in plan mode is asked about once its turn ends ("Implement this plan?", as Codex's TUI asks): Yes switches to Default and sends "Implement the plan." in the same corrallm turn, so the queues' Run hears its end once the plan is carried out; feedback keeps planning; no feedback ends it.
  - Codex's requests are prompts, answered as its TUI answers them (`availableDecisions`): Yes is `accept`, "always" the decision Codex offers to keep (this session, a command prefix, a host), No `cancel`, which stops the turn. Codex remembers what "always" allowed: corrallm never answers for the user. Questions (`request_user_input`), MCP elicitations (a form's fields as questions, a link) and permission requests are prompts too; a request Codex stops waiting for is withdrawn, and every one is answered.
  - Tools keep the names Codex's model knows (`exec_command`, its command unwrapped from the user's shell; `apply_patch`, an entry per file with its diff; `web_search`; `mcp__server__tool`; `spawn_agent`…: a subagent's thread nests under the call that spawned it). Reasoning summaries are thinking (Markdown), `update_plan` the turn's to-do list, compaction and reviews notices, and command output streams at most every 150 ms. Usage is the last request's context and the plan's 5-hour and weekly limits (`account/rateLimits/read`, then updates; read once, `limits.ts`, for the composer and for the usage readings); errors say what to do by `codexErrorInfo` (log in again, when a usage limit resets, /compact).
  - Slash commands are Codex's (commands.ts), run as its TUI runs them: /review, /compact and /init are turns of the thread; /model, /permissions (never to Full access: see Security rules), /status, /mcp, /skills, /diff (git, run by the core with the repository kept from running anything), /new, /clear, /rename are answered by the session. Skills are slash commands too (`/name` is sent as `$name`, with the skill attached). Pasted images go as data: URLs (the app server refuses remote ones), and not to a model that reads none.
- App Server interruption currently sends `turn/interrupt`, cancelling the turn without explicitly terminating its unified-exec commands. An interrupted turn is not a command-exit acknowledgement: the recorded interrupt ends without one, and the fake's slow command is only a timer loop. Codex has separate experimental `thread/backgroundTerminals/clean` (all thread terminals) and, in its current protocol, `thread/backgroundTerminals/terminate` (one app-server process id); `command/exec/terminate` belongs to client-started `command/exec` sessions, not the agent's `exec_command` tool. Command cleanup needs a separate choice of scope and supported CLI versions; interruption does not currently promise it.
- Codex · Terminal (`codex/terminal/`) runs Codex's own interactive CLI on the shared Terminal session (see Terminal), so the user has all of Codex in the agent view: its approvals, questions, plans, slash commands, models, @-mentions and images are answered there, and answers, modes and models are refused over the session channels. corrallm checks its version (`MIN_CODEX_VERSION`), then starts `codex --no-daemon -C <folder>` (its own agent, never the shared daemon a desktop app runs; `codex resume <id> …` to resume, and "No saved session found" starts afresh) with overrides for that session alone (`-c`; the user's config.toml is never written): the folder trusted (the folder dialog is the trust gate), corrallm's hooks (`hooks.ts`: UserPromptSubmit, Stop and Interrupt, each a command that posts the event to `terminal/hooks.ts`'s server with the session's token, through `/bin/sh` and curl, printing nothing and always succeeding) and their trust (`hooks.state`, by the key and hash Codex trusts each by: computed as Codex 0.160 does, and checked once per Codex executable and version with Codex itself, `hooks/list` on a private app server, `trust.ts`; without it Codex stops at "Hooks need review"), its window title set to `["activity","run-state"]`, no update prompt, no automatic recaps. Only Read only starts it from its command line (`-s read-only -a on-request`: the connection's one `startModes` entry); Default and Plan leave the user's own defaults (Plan is Shift+Tab in its terminal), and Full access, which never asks, is never a start mode (it is chosen in its terminal). The model and reasoning effort the agent is set to (see Agent settings) start it with `-m` and `-c model_reasoning_effort`. Codex picks its thread id; its hooks tell it (a subagent's are left out). Their permission_mode also reports whether it asks: bypassPermissions (or dontAsk) is Full access, default/acceptEdits asks again, plan is Plan. A switch in its terminal reaches delivery only once the next hook fires; until then the last report remains in force. Its usage limits are read apart from its terminal, never by typing /status into it (see Usage readings and rules).
- corrallm follows Codex by its window title (`tui.ts`): a spinner and Working, Thinking or Waiting is working, "Action Required" waits on the user, "Starting" is its MCP servers starting (a message sent meanwhile is held, and waited for), Ready ends the turn: done after its Stop hook (whose reply is the turn's), interrupted after its Interrupt hook, failed if it took a prompt (UserPromptSubmit) without either (Stop does not run for a turn that errs, as at a usage limit). Its composer (`composer.ts`) is where its cursor shows (Codex hides it during dialogs): a message is pasted in there (bracketed paste, without control characters, then Enter a little later) only while it is drawn and empty, and only once its title has said something (it says nothing while a startup screen is up). Its Enter is not held until the composer shows the message (no `waitsForEcho`): 0.160.1 sends on an Enter read in one go with the paste, as keys that piled up while it was busy are.

## Usage readings and rules

A backend's usage limits belong to its account, so the core keeps one reading per backend (`src/main/usage.ts`, types and checks in `src/shared/usage.ts`): how much of each window (`fiveHour`, `weekly`) is used and when it resets, with when it was read, remembered across restarts in the app's user data (`usage.json`, version 2), and nothing else the CLI said. The backends are the catalog's (each adapter declares those its connections spend, and each connection's `usage` names one: `claude-code` for Claude Code's Terminal, `codex` for both of Codex's, none for the Agent SDK); the core keeps no reading of another, and a `.corral` file or checkpoint naming a backend this build lacks keeps it, unread. The renderer’s usage store follows the `usage` topic through its mirror (`renderer/api/topics.ts`), and calls the generated `usage.setRule` and `usage.simulate` operations for edits. `usage:changed` and its preload listener are gone; the remaining hand-written usage channels stay until their deletion. Rules are the user's, one per backend, kept by the core with the readings, not in `.corral` files.

- **A hit hard limit.** A turn that fails with `usage-limit` and a `resetsAt` marks its usage backend exhausted until that reset, independently of any rule. The core forces this fact to disk in `usage.json` (`exhausted`, with the window when known) before publishing the hold or the failed turn, across restarts, for every agent spending that backend on every canvas. A hold it can't force to disk is never published (`UsageReadings.exhaust` rejects): it holds all the same until the core stops, the core says so on stderr, and the failed turn still ends; the next turn to hit the limit writes it again. Parties’ messages wait, with one notice to each sender naming the agent, backend and reset in the host’s locale; delivery’s own clock wakes them at the reset. A fresh reading showing room in the exhausted window, including a simulated reading, releases them too; an omitted window says nothing, and forgetting a reading or removing a rule releases no hard limit. Since nothing is delivered to a held backend's agents, no session of it starts to report a limit that ends early (the user resetting their plan's usage), so the core reads a held backend itself (`core/usage-probe.ts`): by its adapter's `readUsage`, which spends nothing (Codex's: a private `codex app-server` asked only `account/rateLimits/read`, run as a CLI the core owns, with the agents' environment, in the home folder, since the limits are the account's), as the core starts and then every 10 minutes (`PROBE_MS`) while the backend is held, one read at a time; a reading goes to `UsageReadings.take`, and one that fails or says nothing changes nothing. A backend whose adapter has no reader (Claude Code's) holds until its reset. Tests give the core their own readers (`CoreConfig.sessions.readUsage`); fake sessions read none. The user’s own messages still go as typed, past the hold. `status` and `agents` show an otherwise idle agent as `limited`; Needs lists its exhausted usage until the reset, without choices, even when no message waits. The state and Need disappear at the reset. Rules still act before the hard limit.
- **Where readings come from.** `UsageReadings.take(backend, windows)` is the one way in; each connection gets it from `createConnectors({ usage })` and adapts what its CLI reports. Claude's Terminal connection: `sessions/claude-code/statusline.ts` (below), heard through its TerminalCli's `statusLine` (a Terminal session passes what its CLI says of usage to `TerminalSessionDeps.usage`). The Agent SDK connection runs on an API key (decided Oct 12, 2026), which has no usage windows: it reads nothing, and its agents are not held by rules (`usageBackendOf` in the engine's catalog, `src/shared/engine/catalog.ts`).
- **Codex's readings.** `codex app-server` reports the plan's limits as a RateLimitSnapshot (`account/rateLimits/read`'s `rateLimits`, and each `account/rateLimits/updated`): `sessions/codex/limits.ts` reads Codex's own (`limitId` codex; a model's are not the plan's) once, for both the App Server's composer and the readings, naming each window by its length (300 minutes → `fiveHour`, 10080 → `weekly`; where Codex says no length, `primary` → `fiveHour`, `secondary` → `weekly`), `usedPercent` kept from 0 to 100, `resetsAt` (epoch seconds) × 1000 if within a week and a day. The App Server connection reads them as it connects and hears each update (its Translator's `usage`). Codex · Terminal's TUI tells corrallm nothing of them, so its TerminalCli's `readUsage` asks a private `codex app-server` (`codex/terminal/usage.ts`: the user's own `codex`, in the project folder, asked only `account/rateLimits/read`, then closed, through `askAppServer` as for its hooks' trust) when the session starts and after each turn ends; one read at a time for every Codex Terminal session, and one more after it for whatever asked meanwhile. Reading them asks no model, so it spends no usage and needs no consent on a ChatGPT plan, in any build (the App Server connection still refuses a ChatGPT login in a commercial or hosted build, before it reads anything). On an API key Codex has no plan limits: no reading.
- **The status-line wrapper.** Claude Code gives its status line command a JSON input with `rate_limits.five_hour`/`.seven_day` (`used_percentage`, `resets_at` in epoch seconds), after the first API response of a subscription login. A Claude Code Terminal session's `--settings` (written by its TerminalCli's `prepare`, `claude-code.ts`) add corrallm's status line (they win over user, project and local settings): `/bin/sh <session dir>/statusline.sh`. The script reads its input with the shell's own commands, posts it in the background (curl, at most 2 s, headers from a 0600 file holding the session's token) to the hook server's `/status` path, then runs the user's own status line as Claude Code would (`/bin/sh -c '<their command>'`, the same input on stdin, in the same folder and environment) and exits as it does; with none, it prints nothing (Claude Code's footer is then as it was). The user's own is found when the session starts, as Claude Code finds it: `.claude/settings.local.json`, then `.claude/settings.json` in the project folder, then `settings.json` in `CLAUDE_CONFIG_DIR` (or `~/.claude`); its padding, refresh interval and vim indicator setting are kept. Claude Code runs status lines only in a trusted folder, the same gate as the user's own. Not covered: a status line changed during a session (it shows from the next one), managed (policy) status lines and `disableAllHooks` (they turn corrallm's off too: no readings; the session says so as it starts, see Terminal), `CLAUDE_CODE_SHELL_PREFIX` (applied to corrallm's command, not again to the user's), a local settings file in a worktree's main checkout, and Windows, where Claude Code runs status lines through Git Bash or PowerShell: there corrallm adds no status line (the user's shows as it is) and reads no usage. Without curl, the user's line still shows and nothing is read.
- **Rules** (`UsageRule`: a window, a share 1–99, an action) act between tasks: before a step or message would start (`RunStore.#gate`), an agent on the backend whose latest reading is over the share of the window (and the window not reset since) is warned about once a window (a notice in its session; it goes on), asked (status `asking`, `AgentRun.usage`, in the four places: row, All queues' lane head, the Needs you sidebar, the bar above the composer or under the terminal: Go on, Wait for the reset, Stop here; it asks no longer than its window lasts), or held until the window resets (status `waiting`; Go on now). Go on and Wait for the reset apply to every agent on that backend until the window resets; Stop here stops the queue at the top-level item holding the task. A new reading (`RunStore.usageChanged`) re-checks them. "Carry on with the next backend" comes with the fallback chain: it will be one more `UsageAction`.
- **In queues.** An If may check `{ kind: 'usageAbove', backend, window, percent }` against the latest reading when the run reaches it (never by chance). A time may be `{ resets, backend }`: a delay (or a wait's limit) until the window resets, taken from the reading when the queue reaches it and kept (the next window's reset, read meanwhile, does not hold it again); with no reading of that window it goes on at once and says so. A Claude or Codex agent's pickers offer both.
- **Trying it.** "Simulate usage…" in a gauge's panel sets a simulated reading (marked so; a real reading replaces it), so rules, Ifs and waits can be tried with explicit sample usage readings.

## Native modules

- Forge's Vite plugin packages only `.vite/`. `package.json` `dependencies` therefore holds only native modules that ship unbundled; everything Vite bundles (React, electron-squirrel-startup, …) belongs in `devDependencies`.
- To add one (e.g. `better-sqlite3`): add it to `dependencies`; add it to `NATIVE_EXTERNALS` in `vite.main.config.mts` (external in main's, the core's and the CLI's bundles); add it to `NATIVE_MODULES` in `forge.config.mts` (runtime files, build-only deps); extend `asar.unpack` so its binaries are real files; keep it in `rebuildConfig.ignoreModules` if it ships Node-API prebuilds; approve its install script in `pnpm-workspace.yaml` `allowBuilds` only if it needs one. Then load and exercise it in the native self-test's checks (`src/main/core/selftest.ts`) so the packaged self-test (in main and in the core process), the CLI's and CI cover it.
- node-pty is pinned to `1.2.0-beta.14` exactly: 1.1.0 ships a non-executable macOS `spawn-helper` and no Linux prebuilds; beta.15 has a Windows regression (microsoft/node-pty#955).
- node-pty runs Terminal agents (`sessions/terminal/pty.ts`, loaded only when one starts) and the native self-test. Its Node-API prebuild loads under plain Node too (the CLI bundle).
- node-pty on Windows: pass `useConptyDll: true` (its default `kill()` path uses `child_process.fork`, which the RunAsNode fuse breaks). The bundled ConPTY sends a DA1 query (`ESC[c`) at startup and holds output for about 3 s until answered: attach the pty to xterm.js (which answers) or, for headless consumers, reply `\x1b[?1;2c` when the query appears. Kill or await every pty before the app quits (teardown crashes, node-pty #904/#951).
- Unit tests must never import native modules or the real `electron` module: `vi.mock('electron', ...)` (importing it downloads the Electron binary).

## Toolchain notes

- TypeScript is pinned to `~6.0.3`. typescript-eslint does not support TypeScript 7 yet; don't upgrade.
- pnpm 11+ reads only auth/registry settings from `.npmrc`. Everything else (`nodeLinker: hoisted`, which Forge requires; `engineStrict`; `allowBuilds`; `minimumReleaseAge`) lives in `pnpm-workspace.yaml`. Dependency build scripts fail the install unless listed in `allowBuilds`.
- `minimumReleaseAge: 1440` is set explicitly, which makes it strict: an install that needs a version under a day old fails. Wait instead of approving it, and treat any `minimumReleaseAgeExclude` diff as a red flag.
- `peerDependencies.electron-winstaller` in `package.json` is intentional (from Forge 8's pnpm template): it keeps maker-squirrel's dependencies resolvable when Forge loads `forge.config.mts` under pnpm. Don't remove it.
- Electron 44 downloads its binary on first use: `pnpm exec install-electron` fetches it up front.
- Unsigned macOS builds are re-signed ad hoc in the `postPackage` hook so the bundle signature verifies. Signing and notarization turn on from env vars (`.env.example`); `CORRALLM_UNSIGNED=1` forces an unsigned build.
- `build/rpm.spec.ejs` is a patched copy of electron-installer-redhat's template (rpmbuild >= 4.20 fix); delete it once upstream ships the fix.
- Forge 8's terminal UI hides plain logs; set `CI=1` for linear output.
- The main, core and CLI bundles are CommonJS, where `import.meta` does not exist: `vite.main.config.mts` defines `import.meta.url` as the bundle's own file URL (`mainDefine`, which `vite.cli.config.mts` reuses; the Agent SDK uses it when loaded). Without it the bundler writes `{}.url` and main crashes at start; `e2e/sdk.e2e.ts` and the native self-test (packaged, and the CLI's) would catch it.
- The CLI bundle must not import Electron: `vite.cli.config.mts` fails the build if it does.
- Auto-update is a TODO in `src/main/index.ts` (Squirrel + ZIP makers are compatible with `update-electron-app`).
