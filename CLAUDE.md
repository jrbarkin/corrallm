# CLAUDE.md

corrallm is a cross-platform Electron desktop app (Electron Forge + Vite + React + TypeScript). It will become an agent orchestrator that spawns and manages the Claude Code and Codex CLIs as child processes. Today it has a canvas of agents in the renderer (`src/renderer/graph/`), each opening into a Claude Code-style session (`src/renderer/agent/`); canvases saved as `.corral` files over the `canvas:*` IPC channels, with a project folder their agents work in. A Claude agent runs Simulated (a scripted session) or connected to the real `claude` CLI, in a Terminal or through the Agent SDK (see Connected sessions): a Terminal agent runs Claude Code's own interactive CLI in a node-pty pseudo-terminal, shown in its agent view with xterm.js (`src/main/sessions/terminal/`); an Agent SDK agent runs a Claude Code session through the Agent SDK, shown in corrallm's own transcript and composer (`src/main/sessions/sdk/`). A Codex agent runs Simulated, or connected to the real `codex` CLI (`src/main/sessions/codex/`, see Codex): in a Terminal, Codex's own interactive CLI on the same terminal plumbing (`src/main/sessions/codex/terminal/`), or through its app server, shown in corrallm's transcript (`src/main/sessions/codex/app-server/`).

## Commands

Requires Node 24.21.0 (`.nvmrc`) and pnpm 12.11.2 (`packageManager`).

| Command          | Purpose                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `pnpm dev`       | `electron-forge start`: Vite dev server + HMR; press `r` in its terminal UI after main-process changes |
| `pnpm typecheck` | `tsc -b` over the solution (node, web, tooling projects)                                               |
| `pnpm lint`      | ESLint, type-aware, zero warnings allowed (`lint:fix` to autofix)                                      |
| `pnpm format`    | Prettier write (`format:check` to verify)                                                              |
| `pnpm test`      | Vitest: `main`, `preload` (Node) and `renderer` (jsdom) projects                                       |
| `pnpm test:e2e`  | Playwright; its global setup first builds the app unsigned (`electron-forge package`)                  |
| `pnpm package`   | Packaged app for the current OS in `out/`                                                              |
| `pnpm make`      | Installers for the current OS in `out/make/`                                                           |

- Run one Vitest project with `pnpm exec vitest run --project main`.
- `E2E_SKIP_BUILD=1 pnpm test:e2e` reuses the existing production build in `.vite/` (note `pnpm dev` overwrites it). Headless Linux: `xvfb-run -a pnpm test:e2e`.
- `CORRALLM_CLAUDE_PATH=/path/to/claude` makes connected agents run that `claude` instead of the user's own (the e2e tests point it at a fake: `e2e/fake-claude.mjs` for Terminal agents, `src/main/sessions/sdk/fake-claude.mjs` for the Agent SDK). `CORRALLM_CODEX_PATH` does the same for `codex`.
- `CORRALLM_DISTRIBUTION=commercial` (or `hosted`) when building (`pnpm package`, `pnpm make`) makes a build for a commercial or hosted product, whose App Server connection refuses a ChatGPT login (see Codex); the default is `local`.
- Packaged-app native check: after `pnpm package`, run the app binary with `CORRALLM_NATIVE_SELFTEST=1` (e.g. `CORRALLM_NATIVE_SELFTEST=1 out/corrallm-darwin-arm64/corrallm.app/Contents/MacOS/corrallm`). `runNativeSelfTest` (`src/main/native-selftest.ts`) runs a shell that exits in a node-pty pseudo-terminal (through `spawnPty`, as Terminal agents run), then `src/main/selftest.ts`'s checks: main's terminal screen copy (@xterm/headless and its addons) reads a status report and snapshots, and the bundled Agent SDK (its `import.meta.url` define, its spawning) runs a query against `src/main/selftest-claude.mjs`, a tiny fake `claude` bundled as text (`?raw`, typed in `src/main/raw.d.ts`) only for this, written to a temporary folder and run with the `node` on the PATH (no login). It exits 0 on success, 2 if a check fails (saying which), 3 on a timeout. CI runs this on all three OSes; `src/main/selftest.test.ts` runs the same checks in the unit tests.

## Testing

- Test-driven by default. For a bug, first write a test that reproduces it and fails, then fix it, then confirm the test passes. For new behaviour, write the tests with (or before) the code.
- The test suite is the regression guard, not ad-hoc review. Keep tests robust and meaningful: assert behaviour users or callers rely on, not incidental details. Prefer unit tests for logic, and add Playwright e2e only for what needs the real app (pointer interactions, CSP, packaging).
- Tests never run the real Claude or Codex. Main's session tests use the fake connector (`src/main/sessions/fake.ts`, one per CLI), renderer tests a fake backend (`src/renderer/test-backend.ts`), and e2e runs the app with `CORRALLM_FAKE_SESSIONS=1` (`launchApp({ env })`; honoured only by unpackaged builds), which gives each CLI's connections a fake connector. A connector's own tests drive a fake CLI that prints the real one's formats.
- The Agent SDK connector's tests replay what the real CLI did (`src/main/sessions/sdk/fixtures/`, recorded with Haiku in a scratch folder, its paths and the user's own skills and servers taken out) and drive the real SDK against `sessions/sdk/fake-claude.mjs`; e2e (`e2e/sdk.e2e.ts`) points the built app at it with `CORRALLM_CLAUDE_PATH`. With `CLAUDE_CONFIG_DIR` set (only then, so it never writes into the user's own `~/.claude`), the SDK fake keeps its conversations' transcripts there as the CLI does, so the SDK's session functions (listSessions, getSessionMessages, forkSession) read them: `sdk/cli.test.ts` and `e2e/sdk.e2e.ts` point it, and main, at a throwaway folder. It takes the SDK's flags as the SDK passes them (`--flag=value`), really edits the project's notes.txt ("edit"), and with file checkpointing on keeps it as it was before each message, for `rewind_files`. Both fakes answer `claude auth status --json` as the real CLI does: a Claude subscription unless their environment has an API key (the SDK one also takes a cloud provider, or an apiKeyHelper in the project's settings), so tests of a working SDK session give the agents a fake ANTHROPIC_API_KEY. On a machine logged in only with claude.ai, the real Agent SDK connection refuses to start: check it live that way, with no prompt, and use Terminal for live checks. To record new fixtures, run a few tiny prompts through the SDK in a throwaway folder, never a real repository, and keep the same sanitizing.
- The Terminal connector's unit tests run `sessions/terminal/fake-claude.ts` behind a fake pty, and `e2e/terminal.e2e.ts` runs the real connector with `CORRALLM_CLAUDE_PATH` pointing at `e2e/fake-claude.mjs` in a real pty (it logs what it gets in the project folder, since the terminal draws its text on a canvas; its `--help` lists `--effort`), and with `CLAUDE_CONFIG_DIR` a throwaway folder, so the user's own settings are never read.
- Codex: what the real CLI did is recorded in `sessions/codex/app-server/fixtures/` (its app server's JSON-RPC, both ways, with timestamps: the handshake, models and limits; three turns with a command, an approval, plan mode, `thread/read`; and, recorded through corrallm's own App Server session, a patch and a command with /diff, /status, /mcp and /skills, an interrupt, a pasted image, a resume with its history and /compact; and, as asked for an agent's settings, config/read and model/list, `options`: the connector's tests replay these through `replay.ts`, which fails on any request the recording did not make) and `sessions/codex/terminal/fixtures/` (its TUI in a pty: everything it printed, its window titles, the hooks it posted, the keys sent; two sessions of prompts, one of them corrallm's own (`turns`: an approval and an interrupt, with no view, so its composer is unshaded), a resume, and a resume of a missing session; `recorded.ts` reads them). They were recorded with Codex CLI 0.160.1 and GPT-6-Luna (low effort) in a scratch folder, paths, names, account and the user's own MCP servers replaced with stand-ins of the same length. `sessions/codex/fake-codex.mjs` is a fake `codex` (`--version`, `app-server`: what a message starts with makes it run a command, patch, ask, plan, fail or crash; it keeps threads in `FAKE_CODEX_STATE` to resume them, and is logged in as `FAKE_CODEX_LOGIN` says: an API key, ChatGPT or none) in the same shapes; tests run it with node, and `e2e/app-server.e2e.ts` runs the built app against it (`CORRALLM_CODEX_PATH`).
- The Codex Terminal connector's tests replay those recordings into a real Terminal session (`codex/terminal/session.test.ts`: each pty plays one back, in order, waiting wherever keys were sent until the session sends the same), and `e2e/codex-terminal.e2e.ts` runs the real connector with `CORRALLM_CODEX_PATH` pointing at `e2e/fake-codex-tui.mjs` (Codex's TUI in its real formats, running its `-c` hooks as Codex does, only if trusted as Codex trusts them; its app server answers hooks/list, account/rateLimits/read, model/list and config/read) in a real pty.
- jsdom cannot draw xterm.js: renderer tests that show a Terminal agent mock `src/renderer/terminal/screen.ts` with `fakeScreens` (`src/renderer/terminal/test-screen.ts`), which also fakes main's terminals (`fakeTerminals`).
- Before calling a change done: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm test:e2e`.

Queues: there is one queue component, QueueEditor.tsx. Every queue the app shows (an agent's own, the one shown beside it to pick from, the work panel between two agents, the lanes of All queues) is built from its rows (`QueueRow`), its end (`QueueEnd`) and its picking (`PickTask`), styled once in GraphEditor.css (cards at rest; what edits a task shows on the one pointed at; the drag handle always shows). Bind edits to an agent with `editsOf` (graph/edits.ts), word tasks with labels.ts, and mark them with `queueMarks` (queues/marks.ts) rather than adding another copy.

TypeScript: `tsconfig.json` is solution-style and references `tsconfig.node.json` (main, preload, shared), `tsconfig.web.json` (renderer, shared) and `tsconfig.tooling.json` (config files, e2e). All extend `tsconfig.base.json` (strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`). Every new `.ts` file must fall under one of these `include`s, or type-aware lint fails with "not found by the project service".

ESLint enforces the process boundaries: renderer and shared code cannot import Electron, Node built-ins or main/preload code; the preload cannot import Node built-ins.

Forge's Vite plugin builds `src/main/index.ts` to `.vite/build/main.cjs`, `src/preload/index.ts` to `.vite/build/preload.cjs`, and the renderer to `.vite/renderer/main_window/`.

## Security rules (do not regress)

- Never enable `nodeIntegration`, and never disable `contextIsolation`, `sandbox` or `webSecurity`. No `<webview>`.
- The preload exposes one typed function per IPC channel through `contextBridge`. Never expose `ipcRenderer`, a generic `invoke`/`send`, or Electron event objects to the renderer.
- All IPC goes through the contract in `src/shared/ipc.ts` and the `handle()` wrapper in `src/main/ipc.ts`, which validates the sender frame (top-level frame of our own origin) and parses arguments. Never call `ipcMain.handle`/`ipcMain.on` directly.
- Production renderer is served from `app://main_window/` by `src/main/app-protocol.ts` (not `file://`, not `loadFile`). The CSP is a response header from `src/main/csp.ts`: never add `'unsafe-inline'` or `'unsafe-eval'` to `PROD_CSP`. Dev-only relaxations go in `DEV_CSP`. The only inline styles allowed are the two exact ones xterm.js writes for its scrollbar, by hash (`TERMINAL_STYLES`); xterm.js draws only with its WebGL renderer, loaded before the terminal opens (its DOM renderer's inline styles are blocked).
- Dev vs production is decided by `MAIN_WINDOW_VITE_DEV_SERVER_URL` (defined only under `pnpm dev`), not `app.isPackaged`. e2e runs the production build unpackaged.
- Navigation and redirects away from the app origin, and renderer-created windows, are blocked (`security.ts`; one to an allowlisted site, `allowedExternalUrl`, opens in the browser instead). Links the user clicks (Markdown links in a transcript, links Cmd-clicked in a terminal, OSC 8 or found by xterm.js's web-links addon) go to main over `link:open` with only their URL (`OpenLinkContext` in the renderer), never through `window.open` or `target="_blank"`. Main decides, never on the renderer's say-so (`links.ts`): the URL is validated and length-capped (`MAX_LINK_LENGTH`) and normalized by `linkTarget` (`url-policy.ts`: https, or http to localhost or 127.0.0.1 only; no credentials); a site on `EXTERNAL_URL_ALLOWLIST` (https, default port) opens at once; any other asks in a native dialog ("Open docs.example.com in your browser?", with "Always for this site"), one question per window at a time, and a site allowed always is remembered by origin in user data (`links.json`). Always open the normalized URL, never the raw input.
- All permission requests and checks are denied (`ALLOWED_PERMISSIONS` in `security.ts`). Add entries deliberately.
- Packaged builds exit if launched with a switch in `FORBIDDEN_SWITCHES` (`src/main/index.ts`): remote debugging, or launcher prefixes such as `--gpu-launcher` that would make the app run an arbitrary executable. CI asserts this.
- Fuses (`forge.config.mts`) must stay as configured: RunAsNode, `NODE_OPTIONS` and Node inspect flags disabled; ASAR integrity and OnlyLoadAppFromAsar enabled (integrity is enforced on macOS and Windows only). Consequences: `child_process.fork` throws in packaged builds (use `utilityProcess.fork` or `spawn`), and Playwright cannot drive the packaged app.
- Credentials only come from environment variables (see `.env.example`). Never commit `.env` or key files; `pnpm dev` strips the signing variables before launching the app. Agents use the `claude` and `codex` CLIs' own logins; corrallm never reads, stores or passes credentials (the Agent SDK connection asks `claude auth status` only what kind of login it has, the App Server connection asks Codex's `account/read` the same).
- Agents run only in the project folder the user picked in main's folder dialog (`project.ts`): that choice is the trust gate (SDK sessions skip Claude Code's own trust dialog, Codex is told the folder is trusted for its session alone). The renderer never passes a path, a command line or an environment, and names a session to resume only by picking one main listed for the canvas's project folder (`session:list`, then `session:resume`): main resolves `claude` (`sessions/claude.ts`) and `codex` (`sessions/codex/codex.ts`), the environment and the folder, and remembers session ids itself. The one path that crosses is a file dropped on a terminal: the page passes the dropped `File` objects, the preload reads their paths with `webUtils.getPathForFile` (a file the page made has none), and main checks them (`terminal:drop`: absolute, length-capped, no control characters; then that they exist) before pasting them, quoted, into that terminal, never using them otherwise. Connectors use an agent's id only to route events, never in a path or a command line. What an agent is set to run with goes on its CLI's command line only as checked values, from the renderer and from `.corral` files alike: a model's name (`MODEL_PATTERN`: never with a dash first, which would read as a flag), an effort (`EFFORT_PATTERN`; Claude Code's only one of its levels) and a mode of its CLI (a file never sets one that never asks). Every session's process is closed before the app quits. A Terminal view sends only keystrokes, its size and dropped files; its CLI's hooks post to a server on 127.0.0.1 that needs the session's own token (from its environment), and corrallm only listens to them (it never answers with a decision, and never answers what the CLI asks in its terminal). Codex's hooks are given and trusted for its session alone, on its command line: corrallm never writes the user's config.toml, and never runs Codex with `--dangerously-bypass-hook-trust` (which would also run the user's and the project's untrusted hooks). Claude Code's status line posts to that server too, with the token read from a file only the user can read (never on a command line), and never puts what Claude Code gives it into a command line; Codex's are read from its app server (a Codex · Terminal session asks a private one nothing but `account/rateLimits/read`). Usage readings keep only shares and times.

## Adding an IPC channel

1. Declare it in `IpcContract` in `src/shared/ipc.ts`: `'domain:action': { args: [path: string]; result: Thing }`. Add the matching method to `InvokeApi` (part of `AppApi`) and its channel to `API_CHANNELS`.
2. Add an entry to `createHandlers` in `src/main/ipc.ts`: `'domain:action': { parseArgs, handler }`. `parseArgs` receives `unknown[]` from an untrusted renderer and must validate every argument (type, length, allowed values) or throw. Use `noArgs` for channels without arguments.
3. Expose it in `src/preload/index.ts`: `action: (path) => invoke(API_CHANNELS.action, path)`.
4. Call it from the renderer as `window.api.action(...)`.
5. Extend `src/main/ipc.test.ts` (sender rejection, argument validation) and `src/preload/index.test.ts`. If the UI uses it, stub it in `src/renderer/App.test.tsx` via `stubApi`.

The compiler enforces that main, preload and renderer agree on argument and result types, and that no contract channel is missing a main handler or an `AppApi` method.

Main-to-renderer events: declare the event in `IpcEvents` in `src/shared/ipc.ts` (`'domain:event': [agentId: string, thing: Thing]`), add a function to `EventApi` and its event to `API_EVENTS` (the compiler checks none is missing), expose it in the preload with `listen` (`onThing: (listener) => listen(API_EVENTS.onThing, listener)`: it returns a function that stops listening, and never passes the `IpcRendererEvent` on), and send it from main with `sendEvent(contents, 'domain:event', ...)` (src/main/ipc.ts) to the renderer it concerns only.

## Connected sessions

An agent's connection (`AgentConnection` in agents.ts: `simulated`, or a `Connection` its type offers: Claude's `terminal` and `sdk`, Codex's `codex-terminal` and `app-server`; saved in `.corral` files when not simulated) decides what drives its session. A connection names what runs it, so it implies its CLI (`CONNECTION_CLI` in `src/shared/session.ts`) and its view (`TERMINAL_CONNECTIONS`: the CLI's own terminal; the others, corrallm's transcript). Modes are the CLI's (`CLI_MODES`: Claude Code's permission modes; Codex's presets, Read only, Default ('auto'), Full access, and Plan), validated against the connection's CLI in args.ts and the manager; the composer offers an agent's own (`modesOf` in renderer session.ts). Simulated sessions are scripted in the renderer. Connected ones run in main, over the `session:*` channels and the `session:event` event, in the protocol of `src/shared/session.ts`:

- The renderer (`connected.ts`) starts an agent's session when its view opens or a message is sent (`session:start`: connection, and what the agent is set to run with in its CLI, its settings (see Agent settings: the store has them from the canvas, `SessionStore.sync`, and the driver reads them as it starts, `DriverIO.settings`); null for a model or mode not set, no effort for an effort not set; `Session.running` keeps what the session that runs started with), sends one message at a time (it keeps its own editable queue; the runner hears each turn's end through `SessionStore.send`'s `onDone`, with what the agent replied in it, and takes a message back with the function `send` returns: off the queue, or interrupting its turn), passes on answers to prompts, interrupts, mode, model and effort changes, and closes the session when the agent goes or runs another way. Session events from main are routed to the agent's driver only if they come from its current connection. A start that fails after a `notice` offering another connection (`switchTo`) is a refusal, not a failed turn: the message that started it goes back to the head of the queue, unsent (never a turn in the transcript; the refusal is said once), its sender hears through `send`'s `onRefused` (as do those of every message queued behind it), and it goes once the agent runs another way, or once the session starts after all (when its view opens again, or another message tries it again). main's `user` echo of a message marks it as the CLI's (`reached`), the only messages a rewind offers.
- Main (`sessions/manager.ts`) starts the session with the connection's `Connector` in the canvas's project folder (it refuses without one), with the agents' environment (the user's login shell's, cleaned of what corrallm was started from: `environment.ts`), resuming the agent's last session id (remembered per canvas file in `memory.ts`, so sessions survive a restart: one per CLI, Claude Code's in `sessions` and Codex's threads in `threads`; the same id is resumed whichever of its CLI's connections the agent switches to). It starts it with what the renderer gives (the agent's settings), nothing of its own: what is not given goes to the connector as null, meaning the user's own default model, mode (Codex's Default, which leaves their own sandbox settings) and effort, else the CLI's. A mode that never asks (`UNASKING_MODES`: bypassing permissions, Codex's Full access) is never an agent's setting: choosing it in the composer unsets the agent's mode, so a session never starts in one unless the user just chose to (the composer keeps them out of Shift+Tab, and asks before switching to one). Opening or forgetting a canvas, choosing another project folder (which forgets the ids), a renderer that goes or reloads, and quitting (`before-quit` in index.ts) close sessions.
- A connector emits `SessionEvent`s through its `SessionHost`: `started` (model, mode, the models it offers, which the composer's model picker lists; a model may offer reasoning `efforts` (`EffortChoice`s: Claude Code's /effort levels, Codex's reasoning efforts, worded alike by `effortChoice` in transcript.ts) and its `defaultEffort` where its CLI says it, which the composer's one effort picker lists, and then `started` says the `effort` it runs at (null: the model's default); and `modes` when it can't switch to every mode: bypassing permissions turned off by the CLI's settings, so the mode menu leaves it out), then per turn: `user` (with the renderer's message id, or a new one for a message typed in a terminal), `status` (working, or waiting on the user) and entries by id (`text`/`thinking` stream in, `tool`/`todos` replace; `parent` nests a subagent's entries; a `tool`'s `progress`: how long it has run, what a subagent is doing and has used), prompts (`permission` with what "always" allows, `question` for AskUserQuestion with its header, its answers' meanings and whether several may be picked, `plan` for ExitPlanMode, `elicitation` for an MCP server's form or link; `withdrawn` when no longer asked), `notice` (compaction, retries, usage limits with their reset time, login problems, hooks that failed or blocked; `switchTo` offers another connection, shown as a button that switches the agent: a connector that refuses to start says why this way, before `start` rejects with the same words), `cleared` (/clear: the transcript marks it), `usage`, `mode`, `model`, `effort`, and exactly one `end` naming the messages it answered (interrupted, or failed). `status` is never sent outside a turn: only `end` makes a session idle. In a turn or not: `tasks` (the work it runs in the background now, the whole list each time; the composer lists them with a Stop, as does each one's tool line), `suggestion` (what the user might send next, after a turn: the composer's empty box offers it, Tab takes it) and, from a Terminal session, `asking` (what its CLI asks the user in its terminal now, `TerminalAsk`s, the whole list each time, none once it goes on: listed in the canvas's Needs you sidebar, never answered from corrallm). `closed` if the session stops by itself; it calls `remember(sessionId)` whenever its CLI's session id is known or changes (as after /clear).
- Restarting (`SessionStore.restart`, a Terminal agent's "Restart with these"): the renderer ends the session (`session:close`) and starts it again with the agent's settings now; main resumes its conversation as for any start.
- Besides the turn, the renderer may answer a permission with a no and `feedback` (what to do instead: Claude's; Codex's No stops the turn), set the effort (`session:effort`, one its model offers or null for the model's default, for the session only; a session that starts again starts at the effort chosen, which the start carries) and stop a background task by the id `tasks` gave (`session:stopTask`). A connection that does neither leaves `LiveSession.setEffort`/`stopTask` out, and the manager refuses them (a Terminal agent sets them in its terminal).
- To build a connection: write its `Connector` in its own folder (`src/main/sessions/sdk/`, `src/main/sessions/terminal/`, `src/main/sessions/codex/app-server/`), find the CLI with `requireClaude(spec.env)` (or `requireCodex`), and register it in `connectors.ts` (`Connectors`: each connection's connector, typed with its CLI's modes; a new connection is added to `CONNECTIONS` and `CONNECTION_CLI` too). Its tests drive a fake CLI; the manager, IPC, renderer and UI need no change unless the protocol grows (then extend `session.ts`'s types, `connected.ts`'s `receive`, and their tests).
- Rewind: a `LiveSession` may restore its files to before a message (`rewindFiles`, with a dry run to preview: an Agent SDK session's, Claude Code's file checkpoints, `enableFileCheckpointing`; never while a turn goes on), over `session:rewind-preview` and `session:rewind` (`code`, `conversation` or `both`). Main rewinds a conversation by forking it (`sdk/conversations.ts`: a copy up to the entry before the message, `forkSession`), so either connection resumes the copy, across restarts too: the copy becomes the agent's own and its session ends, to resume it when it starts again (rewound to its first message, the agent starts afresh); the original stays, for /resume. It checks the message is in the conversation, and restores the files, before it forks or ends anything, so a failure changes nothing. A copy has no file checkpoints from before it (the SDK copies none), so its earlier files can no longer be restored, as the preview then says. A Terminal session rewinds in its terminal (Esc twice there).
- /mcp: a `LiveSession` may show its MCP servers itself (`mcpServers`, `changeMcpServer`: an Agent SDK session's, from the CLI's `mcpServerStatus`, `reconnectMcpServer`, `toggleMcpServer`), over `session:mcp` and `session:mcp-change`; a Terminal session's are its terminal's own /mcp, and Codex's App Server answers /mcp itself.
- /resume: `session:list` lists the conversations Claude Code kept for the canvas's project folder (`sdk/conversations.ts`: the SDK's `listSessions` for the folder's real path, not its worktrees', most recent first), saying which is the agent's own; `session:resume` makes one the agent's own (its session ends; it resumes that one when it starts again). Main opens only a conversation it listed for that renderer and the folder it has now: the renderer names one, never a path.
- Beyond turns, a session can send `commands` (the slash commands the composer completes; again when they change) and `history` (a resumed session's past turns, as events: the renderer puts them ahead of its transcript unless it shows them already, matching entries by id). A message may carry pasted `images` (validated in args.ts: kinds Claude reads, base64, at most 5 MB each). The composer's @-mentions search the project folder over `project:files` (`src/main/files.ts`); the renderer sends only what was typed.

### Agent settings

What an agent runs with in a CLI (`AgentSettings` in `src/shared/session.ts`: its model, reasoning effort and the mode its sessions start in, each only if set) is the agent's, in its node's data (`settings`, by CLI: `{ claude?, codex? }`, so switching between Claude and Codex loses neither), saved in its `.corral` file (file.ts checks it: a model by `MODEL_PATTERN`, which never starts with a dash, an effort by `EFFORT_PATTERN`, a mode of that CLI that asks, never one of `UNASKING_MODES`, and nothing else) and copied to an agent spawned from it. Both of a CLI's connections start with them (`session:start`); main keeps none of its own. They are set:

- For a Terminal agent, beside its agent chip (`Settings.tsx`): a button saying what its CLI starts with ("Opus · Extra high · Auto", the user's own defaults where nothing is set), opening a panel with Model, Effort (where the model has efforts; one the newly chosen model lacks is unset) and Mode (`STARTING_MODES`: Claude Code's `--permission-mode`s; Codex's Read only, its Default being the user's own config and its Plan Shift+Tab in its terminal), each with "Default (…)" first, the user's own. A session that runs keeps what it started with; when they differ the panel offers "Restart with these" (once the agent is not working), which resumes its conversation.
- For a structured agent (Agent SDK, App Server), by its composer: a model, effort or mode picked there switches its session and is what the agent is set to (GraphEditor's `updateSettings`); bypassing permissions or Full access unsets the mode instead.

What a CLI's agents can be set to, and the user's own defaults, come over `session:options` (one CLI; main reads in the canvas's project folder, else the home folder, with the agents' environment, never changing anything; the renderer asks once per CLI and project folder, `SessionStore.settingsOptions`):

- Claude Code (`claude-settings.ts`): no prompt, no session, and never the Agent SDK on a subscription, so no model list from the CLI. The models are the aliases `claude --model` takes (opus, fable, sonnet, haiku: Claude Code's descriptions from 2.1.296's list), only those in the user's `availableModels` where set, plus their own model if it is none of them, each with Claude Code's effort levels. The defaults are read as Claude Code reads its settings (project local, project, user in CLAUDE_CONFIG_DIR or ~/.claude: `model`, `effortLevel`, `permissions.defaultMode`), with ANTHROPIC_MODEL and CLAUDE_CODE_EFFORT_LEVEL (environment, or a settings file's `env`) over them; managed settings are not read.
- Codex (`codex/options.ts`): a private `codex app-server` (the folder trusted for it alone, as a Terminal session trusts it) asked only `model/list` and `config/read` (no thread, no model asked, so no usage and no consent on a ChatGPT plan), then closed: Codex's models with their efforts and default effort, and the config's model (else model/list's `isDefault`), `model_reasoning_effort` and the preset its sandbox and approvals make (recorded in `app-server/fixtures/options.jsonl`).

The Agent SDK connection likewise shows what will be used before the first turn: get_settings' `effective.model` (by alias, else its id) or `applied.model` (ANTHROPIC_MODEL…, unless it is just the account's default) is `started`'s model, and the user's effort (`applied.effort`, else `effortLevel`) each model's `defaultEffort` where it has that level (`sdk/settings.ts`, `startingModel` in `sdk/connector.ts`).

### Agent SDK

`src/main/sessions/sdk/` runs a Claude agent through `@anthropic-ai/claude-agent-sdk` (bundled into main: devDependency, root entry only; its per-platform CLI copies are skipped in `pnpm-workspace.yaml`, `ignoredOptionalDependencies`). Rules it keeps:

- One streaming `query()` per session, fed by an `Inbox`, so the CLI runs between turns (interrupts, mode and model changes need it). It runs the user's own `claude` (`pathToClaudeCodeExecutable`), never a JS CLI, with Claude Code's own system prompt (`systemPrompt: { type: 'preset', preset: 'claude_code' }`; without it the agent is bare), the user, project and local settings, `permissionMode` only when the agent was given a mode (Manual is the SDK's `default`; otherwise the user's own default mode applies, and `started` reports it from the CLI's settings: `settings.ts` asks the running CLI with `get_settings`, which the SDK's Query has at runtime though its types leave it out; the first turn's `init` corrects it if the CLI says otherwise), `allowDangerouslySkipPermissions` (so the mode menu can switch to bypassing permissions once the user confirms it there; as in Claude Code, Shift+Tab never cycles into it, and where the CLI's settings turn it off, `permissions.disableBypassPermissionsMode`, read with `get_settings`, it is not offered), partial messages (streaming), summarized thinking (`--thinking-display`), `perTaskStopAffordance` (interrupting stops the turn, not background work), file checkpoints (`enableFileCheckpointing`, which rewinds restore) and `onElicitation` (MCP servers' requests).
- Each message is sent with the renderer's id as its uuid and `origin: { kind: 'human' }`; a turn ends on the `result` whose `user_message_uuids` name it. A result naming none of the messages waiting (a background task's follow-up) ends none of them. Interrupt asks the CLI to cancel what it queued too, and ends what it cancelled.
- Its session id is remembered once a turn has run (the CLI writes the transcript from the first message), and again after /clear. An id with no conversation (one a Terminal session of the agent was given before its first message: the connections share the agent's id; or one whose transcript is gone) starts afresh quietly, as a Terminal session does; a session that cannot be resumed otherwise starts afresh, with a warning. A resumed session's history comes from `getSessionMessages` (history.ts).
- Entry ids are stable between live and history: text and thinking are `<API message id>:<block index>`, tool calls their `tool_use` id, user messages their uuid.
- Prompts are canUseTool calls: permissions offer "always" only where the CLI suggests a rule to keep (its suggestions, worded as Claude Code words them); No denies and stops the turn, as the CLI's No does; No with what to do instead denies with Claude Code's own message and those words, and the turn goes on. An approved plan is carried out in the mode chosen once the CLI has left plan mode (it reports the mode it goes back to). An MCP server's request (`onElicitation`) is a prompt too: a form, in the flat JSON Schema the protocol allows (`mcp.ts`; one corrallm can't show is declined, and the user told), whose answer main checks against the form before it goes back (one that does not fit is refused and the form still waits), or a link the user opens through `link:open`.
- Live progress and the background (translate.ts): `tool_progress` and `task_progress` become a tool's `progress`; `task_started` ties a task to the call that started it, and `background_tasks_changed` (a level: each one replaces the list; housekeeping tasks left out) becomes `tasks`. `stopTask` stops only a task in that list (query.stopTask; its notification ends its line). Hook events (`includeHookEvents`) show only what Claude Code shows: a hook that failed ("… hook error: …") or blocked ("… hook returned blocking error: …"; a Stop hook's "… hook feedback: …"), never what hooks print when they work. Predictions of the next message (`promptSuggestions`) arrive after a turn's result. The effort is set for the session only (`applyFlagSettings({ effortLevel })`, as /effort does without saving; null goes back to the model's default; only one of Claude Code's levels), and set as the session starts when it was given one its model takes (`started` says it). Each model's levels are offered with Claude Code's own words for them (`CLAUDE_EFFORTS`).
- History (history.ts): a turn lasts until its own last work (never the next message, nor what the CLI noted later); a slash command's output shows even when the transcript keeps it as meta (as /context's is).
- Logins ("Terminal for subscriptions"): Anthropic doesn't allow other products to offer claude.ai logins or subscription rate limits through the Agent SDK without its approval. So wherever corrallm offers a Claude connection, Terminal comes first (`AGENT_CONNECTIONS`; agents stay Simulated until connected, and a spawned agent keeps its source's connection), and the Agent SDK connection starts only with an API key (ANTHROPIC_API_KEY, an apiKeyHelper, ANTHROPIC_AUTH_TOKEN) or a cloud provider (Bedrock, Vertex, Foundry, a gateway). Before `query()`, `login.ts` asks the CLI how it is logged in: `claude auth status --json`, run by main with the agents' environment in the project folder (so a project's apiKeyHelper counts). That is the check, not the SDK's own `account`/`apiKeySource` reports, which come only once the CLI runs under the SDK. A claude.ai login (`authMethod: "claude.ai"`), a `claude setup-token` token (`"oauth_token"`), or a status it can't read refuses the start: a `notice` (one sentence, offering Terminal) and a rejection. Not being logged in at all starts, and the CLI says so. corrallm reads only what kind of login the CLI reports, and whether ANTHROPIC_AUTH_TOKEN is set, never a credential's value; it passes none. The Terminal connection runs the CLI itself, with any login.

### Terminal

- A Terminal session (`sessions/terminal/session.ts`) runs whatever CLI its TerminalCli describes (`cli.ts`): how to start and resume it (in the user's own default mode, `defaultMode`, unless given one), what its screen reports (Program Status, or its window title), what its hooks mean (`TerminalSignal`s: its session id, prompts it took, its reply, a failure, its state when its screen does not say, its mode and model, what it is about to ask the user, what its notifications say it needs), how to read its prompt's draft and type into it, and its words (`words`: what it waits on, by its report's kind). Turns, waiting on the user, what it asks listed outside its terminal (`asking`), typing the queue's messages once the prompt is ready, files dropped on it pasted in, views and closing are the same for every CLI. A CLI that picks its own session ids (`newId()` is null) is remembered once its hooks tell it. A CLI whose reports leave out some dialogs (`waitsForPrompt`) is typed into only while its prompt is drawn, one that holds a message while it gets ready (`holds()`) is waited for rather than given up on, and one that reads keys late (`waitsForEcho`: Claude Code) gets Enter once its prompt shows the end of what was typed (at most `TerminalTiming.echo`).
- The Terminal connection (`sessions/terminal/`) runs Claude Code's own interactive CLI, so the user has all of Claude Code in the agent view (`TerminalPane.tsx` in place of the transcript and composer): its prompts, modes, models, slash commands and dialogs are answered there. It is started with `--settings` (a file in the temp folder: corrallm's HTTP hooks, merged with the user's, and corrallm's status line: see Usage readings and rules), `--session-id` (new) or `--resume` (one with no transcript starts afresh under the same id), and `--model`/`--effort`/`--permission-mode` only when the agent is set to them (an explicit Manual too, as `manual`, one of the flag's choices; `default` as a model is left out; `--effort` only with one of Claude Code's levels, and only where its `claude --help` lists the flag, asked once per executable: `claudeFlags` in claude.ts, since an older CLI would not start with it): otherwise the user's own defaults apply. corrallm follows it to orchestrate it: Claude Code's Program Status reports (OSC 7501, answered and read in main's copy of the screen) say when it works, waits on the user, is done, was interrupted (idle) or failed; its hooks (`hooks.ts`) tell the session id (it changes with /clear), prompts typed in the terminal, the last reply, failures, mode and model. A message corrallm sends is typed in (a few characters at a time, Ctrl+J for line breaks, then Enter: never a paste, which Claude Code collapses and treats as untrusted) once the prompt is ready: Claude Code idle or done, and nothing the user typed in it; Enter goes once the prompt shows what was typed (keys that pile up while Claude Code is busy, as right after the folder trust dialog or as a turn ends, are read in one go as a paste, where 2.1.296 keeps an Enter as an invisible character, not a submit). Meanwhile, a dialog (the folder trust prompt) or the user's draft makes the turn wait on the user. A turn ends once Claude Code has taken every message sent in it and stopped working; one the user started in the terminal is a turn too. Answers, modes and models are refused over the session channels: they belong to the terminal.
- What Claude Code asks in its terminal (`asking`, from its TerminalCli's hook signals, `claude-code.ts`): its PermissionRequest hook tells a permission prompt's tool and input (worded by `sdk/tools.ts`), PreToolUse (only for AskUserQuestion and ExitPlanMode) its questions and plan (PermissionRequest tells them too, without a call id: told once), Notification what it needs when nothing else says (an MCP server's question). Recorded from 2.1.296: the hooks come just before its Program Status says `blocked` (with `kind` permission, question or auth, and `msg`, as "approve Bash: git init" or "answer: Pick a color (Red · Blue)"). The session lists what the hooks told within a few seconds before a wait began, or else the wait's `msg` (or the notification's words, or the CLI's own for the wait's kind), while it waits; once it goes on (the user answered in the terminal), the turn ends or the CLI exits, it lists nothing. Without status reports, what the hooks told is listed until the turn ends. Every hook is answered with no decision. Codex tells nothing ahead: while its title says Action Required, its wait is listed in its own words.
- The view, for every Terminal agent: files dropped on it are pasted as their paths (the preload reads them from the files with `webUtils.getPathForFile`; `terminal:drop` checks them; main pastes those that exist, quoted for a shell, `drop.ts`, bracketed when the CLI asked, so Claude Code takes an image's path as the image). On a Mac, Option works as Meta only on a US-like keyboard layout (`navigator.keyboard.getLayoutMap`; elsewhere Option types characters, as @ on a German layout), unless the user chose otherwise with the switch in the bar (kept in localStorage). When the screen is reset (a snapshot, as for a new CLI process), the view fits it and draws it afresh (`Screen.redraw`). Links Cmd-clicked in it go to main (`link:open`).
- Terminal views: `terminal:attach` asks main to show an agent's terminal; main sends `terminal:event`s (`src/shared/terminal.ts`): the screen as it is (a snapshot of its headless copy, now or once the session starts, and again for each new process), then the CLI's output, then its exit. The view (`link.ts`) writes the snapshot from scratch, drops what its terminal answers while doing so, then passes keystrokes (`terminal:input`) and its size (`terminal:resize`) on. The pty lives in main: closing the view (`terminal:detach`) leaves the session running. While no view is shown, main's copy answers the terminal queries a pty needs answered (DA1, which Windows' ConPTY waits on).

### Codex

- `codex.ts` finds the user's `codex` (CORRALLM_CODEX_PATH, the standalone installer's ~/.local/bin, the login shell's PATH; on Windows npm's native `codex.exe`, never its `.cmd`) and checks its version against `MIN_CODEX_VERSION` (0.160.0: what the fixtures and protocol were read from). Codex keeps its own home (~/.codex: config.toml, AGENTS.md, skills, MCP servers, sessions), so corrallm's threads are the user's (`codex resume` sees them, and corrallm can resume theirs).
- `rpc.ts` runs a private `codex app-server` per session over stdio (never the shared daemon a desktop app runs, never `--listen`: its sockets are unauthenticated), says hello (`initialize` with the experimental API, then `initialized`), always sends params (Codex refuses a request without them), answers every request the server makes (an unanswered approval stalls the turn; unhandled methods get -32601), drains stderr, and closes by ending its input, then SIGTERM, never SIGKILL (that orphans what it runs). The renderer never gets raw JSON-RPC or a generic channel: each action gets a typed `session:*` channel.
- Logins: corrallm never reads, stores or passes credentials; Codex uses its own (`codex login`), and corrallm asks its app server only which kind it is (`account/read`, `login.ts`). The App Server connection runs on any login, a ChatGPT plan included, because OpenAI allows it for local apps (learn.chatgpt.com/docs/app-server, Auth endpoints: "If you’ve built a local or open-source application using Codex app-server authentication, you can continue using it… App-server authentication has never been permitted for commercial or hosted services."). So on a ChatGPT login a session's first turn that would use the plan (a message, /review, /compact, /init) first asks (`planPrompt`, quoting that): Yes allows it for the session, "don't ask again" for good (`chatgptPlan` in `settings.ts`, through `PlanConsent`), No sends nothing; interrupting withdraws it. A build made as a commercial or hosted product (`CORRALLM_DISTRIBUTION=commercial` or `hosted` when building: vite.main.config.mts defines `CORRALLM_DISTRIBUTION`, 'local' by default) refuses a ChatGPT login instead (`appServerRefusal`), leaving the plan to Codex · Terminal, which is Codex's own CLI. Sign in with ChatGPT (developers.openai.com/siwc), which OpenAI recommends instead, is not built: it would have corrallm keep and refresh the user's OAuth tokens.
- The App Server connection (`codex/app-server/`) runs a Codex thread in corrallm's transcript. Rules it keeps:
  - One private app server per session, closed with it. Its thread starts (`thread/start`) in the project folder with the approval policy and sandbox of the mode it was given (else Default). Modes are Codex's /permissions presets (Read only: read-only sandbox, on-request; Default: workspace-write, on-request; Full access: no sandbox, never) and Plan (Codex's plan collaboration mode, with Default's permissions). Every `turn/start` carries the model, effort, approval policy, sandbox policy (the one Codex reported for the thread when of the same kind: it carries the user's own config.toml settings) and collaboration mode, which Codex keeps, so a mode switched mid-turn applies from the next turn. `clientUserMessageId` is the renderer's message id, so a resumed thread's history (`thread/resume`'s `initialTurnsPage`, its last 30 turns) matches what was shown live. A thread is remembered once it has a turn (Codex keeps none without), and one that cannot be found starts afresh quietly.
  - A turn ends with `turn/completed`. A plan proposed in plan mode is asked about once its turn ends ("Implement this plan?", as Codex's TUI asks): Yes switches to Default and sends "Implement the plan." in the same corrallm turn, so the queues' Run hears its end once the plan is carried out; feedback keeps planning; no feedback ends it.
  - Codex's requests are prompts, answered as its TUI answers them (`availableDecisions`): Yes is `accept`, "always" the decision Codex offers to keep (this session, a command prefix, a host), No `cancel`, which stops the turn. Codex remembers what "always" allowed: corrallm never answers for the user. Questions (`request_user_input`), MCP elicitations (a form's fields as questions, a link) and permission requests are prompts too; a request Codex stops waiting for is withdrawn, and every one is answered.
  - Tools keep the names Codex's model knows (`exec_command`, its command unwrapped from the user's shell; `apply_patch`, an entry per file with its diff; `web_search`; `mcp__server__tool`; `spawn_agent`…: a subagent's thread nests under the call that spawned it). Reasoning summaries are thinking (Markdown), `update_plan` the turn's to-do list, compaction and reviews notices, and command output streams at most every 150 ms. Usage is the last request's context and the plan's 5-hour and weekly limits (`account/rateLimits/read`, then updates; read once, `limits.ts`, for the composer and for the usage readings); errors say what to do by `codexErrorInfo` (log in again, when a usage limit resets, /compact).
  - Slash commands are Codex's (commands.ts), run as its TUI runs them: /review, /compact and /init are turns of the thread; /model, /permissions, /status, /mcp, /skills, /diff (git, run by main with the repository kept from running anything), /new, /clear, /rename are answered by the session. Skills are slash commands too (`/name` is sent as `$name`, with the skill attached). Pasted images go as data: URLs (the app server refuses remote ones), and not to a model that reads none.
- Codex · Terminal (`codex/terminal/`) runs Codex's own interactive CLI on the shared Terminal session (see Terminal), so the user has all of Codex in the agent view: its approvals, questions, plans, slash commands, models, @-mentions and images are answered there, and answers, modes and models are refused over the session channels. corrallm checks its version (`MIN_CODEX_VERSION`), then starts `codex --no-daemon -C <folder>` (its own agent, never the shared daemon a desktop app runs; `codex resume <id> …` to resume, and "No saved session found" starts afresh) with overrides for that session alone (`-c`; the user's config.toml is never written): the folder trusted (the folder dialog is the trust gate), corrallm's hooks (`hooks.ts`: UserPromptSubmit, Stop and Interrupt, each a command that posts the event to `terminal/hooks.ts`'s server with the session's token, through `/bin/sh` and curl, printing nothing and always succeeding) and their trust (`hooks.state`, by the key and hash Codex trusts each by: computed as Codex 0.160 does, and checked once per Codex executable and version with Codex itself, `hooks/list` on a private app server, `trust.ts`; without it Codex stops at "Hooks need review"), its window title set to `["activity","run-state"]`, no update prompt, no automatic recaps. Its modes start it with `-s`/`-a` (Read only, Full access); Default and Plan leave the user's own defaults (Plan is Shift+Tab in its terminal). The model and reasoning effort the agent is set to (see Agent settings) start it with `-m` and `-c model_reasoning_effort`. Codex picks its thread id; its hooks tell it (a subagent's are left out). Its usage limits are read apart from its terminal, never by typing /status into it (see Usage readings and rules).
- corrallm follows Codex by its window title (`tui.ts`): a spinner and Working, Thinking or Waiting is working, "Action Required" waits on the user, "Starting" is its MCP servers starting (a message sent meanwhile is held, and waited for), Ready ends the turn: done after its Stop hook (whose reply is the turn's), interrupted after its Interrupt hook, failed if it took a prompt (UserPromptSubmit) without either (Stop does not run for a turn that errs, as at a usage limit). Its composer (`composer.ts`) is where its cursor shows (Codex hides it during dialogs): a message is pasted in there (bracketed paste, without control characters, then Enter a little later) only while it is drawn and empty, and only once its title has said something (it says nothing while a startup screen is up). Its Enter is not held until the composer shows the message (no `waitsForEcho`): 0.160.1 sends on an Enter read in one go with the paste, as keys that piled up while it was busy are.

## Usage readings and rules

A backend's usage limits belong to its account, so main keeps one reading per backend (`src/main/usage.ts`, types and checks in `src/shared/usage.ts`): how much of each window (`fiveHour`, `weekly`) is used and when it resets, with when it was read, remembered across restarts in the app's user data (`usage.json`), and nothing else the CLI said. Every renderer gets them over `usage:get` and hears each change as `usage:changed`; `usage:rule` sets a backend's rule and `usage:simulate` sets a simulated reading (or forgets it), validated in `src/main/ipc.ts`. Rules are the user's, one per backend, kept by main with the readings, not in `.corral` files.

- **Where readings come from.** `UsageReadings.take(backend, windows)` is the one way in; each connection gets it from `createConnectors({ usage })` and adapts what its CLI reports. Claude's Terminal connection: `sessions/terminal/statusline.ts` (below), heard through its TerminalCli's `statusLine` (a Terminal session passes what its CLI says of usage to `TerminalSessionDeps.usage`). The Agent SDK connection runs on an API key (decided Oct 12, 2026), which has no usage windows: it reads nothing, and its agents are not held by rules (`usageBackendOf` in `src/renderer/usage/usage.ts`).
- **Codex's readings.** `codex app-server` reports the plan's limits as a RateLimitSnapshot (`account/rateLimits/read`'s `rateLimits`, and each `account/rateLimits/updated`): `sessions/codex/limits.ts` reads Codex's own (`limitId` codex; a model's are not the plan's) once, for both the App Server's composer and the readings, naming each window by its length (300 minutes → `fiveHour`, 10080 → `weekly`; where Codex says no length, `primary` → `fiveHour`, `secondary` → `weekly`), `usedPercent` kept from 0 to 100, `resetsAt` (epoch seconds) × 1000 if within a week and a day. The App Server connection reads them as it connects and hears each update (its Translator's `usage`). Codex · Terminal's TUI tells corrallm nothing of them, so its TerminalCli's `readUsage` asks a private `codex app-server` (`codex/terminal/usage.ts`: the user's own `codex`, in the project folder, asked only `account/rateLimits/read`, then closed, through `askAppServer` as for its hooks' trust) when the session starts and after each turn ends; one read at a time for every Codex Terminal session, and one more after it for whatever asked meanwhile. Reading them asks no model, so it spends no usage and needs no consent on a ChatGPT plan, in any build (the App Server connection still refuses a ChatGPT login in a commercial or hosted build, before it reads anything). On an API key Codex has no plan limits: no reading.
- **The status-line wrapper.** Claude Code gives its status line command a JSON input with `rate_limits.five_hour`/`.seven_day` (`used_percentage`, `resets_at` in epoch seconds), after the first API response of a subscription login. A Claude Code Terminal session's `--settings` (written by its TerminalCli's `prepare`, `claude-code.ts`) add corrallm's status line (they win over user, project and local settings): `/bin/sh <session dir>/statusline.sh`. The script reads its input with the shell's own commands, posts it in the background (curl, at most 2 s, headers from a 0600 file holding the session's token) to the hook server's `/status` path, then runs the user's own status line as Claude Code would (`/bin/sh -c '<their command>'`, the same input on stdin, in the same folder and environment) and exits as it does; with none, it prints nothing (Claude Code's footer is then as it was). The user's own is found when the session starts, as Claude Code finds it: `.claude/settings.local.json`, then `.claude/settings.json` in the project folder, then `settings.json` in `CLAUDE_CONFIG_DIR` (or `~/.claude`); its padding, refresh interval and vim indicator setting are kept. Claude Code runs status lines only in a trusted folder, the same gate as the user's own. Not covered: a status line changed during a session (it shows from the next one), managed (policy) status lines and `disableAllHooks` (they turn corrallm's off too: no readings), `CLAUDE_CODE_SHELL_PREFIX` (applied to corrallm's command, not again to the user's), a local settings file in a worktree's main checkout, and Windows, where Claude Code runs status lines through Git Bash or PowerShell: there corrallm adds no status line (the user's shows as it is) and reads no usage. Without curl, the user's line still shows and nothing is read.
- **Rules** (`UsageRule`: a window, a share 1–99, an action) act between tasks: before a step or message would start (`RunStore.#gate`), an agent on the backend whose latest reading is over the share of the window (and the window not reset since) is warned about once a window (a notice in its session; it goes on), asked (status `asking`, `AgentRun.usage`, in the four places: row, All queues' lane head, the Needs you sidebar, the bar above the composer or under the terminal: Go on, Wait for the reset, Stop here), or held until the window resets (status `waiting`; Go on now). Go on and Wait for the reset apply to every agent on that backend until the window resets; Stop here stops the queue at the top-level item holding the task. A new reading (`RunStore.usageChanged`) re-checks them. "Carry on with the next backend" comes with the fallback chain: it will be one more `UsageAction`.
- **In queues.** An If may check `{ kind: 'usageAbove', backend, window, percent }` against the latest reading when the run reaches it (never by chance, simulated agent or not). A time may be `{ resets, backend }`: a delay (or a wait's limit) until the window resets, taken from the reading when the queue reaches it and kept (the next window's reset, read meanwhile, does not hold it again); with no reading of that window it goes on at once and says so. A Claude or Codex agent's pickers offer both.
- **Trying it.** "Simulate usage…" in a gauge's panel sets a simulated reading (marked so; a real reading replaces it), so rules, Ifs and waits can be tried with simulated agents.

## Native modules

- Forge's Vite plugin packages only `.vite/`. `package.json` `dependencies` therefore holds only native modules that ship unbundled; everything Vite bundles (React, electron-squirrel-startup, …) belongs in `devDependencies`.
- To add one (e.g. `better-sqlite3`): add it to `dependencies`; add it to `external` in `vite.main.config.mts`; add it to `NATIVE_MODULES` in `forge.config.mts` (runtime files, build-only deps); extend `asar.unpack` so its binaries are real files; keep it in `rebuildConfig.ignoreModules` if it ships Node-API prebuilds; approve its install script in `pnpm-workspace.yaml` `allowBuilds` only if it needs one. Then load and exercise it in `runNativeSelfTest` (`src/main/native-selftest.ts`) so the packaged self-test and CI cover it.
- node-pty is pinned to `1.2.0-beta.14` exactly: 1.1.0 ships a non-executable macOS `spawn-helper` and no Linux prebuilds; beta.15 has a Windows regression (microsoft/node-pty#955).
- node-pty runs Terminal agents (`sessions/terminal/pty.ts`, loaded only when one starts) and the packaged self-test.
- node-pty on Windows: pass `useConptyDll: true` (its default `kill()` path uses `child_process.fork`, which the RunAsNode fuse breaks). The bundled ConPTY sends a DA1 query (`ESC[c`) at startup and holds output for about 3 s until answered: attach the pty to xterm.js (which answers) or, for headless consumers, reply `\x1b[?1;2c` when the query appears. Kill or await every pty before the app quits (teardown crashes, node-pty #904/#951).
- Unit tests must never import native modules or the real `electron` module: `vi.mock('electron', ...)` (importing it downloads the Electron binary).

## Toolchain notes

- TypeScript is pinned to `~6.0.3`. typescript-eslint does not support TypeScript 7 yet; don't upgrade.
- pnpm 11+ reads only auth/registry settings from `.npmrc`. Everything else (`nodeLinker: hoisted`, which Forge requires; `engineStrict`; `allowBuilds`; `minimumReleaseAge`) lives in `pnpm-workspace.yaml`. Dependency build scripts fail the install unless listed in `allowBuilds`.
- `minimumReleaseAge: 1440` is set explicitly, which makes it strict: an install that needs a version under a day old fails. Wait instead of approving it, and treat any `minimumReleaseAgeExclude` diff as a red flag.
- `peerDependencies.electron-winstaller` in `package.json` is intentional (from Forge 8's pnpm template): it keeps maker-squirrel's dependencies resolvable when Forge loads `forge.config.mts` under pnpm. Don't remove it.
- Electron 44 downloads its binary on first use: `pnpm exec install-electron` fetches it up front.
- Unsigned macOS builds are re-signed ad hoc in the `postPackage` hook so the bundle signature verifies. Signing and notarization turn on from env vars (`.env.example`); `CORRALLM_UNSIGNED=1` forces an unsigned build.
- `build/rpm.spec.ejs` is a patched copy of electron-installer-redhat's template (rpmbuild >= 4.20 fix); delete it once upstream ships the fix.
- Forge 8's terminal UI hides plain logs; set `CI=1` for linear output.
- The main bundle is CommonJS, where `import.meta` does not exist: `vite.main.config.mts` defines `import.meta.url` as the bundle's own file URL (the Agent SDK uses it when loaded). Without it the bundler writes `{}.url` and main crashes at start; `e2e/sdk.e2e.ts` and the packaged self-test would catch it.
- Auto-update is a TODO in `src/main/index.ts` (Squirrel + ZIP makers are compatible with `update-electron-app`).
