# Canvas identity and model

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/shared/model/`

The canvas as the model keeps it, read wherever the engine runs: canvas.ts (AgentNode, FrameNode, Link, CanvasDocument: by what they mean, with no React Flow, selection or sizes; labels are nonblank and at most 200 characters; local positions are within ±1,000,000 on each axis in files and operation inputs; NodeLike, what reading a canvas's nodes needs, whoever keeps them), queue.ts (an agent's queue items, their checks, and live submissions' records), references.ts (clears surviving queues when agents are deleted, returning what changed in words; used by structure.ts's remove), time.ts (times read from what is typed, and when each comes), queries.ts (groups' members, links, an agent's name, its manager, its team and what it is nested in), geometry.ts (fixed CARD_SIZE, group colours, autosize, bounds, hit testing and absolute positions over model nodes, with no DOM sizes; a view may provide its box reader and writer), structure.ts (pure structure edits over CanvasDocument, with explicit ids, caller-supplied new ids and default adapter, selection hints and unchanged objects kept by reference), queue-ops.ts (add, remove, move by neighbour, and a field change union, preserving text authorship), agent-ops.ts (adapter, connection, settings and role edits, translating steps by catalog jobs), layout.ts (dagre over model nodes, fitting groups from CARD_SIZE), insert.ts (inserts a template’s own top-level nodes, optionally under a parent, remapping every node id and reference without adding a wrapper), templates.ts (fills blanks and chooses adapters and native connections from the supplied catalog, preserving untouched nodes and queue items), work.ts (the work arrows derived from agents' queues), file.ts (the .corral format: a CanvasDocument read against the catalog, an agent naming no adapter running the default it is given, and written back, its items' and settings' fields in the order they are read, `inFileOrder`, an empty queue as none, so its text depends only on what it means; item ids unique across a whole queue), rows.ts (a CanvasDocument as the rows the core keeps it in and its topics carry: `toRows`, `fromRows`, one row an entity under node/<id>, link/<a>/<b> with a before b by code point, item/<agent>/<id> and meta, ids escaped as Needs ids are; places that keep while their order holds, so a move rewrites one row; `diffRows`, what a next document changes, entity by entity, and given the document the rows keep, by reference: what the next shares with it is never read again), words.ts (how the queue's items, times and usage holds read, in what the run says and wherever they are shown: words that may name a usage backend take the catalog that names it, and words that tell a time of day the locale), session.ts (an agent's session as its views show it: its entries and pure helpers, turnReply, rewindPoints, chatStart, threadTitle), messages.ts (a Message: what parties send each other, PartyId, its states) and needs.ts (a NeedsItem: what waits for someone).

## Canvas identity

The read-only runtime data sits alongside the document model: `src/shared/model/run.ts` (run data types), `src/shared/model/views.ts` (RunView, SessionSummary, SessionView, MessageView and authored/message queue rows), and the pure display queries in `src/shared/model/run-display.ts`, `src/shared/model/run-words.ts` and `src/shared/model/queue-marks.ts`. These views contain no stores, methods or timers. Projecting messages for display never writes an authored queue item or a canvas row; origin comes from the runtime, and image bytes stay outside general topic state. See [Engine](engine.md) for the existing engine's compatibility exports and ownership.

- Every canvas has a stable id, a UUID (`CanvasId`, `src/shared/canvas.ts`): in its `.corral` file (`{ "format": "corrallm", "version": 2, "id", … }`; another version is refused), or a draft's journal record. The core keeps everything of a canvas by it: its file, project folder and agents' conversations, by the workspace each ran in (`memory.ts`, which never forgets a canvas that owns a workspace record), its run (`run-journal.ts`), both in the core's database, its sessions (`sessions/manager.ts`) and folder (`project.ts`). `core/windows.ts` maps each window to the canvas it shows, and the hand-written channels' handlers look the canvas up there first.
- A canvas's lifetime is the core's operations (B9 Design §1, `core/ops/files.ts`): `canvas.create` (empty or from a template, shown in your window; a token's, made itself or by your Allow of its proposal, is its party's, `document.created_by`, which `Core.clientOf` adds to its reach, open and editable with no folder until you pick one, so nothing runs), `canvas.open`, `canvas.save`, `canvas.saveAs`, `canvas.close` (keeping its edits for when it opens again, unless `discard`) and `project.choose`, which the window's New, Open, Save, Save As and project folder call. New and a template give a canvas with a fresh id (`canvas.create` resolves with it), a draft until it is saved; Save As keeps the id. Opening a file makes it that canvas, unless the canvas is kept in another file that still holds its id (the original after Save As, or a copy made in the Finder): it opens as a copy with an id of its own (kept the next time it opens), and says so. A moved or renamed file keeps its canvas. Save As confirms overwriting the final filename, including when the host adds `.corral` after the file dialog. If the atomic write associating that file with its canvas fails, its previous file association and any displaced canvas's association stay as they were, and later memory writes cannot persist the failed change. Opening the file of the canvas already shown checks the file as usual but keeps its sessions, run stores and generation token; showing that same canvas again never leaves it. A file belongs to one canvas. A file that isn't a canvas this corrallm reads is refused, naming it, before any canvas takes it as its file. A canvas's document is read from its file once, when the core keeps no rows of it, and its rows are what it is from then on: a file changed on disk is not read over them, but raises a file review, yours to Apply or Keep (`core/canvas/reviews.ts`).
- Stores are version 2, with no migration: a version-1 `.corral` is refused; `settings.json` (consents by adapter, the API server's port) and `tokens.json` of version 1 read as empty, and a run journaled in no envelope the journal reads (from schema 4, `{ format: 3 }`) is discarded with the journal's warning. The core's database (`core.db`) keeps its own schema version (`core/store/migrations.ts`), and started empty (B9.0, no import): `canvases.json` and the `runs/<id>/record.json`, `runs/<id>/messages.jsonl` and `runs/last.json` of before are left as they were and never read, so each canvas's folder is picked again in the app, and its messages start anew. The JSON stores (`settings.json`, `tokens.json`, `usage.json`, `links.json`: `readWhole` in `whole-file.ts`) read as empty only when the file is missing: one of another version (version 1 included), or not JSON, also reads as empty, but is first set aside as `<name>.rejected-<uuid>.json` and said on stderr, so nothing it held is written over; one that is there but can't be read (its permissions, the disk, too many files open) is never read as empty nor written over: what needs it fails, saying why, and it is read again next time (`tokens.json` and `usage.json`, read once as the core starts, keep it from starting). Until milestone 1 settles them, a phase may change a version-2 shape (B6: a run checkpoint's pause causes became `{ id, by }`, so a B5b-era record is set aside once; a `.corral` file's node ids are at most `MAX_NODE_ID` characters); after that, phases only add optional fields, which a version-2 reader accepts when absent. `settings.json`, `usage.json`, `tokens.json` and `links.json` also write back what they hold that the running corrallm doesn't know (`unknownFields` in `whole-file.ts`): a newer one's fields, of the file and of each entry it rewrites as it read it (a reading, rule or hard limit replaced is the writer's own), and `usage.json`'s entries for backends this build lacks, so an older corrallm sharing the profile never erases them; a token this build can't read is still dropped, never carried unchecked.

## Gallery workspace grouping

The shipped templates in `src/shared/examples/` use outer frames to share repository workspaces (see [Workspaces](workspaces.md#shipped-template-workspaces)). A frame shares files without creating a manager. Team lead retains its Lead-managed children with Planner alongside Lead; Fan-out research retains its nested Research frame. Head to head alone keeps its contestants and Judge in three independent trees. Existing agent ids, recursive queue-item ids, links and Lead parenting are preserved; existing saved canvases are not migrated. The descriptions in `src/shared/examples.ts` explain these handoffs. `src/shared/model/templates-workspaces.test.ts` pins the grouping and rejects native worktree allocation steps; `src/main/core/engine/run/templates-run.test.ts` runs every shipped queue with that grouping.

Template insertion preserves the template's workspace grouping: `canvas.insertTemplate` returns ordered `roots` and `agents`, mints every inserted node id, and remaps internal parents, links and queue references. Without a parent, the roots remain top-level; with one (a lead defaults to its own agent), they go under it and share its tree. The gallery selects and fits all roots after one operation. `canvas.create` instead keeps the template's original node ids, including its frames, in the new canvas.
