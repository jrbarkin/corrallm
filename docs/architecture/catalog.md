## The catalog

What every adapter declares about the agent it runs is plain data, the catalog (`src/shared/adapter.ts`: `Catalog`, `AdapterDescriptor`, `ConnectionDescriptor`, `ModeDescriptor`, `UsageBackendDescriptor`, `AgentAction`; every id has `ID_PATTERN`'s shape; a step's job is one of `JOBS`). Each adapter fills in its own descriptor in its folder (`sessions/claude-code/adapter.ts`, `sessions/codex/adapter.ts`), and the registry (`sessions/adapters.ts`, the only file meant to import adapters' folders; ESLint's `app/adapters` allowlist names the platform files that still do, each to go: see Layout) builds the catalog from them (`CATALOG`: adapters sorted by name, and the usage backends they spend). The shared types name no CLI, and their comments give no CLI's examples.

- The ids: adapters `claude-code` and `codex`; connections `<adapter>.<name>`, in their adapter's order, the first its default (`claude-code.terminal`, `claude-code.sdk`; `codex.terminal`, `codex.app-server`); usage backends `claude-code` (Claude Code's Terminal spends it) and `codex` (both of Codex's), each with the windows `fiveHour` and `weekly`. They name everything stored (`.corral` files, the database's conversations, `settings.json`'s consents, `usage.json`, run checkpoints) and every IPC argument.
- Each adapter's contract test (`<its folder>/adapter.test.ts`) pins its descriptor: its ids and connection order, each mode's `asks` and `rank`, each connection's `startModes`, `shellPrefix` and `usage`, its `logo`, `registerMcp` and `registerMcpHelper` (none for an adapter whose CLI has no headers helper), and that each connection's `live` and `panels` match the methods of the LiveSession its connector starts. `adapters.test.ts` checks what holds for every adapter (unique ids of the right shape, start modes that ask, declared backends, a connector and an options reader for each) and keeps the renderer tests' copy (see Testing).
- The core reads it in args.ts (a connection, an adapter, a mode a connection starts in, a usage backend), the manager (a connection's adapter and its modes) and usage.ts (the backends it keeps, in the app and in `createCore`; `usage.get`'s schema takes a backend by `ID_PATTERN`'s shape, since the registry names no adapter). The renderer gets it through `api.catalogGet()` (`catalog.get`) before it mounts (boot.ts) and reads it in usage.ts and catalog.ts's lookups, and reads files against it (`src/shared/model/file.ts`, as the core does); the engine (the run and the sessions) reads it through the `EngineCatalog` it is given (`src/shared/engine/catalog.ts`: an agent's adapter and connection, the adapter an agent naming none runs, its actions, the usage backend it spends, whether a connection starts in a mode, whether a mode never asks, a connection's label and a usage backend's name; `runCatalog` in agents.ts makes the renderer's, which its views also pass to the words they share with the run; the core makes its own, its default adapter the registry's `DEFAULT_ADAPTER`), never a table of its own nor the loaded catalog. The renderer's own tables (agents.ts: connections' words and actions; agent/modes.ts: modes) remain until the UI reads the catalog throughout, kept equal to it by agents.test.ts (connections' words, actions), model/agent-ops.test.ts (translation by the actions' `job`s) and agent/modes.test.ts (modes, and the modes Shift+Tab cycles: those that ask); agents.ts' names (an agent's, its CLI's) are the UI's own words, not the catalog's `name`.
- Declared for what comes next: `logo` (an SVG document of the adapter's, drawn only as an `<img>` from a `data:` URL; today the UI guide's stand-in marks), `accent`, `words`, `continueIn`, `keys`, `images`, `panels`, `role`, `resume`, `list`, and actions' `job`s. `registerMcp` and `registerMcpHelper` are read by `corrallm serve --new-token` and `corrallm token` (`src/main/cli/register.ts`): how to register corrallm's MCP server by the token's variable, and by a headers helper reading the token's file at each connect.

## Workspace instructions and native worktree actions

Workspace-managed gallery templates use the core's grouping rather than native worktree actions. Their tests reject EnterWorktree and /worktree in shipped queues; the adapters' action catalogs and their native capabilities are unchanged. The prepared `SessionSpec.workspaceContext` consumer uses each connector's existing standing-instruction mechanism alongside its separate saved role, with no new descriptor or renderer-side CLI table. The authorized context producer and context/conversation invalidation are still C gaps; see [Workspaces](workspaces.md#prepared-workspace-context-consumer-c-gaps).
