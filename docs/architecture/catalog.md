## The catalog

What every adapter declares about the agent it runs is plain data, the catalog (`src/shared/adapter.ts`: `Catalog`, `AdapterDescriptor`, `ConnectionDescriptor`, `ModeDescriptor`, `UsageBackendDescriptor`, `AgentAction`; every id has `ID_PATTERN`'s shape; a step's job is one of `JOBS`). Each adapter fills in its own descriptor in its folder (`sessions/claude-code/adapter.ts`, `sessions/codex/adapter.ts`), and the registry (`sessions/adapters.ts`, the only file meant to import adapters' folders; ESLint's `app/adapters` allowlist names the platform files that still do, each to go: see Layout) builds the catalog from them (`CATALOG`: adapters sorted by name, and the usage backends they spend). The shared types name no CLI, and their comments give no CLI's examples.

- The ids: adapters `claude-code` and `codex`; connections `<adapter>.<name>`, in their adapter's order, the first its default (`claude-code.terminal`, `claude-code.sdk`; `codex.terminal`, `codex.app-server`); usage backends `claude-code` (Claude Code's Terminal spends it) and `codex` (both of Codex's), each with the windows `fiveHour` and `weekly`. They name everything stored (`.corral` files, the database's conversations, `settings.json`'s consents, `usage.json`, run checkpoints) and every IPC argument.
- Each adapter's contract test (`<its folder>/adapter.test.ts`) pins its descriptor: its ids and connection order, each mode's `asks` and `rank`, each connection's `startModes`, `shellPrefix`, `fileMentions` and `usage`, its `logo`, `registerMcp` and `registerMcpHelper` (none for an adapter whose CLI has no headers helper), and that each connection's `live` and `panels` match the methods of the LiveSession its connector starts. `adapters.test.ts` checks what holds for every adapter (unique ids of the right shape, start modes that ask, declared backends, a connector and an options reader for each) and keeps the renderer tests' copy (see Testing).
- The core reads it for operation validation, the session manager and usage. The renderer loads the same `catalog.get` object before mounting (`src/renderer/boot.ts`): a failed read mounts only a fixed error and Retry; a successful retry mounts the app with the catalog it returned. There is no catalog topic, preference, installation state or projection in this build metadata.
- Renderer selectors (`src/renderer/graph/agents.ts`, `src/renderer/agent/modes.ts`) read the loaded catalog at render time for names, connections, descriptions, actions and modes; the chip builds its choices then. Start, the chip and settings retain declared connection order. Shift+Tab cycles only modes whose descriptor says they ask. Settings use the adapter's `words.defaults`, or “The agent’s own default”; the MCP panel uses `words.mcpHint` or a neutral instruction. `src/renderer/AdapterLogo.css` supplies a fixed two-colour accent palette by index, with unknown indices using zero; windows, chips, cards and fallback marks read that index rather than a vendor selector. A canvas's usage gauges read each agent's actual connection, so a connection declaring no usage backend adds no gauge.
- The engine receives `EngineCatalog` (`src/shared/model/catalog.ts`), never the renderer's loaded catalog. `runCatalog` builds the renderer's shared wording lookups. Every lookup resolves the agent's own endpoint; an unchosen or unavailable endpoint has no connection, actions, usage backend, start mode or shell capability.
- An agent's identity is read in one place, `agentEndpoint` (`src/shared/model/catalog.ts`, B12 C3): `known` (an adapter the catalog has, on its first connection when it names none or on one it offers; or, naming no adapter, a connection the catalog knows, as that connection's adapter), `unavailable` (an adapter the catalog lacks, or a connection its adapter doesn't offer, both kept as written) or `unchosen` (neither; an unknown connection kept as written). It never reads a preference, registry order or label, and no string stands for unchosen in a connection's place; `sameEndpoint` compares two as it reads them. The token rules (R1, R6, R8, R11: see [Security](security.md)) read identity through it alone.
- Other catalog metadata: `logo` (an SVG document of the adapter's, drawn only as an `<img>` from a `data:` URL; absent logos use a first-letter mark), `continueIn`, `keys`, `images`, `panels`, `role`, `resume`, `list`, and actions' `job`s. `registerMcp` and `registerMcpHelper` are read by `corrallm serve --new-token` and `corrallm token` (`src/main/cli/register.ts`): how to register corrallm's MCP server by the token's variable, and by a headers helper reading the token's file at each connect.

## Consents

An adapter declares the consents its connections ask you for (B22a C3): `consents`, a list of `ConsentDescriptor`s (`src/shared/adapter.ts`), each a key unique within its adapter (an id's shape, the key its connectors ask by and settings keep a "don't ask again" under), a title (at most `MAX_CONSENT_TITLE`, 120 characters), a description (at most `MAX_CONSENT_DESCRIPTION`, 2 KiB) and the connections of its own adapter that ask for it (at least one, each once), at most `MAX_CONSENTS` (16) an adapter. `catalog.get`'s schema refuses anything else, so a declaration holds no grant and nothing about your account; it is words for the settings page, which reads them from the catalog with no table of its own (`consentIn`). A declaration gives nothing: only your answer to the prompt its connection raises does. `adapters.test.ts` checks that every adapter declares exactly the keys its connectors ask for. Codex declares one, `plan`, for its App Server; the made-up catalogs declare two unfamiliar ones on different connections, and a second adapter asking by one of the same keys.

## Prompt capabilities

Each connection declares `prompts`, one of `none`, `seen` or `answerable` for each of approval, question, plan and form, and `signals`, whether its ask-rule and safety-check reporting is proven. The Agent SDK and App Server declare all four answerable. Claude Terminal declares approval, question and plan seen, form none; Codex Terminal declares approval seen and the other kinds none. All four declare signals false until recordings prove coverage. The strict `PromptDescriptor` schema in `src/shared/model/prompts.ts` validates these fields in catalog.get. These declarations grant no answer authority; an occurrence's answerIn controls where it can be answered. The made-up catalog deliberately declares a different mixture and signals true to exercise consumers without CLI-name assumptions.

## Workspace instructions and native worktree actions

Workspace-managed gallery templates use the core's grouping rather than native worktree actions. Their tests reject EnterWorktree and /worktree in shipped queues; the adapters' action catalogs and their native capabilities are unchanged. The prepared `SessionSpec.workspaceContext` consumer uses each connector's existing standing-instruction mechanism alongside its separate saved role, with no new descriptor or renderer-side CLI table. The authorized context producer and context/conversation invalidation are still C gaps; see [Workspaces](workspaces.md#prepared-workspace-context-consumer-c-gaps).

## Prepared context capability

Each connection declares `context`, true for Claude Code’s Terminal and Agent SDK and Codex’s App Server, false for Codex’s Terminal and the made-up catalogs. It becomes true only when a sanitized recording proves its context reports. Session usage prepares a separate nullable token context (`used`, `window`, `compactAt`); a connection without a proven report keeps it null. No percentage or compaction point is inferred by the platform.

`fileMentions?: true` declares that a connection expands native `@` file mentions without asking. `EngineCatalog.fileMentions` reads it for any adapter; `hasFileMention` and `fileMentionRefusal` provide the shared text-only decision used by token rules and automated sends. Only Claude Code's Terminal sets it; neither Codex connection nor the Agent SDK does.

## Prepared agent API gate

Each connection declares `api: 'http' | 'channel' | null` in `ConnectionDescriptor`. The strict catalog schema carries it as plain metadata, including for unfamiliar adapters. Every shipped connection and the made-up catalog declares `null`, pinned by the adapter contracts and regenerated test catalog: a native route is enabled only with that connection's evidence gate. This declaration alone creates no credential or running API.

## Template jobs

Shipped templates declare `Job`s directly in their own format; `templates.list` reports only each role's id, name and received jobs, with no adapter. The gallery compares those jobs with each adapter's declared actions, without inferring capability from a CLI name or installation. At the core's template boundary, each job becomes the recipient's first action declaring that job; an unsupported job is invalid before a canvas change or workspace allocation. Runtime action translation for an explicit adapter change remains separate.

B11a's shared fallback picker consumes these same selectors.
