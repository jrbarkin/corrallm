# Claude Code connections

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/sessions/claude-code/`

Claude Code's adapter: adapter.ts declares it (with logo.svg), claude.ts finds the executable and flags, claude-errors.ts reads failures, claude-settings.ts reads startup choices, and efforts.ts labels its effort levels. connector.ts starts its Terminal connection, with claude-code.ts as its TerminalCli (command line, hook signals, prompt draft parser and usage); typing.ts types its prompt, first-run.ts takes turns starting it until its folder is trusted, hooks.ts writes its hook settings, hooks-off.ts reads settings that disable them, and statusline.ts wraps the user's status line to read usage. fake-claude.ts fakes its terminal for tests. selftest.ts checks the bundled SDK against its own tiny selftest-claude.mjs, exposed through the adapter to the native self-test.

## `src/main/sessions/claude-code/sdk/`

The Agent SDK connection (see Agent SDK below): connector.ts starts a session (query() with Claude Code's options) once login.ts has checked the CLI's login (an API key or a cloud provider, never a subscription), session.ts runs it (turns, interrupts, mode, model; settings.ts reads the CLI's default mode), translate.ts turns SDK messages into session events (tools.ts words tool calls: summaries, diffs, output), prompts.ts raises what canUseTool (permissions, AskUserQuestion, plans) and MCP servers' requests (onElicitation: forms and links) ask to the core's prompt owner and answers only what it accepts, raise.ts maps each to its prompt and its answer to what the CLI is told, mcp.ts words /mcp's servers, history.ts replays a resumed session's transcript, inbox.ts feeds the streaming query; conversations.ts reads the conversations Claude Code kept for a folder (the SDK's listSessions), whichever connection ran them, for /resume, and forks one to rewind it (getSessionMessages, forkSession). fixtures/ holds what the real CLI did (recorded.ts reads it); fake-claude.mjs is a fake `claude` that speaks the SDK's protocol.

## Agent SDK

`src/main/sessions/claude-code/sdk/` runs a Claude agent through `@anthropic-ai/claude-agent-sdk` (bundled into main: devDependency, root entry only; its per-platform CLI copies are skipped in `pnpm-workspace.yaml`, `ignoredOptionalDependencies`). Rules it keeps:

- One streaming `query()` per session, fed by an `Inbox`, so the CLI runs between turns (interrupts, mode and model changes need it). It runs the user's own `claude` (`pathToClaudeCodeExecutable`), never a JS CLI, with Claude Code's own system prompt (`systemPrompt: { type: 'preset', preset: 'claude_code' }`; without it the agent is bare), the user, project and local settings, `permissionMode` only when the agent was given a mode (Manual is the SDK's `default`; otherwise the user's own default mode applies, and `started` reports it from the CLI's settings: `settings.ts` asks the running CLI with `get_settings`, which the SDK's Query has at runtime though its types leave it out; the first turn's `init` corrects it if the CLI says otherwise), `allowDangerouslySkipPermissions` (so the mode menu can switch to bypassing permissions once the user confirms it there; as in Claude Code, Shift+Tab never cycles into it, and where the CLI's settings turn it off, `permissions.disableBypassPermissionsMode`, read with `get_settings`, it is not offered), partial messages (streaming), summarized thinking (`--thinking-display`), `perTaskStopAffordance` (interrupting stops the turn, not earlier background work: a turn interrupted, by Stop, Kill or taking back a delivered message, still ends the background tasks it started itself, those `task_started` named while it went on, by id with `stopTask`, each bounded to two seconds, before its `end` lets the next message go; one that won't stop is a warning in the session that it may still run), file checkpoints (`enableFileCheckpointing`, which rewinds restore) and `onElicitation` (MCP servers' requests).
- Each message is sent with the core's message id as its uuid and `origin: { kind: 'human' }`, but another party's (one the core delivers for an agent or an outside orchestrator, `UserMessage.from`: the renderer can name no sender) as a peer's, `{ kind: 'peer', from: <its party>, name }` with no `fromMode`, so its trust gates never take it for the user's. A peer's message the CLI would hold for its user's review (nowhere corrallm shows it) or refuse, which no result would ever end, is never sent: where the settings' `crossSessionInbound` (read with `get_settings`) holds or refuses messages from other sessions, or, unless it accepts them, while the session bypasses permissions, the send rejects saying why, and the turn fails with those words, which its sender's reply carries (Delivery holds a party's message while a session runs in a mode that never asks anyway, so the latter only meets a mode switched as it was sent). The fake CLI holds such a message, never answering it, as the CLI does; a turn ends on the `result` whose `user_message_uuids` name it. A result naming none of the messages waiting (a background task's follow-up) ends none of them. Interrupt asks the CLI to cancel what it queued too, and ends what it cancelled.
- Its session id is remembered once a turn has run (the CLI writes the transcript from the first message), and again after /clear. An id with no conversation (one a Terminal session of the agent was given before its first message: the connections share the agent's id; or one whose transcript is gone) starts afresh quietly, as a Terminal session does; a session that cannot be resumed otherwise starts afresh, with a warning. A resumed session's history comes from `getSessionMessages` (history.ts).
- Entry ids are stable between live and history: text and thinking are `<API message id>:<block index>`, tool calls their `tool_use` id, user messages their uuid.
- Prompts (B13 C4: `src/main/sessions/claude-code/sdk/prompts.ts`, `raise.ts`) are canUseTool calls and MCP servers' requests (onElicitation), each raised to the core's prompt owner under a key minted for that native request (see [Sessions](sessions.md)); only the owner's accepted answer, by that key, resolves the native callback, at once, and nothing else answers it but the CLI ending it (aborted: the prompt ends, withdrawn) or the session closing (each still waiting gets the nonapproval below, and ends). The core's decline (a prompt past its bounds or budgets, a link it won't open) and a close answer with the nonapproval: a denial that never stops the turn, an elicitation's decline (a close's: cancel). What each raises, as the real CLI asked it (`fixtures/`: Claude Code 2.1.311): a permission is an approval whose subject is the tool and its exact input (an MCP server's tool names its server: `mcpServer.name`), titled as the CLI titles it (its `title`, or the path it would reach, or the tool), with its `decisionReason` as the reason and the proposed diff or command in twelve lines, marked cut where cut (a command whole, else declined; another tool's input past 64 KiB as a marked preview); its choices are Claude Code's: Yes (allow once, effects none), always (the request's own suggestions, all of them, verbatim, offered only where it suggests any and doesn't say always would allow too much, `suppressAlwaysAllowRule`; its label words every one, a deny or ask rule and a change of rules, folders or mode included, or it is left out and the core's reason says a choice was left out; its effects map rules by where they are kept: session and cliArg the session's, local and project settings the project's, the user's the user's; folders; and a mode kept for the session, and are unknown where a suggestion can't be said so: rules replaced or removed, folders removed, a mode kept beyond the session), No (stops the turn, as the CLI's No does) and No with what to do instead (Claude Code's own message and those words; the turn goes on). Another party's words would be framed as theirs, never the user's; a question's or form's answer from anyone but the user is refused, since the CLI takes it as the user's. AskUserQuestion (the built-in: an MCP server's tool of that name is an approval) is a question prompt, each question an id of corrallm's (`q1`…), a pick or its own words, answered keyed by its text with picks joined by ", " as the CLI's own UI does; questions it can't key so (two the same) are declined, the user told. ExitPlanMode (the built-in) is a plan: Yes into auto (where the session lists it), Accept edits or Manual, each allowed with that mode kept for the session, which the CLI goes into at once (recorded: plan-into-mode), or keep planning, with words or none; a plan with no text is declined. An MCP server's form is a form in the flat schema the shared reader (`src/shared/model/prompt-forms.ts`) re-serialized, naming its server, its message for you alone (the card); one corrallm can't show is declined, the user told by a notice naming the server, never quoting it; a link is a form holding it only in `form.url`, titled in the core's words naming its host (`mcpRequestTitle`: MCP server “tracker” asks you to open a link on tracker.example.com), the server's words nowhere, since they may hold the link, as it is or encoded. Signals (`signalsOf`): an ask rule (`matchedAskRule`, or the reason `rule` or `hook`), a safety check (`safetyCheck`, or `subcommandResults`, which can hide one only a person may approve), or a person's (`classifier`, `serverPolicyAskOnly`, `requiresUserInteraction` but on the built-in question and plan, `other`, or a reason it doesn't know); the connection declares `signals: true`, pinned by the recorded ask rule and safety check. Until X10 converts the renderer, each is shown as before too (a permission, questions, a plan, an MCP server's request, by the ids they had), and an answer to that is translated and answered through the owner (`bridge`: [Sessions](sessions.md)).
- Live progress and the background (translate.ts): `tool_progress` and `task_progress` become a tool's `progress`; `task_started` ties a task to the call that started it, and `background_tasks_changed` (a level: each one replaces the list; housekeeping tasks left out) becomes `tasks`. `stopTask` stops only a task in that list (query.stopTask; its notification ends its line). Hook events (`includeHookEvents`) show only what Claude Code shows: a hook that failed ("… hook error: …") or blocked ("… hook returned blocking error: …"; a Stop hook's "… hook feedback: …"), never what hooks print when they work. Predictions of the next message (`promptSuggestions`) arrive after a turn's result. The effort is set for the session only (`applyFlagSettings({ effortLevel })`, as /effort does without saving; null goes back to the model's default; only one of Claude Code's levels), and set as the session starts when it was given one its model takes (`started` says it). Each model's levels are offered with Claude Code's own words for them (`CLAUDE_EFFORTS`).
- History (history.ts): a turn lasts until its own last work (never the next message, nor what the CLI noted later); a slash command's output shows even when the transcript keeps it as meta (as /context's is). The SDK keeps no live result records: replay uses saved completion, refusal and interruption markers, and emits no `end` for an unknown outcome. An App Server turn still in progress likewise has no historical `end`.
- Logins ("Terminal for subscriptions"): Anthropic doesn't allow other products to offer claude.ai logins or subscription rate limits through the Agent SDK without its approval. So wherever corrallm offers a Claude connection, Terminal comes first (Claude Code's descriptor lists it first, and its contract test pins that; new agents default to an adapter's first connection, and spawned agents keep their source's connection), and the Agent SDK connection starts only with an API key (ANTHROPIC_API_KEY, an apiKeyHelper, ANTHROPIC_AUTH_TOKEN) or a cloud provider (Bedrock, Vertex, Foundry, a gateway). Before `query()`, `login.ts` asks the CLI how it is logged in: `claude auth status --json`, run by main with the agents' environment in the project folder (so a project's apiKeyHelper counts). That is the check, not the SDK's own `account`/`apiKeySource` reports, which come only once the CLI runs under the SDK. A claude.ai login (`authMethod: "claude.ai"`), a `claude setup-token` token (`"oauth_token"`), or a status it can't read refuses the start: a `notice` (one sentence, offering Terminal) and a rejection. Not being logged in at all starts, and the CLI says so. corrallm reads only what kind of login the CLI reports, and whether ANTHROPIC_AUTH_TOKEN is set, never a credential's value; it passes none. The Terminal connection runs the CLI itself, with any login.

## Terminal

- The Terminal connection (`sessions/claude-code/connector.ts`, on the toolkit in `sessions/terminal/`) runs Claude Code's own interactive CLI, so the user has all of Claude Code in the agent view (`TerminalPane.tsx` in place of the transcript and composer): its prompts, modes, models, slash commands and dialogs are answered there. It is started with `--settings` (a file in the temp folder: corrallm's HTTP hooks and command-type SessionStart hook, merged with the user's, and corrallm's status line: see Usage readings and rules), `--session-id` (new) or `--resume` (one with no transcript starts afresh under the same id), and `--model`/`--effort`/`--permission-mode` only when the agent is set to them (an explicit Manual too, as `manual`, one of the flag's choices; `default` as a model is left out; `--effort` only with one of Claude Code's levels, and only where its `claude --help` lists the flag, asked once per executable: `claudeFlags` in claude.ts, since an older CLI would not start with it): otherwise the user's own defaults apply. corrallm follows it to orchestrate it: Claude Code's Program Status reports (OSC 7501, answered and read in main's copy of the screen) say when it works, waits on the user, is done, was interrupted (idle) or failed; its hooks (`hooks.ts`) tell the session id (it changes with /clear), prompts typed in the terminal, the last reply, failures (StopFailure names its error, which the turn's end carries as its reason, mapped as the Agent SDK's are: `claude-errors.ts`; its `rate_limit` is `usage-limit`, and says nothing of when the limit lifts, which the core takes from the backend's latest reading: see Usage readings and rules), mode and model. A message corrallm sends is typed in (a few characters at a time, Ctrl+J for line breaks, then Enter: never a paste, which Claude Code collapses and treats as untrusted) once the prompt is ready: Claude Code idle or done, and nothing the user typed in it; Enter goes once the prompt shows what was typed (keys that pile up while Claude Code is busy, as right after the folder trust dialog or as a turn ends, are read in one go as a paste, where 2.1.296 keeps an Enter as an invisible character, not a submit). Meanwhile, a dialog (the folder trust prompt) or the user's draft makes the turn wait on the user. A turn ends once Claude Code has taken every message sent in it and stopped working; one the user started in the terminal is a turn too. Answers, modes and models are refused over the session channels: they belong to the terminal.
- Folder trust: Claude Code asks whether to trust a folder the first time it runs there ("Quick safety check…", default "No, exit"), before it reports anything or runs a hook, so the session reads it from the screen (TerminalCli's `trusting`): while it shows, `asking` lists a `trust` ask, turn or not, and a message waiting for the prompt waits on the user at once. The CLI is past its first-run dialogs once it reports its state, a hook posts, or its prompt shows. Every Claude Code started before the user answers would ask again, so Claude's Terminal connector has its sessions in a folder (by real path) take turns (`first-run.ts`): one starts first; the others wait (held: `started` is sent, their screen says why, a message for them is `working`) until it is past them (then all start, and so does every later one) or it ends without (the next one goes, and asks). Codex is told the folder is trusted on its command line, and never asks (checked with 0.160.1 in a fresh folder).
- What Claude Code asks in its terminal (`asking`, from its TerminalCli's hook signals, `claude-code.ts`): its PermissionRequest hook tells a permission prompt's tool and input (worded by `sdk/tools.ts`: its summary, and what the prompt shows, `proposedDetail`, cut to 12 lines by `preview` in transcript.ts), PreToolUse (only for AskUserQuestion and ExitPlanMode) its questions and plan (PermissionRequest tells them too, without a call id: told once), Notification what it needs when nothing else says (an MCP server's question). Recorded from 2.1.296: the hooks come just before its Program Status says `blocked` (with `kind` permission, question or auth, and `msg`, as "approve Bash: git init" or "answer: Pick a color (Red · Blue)"). The session lists what the hooks told within a few seconds before a wait began, or else the wait's `msg` (or the notification's words, or the CLI's own for the wait's kind), while it waits; once it goes on (the user answered in the terminal), the turn ends or the CLI exits, it lists nothing. Without status reports, what the hooks told is listed until the turn ends. Every hook is answered with no decision. Codex tells nothing ahead: while its title says Action Required, its wait is listed in its own words.
- Hooks turned off: corrallm hears Claude Code's replies, prompts, session ids and asks only through its hooks. When a session starts, `hooks-off.ts` reads the settings Claude Code reads (never writing them): the organization's managed settings (`managed-settings.json` and `managed-settings.d/*.json` in the OS's folder: `/Library/Application Support/ClaudeCode`, `/etc/claude-code`, `C:\Program Files\ClaudeCode`), then the project's `.claude/settings.local.json` and `.claude/settings.json`, then the user's (`CLAUDE_CONFIG_DIR` or `~/.claude`). They turn corrallm's hooks off with `disableAllHooks` (the most particular that sets it wins; the status line goes too, so no usage readings), `allowManagedHooksOnly` or `strictPluginOnlyCustomization` locking hooks (managed only), or `allowedHttpHookUrls` without a pattern matching its server on 127.0.0.1 (lists merged across files). corrallm omits its hooks when any such restriction is detected, and the session says so once, as it starts (`unheard`: which setting, where, and that the run can't read its replies). `httpHookAllowedEnvVars` controls only [header-variable interpolation](https://code.claude.com/docs/en/hooks#http-hook-fields); corrallm's literal HTTP headers and file-backed commands use none, so this setting does not disable them or cause an `unheard` warning. Not read: managed settings from a server or an OS policy.

## Tests and recordings

The SDK fake also accepts `FAKE_CLAUDE_TURN_GATES`, a test-only JSON map from exact prompt text to release-file paths. A selected turn writes `<path>.waiting` after its initial thinking, then waits for `<path>` or an interrupt; other prompts proceed normally. This lets the Pause e2e assert Pausing and independent progress before releasing the native turn, instead of racing the UI against the fake's forty sequential 100 ms timers for a "slow" prompt. The connector test proves an unselected turn completes normally, a gated one emits no end before release and completes once after it, and an interrupt releases the gate with a cancelled end.

- The Agent SDK connector's tests replay what the real CLI did (`src/main/sessions/claude-code/sdk/fixtures/`, recorded with Haiku in a scratch folder, its paths and the user's own skills, servers, plugins and usage limits taken out; `recorded.ts` says what each holds: since B13 C4 an ask rule, a safety check, the suggestions offered together, both denials, an MCP server's tool calls, form and link, and a plan approved into a mode) and drive the real SDK against `sessions/claude-code/sdk/fake-claude.mjs`; e2e (`e2e/sdk.e2e.ts`) points the built app at it with `CORRALLM_AGENT_PATHS`. With `CLAUDE_CONFIG_DIR` set (only then, so it never writes into the user's own `~/.claude`), the SDK fake keeps its conversations' transcripts there as the CLI does, so the SDK's session functions (listSessions, getSessionMessages, forkSession) read them: `sdk/cli.test.ts` and `e2e/sdk.e2e.ts` point it, and main, at a throwaway folder. It takes the SDK's flags as the SDK passes them (`--flag=value`), asks as the recordings did ("secret": an ask rule's Read, in any mode; "safety": a safety check's Write, in any mode; "touch": a command offering a rule, the folder and Accept edits together; "a link": its tracker server's tool call, asked as that server's policy says, then that server's link; "a plan": ExitPlanMode; an answer keeping a session mode switches to it, saying so), really edits the project's notes.txt ("edit"), and with file checkpointing on keeps it as it was before each message, for `rewind_files`. Both fakes answer `claude auth status --json` as the real CLI does: a Claude subscription unless their environment has an API key (the SDK one also takes a cloud provider, or an apiKeyHelper in the project's settings), so tests of a working SDK session give the agents a fake ANTHROPIC_API_KEY. On a machine logged in only with claude.ai, the real Agent SDK connection refuses to start: check it live that way, with no prompt, and use Terminal for live checks. To record new fixtures, run a few tiny prompts through the SDK in a throwaway folder, never a real repository, and keep the same sanitizing.

- The Terminal connector's unit tests run `sessions/claude-code/fake-claude.ts` behind a fake pty, and `e2e/terminal.e2e.ts` runs the real connector with `CORRALLM_AGENT_PATHS` pointing at `e2e/fake-claude.mjs` in a real pty (it logs what it gets in the project folder, since the terminal draws its text on a canvas; its `--help` lists `--effort`), and with `CLAUDE_CONFIG_DIR` a throwaway folder, so the user's own settings are never read.

## Native IDs and safety

- Native session ids follow [R42a](sessions.md#connected-sessions): `sessions/id.ts` supplies the platform minimum, then this adapter's `isConversationId` requires UUIDs. Checks cover hook signals, resume IPC arguments, remembered sessions loaded from disk and its Terminal argv builder. Claude resume uses `--resume=<id>`; an id must never be read as a CLI flag. The Terminal's invalid-conversation-id warning is emitted once per reported invalid id in that session (`ClaudeCode`'s `#invalidIds`, as Codex Terminal's); later hooks with that id still report prompts, modes and turn state.

The SDK's conversation list skips entries whose sessionId fails the platform minimum or UUID
shape, keeping the valid entries sorted by lastModified. One count-only warning per listing says
how many were skipped. Explicit rewind reads, forks and fork results retain their strict id checks.

corrallm only reads Claude Code's settings files (the user's, the project's and the organization's managed ones) to tell whether they turn its hooks off (`hooks-off.ts`), and never overrides them (its `--settings` never set `disableAllHooks` or the hook allowlists).

The [SessionStart hook](https://code.claude.com/docs/en/hooks#sessionstart) fires at startup but has no `permission_mode` in Claude Code 2.1.310, even when `--permission-mode acceptEdits` was given. Its quiet command hook (HTTP hooks cannot handle SessionStart) posts JSON stdin with the session token from its private 0600 header file; no event text enters a command line, no response is printed or used as a decision, and curl gives up after five seconds. Claude Code runs command hooks in Bash (Git Bash on Windows); the post uses `/bin/sh` and the same shared command-post helper as Codex’s POSIX hooks. All other events keep their HTTP hooks. The startup command is omitted whenever the existing hooks-off reader finds restrictions, including the HTTP URL allowlist, so the command transport does not bypass them. Native folder trust still precedes hooks. Delivery uses the explicit start mode or the trusted pre-launch default carried in `started.asks` until later native hooks report permissions (see [Sessions](sessions.md)). The fake's SessionStart likewise omits permissions; prompt and turn hooks can report them.

Hook commands inherit only `CORRALLM_HOOK_HEADER`, the path of a 0600 header file in the session's own folder, and use curl's `-H @<file>` in Bash (Git Bash on Windows). Native HTTP hooks read a literal header from the session's 0600 settings file. The hook token is absent from the CLI and every hook child's environment and command line; closing the session removes both private files.

## Prepared workspace context

Both connections accept the separate, C-owned `SessionSpec.workspaceContext` consumer described in [Sessions](sessions.md#prepared-workspace-context-adapter-seam). Terminal appends the combined role/context through --append-system-prompt; the SDK keeps its claude_code preset and appends it there. No user turn, hook answer or permission override carries context. Role-only startup and snapshot behavior remain unchanged. No production producer is composed: C must authorize the projection and define context-generation/native-snapshot invalidation before enabling it.

## Context readings

Both connections prepare `SessionUsage.context` in whole tokens, while their catalog `context` capability remains false until sanitized real-CLI recordings verify the readings through automatic compaction. These readings do not arm or request handoffs.

The Agent SDK translator uses only the last top-level assistant response's input, cache creation, cache read and output tokens, never cumulative `modelUsage` counts or a subagent's response. Its window and output allowance come from that model's result entry; The last top-level response identifies the model after a native model change; only with no model identity at all is a single-model result unambiguous. Before publishing the result and ending the turn, the session asks `getContextUsage({ detail: 'summary' })` for `autoCompactThreshold`, with a two-second bound. An absent, refused or timed-out summary uses the CLI's default: window minus the smaller of `maxOutputTokens` and 20,000, minus 13,000 (floored at zero). A missing output allowance reserves 20,000. A reported threshold is capped at the window. Malformed counts or an unknown window leave context unknown.

The Terminal status-line wrapper posts inputs containing `context_window` as well as `rate_limits`. `statusLineContext` reads `context_window_size` and the current request's input, cache creation, cache read and output counts; without current request counts it converts `used_percentage` to tokens, rounded to the nearest token. It never takes cumulative session token totals as current context. This connection has no reported output allowance, so its default compaction point reserves 20,000 output tokens plus 13,000. The Terminal toolkit publishes changed context, including clearing a previous reading, without treating timer refreshes as work. Windows still installs no wrapper. A lowered native compaction setting or idle compaction can precede this estimate.

The SDK fake's `FAKE_CLAUDE_COMPACT_AT` supplies an optional native `autoCompactThreshold`; connector tests exercise both that control response and the default rule. Status-line tests drive the wrapper and the fake Terminal session with context-only and combined inputs. No test runs a real agent CLI.
