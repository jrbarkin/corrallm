# Claude Code connections

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/sessions/claude-code/`

Claude Code's adapter: adapter.ts declares it (with logo.svg), claude.ts finds the executable and flags, claude-errors.ts reads failures, claude-settings.ts reads startup choices, and efforts.ts labels its effort levels. connector.ts starts its Terminal connection, with claude-code.ts as its TerminalCli (command line, hook signals, prompt draft parser and usage); typing.ts types its prompt, first-run.ts takes turns starting it until its folder is trusted, hooks.ts writes its hook settings, hooks-off.ts reads settings that disable them, and statusline.ts wraps the user's status line to read usage. fake-claude.ts fakes its terminal for tests. selftest.ts checks the bundled SDK against its own tiny selftest-claude.mjs, exposed through the adapter to the native self-test.

## `src/main/sessions/claude-code/sdk/`

The Agent SDK connection (see Agent SDK below): connector.ts starts a session (query() with Claude Code's options) once login.ts has checked the CLI's login (an API key or a cloud provider, never a subscription), session.ts runs it (turns, interrupts, mode, model; settings.ts reads the CLI's default mode), translate.ts turns SDK messages into session events (tools.ts words tool calls: summaries, diffs, output), prompts.ts answers canUseTool (permissions, AskUserQuestion, plans) and MCP servers' requests (onElicitation: forms, which mcp.ts reads and checks, and links), mcp.ts also words /mcp's servers, history.ts replays a resumed session's transcript, inbox.ts feeds the streaming query; conversations.ts reads the conversations Claude Code kept for a folder (the SDK's listSessions), whichever connection ran them, for /resume, and forks one to rewind it (getSessionMessages, forkSession). fixtures/ holds what the real CLI did (recorded.ts reads it); fake-claude.mjs is a fake `claude` that speaks the SDK's protocol.

## Agent SDK

`src/main/sessions/claude-code/sdk/` runs a Claude agent through `@anthropic-ai/claude-agent-sdk` (bundled into main: devDependency, root entry only; its per-platform CLI copies are skipped in `pnpm-workspace.yaml`, `ignoredOptionalDependencies`). Rules it keeps:

- One streaming `query()` per session, fed by an `Inbox`, so the CLI runs between turns (interrupts, mode and model changes need it). It runs the user's own `claude` (`pathToClaudeCodeExecutable`), never a JS CLI, with Claude Code's own system prompt (`systemPrompt: { type: 'preset', preset: 'claude_code' }`; without it the agent is bare), the user, project and local settings, `permissionMode` only when the agent was given a mode (Manual is the SDK's `default`; otherwise the user's own default mode applies, and `started` reports it from the CLI's settings: `settings.ts` asks the running CLI with `get_settings`, which the SDK's Query has at runtime though its types leave it out; the first turn's `init` corrects it if the CLI says otherwise), `allowDangerouslySkipPermissions` (so the mode menu can switch to bypassing permissions once the user confirms it there; as in Claude Code, Shift+Tab never cycles into it, and where the CLI's settings turn it off, `permissions.disableBypassPermissionsMode`, read with `get_settings`, it is not offered), partial messages (streaming), summarized thinking (`--thinking-display`), `perTaskStopAffordance` (interrupting stops the turn, not background work), file checkpoints (`enableFileCheckpointing`, which rewinds restore) and `onElicitation` (MCP servers' requests).
- Each message is sent with the renderer's id as its uuid and `origin: { kind: 'human' }`, but another party's (one the core delivers for an agent or an outside orchestrator, `UserMessage.from`: the renderer can name no sender) as a peer's, `{ kind: 'peer', from: <its party>, name }` with no `fromMode`, so its trust gates never take it for the user's. A peer's message the CLI would hold for its user's review (nowhere corrallm shows it) or refuse, which no result would ever end, is never sent: where the settings' `crossSessionInbound` (read with `get_settings`) holds or refuses messages from other sessions, or, unless it accepts them, while the session bypasses permissions, the send rejects saying why, and the turn fails with those words, which its sender's reply carries (Delivery holds a party's message while a session runs in a mode that never asks anyway, so the latter only meets a mode switched as it was sent). The fake CLI holds such a message, never answering it, as the CLI does; a turn ends on the `result` whose `user_message_uuids` name it. A result naming none of the messages waiting (a background task's follow-up) ends none of them. Interrupt asks the CLI to cancel what it queued too, and ends what it cancelled.
- Its session id is remembered once a turn has run (the CLI writes the transcript from the first message), and again after /clear. An id with no conversation (one a Terminal session of the agent was given before its first message: the connections share the agent's id; or one whose transcript is gone) starts afresh quietly, as a Terminal session does; a session that cannot be resumed otherwise starts afresh, with a warning. A resumed session's history comes from `getSessionMessages` (history.ts).
- Entry ids are stable between live and history: text and thinking are `<API message id>:<block index>`, tool calls their `tool_use` id, user messages their uuid.
- Prompts are canUseTool calls: permissions offer "always" only where the CLI suggests a rule to keep (its suggestions, worded as Claude Code words them); No denies and stops the turn, as the CLI's No does; No with what to do instead denies with Claude Code's own message and those words, and the turn goes on. An approved plan is carried out in the mode chosen once the CLI has left plan mode (it reports the mode it goes back to). An MCP server's request (`onElicitation`) is a prompt too: a form, in the flat JSON Schema the protocol allows (`mcp.ts`; one corrallm can't show is declined, and the user told), whose answer main checks against the form before it goes back (one that does not fit is refused and the form still waits), or a link the user opens through `link.open`.
- Live progress and the background (translate.ts): `tool_progress` and `task_progress` become a tool's `progress`; `task_started` ties a task to the call that started it, and `background_tasks_changed` (a level: each one replaces the list; housekeeping tasks left out) becomes `tasks`. `stopTask` stops only a task in that list (query.stopTask; its notification ends its line). Hook events (`includeHookEvents`) show only what Claude Code shows: a hook that failed ("… hook error: …") or blocked ("… hook returned blocking error: …"; a Stop hook's "… hook feedback: …"), never what hooks print when they work. Predictions of the next message (`promptSuggestions`) arrive after a turn's result. The effort is set for the session only (`applyFlagSettings({ effortLevel })`, as /effort does without saving; null goes back to the model's default; only one of Claude Code's levels), and set as the session starts when it was given one its model takes (`started` says it). Each model's levels are offered with Claude Code's own words for them (`CLAUDE_EFFORTS`).
- History (history.ts): a turn lasts until its own last work (never the next message, nor what the CLI noted later); a slash command's output shows even when the transcript keeps it as meta (as /context's is). The SDK keeps no live result records: replay uses saved completion, refusal and interruption markers, and emits no `end` for an unknown outcome. An App Server turn still in progress likewise has no historical `end`.
- Logins ("Terminal for subscriptions"): Anthropic doesn't allow other products to offer claude.ai logins or subscription rate limits through the Agent SDK without its approval. So wherever corrallm offers a Claude connection, Terminal comes first (Claude Code's descriptor lists it first, and its contract test pins that; new agents default to an adapter's first connection, and spawned agents keep their source's connection), and the Agent SDK connection starts only with an API key (ANTHROPIC_API_KEY, an apiKeyHelper, ANTHROPIC_AUTH_TOKEN) or a cloud provider (Bedrock, Vertex, Foundry, a gateway). Before `query()`, `login.ts` asks the CLI how it is logged in: `claude auth status --json`, run by main with the agents' environment in the project folder (so a project's apiKeyHelper counts). That is the check, not the SDK's own `account`/`apiKeySource` reports, which come only once the CLI runs under the SDK. A claude.ai login (`authMethod: "claude.ai"`), a `claude setup-token` token (`"oauth_token"`), or a status it can't read refuses the start: a `notice` (one sentence, offering Terminal) and a rejection. Not being logged in at all starts, and the CLI says so. corrallm reads only what kind of login the CLI reports, and whether ANTHROPIC_AUTH_TOKEN is set, never a credential's value; it passes none. The Terminal connection runs the CLI itself, with any login.

## Terminal

- The Terminal connection (`sessions/claude-code/connector.ts`, on the toolkit in `sessions/terminal/`) runs Claude Code's own interactive CLI, so the user has all of Claude Code in the agent view (`TerminalPane.tsx` in place of the transcript and composer): its prompts, modes, models, slash commands and dialogs are answered there. It is started with `--settings` (a file in the temp folder: corrallm's HTTP hooks and command-type SessionStart hook, merged with the user's, and corrallm's status line: see Usage readings and rules), `--session-id` (new) or `--resume` (one with no transcript starts afresh under the same id), and `--model`/`--effort`/`--permission-mode` only when the agent is set to them (an explicit Manual too, as `manual`, one of the flag's choices; `default` as a model is left out; `--effort` only with one of Claude Code's levels, and only where its `claude --help` lists the flag, asked once per executable: `claudeFlags` in claude.ts, since an older CLI would not start with it): otherwise the user's own defaults apply. corrallm follows it to orchestrate it: Claude Code's Program Status reports (OSC 7501, answered and read in main's copy of the screen) say when it works, waits on the user, is done, was interrupted (idle) or failed; its hooks (`hooks.ts`) tell the session id (it changes with /clear), prompts typed in the terminal, the last reply, failures (StopFailure names its error, which the turn's end carries as its reason, mapped as the Agent SDK's are: `claude-errors.ts`; its `rate_limit` is `usage-limit`, and says nothing of when the limit lifts, which the core takes from the backend's latest reading: see Usage readings and rules), mode and model. A message corrallm sends is typed in (a few characters at a time, Ctrl+J for line breaks, then Enter: never a paste, which Claude Code collapses and treats as untrusted) once the prompt is ready: Claude Code idle or done, and nothing the user typed in it; Enter goes once the prompt shows what was typed (keys that pile up while Claude Code is busy, as right after the folder trust dialog or as a turn ends, are read in one go as a paste, where 2.1.296 keeps an Enter as an invisible character, not a submit). Meanwhile, a dialog (the folder trust prompt) or the user's draft makes the turn wait on the user. A turn ends once Claude Code has taken every message sent in it and stopped working; one the user started in the terminal is a turn too. Answers, modes and models are refused over the session channels: they belong to the terminal.
- Folder trust: Claude Code asks whether to trust a folder the first time it runs there ("Quick safety check…", default "No, exit"), before it reports anything or runs a hook, so the session reads it from the screen (TerminalCli's `trusting`): while it shows, `asking` lists a `trust` ask, turn or not, and a message waiting for the prompt waits on the user at once. The CLI is past its first-run dialogs once it reports its state, a hook posts, or its prompt shows. Every Claude Code started before the user answers would ask again, so Claude's Terminal connector has its sessions in a folder (by real path) take turns (`first-run.ts`): one starts first; the others wait (held: `started` is sent, their screen says why, a message for them is `working`) until it is past them (then all start, and so does every later one) or it ends without (the next one goes, and asks). Codex is told the folder is trusted on its command line, and never asks (checked with 0.160.1 in a fresh folder).
- What Claude Code asks in its terminal (`asking`, from its TerminalCli's hook signals, `claude-code.ts`): its PermissionRequest hook tells a permission prompt's tool and input (worded by `sdk/tools.ts`: its summary, and what the prompt shows, `proposedDetail`, cut to 12 lines by `preview` in transcript.ts), PreToolUse (only for AskUserQuestion and ExitPlanMode) its questions and plan (PermissionRequest tells them too, without a call id: told once), Notification what it needs when nothing else says (an MCP server's question). Recorded from 2.1.296: the hooks come just before its Program Status says `blocked` (with `kind` permission, question or auth, and `msg`, as "approve Bash: git init" or "answer: Pick a color (Red · Blue)"). The session lists what the hooks told within a few seconds before a wait began, or else the wait's `msg` (or the notification's words, or the CLI's own for the wait's kind), while it waits; once it goes on (the user answered in the terminal), the turn ends or the CLI exits, it lists nothing. Without status reports, what the hooks told is listed until the turn ends. Every hook is answered with no decision. Codex tells nothing ahead: while its title says Action Required, its wait is listed in its own words.
- Hooks turned off: corrallm hears Claude Code's replies, prompts, session ids and asks only through its hooks. When a session starts, `hooks-off.ts` reads the settings Claude Code reads (never writing them): the organization's managed settings (`managed-settings.json` and `managed-settings.d/*.json` in the OS's folder: `/Library/Application Support/ClaudeCode`, `/etc/claude-code`, `C:\Program Files\ClaudeCode`), then the project's `.claude/settings.local.json` and `.claude/settings.json`, then the user's (`CLAUDE_CONFIG_DIR` or `~/.claude`). They turn corrallm's hooks off with `disableAllHooks` (the most particular that sets it wins; the status line goes too, so no usage readings), `allowManagedHooksOnly` or `strictPluginOnlyCustomization` locking hooks (managed only), `allowedHttpHookUrls` without a pattern matching its server on 127.0.0.1, or `httpHookAllowedEnvVars` without its token's variable (both lists merged across files). Then the session says so once, as it starts (`unheard`: which setting, where, and that the run can't read its replies). Not read: managed settings from a server or an OS policy.

## Tests and recordings

The SDK fake also accepts `FAKE_CLAUDE_TURN_GATES`, a test-only JSON map from exact prompt text to release-file paths. A selected turn writes `<path>.waiting` after its initial thinking, then waits for `<path>` or an interrupt; other prompts proceed normally. This lets the Pause e2e assert Pausing and independent progress before releasing the native turn, instead of racing the UI against the fake's forty sequential 100 ms timers for a "slow" prompt. The connector test proves an unselected turn completes normally, a gated one emits no end before release and completes once after it, and an interrupt releases the gate with a cancelled end.

- The Agent SDK connector's tests replay what the real CLI did (`src/main/sessions/claude-code/sdk/fixtures/`, recorded with Haiku in a scratch folder, its paths and the user's own skills and servers taken out) and drive the real SDK against `sessions/claude-code/sdk/fake-claude.mjs`; e2e (`e2e/sdk.e2e.ts`) points the built app at it with `CORRALLM_AGENT_PATHS`. With `CLAUDE_CONFIG_DIR` set (only then, so it never writes into the user's own `~/.claude`), the SDK fake keeps its conversations' transcripts there as the CLI does, so the SDK's session functions (listSessions, getSessionMessages, forkSession) read them: `sdk/cli.test.ts` and `e2e/sdk.e2e.ts` point it, and main, at a throwaway folder. It takes the SDK's flags as the SDK passes them (`--flag=value`), really edits the project's notes.txt ("edit"), and with file checkpointing on keeps it as it was before each message, for `rewind_files`. Both fakes answer `claude auth status --json` as the real CLI does: a Claude subscription unless their environment has an API key (the SDK one also takes a cloud provider, or an apiKeyHelper in the project's settings), so tests of a working SDK session give the agents a fake ANTHROPIC_API_KEY. On a machine logged in only with claude.ai, the real Agent SDK connection refuses to start: check it live that way, with no prompt, and use Terminal for live checks. To record new fixtures, run a few tiny prompts through the SDK in a throwaway folder, never a real repository, and keep the same sanitizing.

- The Terminal connector's unit tests run `sessions/claude-code/fake-claude.ts` behind a fake pty, and `e2e/terminal.e2e.ts` runs the real connector with `CORRALLM_AGENT_PATHS` pointing at `e2e/fake-claude.mjs` in a real pty (it logs what it gets in the project folder, since the terminal draws its text on a canvas; its `--help` lists `--effort`), and with `CLAUDE_CONFIG_DIR` a throwaway folder, so the user's own settings are never read.

## Native IDs and safety

- Session ids are UUIDs (`sessions/id.ts`), checked in hook signals, resume IPC arguments, remembered sessions loaded from disk, and both Terminal CLIs' argv builders. Claude resume uses `--resume=<id>`; an id must never be read as a CLI flag.

corrallm only reads Claude Code's settings files (the user's, the project's and the organization's managed ones) to tell whether they turn its hooks off (`hooks-off.ts`), and never overrides them (its `--settings` never set `disableAllHooks` or the hook allowlists).

The [SessionStart hook](https://code.claude.com/docs/en/hooks#sessionstart) reports `permission_mode` without needing a prompt. It uses a quiet command hook (HTTP hooks cannot handle SessionStart) to post JSON stdin with the session token from its environment; no event text enters a command line, no response is printed or used as a decision, and curl gives up after five seconds. Claude Code runs command hooks in Bash (Git Bash on Windows); the post uses `/bin/sh` and the same shared command-post helper as Codex’s POSIX hooks. All other events keep their HTTP hooks. The startup command is omitted whenever the existing hooks-off reader finds restrictions, including HTTP URL or environment-variable allowlists, so the command transport does not bypass them. Native folder trust still precedes hooks. The fake CLI can emulate this startup report separately from its older recorded prompt/turn behavior.
