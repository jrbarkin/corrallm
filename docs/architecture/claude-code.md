# Claude Code connections

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/sessions/claude-code/`

Claude Code's adapter: adapter.ts declares it (with logo.svg), claude.ts finds the executable and flags, claude-errors.ts reads failures, claude-settings.ts reads startup choices, and efforts.ts labels its effort levels. connector.ts starts its Terminal connection, with claude-code.ts as its TerminalCli (command line, hook signals, prompt draft parser and usage); typing.ts types its prompt, first-run.ts takes turns starting it until its folder is trusted, hooks.ts writes its hook settings, hooks-off.ts reads settings that disable them, and statusline.ts wraps the user's status line to read usage. fake-claude.ts fakes its terminal for tests. selftest.ts checks the bundled SDK against its own tiny selftest-claude.mjs, exposed through the adapter to the native self-test.

## `src/main/sessions/claude-code/sdk/`

The Agent SDK connection (see Agent SDK below): connector.ts starts a session (query() with Claude Code's options) once login.ts has checked the CLI's login (an API key or a cloud provider, never a subscription), session.ts runs it (turns, interrupts, mode, model; settings.ts reads the CLI's default mode), translate.ts turns SDK messages into session events (tools.ts words tool calls: summaries, diffs, output), prompts.ts raises what canUseTool (permissions, AskUserQuestion, plans) and MCP servers' requests (onElicitation: forms and links) ask to the core's prompt owner and answers only what it accepts, raise.ts maps each to its prompt and its answer to what the CLI is told, mcp.ts words /mcp's servers, history.ts replays a resumed session's transcript, inbox.ts feeds the streaming query; conversations.ts reads the conversations Claude Code kept for a folder (the SDK's listSessions), whichever connection ran them, for /resume, and forks one to rewind it (getSessionMessages, forkSession). fixtures/ holds what the real CLI did (recorded.ts reads it); fake-claude.mjs is a fake `claude` that speaks the SDK's protocol.

## Agent SDK

`src/main/sessions/claude-code/sdk/` runs a Claude agent through `@anthropic-ai/claude-agent-sdk` (bundled into main: devDependency, root entry only; its per-platform CLI copies are skipped in `pnpm-workspace.yaml`, `ignoredOptionalDependencies`). Rules it keeps:

- One streaming `query()` per session, fed by an `Inbox`, so the CLI runs between turns (interrupts, mode and model changes need it). It runs the user's own `claude` (`pathToClaudeCodeExecutable`), never a JS CLI, with Claude Code's own system prompt (`systemPrompt: { type: 'preset', preset: 'claude_code' }`; without it the agent is bare), the user, project and local settings, `permissionMode` only when the agent was given a mode (Manual is the SDK's `default`; otherwise the user's own default mode applies, and `started` reports it from the CLI's settings: `settings.ts` asks the running CLI with `get_settings`, which the SDK's Query has at runtime though its types leave it out; the first turn's `init` corrects it if the CLI says otherwise), `allowDangerouslySkipPermissions` (so the mode menu can switch to bypassing permissions once the user confirms it there; as in Claude Code, Shift+Tab never cycles into it, and where the CLI's settings turn it off, `permissions.disableBypassPermissionsMode`, read with `get_settings`, it is not offered), partial messages (streaming), summarized thinking (`--thinking-display`), `perTaskStopAffordance` (interrupting stops the turn, not earlier background work: a turn interrupted, by Stop, Kill or taking back a delivered message, still ends the background tasks it started itself, those `task_started` named while it went on, by id with `stopTask`, each bounded to two seconds, before its `end` lets the next message go; one that won't stop is a warning in the session that it may still run), file checkpoints (`enableFileCheckpointing`, which rewinds restore) and `onElicitation` (MCP servers' requests).
- Each message is sent with the core's message id as its uuid and `origin: { kind: 'human' }`, but another party's (one the core delivers for an agent or an outside orchestrator, `UserMessage.from`: the renderer can name no sender) as a peer's, `{ kind: 'peer', from: <its party>, name }` with no `fromMode`, and `client_composed: true` so the CLI keeps its text literal (your typing and the run's own canvas text leave that flag absent), so its trust gates never take it for the user's. A peer's message the CLI would hold for its user's review (nowhere corrallm shows it) or refuse, which no result would ever end, is never sent: where the settings' `crossSessionInbound` (read with `get_settings`) holds or refuses messages from other sessions, or, unless it accepts them, while the session bypasses permissions, the send rejects saying why, and the turn fails with those words, which its sender's reply carries (Delivery holds a party's message while a session runs in a mode that never asks anyway, so the latter only meets a mode switched as it was sent). The fake CLI holds such a message, never answering it, as the CLI does; a turn ends on the `result` whose `user_message_uuids` name it. A result naming none of the messages waiting (a background task's follow-up) ends none of them. Interrupt asks the CLI to cancel what it queued too, and ends what it cancelled.
- Its session id is remembered once a turn has run (the CLI writes the transcript from the first message), and again after /clear. An id with no conversation (one a Terminal session of the agent was given before its first message: the connections share the agent's id; or one whose transcript is gone) starts afresh quietly, as a Terminal session does; a session that cannot be resumed otherwise starts afresh, with a warning. A resumed session's history comes from `getSessionMessages` (history.ts).
- Entry ids are stable between live and history: text and thinking are `<API message id>:<block index>`, tool calls their `tool_use` id, user messages their uuid.
- Prompts (B13 C4: `src/main/sessions/claude-code/sdk/prompts.ts`, `raise.ts`) are canUseTool calls and MCP servers' requests (onElicitation), each raised to the core's prompt owner under a key minted for that native request (see [Sessions](sessions.md)); only the owner's accepted answer, by that key, resolves the native callback, at once, and nothing else answers it but the CLI ending it (aborted: the prompt ends, withdrawn) or the session closing (each still waiting gets the nonapproval below, and ends). The core's decline (a prompt past its bounds or budgets, a link it won't open) and a close answer with the nonapproval: a denial that never stops the turn, an elicitation's decline (a close's: cancel). What each raises, as the real CLI asked it (`fixtures/`: Claude Code 2.1.311): a permission is an approval whose subject is the tool and its exact input (an MCP server's tool names its server: `mcpServer.name`), titled as the CLI titles it (its `title`, or the path it would reach, or the tool), with its `decisionReason` as the reason and the proposed diff or command in twelve lines, marked cut where cut (a command whole, else declined; another tool's input past 64 KiB as a marked preview); its choices are Claude Code's: Yes (allow once, effects none), always (the request's own suggestions, all of them, verbatim, offered only where it suggests any and doesn't say always would allow too much, `suppressAlwaysAllowRule`; its label words every one, a deny or ask rule and a change of rules, folders or mode included, or it is left out and the core's reason says a choice was left out; its effects map rules by where they are kept: session and cliArg the session's, local and project settings the project's, the user's the user's; folders; and a mode kept for the session, and are unknown where a suggestion can't be said so: rules replaced or removed, folders removed, a mode kept beyond the session), No (stops the turn, as the CLI's No does) and No with what to do instead (Claude Code's own message and those words; the turn goes on). Another party's words would be framed as theirs, never the user's; a question's or form's answer from anyone but the user is refused, since the CLI takes it as the user's. AskUserQuestion (the built-in: an MCP server's tool of that name is an approval) is a question prompt, each question an id of corrallm's (`q1`…), a pick or its own words, answered keyed by its text with picks joined by ", " as the CLI's own UI does; questions it can't key so (two the same) are declined, the user told. ExitPlanMode (the built-in) is a plan: Yes into auto (where the session lists it), Accept edits or Manual, each allowed with that mode kept for the session, which the CLI goes into at once (recorded: plan-into-mode), or keep planning, with words or none; a plan with no text is declined. An MCP server's form is a form in the flat schema the shared reader (`src/shared/model/prompt-forms.ts`) re-serialized, naming its server, its message for you alone (the card); one corrallm can't show is declined, the user told by a notice naming the server, never quoting it; a link is a form holding it only in `form.url`, titled in the core's words naming its host (`mcpRequestTitle`: MCP server “tracker” asks you to open a link on tracker.example.com), the server's words nowhere, since they may hold the link, as it is or encoded. Signals (`signalsOf`): an ask rule (`matchedAskRule`, or the reason `rule` or `hook`), a safety check (`safetyCheck`, or `subcommandResults`, which can hide one only a person may approve), or a person's (`classifier`, `serverPolicyAskOnly`, `requiresUserInteraction` but on the built-in question and plan, `other`, or a reason it doesn't know); the connection declares `signals: true`, pinned by the recorded ask rule and safety check. Until X10 converts the renderer, each is shown as before too (a permission, questions, a plan, an MCP server's request, by the ids they had), and an answer to that is translated and answered through the owner (its `Bridge`, installed as the session starts, so one asked as it starts too: [Sessions](sessions.md)).
- Live progress and the background (translate.ts): `tool_progress` and `task_progress` become a tool's `progress`; `task_started` ties a task to the call that started it, and `background_tasks_changed` (a level: each one replaces the list; housekeeping tasks left out) becomes `tasks`. `stopTask` stops only a task in that list (query.stopTask; its notification ends its line). Hook events (`includeHookEvents`) show only what Claude Code shows: a hook that failed ("… hook error: …") or blocked ("… hook returned blocking error: …"; a Stop hook's "… hook feedback: …"), never what hooks print when they work. Predictions of the next message (`promptSuggestions`) arrive after a turn's result. The effort is set for the session only (`applyFlagSettings({ effortLevel })`, as /effort does without saving; null goes back to the model's default; only one of Claude Code's levels), and set as the session starts when it was given one its model takes (`started` says it). Each model's levels are offered with Claude Code's own words for them (`CLAUDE_EFFORTS`).
- History (history.ts): a turn lasts until its own last work (never the next message, nor what the CLI noted later); a slash command's output shows even when the transcript keeps it as meta (as /context's is). The SDK keeps no live result records: replay uses saved completion, refusal and interruption markers, and emits no `end` for an unknown outcome. An App Server turn still in progress likewise has no historical `end`.
- Logins ("Terminal for subscriptions"): Anthropic doesn't allow other products to offer claude.ai logins or subscription rate limits through the Agent SDK without its approval. So wherever corrallm offers a Claude connection, Terminal comes first (Claude Code's descriptor lists it first, and its contract test pins that; new agents default to an adapter's first connection, and spawned agents keep their source's connection), and the Agent SDK connection starts only with an API key (ANTHROPIC_API_KEY, an apiKeyHelper, ANTHROPIC_AUTH_TOKEN) or a cloud provider (Bedrock, Vertex, Foundry, a gateway). Before `query()`, `login.ts` asks the CLI how it is logged in: `claude auth status --json`, run by main with the agents' environment in the project folder (so a project's apiKeyHelper counts). That is the check, not the SDK's own `account`/`apiKeySource` reports, which come only once the CLI runs under the SDK. A claude.ai login (`authMethod: "claude.ai"`), a `claude setup-token` token (`"oauth_token"`), or a status it can't read refuses the start: a `notice` (one sentence, offering Terminal) and a rejection. Not being logged in at all starts, and the CLI says so. corrallm reads only what kind of login the CLI reports, and whether ANTHROPIC_AUTH_TOKEN is set, never a credential's value; it passes none. The Terminal connection runs the CLI itself, with any login.

## Terminal

- The Terminal connection (`sessions/claude-code/connector.ts`, on the toolkit in `sessions/terminal/`) runs Claude Code's own interactive CLI, so the user has all of Claude Code in the agent view (`TerminalPane.tsx` in place of the transcript and composer): its prompts, modes, models, slash commands and dialogs are answered there. It is started with `--settings` (a file in the temp folder: corrallm's HTTP hooks and command-type SessionStart hook, merged with the user's, and corrallm's status line: see Usage readings and rules), `--session-id` (new) or `--resume` (one with no transcript starts afresh under the same id), and `--model`/`--effort`/`--permission-mode` only when the agent is set to them (an explicit Manual too, as `manual`, one of the flag's choices; `default` as a model is left out; `--effort` only with one of Claude Code's levels, and only where its `claude --help` lists the flag, asked once per executable: `claudeFlags` in claude.ts, since an older CLI would not start with it): otherwise the user's own defaults apply. corrallm follows it to orchestrate it: Claude Code's Program Status reports (OSC 7501, answered and read in main's copy of the screen) say when it works, waits on the user, is done, was interrupted (idle) or failed; its hooks (`hooks.ts`) tell the session id (it changes with /clear), prompts typed in the terminal, the last reply, failures (StopFailure names its error, which the turn's end carries as its reason, mapped as the Agent SDK's are: `claude-errors.ts`; its `rate_limit` is `usage-limit`, and says nothing of when the limit lifts, which the core takes from the backend's latest reading: see Usage readings and rules), mode and model. A message corrallm sends is typed in (a few characters at a time, Ctrl+J for line breaks, then Enter: never a paste, which Claude Code collapses and treats as untrusted) once the prompt is ready: Claude Code idle or done, and nothing the user typed in it; Enter goes once the prompt shows what was typed (keys that pile up while Claude Code is busy, as right after the folder trust dialog or as a turn ends, are read in one go as a paste, where 2.1.296 keeps an Enter as an invisible character, not a submit). Meanwhile, a dialog (the folder trust prompt) or the user's draft makes the turn wait on the user. A turn ends once Claude Code has taken every message sent in it and stopped working; one the user started in the terminal is a turn too. Answers, modes and models are refused over the session channels: they belong to the terminal.
- Folder trust: Claude Code asks whether to trust a folder the first time it runs there ("Quick safety check…", default "No, exit"), before it reports anything or runs a hook, so the session reads it from the screen (TerminalCli's `trusting`): while it shows, it waits as an approval whose subject is `trust` (B13 C6: yours alone, answered in the terminal; `asking` lists a `trust` ask too), turn or not, and a message waiting for the prompt waits on the user at once. The CLI is past its first-run dialogs once it reports a state (but that it is going: "No, exit" isn't past them), a hook posts, or its prompt shows: the trust prompt then ends answered in the terminal; one whose CLI exits ends withdrawn. Every Claude Code started before the user answers would ask again, so Claude's Terminal connector has its sessions in a folder (by real path) take turns (`first-run.ts`): one starts first; the others wait (held: `started` is sent, their screen says why, a message for them is `working`) until it is past them (then all start, and so does every later one) or it ends without (the next one goes, and asks). Codex is told the folder is trusted on its command line, and never asks (checked with 0.160.1 in a fresh folder).
- What Claude Code asks in its terminal is raised to the core's prompt owner (B13 C6: [Sessions](sessions.md)'s Terminal observations), answered there, never by corrallm, and listed as `asking` too until X11, from its TerminalCli's hook signals (`claude-code.ts`): its PermissionRequest hook tells a permission prompt's tool and input, an approval worded as the Agent SDK's card words the same request (Claude wants to use the tool, its summary from `sdk/tools.ts`, what the prompt shows, `proposedDetail`, in twelve lines, and the tool and its input as its subject, an input past its bound, a command's too, as a marked preview: nothing it asks is declined), PreToolUse (only for AskUserQuestion and ExitPlanMode) its questions (each an id of corrallm's, `q1`…, its own words always allowed) and plan (PermissionRequest tells them too, without a call id: told once); one it can't read describes nothing, so its report's words do. Notification tells what it needs when nothing else says (an MCP server's question): a title-only approval in its words. Recorded from 2.1.296: the hooks come just before its Program Status says `blocked` (with `kind` permission, question or auth, and `msg`, as "approve Bash: git init" or "answer: Pick a color (Red · Blue)"). The session raises what the hooks told within a few seconds before a wait began (`ASK_WINDOW`), or else a title-only approval or question in the wait's `msg` (or the notification's words, or the CLI's own for the wait's kind), while it waits, which you may say isn't waiting (B13 C7); once it goes on working (the user answered in the terminal) that ends answered there, and once the turn ends or the CLI exits, withdrawn. Without status reports, what the hooks told waits until the turn ends, withdrawn then. Every hook is answered with no decision. Codex tells nothing ahead: while its title says Action Required, its wait is raised in its own words, with its screen's last rows ([Codex](codex.md)).
- Hooks turned off: corrallm hears Claude Code's replies, prompts, session ids and asks only through its hooks. When a session starts, `hooks-off.ts` reads the settings Claude Code reads (never writing them): the organization's managed settings (`managed-settings.json` and `managed-settings.d/*.json` in the OS's folder: `/Library/Application Support/ClaudeCode`, `/etc/claude-code`, `C:\Program Files\ClaudeCode`), then the project's `.claude/settings.local.json` and `.claude/settings.json`, then the user's (`CLAUDE_CONFIG_DIR` or `~/.claude`). They turn corrallm's hooks off with `disableAllHooks` (the most particular that sets it wins; the status line goes too, so no usage readings), `allowManagedHooksOnly` or `strictPluginOnlyCustomization` locking hooks (managed only), or `allowedHttpHookUrls` without a pattern matching its server on 127.0.0.1 (lists merged across files). corrallm omits its hooks when any such restriction is detected, and the session says so once, as it starts (`unheard`: which setting, where, and that the run can't read its replies). `httpHookAllowedEnvVars` controls only [header-variable interpolation](https://code.claude.com/docs/en/hooks#http-hook-fields); corrallm's literal HTTP headers and file-backed commands use none, so this setting does not disable them or cause an `unheard` warning. Not read: managed settings from a server or an OS policy.

This lets the Pause e2e assert Pausing and independent progress before releasing the native turn, instead of racing the UI against the fake's forty sequential 100 ms timers for a "slow" prompt. ## Native IDs and safety

- Native session ids follow [R42a](sessions.md#connected-sessions): `sessions/id.ts` supplies the platform minimum, then this adapter's `isConversationId` requires UUIDs. Checks cover hook signals, resume IPC arguments, remembered sessions loaded from disk and its Terminal argv builder. Claude resume uses `--resume=<id>`; an id must never be read as a CLI flag. The Terminal's invalid-conversation-id warning is emitted once per reported invalid id in that session (`ClaudeCode`'s `#invalidIds`, as Codex Terminal's); later hooks with that id still report prompts, modes and turn state.

The SDK's conversation list skips entries whose sessionId fails the platform minimum or UUID
shape, keeping the valid entries sorted by lastModified. One count-only warning per listing says
how many were skipped. Explicit rewind reads, forks and fork results retain their strict id checks.

corrallm only reads Claude Code's settings files (the user's, the project's and the organization's managed ones) to tell whether they turn its hooks off (`hooks-off.ts`), and never overrides them (its `--settings` never set `disableAllHooks` or the hook allowlists).

The [SessionStart hook](https://code.claude.com/docs/en/hooks#sessionstart) fires at startup but has no `permission_mode` in Claude Code 2.1.310, even when `--permission-mode acceptEdits` was given. Its quiet command hook (HTTP hooks cannot handle SessionStart) posts JSON stdin with the session token from its private 0600 header file; no event text enters a command line, no response is printed or used as a decision, and curl gives up after five seconds. Claude Code runs command hooks in Bash (Git Bash on Windows); the post uses `/bin/sh` and the same shared command-post helper as Codex’s POSIX hooks. All other events keep their HTTP hooks. The startup command is omitted whenever the existing hooks-off reader finds restrictions, including the HTTP URL allowlist, so the command transport does not bypass them. Native folder trust still precedes hooks. Delivery uses the explicit start mode or the trusted pre-launch default carried in `started.asks` until later native hooks report permissions (see [Sessions](sessions.md)). The fake's SessionStart likewise omits permissions; prompt and turn hooks can report them.

Hook commands inherit only `CORRALLM_HOOK_HEADER`, the path of a 0600 header file in the session's own folder, and use curl's `-H @<file>` in Bash (Git Bash on Windows). Native HTTP hooks read a literal header from the session's 0600 settings file. The hook token is absent from the CLI and every hook child's environment and command line; closing the session removes both private files.

## Prepared workspace context

Both connections accept the separate, C-owned `SessionSpec.workspaceContext` consumer described in [Sessions](sessions.md#prepared-workspace-context-adapter-seam). Terminal appends the combined role/context through --append-system-prompt; the SDK keeps its claude_code preset and appends it there. No user turn, hook answer or permission override carries context. Role-only startup and snapshot behavior remain unchanged. No production producer is composed: C must authorize the projection and define context-generation/native-snapshot invalidation before enabling it.

## Context readings

Both connections report `SessionUsage.context` in whole tokens and declare `context: true`, proven by sanitized recordings of Claude Code 2.1.316 compacting by itself (B11a C4). These readings do not arm or request handoffs.

What was recorded, with Haiku 5.5 in a scratch folder (only the Read tool; user, MCP and plugin settings left out) and `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` set for the recording alone, so that the CLI compacts at 67,000 tokens (the minimum window less 20,000 and 13,000) rather than near 967,000:

- Agent SDK (`sdk/fixtures/auto-compact.jsonl`, `no-auto-compact.jsonl`; replayed in `sdk/translate.test.ts`). The model's window (`modelUsage[model].contextWindow`) was 1,000,000 and its `maxOutputTokens` 128,000, whatever the compaction window; the last top-level response's `input + cache_creation_input + cache_read_input + output` tokens matched `getContextUsage().totalTokens` to within four tokens (25,309 against 25,306; 72,310 against 72,306). `getContextUsage({ detail: 'summary' })` gave `autoCompactThreshold: 67000` (the lowered window's rule: `window − min(max output, 20,000) − 13,000`, which `compactAt()` computes) with `isAutoCompactEnabled: true`. After a turn left 72,310 tokens in context (over the threshold; the turn before it, 48,846, was not compacted) the CLI compacted as the next began: `compact_boundary` with `trigger: "auto"`, `pre_tokens: 72344`, `post_tokens: 1446`; the next response held 3,506. With auto-compact turned off (`DISABLE_AUTO_COMPACT=1`) the summary has no `autoCompactThreshold` and says `isAutoCompactEnabled: false`: the translator then reports `compactAt: null`, since the CLI will not compact, rather than the default rule's point (B11a C4 found X3 reporting 967,000 there).
- Terminal (`fixtures/status-line-compaction.jsonl`, `status-recorded.ts`; replayed in `statusline.test.ts`). Its status line input before the first response has `context_window.current_usage` and `used_percentage` null and no `rate_limits`; afterwards `current_usage` holds the last response's four counts, `used_percentage` the input side alone (input, cache creation and cache read, not output) as a whole percent of `context_window_size` (the model's 1,000,000, rounded to the nearest percent, so 10,000 tokens a step: 54,263 reads 5), and `rate_limits` had only `seven_day`. Its PreCompact (`trigger: "auto"`), SessionStart (`source: "compact"`) and PostCompact hooks fired once; it compacted when the response that asked to read the next file, at 52,381 tokens, was about to be followed by that file's 20,000-odd (so a reading just under the point is followed by a compaction), and the status line then showed zero counts and 0% until the next response. It shows no sign of a lowered compaction window (`context_window_size` stayed 1,000,000): corrallm reads the default rule's 967,000 and cannot see a user's lowered setting or `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, which is one of the limits the ask point's reserve cannot remove. The recording did not catch a status line with both `five_hour` and `seven_day` windows, so that shape is pinned by the earlier tests alone.

The Agent SDK translator uses only the last top-level assistant response's input, cache creation, cache read and output tokens, never cumulative `modelUsage` counts or a subagent's response. Its window and output allowance come from that model's result entry; The last top-level response identifies the model after a native model change; only with no model identity at all is a single-model result unambiguous. Before publishing the result and ending the turn, the session asks `getContextUsage({ detail: 'summary' })` for `autoCompactThreshold`, with a two-second bound. An absent, refused or timed-out summary uses the CLI's default: window minus the smaller of `maxOutputTokens` and 20,000, minus 13,000 (floored at zero). A missing output allowance reserves 20,000. A reported threshold is capped at the window. Malformed counts or an unknown window leave context unknown.

The Terminal status-line wrapper posts inputs containing `context_window` as well as `rate_limits`. `statusLineContext` reads `context_window_size` and the current request's input, cache creation, cache read and output counts; without current request counts it converts `used_percentage` to tokens, rounded to the nearest token. It never takes cumulative session token totals as current context. This connection has no reported output allowance, so its default compaction point reserves 20,000 output tokens plus 13,000. The Terminal toolkit publishes changed context, including clearing a previous reading, without treating timer refreshes as work. Windows still installs no wrapper. A lowered native compaction setting or idle compaction can precede this estimate.

The SDK fake's `FAKE_CLAUDE_COMPACT_AT` supplies an optional native `autoCompactThreshold`; connector tests exercise both that control response and the default rule. Status-line tests drive the wrapper and the fake Terminal session with context-only and combined inputs. No test runs a real agent CLI.

Terminal declares `fileMentions: true`: token messages containing an `@` mention are refused, and automated canvas and other-party text containing one stays unsent at dispatch, session start and actual send, including after a connection switch; only your typed text passes. The shared selector recognizes `@` at the start or after a character other than an ASCII letter or digit with a non-whitespace character after it, without resolving any path. The SDK keeps that descriptor field absent and instead composes party messages as described above.

## Agent MCP entry (B21 recordings)

B21 gives each agent session its own `corrallm` MCP entry. Both connections still declare no `api`: the entry is turned on only with the evidence below, and the minimum version is the recorded one (Claude Code 2.1.316; Agent SDK 0.3.306). What the CLI does with the entry is recorded in `sessions/claude-code/fixtures/mcp-entry.json` (Terminal) and `sessions/claude-code/sdk/fixtures/mcp-entry.json` (SDK), and replayed by `mcp-entry.test.ts` beside each; nothing in the tests starts a CLI. They were made with a probe (a tiny local MCP server that logs each request's method and credential) in a throwaway `CLAUDE_CONFIG_DIR`, `HOME` and project, with a local stub Messages API in place of the model (`ANTHROPIC_BASE_URL`): the startup recordings need no turn and the turn recordings spent no tokens. Paths, the machine and the user's own servers are replaced by stand-ins; the credentials are canary strings.

Terminal, with `--mcp-config=<file>` and `--settings=<file>`:

- The entry connects at startup with no turn (`initialize`, `tools/list`) and sends the file's `Authorization` header. `--mcp-config` wins over a same-named `corrallm` at local, project (approved) and user scope, whole: nothing of those entries (url, headers, canary) is sent, and none of them connects. Without the flag the local entry connects, also whole (fields are not merged across scopes).
- `deniedMcpServers` in the session's `--settings` file stops the user's own `corrallm-server` from connecting, and its `headersHelper` command is never run (without the denial it runs, and in an agent session it prints nothing: `corrallm token header` refuses under `CORRALLM_AGENT_SESSION`). The user's settings can do the same to us: a user-scope `deniedMcpServers` naming `corrallm`, or an `allowedMcpServers` list naming other servers only, blocks the flag's entry ("MCP server blocked by enterprise policy"), and nothing connects. `allowedMcpServers` merges across files, so naming `corrallm` in the session's own `--settings` lets it through a user's allowlist. A user's `permissions.deny` for a tool wins over the session's allow rule (the tool is listed, never called). The core's observation (it hears the generation list its tools) is what tells these apart.
- `--resume=<id>` with a new generation's file connects with the new file's credential.
- The session's `permissions.allow` entry `mcp__corrallm__<tool>` runs that tool with no prompt. A tool not allowed is denied where nothing can answer (`claude -p`), and in the interactive Terminal shows "Tool use … Do you want to proceed?" with a `PermissionRequest` hook whose payload names the tool and `mcp_server: { name: "corrallm", source: "dynamic" }`; an allowed tool raises neither. The dialog's second choice ("don't ask again") offers a rule for the project's local settings (`permission_suggestions`), so a Terminal answer can write the project's `.claude/settings.local.json`.
- Not recorded: managed settings. They sit in the OS folder (`/Library/Application Support/ClaudeCode`), which a recording must not write; `CLAUDE_CODE_MANAGED_SETTINGS_PATH` (a folder, or a settings file) had no effect on 2.1.316. The documented behaviour (a `managed-mcp.json` or `disableSideloadFlags` refusing `--mcp-config`; a managed denylist winning) stays unrecorded.

Agent SDK, with `mcpServers: { corrallm: { type: 'sdk', name: 'corrallm', instance } }`:

- `mcpServerStatus()` reports `corrallm` connected, `transport: 'sdk'`, `source: 'sdk'`, with its tools, before the first turn; nothing is contacted over the network and no credential exists.
- It does not prove the entry when the user also configures a `corrallm` (local scope): the status and the init event then report that configured entry, `source: 'local'`, though the tool call is still served by the host's instance. The SDK entry therefore cannot be proved by the status alone in that case; the channel's own listing (the core hears `list()`) is the observation. A user's `deniedMcpServers` for `corrallm` does not block the host-registered server.
- The SDK's `settings: { deniedMcpServers }` option stops the user's `corrallm-server` (its helper is never run), as `--settings` does.
- `allowedTools` with the exact name runs the tool with no `canUseTool`; a tool not named raises it; the server's `tools: [{ name, permission_policy: 'always_ask' }]` raises it even for an allowed tool, which is the way to keep a destructive tool asking if it were ever named.

Mentions (Q24 and its edges, recorded, the evidence for `fileMentions`): an `@` mention in a prompt is expanded by the CLI before the model sees it, with no permission prompt, whether the file is in the project or not: by absolute path, `../`, `~/` (against `HOME`) and through a symlink in the project that points elsewhere, in `claude -p` and typed into the interactive Terminal; `@"path with spaces"` and `@path#L2-3` (a line range) work. A mid-word `a@/x` and `@$HOME/x` are not expanded. `client_composed: true` on the user message and `CLAUDE_CODE_DISABLE_FILE_MENTIONS=1` each leave a mention unexpanded. The fixtures' `mentions` sections hold this and `mcp-edges.test.ts` and `mcp-entry.test.ts` replay it. So Terminal declares `fileMentions` (above), the rule reads every mention without resolving a path, and the SDK sends another party's text `client_composed`.
