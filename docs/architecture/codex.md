# Codex connections

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/sessions/codex/`

Codex (see Codex below): codex.ts finds the user's `codex` and its version, rpc.ts runs `codex app-server` and speaks its JSON-RPC, login.ts says which login Codex has and what it allows, limits.ts reads its usage limits (account/rateLimits) as usage windows, for both connections, options.ts what a Codex agent can be set to run with (see Agent settings), fake-codex.mjs fakes the CLI; terminal/ and app-server/ hold its two connections (their connectors, fixtures recorded from the real CLI). terminal/: connector.ts starts Codex's TUI on the shared Terminal session with its TerminalCli (tui.ts: its command line, its window title's states, its hooks, pasting in), composer.ts reads its composer's draft, hooks.ts makes its session hooks (commands posting to hooks.ts's server) and their trust, trust.ts checks that trust with Codex itself and usage.ts reads its usage limits, each from a private app server (rpc.ts askAppServer), recorded.ts reads the fixtures.

## `src/main/sessions/codex/app-server/`

The App Server connection (see Codex below): connector.ts starts the app server (the project folder trusted for it alone) and its thread (or resumes it, with its history), session.ts runs the thread's turns (modes, model, effort, interrupts, plans, slash commands), translate.ts turns its items and notifications into session events, raise.ts maps what it asks (approvals, questions, elicitations, and the session's own asks) to the core's prompts and their answers to what Codex is told, prompts.ts raises them to the core's prompt owner and answers each request with the owner's answer, commands.ts and diff.ts are its slash commands (and /diff's git), protocol.ts what corrallm sends. recorded.ts reads fixtures/; replay.ts replays one as an app server, for tests.

## Codex

- The registry's `locate()` supplies the user's `codex`; `codex.ts` discovers it only when the override is unset (the standalone installer's ~/.local/bin, then the login shell's PATH; on Windows npm's native `codex.exe`, never its `.cmd`) and checks its version against `MIN_CODEX_VERSION` (0.160.0: what the fixtures and protocol were read from). Codex keeps its own home (~/.codex: config.toml, AGENTS.md, skills, MCP servers, sessions), so corrallm's threads are the user's (`codex resume` sees them, and corrallm can resume theirs).
- `rpc.ts` runs a private `codex app-server` per session over stdio (never the shared daemon a desktop app runs, never `--listen`: its sockets are unauthenticated), says hello (`initialize` with the experimental API, then `initialized`), always sends params (Codex refuses a request without them), answers every request the server makes (an unanswered approval stalls the turn; unhandled methods get -32601), drains stderr, and closes by ending its input, then SIGTERM, never SIGKILL (that orphans what it runs). The renderer never gets raw JSON-RPC or a generic channel: each action gets a typed `session:*` channel.
- Logins: corrallm never reads, stores or passes credentials; Codex uses its own (`codex login`), and corrallm asks its app server only which kind it is (`account/read`, `login.ts`). The App Server connection runs on any login, a ChatGPT plan included, because OpenAI allows it for local apps (learn.chatgpt.com/docs/app-server, Auth endpoints: "If you’ve built a local or open-source application using Codex app-server authentication, you can continue using it… App-server authentication has never been permitted for commercial or hosted services."). So on a ChatGPT login a session's first turn that would use the plan (a message, /review, /compact, /init) first asks, quoting that: a prompt raised to the core's owner, an approval whose subject is a `consent` (`chatgpt-plan`, so yours alone: `consentPrompt` in raise.ts, its words `planConsent` in login.ts). Yes allows it for the session, "don't ask again" for good (the `codex` consent `plan` in `settings.ts`, through `Consent` in sessions/adapter.ts), No (or the core declining to ask) sends nothing; interrupting withdraws it. A build made as a commercial or hosted product (`CORRALLM_DISTRIBUTION=commercial` or `hosted` when building: vite.main.config.mts defines `CORRALLM_DISTRIBUTION`, 'local' by default) refuses a ChatGPT login instead (`appServerRefusal`), leaving the plan to Codex · Terminal, which is Codex's own CLI. Sign in with ChatGPT (developers.openai.com/siwc), which OpenAI recommends instead, is not built: it would have corrallm keep and refresh the user's OAuth tokens.
- The App Server connection (`codex/app-server/`) runs a Codex thread in corrallm's transcript. Rules it keeps:
  - One private app server per session, closed with it, told on its command line that the project folder is trusted, for that server alone, as Codex · Terminal is (`-c projects=…`: `folderTrust` in `codex/terminal/hooks.ts`, by the path its thread works in and, where it differs, the folder's real path; the user's config.toml is never written). Its thread starts (`thread/start`) in the project folder with the approval policy and sandbox of the mode it was given; with none, it passes no permission overrides and reports Codex's actual policy. Modes are Codex's /permissions presets (Read only: read-only sandbox, on-request; Default: workspace-write, on-request; Full access: no sandbox, never) and Plan (Codex's plan collaboration mode, with Default's permissions). Every `turn/start` carries the model and effort; only a chosen mode adds approval policy, sandbox policy (the one Codex reported for the thread when of the same kind: it carries the user's own config.toml settings) and collaboration mode, which Codex keeps, so a mode switched mid-turn applies from the next turn. `clientUserMessageId` is the renderer's message id, so a resumed thread's history (`thread/resume`'s `initialTurnsPage`, its last 30 turns) matches what was shown live. A thread is remembered once it has a turn (Codex keeps none without), and one that cannot be found starts afresh quietly.
  - A turn ends with `turn/completed`. A plan proposed in plan mode is asked about once its turn ends ("Implement this plan?", as Codex's TUI asks), a `plan` prompt raised to the core's owner with Codex's two choices only: "Yes, implement this plan" (its effect the mode `auto`, Codex's Default) switches to Default and sends "Implement the plan." in the same corrallm turn, so the queues' Run hears its end once the plan is carried out; "No, stay in Plan mode" with words keeps planning (another party's framed as theirs), without them (or declined by the core) ends it. No other mode is offered.
  - What Codex asks (B13 C5) is raised to the core's prompt owner (`prompt`, under a key minted for each request, its typed JSON-RPC id kept privately: `1` is not `"1"`), and nothing answers Codex but the owner's accepted answer by that key: a definitive refusal (a decision it doesn't offer) leaves it waiting. Codex stopping waiting (`serverRequest/resolved`) ends it, withdrawn; the core's decline, and a close, answer with Codex's nonapproval (a command or change `cancel`, no permissions for the turn, no answers, an elicitation `cancel`): every request is answered. Each maps as Codex's TUI words and answers it (raise.ts, pinned by the 0.162.1 recordings):
    - A command's approval offers each decision Codex lists (`availableDecisions`), in its order: `accept` (once, nothing more), `acceptForSession` (this command, or this host, for the session), `acceptWithExecpolicyAmendment` (commands that start alike, a rule of the user's), `applyNetworkPolicyAmendment` (a host allowed, or blocked, for good), `decline` (No, going on) and `cancel` (No, stopping the turn), each with its hint and effects; with none listed, Yes and No (stop) only, never a made-up "always". One it can't word (a prefix that isn't one line, a decision it doesn't know) is left out, and the core says so. Its subject is the command and its folder, a host's approval the host; input written to a running command (`kind: writeStdin`) is its own approval, under its own `approvalId` on the command's item; extra permissions it asks for are worded whole in its summary, or it is declined.
    - A file change offers Yes, its files (or the folder it asks to write in, `grantRoot`) for the session, and No; its subject names each file with its diff while they fit. More permissions (`item/permissions/requestApproval`): this turn, this turn with strict auto review (`strictAutoReview`), this session, or No; its subject the network and folders asked for, declined where it asks for a pattern, a special place or a denial it can't name.
    - Questions (`request_user_input`) keep Codex's ids, its own-words answer (`isOther`) and secrecy (`isSecret`), all of them (no longer cut to four); an answer is the label picked or the words given, one string, by id. Questions under one id, or two answers the same, are declined; so is a secret one while prompts are shown as the events B13 replaces (below), which show every answer (Codex 0.162.1 marks none secret).
    - Codex asks before an MCP tool call through an elicitation marked `codex_approval_kind: mcp_tool_call` (or, with its `tool_call_mcp_elicitation` off, as a question of its own whose id names the call: Codex marks every question its model asks `isOther`, never this one). Either is an approval of that tool and its input: Allow, for this session or for good (a rule of the user's) only where Codex offers to keep it (`persist`), or Cancel; answered with the `persist` Codex reads, or the label. The tool is the call of that server running with those arguments (the translator's); one it can't tell is declined.
    - An elicitation's form (`form`, `openai/form`, `openaiForm`) is a form in the flat schema the core re-serialized, however many fields; a link is a form with its `url` only there, titled by the core with its host: visible only to you. A user verification (`openai/userVerification`, which Codex sends only to its own TUI and desktop app), or a form corrallm can't show, is declined, naming the server, never quoting it.
  - Until the renderer reads the owner's prompts (B13 X10), each is shown as the events B13 replaces too, under a fresh view id; an old card's answer reaches Codex only through the owner (its `Bridge`, installed as the session starts: see [Sessions](sessions.md)), one asked as the thread starts too. An old card's "always" is Codex's first decision that keeps (the one whose words it shows); its No is `cancel` where offered, else `decline`; Codex's decisions carry no words.
  - Tools keep the names Codex's model knows (`exec_command`, its command unwrapped from the user's shell; `apply_patch`, an entry per file with its diff; `web_search`; `mcp__server__tool`; `spawn_agent`…: a subagent's thread nests under the call that spawned it). Reasoning summaries are thinking (Markdown), `update_plan` the turn's to-do list, compaction and reviews notices, and command output streams at most every 150 ms. Usage is the last request's context and the plan's 5-hour and weekly limits (`account/rateLimits/read`, then updates; read once, `limits.ts`, for the composer and for the usage readings); errors say what to do by `codexErrorInfo` (log in again, when a usage limit resets, /compact).
  - Slash commands are Codex's (commands.ts), run as its TUI runs them: /review, /compact and /init are turns of the thread; /model, /permissions (never to Full access: see [Native IDs and safety](#native-ids-and-safety)), /status, /mcp, /skills, /diff (git, run by the core with the repository kept from running anything), /new, /clear, /rename are answered by the session. Skills are slash commands too (`/name` is sent as `$name`, with the skill attached). Pasted images go as data: URLs (the app server refuses remote ones), and not to a model that reads none.
- Interrupting an App Server turn stops the commands it started, as the native CLIs do: the composer's Stop, a token's `session.interrupt`, Kill, taking back a delivered message, a plan prompt's interrupt, and a turn Codex itself reports interrupted all use the same cleanup. corrallm sends `turn/interrupt` while the native turn runs; the plan prompt's native turn has already ended. Its `end` releases another message only after the command cleanup settles. The session records live `commandExecution` items' `processId`s by turn (including a completed item whose process still runs, with no `exitCode`); a `unifiedExecInteraction` with an earlier turn's process does not adopt it, and history from a resume is never included. Once the turn ends, it sends experimental `thread/backgroundTerminals/terminate` for those ids, each `{ threadId, processId }`, never `thread/backgroundTerminals/clean` (which would stop earlier background work). These are Codex's process ids, not OS pids. A `{ terminated: false }` response means the process is already gone. Each request has a two-second bound; a refusal, invalid response or timeout warns in the session with the process id and that its command may still be running, then releases the next turn. A server without the method warns once per session and leaves ordinary interruption working. No minimum-version increase is needed: the installed 0.162.1's generated experimental schema and [0.160.0's protocol](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server-protocol/src/protocol/v2/thread.rs) both carry it; [upstream's introduction](https://github.com/openai/codex/commit/a1a8807e9d67fad4b95f2730a9669eca5a9d27d0) first shipped in stable 0.140.0. `command/exec/terminate` is for client-started exec sessions, not the agent's `exec_command` tool.
- Codex · Terminal (`codex/terminal/`) runs Codex's own interactive CLI on the shared Terminal session (see Terminal), so the user has all of Codex in the agent view: its approvals, questions, plans, slash commands, models, @-mentions and images are answered there, and answers, modes and models are refused over the session channels. corrallm checks its version (`MIN_CODEX_VERSION`), then starts `codex --no-daemon -C <folder>` (its own agent, never the shared daemon a desktop app runs; `codex resume <id> …` to resume, and "No saved session found" starts afresh) with overrides for that session alone (`-c`; the user's config.toml is never written): the folder trusted (the folder dialog is the trust gate), corrallm's hooks (`hooks.ts`: SessionStart, UserPromptSubmit, Stop and Interrupt, each a command that posts the event to `terminal/hooks.ts`'s server with the session's token, through `/bin/sh` (Windows: `cmd`) and curl reading a 0600 header file with `-H @<file>`, printing nothing and always succeeding) and their trust (`hooks.state`, by the key and hash Codex trusts each by: computed as Codex 0.160 does, and checked once per Codex executable and version with Codex itself, `hooks/list` on a private app server, `trust.ts`; without it Codex stops at "Hooks need review"), its window title set to `["activity","run-state"]`, no update prompt, no automatic recaps. Only Read only starts it from its command line (`-s read-only -a on-request`: the connection's one `startModes` entry); Default and Plan leave the user's own defaults (Plan is Shift+Tab in its terminal), and Full access, which never asks, is never a start mode (it is chosen in its terminal). A user's own policy of no sandbox with `on-request` approvals still asks about the commands Codex counts as dangerous, so it counts as asking and parties' messages reach it (the user's decision, G3: see [Messages](messages.md)). The model and reasoning effort the agent is set to (see Agent settings) start it with `-m` and `-c model_reasoning_effort`. Codex picks its thread id; its hooks tell it (a subagent's are left out). Their permission_mode also reports whether it asks: bypassPermissions (or dontAsk) is Full access, default/acceptEdits asks again, plan is Plan. A switch in its terminal reaches delivery only once the next hook fires; until then the last report remains in force. Its usage limits are read apart from its terminal, never by typing /status into it (see Usage readings and rules).
- corrallm follows Codex by its window title (`tui.ts`): a spinner and Working, Thinking or Waiting is working, "Action Required" waits on the user (B13 C6: raised to the core's prompt owner as a title-only approval in its own words, "Codex needs you: see its terminal.", answered there, with what its screen shows as its detail: the last twelve rows that show anything, `waitDetail`, read once the screen has settled after its title changed, since its dialog, drawn in place of its composer, follows the title; its title blinking is the same wait, and going on working ends it answered there; you may say it isn't waiting, B13 C7, until its title leaves Action Required and comes back), "Starting" is its MCP servers starting (a message sent meanwhile is held, and waited for), Ready ends the turn: done after its Stop hook (whose reply is the turn's), interrupted after its Interrupt hook, failed if it took a prompt (UserPromptSubmit) without either (Stop does not run for a turn that errs, as at a usage limit). Nothing it shows outside its screen says why, so before the turn ends its usage is read as after any turn (`readUsage`, a private app server: `terminal/usage.ts`): a window at 100% with a reset to come, where the snapshot's `credits` say Codex has none to go on with (neither `hasCredits` nor `unlimited`, as recorded on a plan without credits; `codexUsedUp` in `codex/limits.ts`), made it fail on its plan's limit (`usage-limit`, until the latest such reset); otherwise it failed for a reason corrallm can't tell (`error`). What its TUI prints at a limit is not recorded, so its screen is not read for it. Its composer (`composer.ts`) is where its cursor shows (Codex hides it during dialogs): a message is pasted in there (bracketed paste, without control characters, then Enter a little later) only while it is drawn and empty, and only once its title has said something (it says nothing while a startup screen is up). Its Enter is not held until the composer shows the message (no `waitsForEcho`): 0.160.1 sends on an Enter read in one go with the paste, as keys that piled up while it was busy are.

## Native IDs and safety

- Native session ids follow [R42a](sessions.md#connected-sessions): `sessions/id.ts` supplies the platform minimum, then this adapter's `isConversationId` requires UUIDs. Checks cover hook signals, resume IPC arguments, remembered sessions loaded from disk and its Terminal argv builder.

The thread/list reader skips a thread in the chosen folder whose id fails the platform minimum
or UUID shape, instead of failing the whole resume list. It emits one count-only warning per
listing and preserves the valid threads' order by updatedAt. Threads from other folders remain
excluded, and a failed request still fails the list and closes its private App Server.

And no message takes Codex's App Server out of its sandbox: `/permissions full-access` is refused, since Full access is the mode menu's, which asks first.

The App Server's `/diff` uses `safeGitDiffArgs` (`src/main/git.ts`) to disable external diff, textconv and filter drivers, and runs git with `SAFE_GIT_ENV` so a partial clone never fetches a blob it lacks (the fetch would run whatever its remote names); file suggestions also use `SAFE_GIT_ENV` (a sparse index can fetch a missing tree), and must never run a repository's fsmonitor.

Codex's hooks are given and trusted for its session alone, on its command line: corrallm never writes the user's config.toml, and never runs Codex with `--dangerously-bypass-hook-trust` (which would also run the user's and the project's untrusted hooks).

The SessionStart command hook can report `permission_mode`, through the same native-mode parser as later hooks ([native input schema](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/hooks/schema/generated/session-start.command.input.schema.json)). In the recorded Codex 0.160.1 sessions it fires only with the first turn, not while an idle session is waiting for its first prompt. Delivery therefore uses the trusted pre-launch default carried in `started.asks`, or the explicit start mode, until a native hook reports otherwise; a Terminal still missing that information has the bounded silent startup hold described in [Sessions](sessions.md). Its hook key uses `session_start` and its trust is checked and scoped to the session as the other hooks are. Replay emits only the recorded hooks in their recorded order; it never invents a startup permission report.

Command hooks inherit only `CORRALLM_HOOK_HEADER`, the path of their Authorization header file in the session's own folder. The token is absent from the CLI and hook children's environments and arguments. Closing the session removes the file. The command's hash still scopes trust to these session hooks; the e2e TUI fake checks the same hash and executes the same file-backed command.

Codex Terminal's invalid-conversation-id warning is emitted once per reported invalid id in that session. Later hooks with that id still report prompts, permissions and turn state; their warning, like other hook notices, waits behind any earlier turn's delayed end.

## Prepared workspace context

Both connections accept the separate, C-owned `SessionSpec.workspaceContext` consumer described in [Sessions](sessions.md#prepared-workspace-context-adapter-seam). They read effective native developer_instructions and append the role/context through the existing native instruction mechanism, never through turn/start or terminal input. Native folder trust, policies and user-message provenance are unchanged. No production producer is composed: C must supply an authorized projection and a context/conversation invalidation contract before enabling it. Appending new context alone does not solve the retained-instruction limitation on exact-ID resume.
