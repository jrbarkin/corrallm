# Core and host

## `src/main/`

Main's entry is index.ts; security.ts, app-protocol.ts, csp.ts and url-policy.ts hold the security baseline. ipc.ts checks the preload's core:connect handshake; main owns windows and native UI, and hosts the core process.

The packaged app's [update checker](updates.md) lives in updates.ts and host/updates.ts, never the core or CLI. Its native Restart action goes through the same quit path as a quit (below), its shutdown barrier prepared for `update`, before installation. A Linux release-page choice uses main's private `openLink` core request, served by `WindowPorts.openLink` through the existing `link.open` operation for a connected window; it shares links.ts's policy rather than opening a raw response URL.

Quitting (index.ts, with closing.ts's Closing; B11 Design §8, §16.5) is: each window finishes the drafts it composes (`flushDrafts`: over its own port, at most 5 s each, a crashed one skipped), then, until B11 X12's cutover, each window showing a canvas freezes and saves its run (RunShutdown's `run:stopping`/`run:ready`), then the core prepares its shutdown barrier (`prepareShutdown`, `quit` or `update`). Any of those failing is the failed-save dialog: Keep corrallm open lifts the barrier (`cancelShutdown`), so the endpoint and every turn go on; Quit anyway, or all of it done, commits it (`commitShutdown`), and only then does an update install. A window's close flushes its drafts, saves its run (until X12) and `flush`es, as before. Opening corrallm again while it runs shows its window, or makes one (`second-instance`, the single-instance lock's), and macOS's Dock does too; on Windows and Linux the last window closing quits only if the core has no work going on (`active`: a run running or a turn, on a canvas it runs), else it runs on with no window, saying so on stderr, until opened again and quit there. Tray, notifications and the run-aware quit question are B14's.

The Electron-free services here are composed only by core/core.ts: canvas.ts asks which canvas file to open or save as and which canvas a file is (core/canvas/documents.ts reads and saves it), project.ts keeps project folders, memory.ts remembers each canvas's file, folder and agents' conversations (by the workspace each CLI ran in) and run-journal.ts journals runs and where each party has read to (both in the core's database, core/store/), settings.ts keeps app consents and api.port, usage.ts keeps readings, exhaustion and spending rules in usage.json, and whole-file.ts writes and reads the files written whole (canvases, api.json and the JSON stores that stay files).

Their state reaches the GUI through operations, topics, and the remaining hand-written channels served by core/channels.ts.

Canvas memory retains failed ordinary updates for retry (native conversation IDs must not be lost). A change with an atomic SQL callback (`setFile` while saving, or `forget`) instead restores its previous pending memory and emits no notification if its write fails. Later memory changes wait for that atomic write to settle, so none can persist a rejected file association; earlier ordinary updates still retry. Notifications of a successful atomic change follow its durable commit.

`src/main/core/workspaces/resolver.ts` is the working-directory seam, composed once by createCore. `WorkingDirectoryResolver.workingDirectory(canvas, agent)` returns ready with a core-owned TrustedPath, workspace (or null), active binding generation and branch (or null), or held with a reason, sentence and optional NeedId. `onAvailability(canvas, listener)` hears when any agent's result may have changed. The legacy `ProjectDirectories` uses ProjectFolders.of: the picked folder, workspace null, generation 0 and branch null, or held no-project. It remains the non-repository/test implementation; createCore uses WorkspaceDirectories over discovery, provisioning and setup (see Workspaces). ProjectFolders notifies on choose, restore, change and forgetting its canvas; core close removes its memory subscription.

Session launch (including a restart or launch after Fresh), conversation listing, resume validation and conversation rewind use the agent resolver. Canvas-wide reads name no agent: its separate `projectRoot(canvas)` accessor supplies settings/options defaults, file pickers without agent context, reveal's base containment root, headless canvas admission and comparison of old and newly picked project roots. Options without a root still read the user's home defaults. The accessor preserves project-wide search and containment rather than choosing an arbitrary agent. Agent-context options and file searches resolve that agent's verified tree. The mutation gate includes window-owned native sessions and their current activity as well as core runtimes. A pending rebind card is available in either host. Conversation records use the active workspace namespace, pinned for a live session; non-repositories use PROJECT_WORKSPACE. The session manager checks generations itself (see [Sessions](sessions.md)): a session is installed, reused and given work only while the binding it launched in is the active one, a held directory (a pending rebind) keeps its session without new work, and its live claims on native conversations (`ConversationClaims`, composed here once) keep two agents' sessions off one conversation.

## `src/main/core/`

The core: corrallm's one server, owning profile stores, messages and sessions (the canvas is the core's; the app's run stays in the renderer until B11), in an Electron utility process in the app and under plain Node headless.

Electron-free: it never imports Electron or src/main/host/ (ESLint's app/boundaries-core); what differs between hosts is passed in. host.ts is HostServices, what it asks of the app that hosts it (dialogs, links, file reveal and run-save acknowledgements), and TrustedPath, the only paths a canvas is opened from or saved to and the only project folders; entry.ts, the core process's entry (core.cjs): main asks it `init` for the app (it takes core.lock first, and while `serve` holds the profile answers who does), then hands it each trusted window's port beside the link, which gui.ts serves over createCore(config, appHost(link)); main passes the profile, distribution, locale and unpackaged fake-session setting. Once composed, it always serves the profile's outside endpoint (`src/main/core/endpoint.ts`, B11 Design §16.6: MCP on 127.0.0.1 on the port the profile keeps, see [Headless](headless.md)), one that can't listen said as a status, never a dialog; then the token socket for `corrallm token` (token-socket.ts, answering as `owner: 'app'` with the endpoint's URL, or with none and why, `unserved`); then api.json, naming this process. Committing the shutdown barrier closes the socket and the endpoint (requests going on ended, api.json removed if still its own) before the core closes; as the process exits, both are removed; a socket it can't serve is said, and the app runs on without it.

A deletion that would leave a worktree holding work (B9a C7: workspaces/cleanup.ts) becomes a proposal too, yours included, carrying what each such tree held (`Proposal.cleanup`), which its choices (Delete, keep its work; Delete, and discard its worktree and branch; Cancel) and Allow's replay are bound to; one of yours is worded as your question ("Delete Builder? Its worktree holds work."), and its record tells you what you confirmed. canvas/proposals.ts keeps them (Proposals: the `proposal` table, read once per canvas; Core Server §6.9, B9 Design §5): each a `proposal/<uuid>` Needs item for you, Allow and Refuse both `humanOnly`, worded with what it would lose ("…asks to delete Reviewer: 3 queued tasks and its conversation"), with the op, its arguments and every entity its change touched with its revision, and the revisions of the whole canvas then (`proposal.touched` holds `{ touched, before }`, `before` only for a change of a document's).

Allow (`reply`) runs the op again as you through ctx.call, recording `revision.proposed_by`, expecting those touched revisions and checking every entity its replay now changes against the earlier canvas, including new queue items, OKs and links: its change, the settlement and the proposer's record in one write (`within`, `stageWithin`); one touched entity changed, or the op no longer applying, settles it `stale`, changing nothing; unrelated edits do not make it stale.

Refuse settles it.

A token sees a proposal's words only when it reaches every agent those words name (all removed agents and an agent proposer); otherwise `needs` omits the whole item and its NeedId resolves as not-found, so `reply` cannot quote the hidden title in a refusal. The user still sees it in full. `Lost.agents` keeps the full list, including agents beyond the five named in the title. Allow carries the original `proposedBy` into its build context: a template's implicit parent and filled text's authorship remain the proposer's, including inside a batch, and so does a `canvas.create`'s new canvas (see the cap below), while the revision itself is the user's and records who proposed it. This uses the party already kept with the proposal, without a caller-supplied authorship override.

One party may keep at most MAX_OPEN_PROPOSALS (32) open proposals per canvas. Identical pending calls with the same arguments (compared as the database keeps them, so an argument left undefined is none), touched revisions and canvas baseline reuse their proposal id, even without a request id and after token renewal or restart; changed baselines or settled proposals are never reused. The lookup and limit run inside the store's write lane, so concurrent raises cannot pass the cap. Settling one frees its slot.

A token's party may have at most MAX_CREATED_CANVASES (16) open canvases it created. `canvas.create` checks the durable creator and open-canvas records in its app scope, across tokens and restarts, refusing before it makes anything. Closing one frees a slot; replacing one of its own open canvases keeps the same count. A canvas you Allow a token's `canvas.create` to make is the proposer's too (`created_by`, kept even when empty), so its reach has it after Allow, and the proposer's cap is checked then: past it, the proposal settles stale. Other parties and the user's canvases have separate counts; the user is not capped. A token's drafts closed but kept for their edits (canvas memory never forgets those) are bounded by R11 instead: a token puts nothing on an empty canvas but through an agent it creates, which counts toward its party's live agents on every canvas the core keeps, closed ones included, until the user deletes it.

A proposal of a close, a replace or a save (R4's argument half) has no snapshot: its document's and file's fingerprints (`document:<c>`, `file:<c>`) guard it, and its replay drains as the op does (`Scopes.draining`: a replace of the canvas the reply is on drains it around the reply, never waiting for the reply).

The proposer's record is a `settled` message from corrallm, which its `wait` returns; proposals survive restarts, in `needs` and `needs:<c>` (in the app, the core's items before B11) and serve's log.

Each commit is told synchronously to `Documents.subscribe`'s listeners (its revision, party, entities changed and renumbered), which canvas/states.ts turns into the `canvas:<c>` topic's change (B9 Design §7): CanvasStates keeps each canvas read (`read`, which loads it) as entities (its rows stamped `{ rev, by }`, and `meta`: arrange, its file's `name`, `edited`, `project`), says each commit's diff at its revision, recomputes `edited` at most every 250 ms (`EDITED_EVERY`) and says a change to the meta alone (edited flipping, a folder chosen, a save) at the canvas's next revision taken in memory between commits (`Documents.between`, `bump`), never written; and lists the canvases the core keeps (`list`, `canvas.list`), invalidating its cached running state on every journal notification, even saves sharing a timestamp. A canvas the core runs (`Engines`, passive or executing) says its live run's `running` instead (B11 §5), never the journal's coalesced write, and the list is read again as that flips and as it closes (core.ts, from `Engines.watch`); a canvas a window runs, or one closed, is as the journal last kept it. canvas/view.ts is what of a canvas a caller sees: all of it, but for an agent (a lead) the agents it reaches, the frames around them, the links between them, a node inside one it doesn't see placed in the nearest it does. delivery/messages.ts is the message store (MessageStore, a canvas's, over MessageTable, every canvas's rows of `message`); delivery/delivery.ts delivers them, framed, and brings replies back; delivery/withdrawals.ts carries durable withdrawal notes into the next CLI message without opening a run for a renderer-owned canvas; delivery/reads.ts each party's `wait` read position, moved only once it is on disk (the journal's read_position). workspaces/store.ts is the workspace store (WorkspaceStore, schema 3's workspace records: see Store), which createCore composes for the document seam's planner (workspaces/planner.ts, Documents' participant, recording who works where within the same write as the document change it follows: see [Workspaces](workspaces.md)); what provisions and cleans up workspaces builds on it too. workspaces/gate.ts is the workspace mutation gate (WorkspaceGate, composed once), which a code rewind's restore runs under, protecting every agent of its tree, and a workspace change's Switch drains (`drain`: every agent of the trees it changes). workspaces/rebind.ts (WorkspaceChanges, composed once) is that change's card in Needs (one per destination, naming no agent) and its Switch, through the reply router. workspaces/cleanup.ts (WorkspaceCleanup) is what becomes of a tree no agent works in any more: assessed before every commit's point of no return (the planner's preflight), removed with its last agent once safe, else kept unless you confirm discarding it (the committer turns a deletion leaving one with work into a proposal for you, yours too), its removal recorded in the deciding write and done outside it, tried again as the core starts (`reconcile`, in the background) and finished or left before the process owner closes; the kept trees (`kept`), named by their owners' last names; and a kept tree's Remove (`worktree.remove`, prepared). createCore composes it by default; `CoreConfig.cleanup` is a test override. Beside it (see [Workspaces](workspaces.md)), also composed: workspaces/git.ts, the one Git runner of the workspaces; workspaces/discovery.ts, safe discovery of the repository a picked folder is, and its record; workspaces/owned.ts, the owned root a repository's checkouts go in, verified before any write; workspaces/provision.ts, a workspace's checkout made from its recorded intent, phase by phase in its repository's lane of the bounded queue (workspaces/queue.ts), reused, and reconciled on restart; workspaces/checkout.ts, a checkout verified and its path minted at each use; workspaces/profile.ts, the profile's id its branches and folders are named by; workspaces/copy.ts, a new workspace's local files copied in safely; workspaces/setup.ts, its setup offered as a card yours alone, answered and run, and workspaces/setup-run.ts, a setup command run as a process group the core owns (`CoreConfig.setups` is a test override for the composed setup service: its cards in what waits for you, `reply`, `project.setSetupCommand` and `project.clearSetupApproval` over it, its recovery before the core serves and its close before the process owner's). `Engines.watch`'s watchers hear each message added (what closing a canvas cuts off included), what newly waits for an answer, and each canvas opened and closed (once it has stopped). topics.ts is the common publisher and runtime-topics.ts the source of each running canvas's runtime topics (see [Operations and topics](registry.md)): it hears the canvas's run and session stores (`SessionStore.observe`, each action as it is reduced, for appends), its message store (`MessageStore.watch`: each message kept, changed or pruned) and `Documents.subscribe`, and keeps each topic's canonical state between publications, across a close and a reopen in one core. ## `src/main/host/`

Main only, as the core's host: services.ts answers HostServices with dialogs (dialogs.ts), external links and file reveal. The Save dialog requests native overwrite confirmation. If adding `.corral` changes the chosen name and that final path exists (including a dangling symlink), it asks Replace or Cancel for that name before returning it; Cancel is the default.

The core checks links (main/links.ts) and project-folder containment (main/reveal.ts) before asking the host to act. core/windows.ts keeps which canvas each window shows and ends its sessions on reload, crash, close or a canvas change, unless the core runs that canvas (`Engines.left`: until B11's cutover every canvas a window shows has its run in that window, and the core's one seam to such a run is `WindowRuns`). core-process.ts forks the core process (utilityProcess.fork, stdio piped back, a CoreLink over its parentPort on which main answers HostServices, and windows' ports posted beside it), which main does before the first window; ports.ts hands each window that asks (core:connect) a MessageChannelMain's end, the core the other (naming the core's epoch), tells the core when a window is gone (closed, crashed, reloaded), and reloads every window once a new core is up after a crash (until B9 and B11 move the canvas and run into the core, a page restores its canvas from the journal, paused); supervise.ts is what to do when the core exits (restart a crash at most 3 times in 60 s, then give up; a clean exit is none), and supervisor.ts carries it out (CoreSupervisor: forks and inits each core, the next epoch each restart, what asks the core waiting while a new one comes up; a new core that can't come up counts as another stop, one refused the profile gives up at once; giving up is "corrallm's core keeps stopping", in a native dialog, and the app exits).

## `src/main/files.ts`

The project folder's files for @-mentions (project.files): git's list, or a walk, which skips dependencies, builds, version control and `.corral`, where the workspaces' checkouts are kept (Git's list leaves them out by the local exclude).

ESLint enforces the process boundaries: renderer and shared code cannot import Electron, Node built-ins or main/preload code; the preload cannot import Node built-ins. In main, `app/boundaries-core` keeps `src/main/{core,sessions,api,cli}/` and the Electron-free services (memory, settings, usage, files, git, canvas, project, run-journal, loopback, links, reveal, whole-file) from importing Electron or `src/main/host/` (what needs the desktop is a `HostServices` request, `core/host.ts`), and `app/adapters` keeps platform files from importing adapter folders (`sessions/claude-code/`, `sessions/codex/`, and the future `sessions/acp/` and `sessions/muse/`). Only the registry, `sessions/adapters.ts`, imports them in production; `ADAPTER_IMPORTERS` in eslint.config.ts is empty. Each adapter may import its own files and the terminal toolkit, but never another adapter. Tests may import adapters directly; the adapter-to-adapter ban also covers their tests. `app/boundaries-shared` keeps every file in src/shared, tests included, from importing the renderer or React Flow: the model and the engine (`src/shared/model/`, `src/shared/engine/`) run in the renderer and in the core, given their sessions' backend and the catalog they read (`engine/catalog.ts`). `src/main/boundaries.test.ts` checks these on fixtures, that no shared file imports the renderer or React Flow, that only the host, index.ts, window.ts, security.ts, app-protocol.ts, ipc.ts, run-shutdown.ts and native-selftest.ts import Electron, that only `core/host.ts` (its definition), `core/host/app.ts` (main's dialogs' answers), memory.ts, run-journal.ts and `core/workspaces/checkout.ts` (a workspace's checkout, once verified) mint a `TrustedPath` (nothing in `src/main/cli/`), that only `core/gui.ts` makes a human caller (`asHuman`) and only the core process's entry loads it, and that the core process's entry composes the profile's stores and main composes none. `src/main/platform-neutral.test.ts` keeps the platform (src/shared, src/preload, src/main outside the adapters' folders, src/renderer with its templates; never tests) from naming a CLI: each file that does today is allowed exactly as many names as it has, so a new one fails, and a file that names fewer lowers its count.

The silent-turn watchdog (`src/main/core/stalled.ts`) is composed once in `createCore` for both hosts. It samples local interface addresses on its existing timer, so app and headless turns receive the same shortened grace after a network change without an Electron event or a network probe. Tests inject its clock and interface snapshots independently through `CoreConfig.watchdog` and `CoreConfig.watchdogNetwork`.
