# Core and host

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/`

Main's entry is index.ts; security.ts, app-protocol.ts, csp.ts and url-policy.ts hold the security baseline. ipc.ts checks the preload's core:connect handshake; main owns windows and native UI, and hosts the core process.

The packaged app's [update checker](updates.md) lives in updates.ts and host/updates.ts, never the core or CLI. Its native Restart action goes through the existing RunShutdown quit path before installation. A Linux release-page choice uses main's private `openLink` core request, served by `WindowPorts.openLink` through the existing `link.open` operation for a connected window; it shares links.ts's policy rather than opening a raw response URL.

The Electron-free services here are composed only by core/core.ts: canvas.ts asks which canvas file to open or save as and which canvas a file is (core/canvas/documents.ts reads and saves it), project.ts keeps project folders, memory.ts remembers each canvas's file, folder and agents' conversations (by the workspace each CLI ran in) and run-journal.ts journals runs and where each party has read to (both in the core's database, core/store/), settings.ts keeps app consents and api.port, usage.ts keeps readings, exhaustion and spending rules in usage.json, and whole-file.ts writes and reads the files written whole (canvases, api.json and the JSON stores that stay files).

Their state reaches the GUI through operations, topics, and the remaining hand-written channels served by core/channels.ts.

Canvas memory retains failed ordinary updates for retry (native conversation IDs must not be lost). A change with an atomic SQL callback (`setFile` while saving, or `forget`) instead restores its previous pending memory and emits no notification if its write fails. Later memory changes wait for that atomic write to settle, so none can persist a rejected file association; earlier ordinary updates still retry. Notifications of a successful atomic change follow its durable commit.

`src/main/core/workspaces/resolver.ts` is the working-directory seam, composed once by createCore. `WorkingDirectoryResolver.workingDirectory(canvas, agent)` returns ready with a core-owned TrustedPath, workspace (or null), active binding generation and branch (or null), or held with a reason, sentence and optional NeedId. `onAvailability(canvas, listener)` hears when any agent's result may have changed. The legacy `ProjectDirectories` uses ProjectFolders.of: the picked folder, workspace null, generation 0 and branch null, or held no-project. It provisions nothing and does not compose WorkspaceStore. ProjectFolders notifies on choose, restore, change and forgetting its canvas; core close removes its memory subscription.

Session launch (including a restart or launch after Fresh), conversation listing, resume validation and conversation rewind use the agent resolver. Canvas-wide reads name no agent: its separate `projectRoot(canvas)` accessor supplies settings/options defaults, both project file pickers, reveal's containment root, headless canvas admission and comparison of old and newly picked project roots. Options without a root still read the user's home defaults. The accessor preserves project-wide search and containment rather than choosing an arbitrary agent. Conversation records remain keyed by PROJECT_WORKSPACE; generations and workspace-specific session lifetime checks wait for provisioning's integration.

## `src/main/core/`

The core: corrallm's one server, owning profile stores, messages and sessions (the canvas is the core's; the app's run stays in the renderer until B11), in an Electron utility process in the app and under plain Node headless.

Electron-free: it never imports Electron or src/main/host/ (ESLint's app/boundaries-core); what differs between hosts is passed in. host.ts is HostServices, what it asks of the app that hosts it (dialogs, links, file reveal and run-save acknowledgements), and TrustedPath, the only paths a canvas is opened from or saved to and the only project folders; entry.ts, the core process's entry (core.cjs): main asks it `init` for the app (it takes core.lock first, and while `serve` holds the profile answers who does), then hands it each trusted window's port beside the link, which gui.ts serves over createCore(config, appHost(link)); main passes the profile, distribution, locale and unpackaged fake-session setting.

then the canvas's engine follows its document (`Engines.changed`).

Each canvas has one runtime at a time in `core/engines.ts` (B11 Design §2), allocated once however often and concurrently asked: `load` allocates it passively (its document, its run restored paused and its messages, open in `open_canvas`, with no project folder needed, starting no CLI and delivering nothing), `open` is serve's admission (a picked project root, and a file holding the canvas or the core's rows of it: one allocated passively and short of either stays passive) and executes it unless `held`, `deliver` executes every passive one, and `initialize` is a cold start's (every canvas `open_canvas` names, once per core, each executing; one that fails is said beside the others). Executing starts its delivery once, after what was being delivered as the core last stopped is settled unresolved on disk. A draft that holds nothing is loaded only while it is live in the core or open; a canvas allocated again while it closes waits for that close. The app composes none of this until B11's cutover (X12/X13): its runs stay the renderer's, so it never loads or initializes a canvas a window owns.

File reviews (`canvas/reviews.ts`, `file_review`) are yours alone, in `needs:<c>`: Apply re-reads the file, checks cancellation and marks its write irreversible (`ctx.noReturn`), then commits the file's document, hashes, writing_hash cleared and settlement together.

Discard clears an abandoned writing hash too.

Keep is bound to the file baseline and the durable file_generation when raised, so the next confirmed write expires it even if it writes identical bytes, across restarts too.

A file matching the live document is adopted with its canonical saved_hash as well as its bytes' file_hash; the canvas and list meta refresh so it becomes clean.

A token's change no rule refuses but R4 reserves to you (it deletes an agent) applies nothing: refusals win, and it becomes a proposal only for an op declaring R4 or R5 (`proposes`), else it is refused. canvas/proposals.ts keeps them (Proposals: the `proposal` table, read once per canvas; Core Server §6.9, B9 Design §5): each a `proposal/<uuid>` Needs item for you, Allow and Refuse both `humanOnly`, worded with what it would lose ("…asks to delete Reviewer: 3 queued tasks and its conversation"), with the op, its arguments and every entity its change touched with its revision, and the revisions of the whole canvas then (`proposal.touched` holds `{ touched, before }`, `before` only for a change of a document's).

Allow (`reply`) runs the op again as you through ctx.call, recording `revision.proposed_by`, expecting those touched revisions and checking every entity its replay now changes against the earlier canvas, including new queue items, OKs and links: its change, the settlement and the proposer's record in one write (`within`, `stageWithin`); one touched entity changed, or the op no longer applying, settles it `stale`, changing nothing; unrelated edits do not make it stale.

Refuse settles it.

A token sees a proposal's words only when it reaches every agent those words name (all removed agents and an agent proposer); otherwise `needs` omits the whole item and its NeedId resolves as not-found, so `reply` cannot quote the hidden title in a refusal. The user still sees it in full. `Lost.agents` keeps the full list, including agents beyond the five named in the title. Allow carries the original `proposedBy` into its build context: a template's implicit parent and filled text's authorship remain the proposer's, including inside a batch, while the revision itself is the user's and records who proposed it. This uses the party already kept with the proposal, without a caller-supplied authorship override.

One party may keep at most MAX_OPEN_PROPOSALS (32) open proposals per canvas. Identical pending calls with the same arguments, touched revisions and canvas baseline reuse their proposal id, even without a request id and after token renewal or restart; changed baselines or settled proposals are never reused. The lookup and limit run inside the store's write lane, so concurrent raises cannot pass the cap. Settling one frees its slot.

A token's party may have at most MAX_CREATED_CANVASES (16) open canvases it created. `canvas.create` checks the durable creator and open-canvas records in its app scope, across tokens and restarts, refusing before it makes anything. Closing one frees a slot; replacing one of its own open canvases keeps the same count. Other parties and the user's canvases have separate counts; the user is not capped.

A proposal of a close, a replace or a save (R4's argument half) has no snapshot: its document's and file's fingerprints (`document:<c>`, `file:<c>`) guard it, and its replay drains as the op does (`Scopes.draining`: a replace of the canvas the reply is on drains it around the reply, never waiting for the reply).

The proposer's record is a `settled` message from corrallm, which its `wait` returns; proposals survive restarts, in `needs` and `needs:<c>` (in the app, the core's items before B11) and serve's log.

Each commit is told synchronously to `Documents.subscribe`'s listeners (its revision, party, entities changed and renumbered), which canvas/states.ts turns into the `canvas:<c>` topic's change (B9 Design §7): CanvasStates keeps each canvas read (`read`, which loads it) as entities (its rows stamped `{ rev, by }`, and `meta`: arrange, its file's `name`, `edited`, `project`), says each commit's diff at its revision, recomputes `edited` at most every 250 ms (`EDITED_EVERY`) and says a change to the meta alone (edited flipping, a folder chosen, a save) at the canvas's next revision taken in memory between commits (`Documents.between`, `bump`), never written; and lists the canvases the core keeps (`list`, `canvas.list`), invalidating its cached running state on every journal notification, even saves sharing a timestamp. canvas/view.ts is what of a canvas a caller sees: all of it, but for an agent (a lead) the agents it reaches, the frames around them, the links between them, a node inside one it doesn't see placed in the nearest it does. delivery/messages.ts is the message store (MessageStore, a canvas's, over MessageTable, every canvas's rows of `message`); delivery/delivery.ts delivers them, framed, and brings replies back; delivery/withdrawals.ts carries durable withdrawal notes into the next CLI message without opening a run for a renderer-owned canvas; delivery/reads.ts each party's `wait` read position, moved only once it is on disk (the journal's read_position). workspaces/store.ts is the workspace store (WorkspaceStore, schema 3's workspace records: see Store), which nothing composes yet: what provisions, binds and cleans up workspaces builds on it, recording its intents within the same write as the document change they follow. `Engines.watch`'s watchers hear each message added (what closing a canvas cuts off included) and what newly waits for an answer. test-registry.ts is a registry for the core's tests, with an op for every check core.call makes, fixtures for every op, and what each party doesn't reach (from which T3b generates its reach calls); test-world.ts the core the registry's generated tests run on (a canvas of the test callers' agents, messages waiting, nothing ever running a turn); test-worker.corral the canvas the engines' test runs.

## `src/main/host/`

Main only, as the core's host: services.ts answers HostServices with dialogs (dialogs.ts), external links and file reveal. The Save dialog requests native overwrite confirmation. If adding `.corral` changes the chosen name and that final path exists (including a dangling symlink), it asks Replace or Cancel for that name before returning it; Cancel is the default.

The core checks links (main/links.ts) and project-folder containment (main/reveal.ts) before asking the host to act. core/windows.ts keeps which canvas each window shows and ends its sessions on reload, crash, close or a canvas change. core-process.ts forks the core process (utilityProcess.fork, stdio piped back, a CoreLink over its parentPort on which main answers HostServices, and windows' ports posted beside it), which main does before the first window; ports.ts hands each window that asks (core:connect) a MessageChannelMain's end, the core the other (naming the core's epoch), tells the core when a window is gone (closed, crashed, reloaded), and reloads every window once a new core is up after a crash (until B9 and B11 move the canvas and run into the core, a page restores its canvas from the journal, paused); supervise.ts is what to do when the core exits (restart a crash at most 3 times in 60 s, then give up; a clean exit is none), and supervisor.ts carries it out (CoreSupervisor: forks and inits each core, the next epoch each restart, what asks the core waiting while a new one comes up; a new core that can't come up counts as another stop, one refused the profile gives up at once; giving up is "corrallm's core keeps stopping", in a native dialog, and the app exits).

## `src/main/files.ts`

The project folder's files for @-mentions (project.files): git's list, or a walk.

ESLint enforces the process boundaries: renderer and shared code cannot import Electron, Node built-ins or main/preload code; the preload cannot import Node built-ins. In main, `app/boundaries-core` keeps `src/main/{core,sessions,api,cli}/` and the Electron-free services (memory, settings, usage, files, git, canvas, project, run-journal, loopback, links, reveal, whole-file) from importing Electron or `src/main/host/` (what needs the desktop is a `HostServices` request, `core/host.ts`), and `app/adapters` keeps platform files from importing adapter folders (`sessions/claude-code/`, `sessions/codex/`, and the future `sessions/acp/` and `sessions/muse/`). Only the registry, `sessions/adapters.ts`, imports them in production; `ADAPTER_IMPORTERS` in eslint.config.ts is empty. Each adapter may import its own files and the terminal toolkit, but never another adapter. Tests may import adapters directly; the adapter-to-adapter ban also covers their tests. `app/boundaries-shared` keeps every file in src/shared, tests included, from importing the renderer or React Flow: the model and the engine (`src/shared/model/`, `src/shared/engine/`) run in the renderer and in the core, given their sessions' backend and the catalog they read (`engine/catalog.ts`). `src/main/boundaries.test.ts` checks these on fixtures, that no shared file imports the renderer or React Flow, that only the host, index.ts, window.ts, security.ts, app-protocol.ts, ipc.ts, run-shutdown.ts and native-selftest.ts import Electron, that only `core/host.ts` (its definition), `core/host/app.ts` (main's dialogs' answers), memory.ts and run-journal.ts mint a `TrustedPath` (nothing in `src/main/cli/`), that only `core/gui.ts` makes a human caller (`asHuman`) and only the core process's entry loads it, and that the core process's entry composes the profile's stores and main composes none. `src/main/platform-neutral.test.ts` keeps the platform (src/shared, src/preload, src/main outside the adapters' folders, src/renderer with its templates; never tests) from naming a CLI: each file that does today is allowed exactly as many names as it has, so a new one fails, and a file that names fewer lowers its count.

The silent-turn watchdog (`src/main/core/stalled.ts`) is composed once in `createCore` for both hosts. It samples local interface addresses on its existing timer, so app and headless turns receive the same shortened grace after a network change without an Electron event or a network probe. Tests inject its clock and interface snapshots independently through `CoreConfig.watchdog` and `CoreConfig.watchdogNetwork`.
