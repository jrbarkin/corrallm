# Headless CLI

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/cli/`

The `corrallm` Node CLI, the core's code under plain Node, built into dist-cli/ (git-ignored) by `pnpm build:cli` (see Headless): index.ts, its entry, checks the Node it runs on (node.ts) before it imports the CLI itself (main.ts); args.ts reads its command lines (never a project folder, never a token), serve.ts is `corrallm serve`, wait.ts `corrallm wait`, token.ts `corrallm token`, register.ts the registration commands each adapter's descriptor gives, token-file.ts a token file's reader, api-file.ts the profile's api.json; with CORRALLM_NATIVE_SELFTEST=1 it runs the native self-test.

It mints no TrustedPath.

## Headless

`corrallm` is one Node CLI on the core's code (`src/main/cli/`; API Spec §8.6, Core Server §7.6). macOS and Linux apps ship it with their own pinned Node, at `Contents/Resources/bin/corrallm` inside the macOS app and `resources/bin/corrallm` on Linux. Debian and RPM packages link `/usr/bin/corrallm` to it. The launcher follows symlinks, locates its files relative to itself and forwards arguments and exit status; it needs no Node on PATH and handles no tokens. Installing the command from macOS settings is deferred to B22a. Windows command shipping is held. `corrallm --help` (or `-h`) prints usage and exits successfully.

For development, `pnpm build:cli` builds the same bundle and `pnpm corrallm` runs it from the checkout, using Node on PATH. See [toolchain](toolchain.md) for packaged resources and checksum verification.

- It runs only on the Node package.json's `engines` names (24.21.0 or later, `NEEDED_NODE` in `cli/node.ts`): on an older one (`pnpm corrallm` runs whatever `node` is on the PATH) it says so in one sentence naming both, on stderr (for `wait`, as its one JSON line too), and exits 64, as a command line that can never work does, before anything else of it loads. Its entry (`cli/index.ts`) imports the CLI (`cli/main.ts`) only once its Node will do, and the build inlines that import to run only then (`codeSplitting: false`); Node's own modules are required as the bundle loads, before the check, so the CLI's code imports one an older Node lacks (`node:sqlite`) only where it uses it, never at the top (`cli/node.test.ts` runs the bundle as Node 22.18 without it).
- `corrallm serve --canvas <file> [--canvas <file>…] [--profile <dir>] [--port <n>] [--new-token [--name <name>] [--hours <1-12>] [--read-only]]` runs the core under plain Node, on the app's profile (`appProfile`) or `--profile`, with the Node host (`core/host/node.ts`: no dialogs). It makes a profile it lacks 0700, takes the profile's `core.lock`, opens its database, opens each `--canvas` only if canvas memory names that very file (by real path) for the canvas it holds and keeps a project folder for it that is still there (`Core.keptCanvas`; otherwise it says, naming the file, to open the canvas and pick its folder in the app), restores each run paused (which holds only the run's own sends, so parties' messages still reach idle agents), starts MCP (`api/mcp.ts`, its callers named by `Core.clientOf`: a token's canvases are those it was granted and those its party made) on `--port` (kept as the profile's port), else `settings.json`'s `api.port` (chosen free once and kept), exiting with a sentence naming a port that is taken, serves the profile's token socket for `corrallm token` (below; one it can't serve is said, and it serves on), writes `api.json` (0600: `{ url, port, pid, started }`; `started` is `{ bootId, ticks }` on Linux and epoch milliseconds on macOS and Windows), and logs a line to stderr per message, reply, notice and need (`Core.watch`, heard from before the canvases open, each named before it opens, so that what one has waiting as it opens is said by its name), every control character in it escaped (`\x1b`), since the names and titles it quotes come from canvases, agents and MCP servers. Canvases open held: nothing is delivered until every check that may refuse the start has passed (`Core.deliver`), so a refused start sends nothing; one told to stop as it starts (while it reads the login shell for `--new-token`, say) makes no token, delivers nothing and stops. It names each canvas by its file and id; on a profile other than the app's, it says to export `CORRALLM_URL`. SIGINT, SIGTERM or SIGHUP close the token socket and the server, hold each run where it is, journal, end the sessions, write out the stores, close the database, remove `api.json` and release the lock; told again meanwhile, it says it is stopping already, and a stderr that went away (its terminal closed) never stops it short. Then it exits, its terminal gone or not: as the CLI exits (`cli/main.ts`' `exit`), it waits only for the streams its command printed on (`serve` never prints on stdout, which Node would open as it is first asked for, and on macOS opening a terminal that hung up never returns), and on a terminal at most a second. It exits 1 when it refuses to start.
- `--new-token` makes an outside token for the canvases named, called `--name` (`orchestrator` by default), read-write unless `--read-only`, for `--hours`, and prints it once, with the URL and each installed adapter's `registerMcp` filled in (`{server}` `corrallm-server`, `{url}`, `{var}` `CORRALLM_OUTSIDE_TOKEN`), so the platform holds no CLI's syntax. Claude Code expands `${CORRALLM_OUTSIDE_TOKEN}` in a header `claude mcp add` saved (checked with 2.1.303: Build Plan Q23).
- `corrallm token new --canvas <file> [--canvas <file>…] [--name <name>] [--hours <1-12>] [--read-only] [--into <file>] [--profile <dir>]`, `corrallm token renew [--name <name>] [--hours <1-12>] [--into <file>] [--profile <dir>]` and `corrallm token revoke [--name <name>] [--profile <dir>]` (`cli/token.ts`; Build Plan B30) make, renew and revoke an outside token while corrallm runs, behind `--new-token`'s gate: only with stderr on a terminal (otherwise it says so and exits 1, making nothing). Each asks whichever corrallm owns the profile, the app's core (`core/entry.ts`) or `serve`, over the profile's token socket (`core/token-socket.ts`; see [Security](security.md)), never MCP, so it takes effect at once, with no restart: the old token's call still going ends with `TOKEN_REPLACED`, and its next call is answered 401 with `TOKEN_REPLACED`'s sentence (`ApiServerOptions.stale`). With nothing owning the profile it writes tokens.json itself under core.lock, taken as `token` (`Core.answerUnowned`), as `serve --new-token` does, naming the URL of the port the profile keeps, if it keeps one; an owner that holds the profile without answering (one starting up, an older corrallm) is waited for up to 10 seconds, then said. `--name` (`orchestrator` by default), `--hours` (1 by default, 12 at most), `--read-only` and `--canvas` (each file accepted only as `serve --canvas` accepts it, at most 32) mean what they mean for `serve --new-token`; `new` replaces any live token of its name, `renew` gives the live token of a name a new value reaching what it reached (no `--canvas` or `--read-only`: that is a new token), and `revoke` removes it; renewing or revoking a name with no live token is refused. A new or renewed token is shown once, on that terminal, or, with `--into <file>`, written only to that file (0600, written whole and forced to disk) and never shown. The file's folder is checked before anything is made, and a token that can't be written after all is shown instead, rather than lost; its path, once absolute, may hold no quote, backslash, `$`, backtick or control character, since a command names it. It says how to register corrallm in each installed CLI (`cli/register.ts`): by the token's variable (`registerMcp`), or, given the file, by a headers helper where the adapter declares one (`registerMcpHelper`: Claude Code's `headersHelper`, which Claude Code runs in a shell at every connect and again after a 401, checked with 2.1.310), so a renewal into the same file needs no restart; Codex takes its bearer token from a variable as it starts, so it must start again after a renewal. `corrallm token header --from <file>` is that helper: with no terminal needed, it prints `{"Authorization":"Bearer …"}` on stdout from a regular file that is the user's alone and holds one token (no final symlink or FIFO, and a bounded read after checking the opened inode) (`cli/token-file.ts`), and refuses any other, saying why without what it holds. `serve` logs each token made, renewed, revoked or refused through the socket, never its value. The owner and client use a canonical profile path with protected user/root-owned ancestors; the unowned writer checks the same path before taking core.lock. On Windows `token` refuses: the control channel needs an owner-only named pipe and the file helper needs a private ACL check, both held with Windows. It exits 0 when done, 1 when refused (saying why), 64 for a command line that can never work.
- `corrallm wait [--for <id>] [--after <cursor>] [--timeout <s>]` makes one `tools/call` POST of `wait` to `CORRALLM_URL`, else to the app profile's `api.json` while its process lives, with the token only from `CORRALLM_OUTSIDE_TOKEN`, else from the file `CORRALLM_OUTSIDE_TOKEN_FILE` names (read afresh at each wait, as `token header` reads it, so a renewal into it needs no restart), and prints one JSON line (the result, or `{ error }`), exiting 0 (something came), 1 (the time limit passed), 2 (its token refused: none, a wrong one, or one expired, revoked or replaced, which its server tells by `TOKEN_REPLACED`, whether as it waits or on its next call), 3 (no server answered, or a URL that isn't corrallm's on this machine, or none that can take the wait now: one that can't wait now, or the token's waits at their limit, told by `TOO_MANY_WAITS`; it may try again later) or 5 (the wait refused for what it asked: a cursor or message id the server doesn't know); a command line that can never work exits 64, with an `invalid` error line. It sends its token only to http on 127.0.0.1 or localhost (`loopbackUrl`), and finds a server in `api.json` only while a process with its pid and start time runs (`stillRuns`). `--timeout` is at most `MAX_WAIT_SECONDS`, an hour, and that by default.
- `corrallm dump [--profile <dir>]` inspects that profile (the app's by default), with no token, server or core.lock: one read-only transaction prints JSON lines of `{ type: 'repository' | 'canvas' | 'run' | 'message', data }`, in that order: from schema 3, each repository first, with its `setup` (its project_setup row, or null); canvas lines also holding `document` (its rows), `conversations` (keyed by workspace from schema 3), on schema 1 `workflow`, and from schema 3 its workspace records, `repository` (its canvas_repository row, or null), `worktrees` (each with its `setup`, or null, and its `jobs`) and `bindings` (its agent_worktree rows); an older schema's lines leave out what it doesn't keep. Known JSON columns are decoded (a job's `payload` too). It reads the running owner's committed WAL, never migrates, repairs or checkpoints, refuses databases this build cannot read before printing, and exits 0 on success or 1 with a diagnostic on stderr. It does not create a missing profile or database. SQLite may create/use its reader sidecars (-shm and an empty -wal), but writes no database pages or WAL frames. A slow pipe is fully drained, with each line awaited.
- `wait` (`core/ops/wait.ts`; MCP only, deviation `transport`; a long poll, `waits` in its surface, which the limit on calls in flight leaves out, counting it against `TOKEN_WAITS` waits in flight instead) returns the messages addressed to the caller's party on its canvases after its starting point, oldest first, a page at most, or waits for the next until `timeoutSeconds` pass, its caller gives up, or its token is replaced, revoked or expires (then it is refused, `TOKEN_REPLACED`). The starting point is `after`'s place in each canvas's store (0 in one the cursor doesn't name), else the party's read position; `for` keeps what concerns one message, and moves nothing. Cursors say which op gave them: `wait` takes only its own and `status`'s (a `messages` cursor names one canvas), and none past what a store holds. Waits that read on from the read position (no `after`, no `for`) take turns, each reading it afresh, so one message wakes only one of them with it. It never consumes. One without `for` moves the party's read position forward (`core/delivery/reads.ts`), only once it is committed (`read_position`), before it returns: the party's, not the token's, so a renewed token reads on from it. Every canvas's position moves in one write (`Engines.advance`), with what each canvas has to journal, or none: a wait whose positions can't be written fails, so no message is skipped. `status`'s cursor is at the end of every canvas the caller has.

Startup serves the token socket, then publishes api.json, before releasing delivery and before printing “serving”. A failed publication is a refused start (exit 1, with its reason on stderr): queued messages remain pending, and nothing says the server is ready. If a stop arrives while publication is in progress, delivery stays held and the published file is still removed during cleanup.

Exiting waits for every pipe to drain fully. Each terminal stream has its own one-second cap, so a terminal on stderr never cuts off wait’s piped JSON line.

The core's silent-turn watchdog also runs under `serve`. Its regular local interface snapshot detects network changes even when there is no sleep or window event; a turn silent since before a change gets two minutes of fresh silence before its warning, sender notice (waking `wait`) and Interrupt need. It never resends or interrupts automatically; see [Sessions](sessions.md) for identity normalization and grace rules.

Server discovery verifies api.json’s OS process identity with the same reader as core.lock and CLI cleanup (`src/main/core/process-identity.ts`). On Linux an address holding only a wall-clock start is not used: it cannot identify the server reliably after a clock step.
