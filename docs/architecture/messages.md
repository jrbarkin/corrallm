# Messages and delivery

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

The window answers an agent's ask with one `reply { answers }` for every question, dismisses only the core's offered asks-to-you or message choices, and replies to a message with `{ text }`. A loop hold's `loop.pair` and `loop.held` identify exactly the pending turn rows it holds, including an expired ask's settlement from corrallm; the human window joins those ids to its messages topic and never infers the hold from sender pairs. The title contains no message text. Attempt reports read only result-row verdicts and open question rows' own `ask.task`, shared by the agent queue and All queues.

## Messages

Message writes distinguish changes still needing SQL from rows already written but awaiting their log flush. Each version is written once; containing writes restore their staged changes on failure before the next savepoint runs, and `durable()` waits for every covered flush. Delivery checks coalesce within a microtask and run before the next event-loop turn, so holds, replies and recovery notices retain their ordering throughout a burst. A check walks what delivery acts on a fixed number of times (what is gone, what is stale, then what waits), however much waits: each agent's line is ordered in one pass (corrallm's handoff requests, then continuations, then the rest, each in the order it came), the canvas's agents are read once, the asks' sweep reads only the open asks and the continuations still to come (`Asks` keeps both as the store changes), and a check, like Needs, reads which waiting messages are turns between two agents only while a pair of them is held (`LoopStore.holding`); a streamed word or thought (`streamed`, reduce.ts), which changes nothing a check reads, makes no check, nor a Needs look (a reply's words were most of the session changes G2's burst made, each a check and two Needs reads); every look at Needs and every other change asks for them, so under G2's load a walk more per check, or a line ordered by insertion, made the core's loop fall behind its backlog.

What parties send a canvas's agents (API Spec §5, Core Server §5.9), served by the core from B6 (headless; the app from B11, whose composer's submissions its run journal keeps as your messages until then: [Run recovery](run-recovery.md)), each with how it came to be (`MessageOrigin`, `src/shared/model/messages.ts`: `manual`, typed by you; `party`, a party's or corrallm's; `run`, the run's own; `resend`, one you asked to send again), which the core records and no caller gives. A party is you, `corrallm`, `agent:<id>` or `outside:<name>` (`PartyId`, `src/shared/model/messages.ts`); no token is ever you. An agent's id is its node's: any text (line breaks too) of at most `MAX_NODE_ID` characters (`model/canvas.ts`), which a canvas file, the API's ids and a party id all hold to.

- **The store** (`core/delivery/messages.ts`): each canvas's messages in order, in memory and in the core's database, a row of `message` each (with how it came to be, `origin`, kept beside the message, never changed; what a view shows of it beside its body, `display`: the task it followed, the held task it corrected, the whole text of one whose body holds it cut (a submission longer than a message holds), its image count and whether it requires them, never their bytes; the message it resends, `resendOf`; the key of what a notice told, `told`; and the note its recipient must still be told of a withdrawal, `withdrawal`, in the same row), written with the database's next commit, and on disk once `durable()` resolves. The order is one every canvas's messages share (`MessageTable`): the core gives each place past the last the table's AUTOINCREMENT sequence gave, which every open raises past every place given before (from the clock: `store/open.ts`), so a cursor survives pruning, restarts and restores, and one naming a place whose row a crash cut off never skips the message given that place next (`end()` is the last place given, in any canvas). It keeps the newest `STORE_SETTLED_PER_PARTY` settled messages of each party within `STORE_BYTES`, and every pending and unresolved one (a party may have at most `MAX_WAITING` messages waiting for an agent: `message` refuses another), deleting the rows of those it drops. Beside them it keeps, in order and as each changes, those delivery still acts on (`active()`, `isActive`: waiting, being delivered, or a text to an agent whose turn goes on), which delivery and every needs pass read instead of every message kept. `watch` hears, by id, each message kept, changed or no longer kept (a staged one once revealed or undone): what `messages:<c>` publishes from. Beside a record the core settled it keeps the association the core wrote with it (`about`, B19 C3, migration 13: the agent whose window shows it, the Needs item it settled, a hold's choice by key), never changed after, and for each agent its window (`records`, `RecordRow`s: the newest `MAX_RECORD_ENTRIES` of the records `shownRecord` shows, in the store's order, within the store's own retention, an unresolved one counted though its row is never dropped), indexed by sequence as records change and read again only once it changed; `watchRecords` hears, by agent, each change of a window, as the message that changed it is heard, never another message's.Each row is written as the message is in memory when its write runs, each column by name (so a newer corrallm's stay), and marked on disk only if it hasn't changed since; a write that fails leaves its rows to the next. It never throws: what it can't write it says on the console, but `durable` rejects then. Rows it doesn't read (a newer corrallm's kind or origin, a display it doesn't know) are left as they are. A store whose rows can't be read (the database couldn't be opened) starts empty, says why, and journals nothing (`durable` rejects once anything has changed), so nothing is sent without its record. What waited in a snapshot a damaged database was restored from may have gone since: the restore makes it unresolved and tells its sender (`store/restored.ts`).
- **Delivery** (`core/delivery/delivery.ts`): a message to an agent is delivered once the agent is idle (no turn, nothing asked, by its session or waiting in the core's prompt owner, its session idle or not: B13 C9's `DeliveryDeps.waitingOn`, nothing queued in its session, nor on its way there from the run: `RunStore.sending`, a message whose record is on its way to disk first), at a delivery point while its queue runs (B19 C2, below), and nothing holds it: its own or its group's pause (a kill too), a session that won't start (it stays first in line), a session that would act on a party's text unchecked (`#asking`: yours still go; you see it in Needs, `unasking/<agent>`, and its sender is told why): one that runs in a mode its adapter says never asks (`EngineCatalog.neverAsks`), or, on settings of its user's that are none of its modes (Codex's App Server on a custom policy), whose `started` event says they never ask (`asks: false`; `asksOf` reads Codex's: approvals `never`, or no sandbox with `on-failure`; `on-request` still asks about dangerous commands); an unreported non-Terminal holds messages until permissions are reported; one yet to start starts in its saved start mode if its connection starts in it (each asks), else in its CLI's own default: a session given no mode starts in the user's own default, which may never ask, so delivery reads it (`defaultAsks`: `session:options`' reader, in the canvas's project folder, its `defaults.asks`) once a session, again once that session ends, or with the next message sent RETRY_AFTER or more after a read that held its messages, and holds a party's message while it reads, while that default never asks, and while corrallm can't tell (a custom Codex policy it doesn't know, settings it couldn't read). A mode switched in either CLI’s terminal is seen only once the next hook fires. Codex’s permission_mode tells whether it asks, without distinguishing every sandbox preset; until that hook its last report stays in force. Claude Code’s managed (policy) settings are not read by `session:options`. Other holds are an exhausted usage backend (a turn hit its hard limit, held until its reset even without a rule), or its backend's usage rule (headless, a rule that asks waits for the reset, and one whose window's reset isn't known only warns, since nothing would read its usage again while messages waited; a usage hold the run set, `AgentRun.usage`, is that rule read now, so one a stopped run left, or whose window has reset, holds nothing), whether or not a run is going. A whole-run Stop, and the paused state a run restores in, hold only the run's own sends and its queue hand-offs (B19 C1, below). A session that refused to start is tried again by the next message sent to its agent a minute or more after the refusal (`RETRY_AFTER`), which delivers the first in line; the sender's notice and the Needs item say so. A message goes only once its own record is on disk; one whose record can't reach it fails its `message` call and is unresolved, never sent; one whose delivering record can't reach it was never sent either, so it waits again, first in line, and nothing on its canvas is delivered until delivery tries again (`RECORD_RETRY`, a second on). Each is journaled delivering, with the id its session is sent it under (`delivery.as`), committed and flushed, then sent; the session's echo marks it delivered. A message may come with pasted images, live-only (its display says how many and that it requires them, so a restart that lost them leaves it unresolved, never sent without them), and a told key what admitted it finds it again by (`MessageStore.toldAs`: Continue in Terminal's `continued:<request>`, so a repeat of its request never sends it twice). Yours go past the run's holds into the session's queue, as typed; everything else is framed. A message's turn ending makes the agent's reply a message to its sender with the turn's `TurnResult`: a turn for an agent (its frame saying how the turn ended, when it didn't complete), a record for you or an outside party, and never answered by another reply. Each sender is told once (a `notice` from corrallm, keeping the key of what it told, so once across restarts too) when its message waits on a pause (naming who set it, and that only they or you can release it), a session that won't start, a mode that never asks, an exhausted backend or a usage window (every party whose messages wait, not only the first; told again once the agent holds again after it was released: a pause let go, a session that started, after a restart too, a mode that asks), when its turn waits for you (on a prompt the core's owner holds, B13 C9: never a hold of the run's, which holds a party's message before its turn instead: B19 C2, below), and when it ends withdrawn by someone else or cut off. A notice quotes a prompt's title (as a token may read it: B13 C11's selector) and an agent's name on one line, cut after 120 characters, and a reason after 1000: never a whole command. Closing the core, or a crash, leaves what was delivering, or delivered with no turn end, unresolved, never sent again. What waits for an agent no longer on the canvas (or from one) is withdrawn by corrallm, its sender told. Before its first party message, delivery starts the session without sending and rechecks the native started mode or asks; an unasking or unknown report holds the message, while yours still go. A Terminal carries its explicit start mode or trusted pre-launch default until a recognized native hook reports otherwise; one still unreported waits silently within its startup bound. While the core's shutdown barrier is prepared (`Delivery.freeze`, a quit or an update's restart), nothing starts being delivered, though what is delivering goes on and its reply comes back; a cancelled quit delivers what waited. Codex on-request can still ask about dangerous commands without a sandbox; on-failure without a sandbox and never remain unasking. Counting a session that can still ask as asking is the user's decision (Oct 24, the second review's G3), consistent with Claude Code's Auto mode, which also acts on most things unasked: delivery holds a party's text only for modes that never ask (Claude Code's Bypass permissions; Codex with approvals `never`, or no sandbox with `on-failure`).
- **Fallback** (B11a C3, C5: `src/main/core/fallback.ts`, see [Usage](usage.md)): before a party's message is handed over, delivery asks admission (never for yours, never while the agent is paused): where corrallm switches the agent's backend, the message waits, silently, and goes to the new endpoint under its own id and sender once the switch is committed, through every hold as any other's does; a fallback rule over its share that can't switch the agent holds it as ask does, and one a simulated reading only previews lets it go. No message is sent again: a sender whose message's turn failed on the limit gets that failed reply, as before, and, once the agent switches, one notice (`carries-on:<message>`): "‹agent› carries on with ‹target›; your message wasn't sent again."
- **Handoff requests** (B11a C7: `src/main/core/handoff.ts`, see [Usage](usage.md)): corrallm's request for an agent's handoff is a message from corrallm to the agent (`Delivery.ask`, kept with a told key starting `handoff:`, origin `party`), recorded before it is sent and first in line for its agent, ahead of every party's message waiting. What holds the agent holds it (its pause, a held workspace, a session that won't start, the barrier, an exhausted backend, a rule that asks or waits over its share, corrallm switching the agent), but never its asking mode (`unasking` doesn't list an agent for it), and it is never admitted as work; delivery withdraws it, by corrallm, as the handoff service says it is stale (not the agent's current request, its handoff off, its connection changed, its backend exhausted), so one left from before a restart is withdrawn as the canvas opens, never sent. Its turn's whole reply goes to the handoff service (`DeliveryDeps.handoff.replied`) in the same tick as the reply's record, which holds it capped as any reply. No notice is ever told of it (corrallm is its sender). The first party's message delivered to an agent after a switch carries the agent's handoff (`DeliveryDeps.handoff.carry`): taken as its delivering record is written, so that write clears the carry and keeps the message with a told key saying it carried one (`HANDOFF_CARRIED`, `carried:` and the switch, never the text: a party's message has no told key of its own), sent as corrallm's switch line, then the message as delivery frames it, then the handoff; one that never went (its record not written, taken back while journaled, held on its recheck, a session that won't start) leaves it for the next, its told key dropped. A message cut off unresolved (closing, or as delivery starts after a crash) keeps that key only where its session never had it (it was delivering, not delivered); as delivery starts, the handoff service gives each such carry back and drops the key, in the write that cuts them off (`DeliveryDeps.handoff.recover`). Yours never carry it.
- **Answers and who decided** (B11 C7: `src/main/core/run-replies.ts`, `src/main/core/decisions.ts`): the typed reply answers a run's hold with one of its choices, or words where it takes them (an OK's changes, a problem's or a repeat's next try: `{ text, images? }`, or `{ choice: 'retry' | 'more', text }`), decided at once (RunStore.decide) and recorded in the same write as the run; a refusal's Switch runs `session.continueIn` as the same caller and the run then sends the held attempt there, once. A hold a pause holds is refused, naming whose pause (no answer releases one, R9); one of a run not going is unavailable. Production prompt cards now send the owner's registered C1 shapes below, with one reply per explicit gesture and drafts local to the occurrence. A URL open is its own `link.open` and never implies acceptance. A Terminal's described ask is answered in its terminal. A prompt's answer is recorded as being made, on disk, before its CLI is told, and told only if the session that asked it (the generation its id names) still runs: one started since, though it asks by the same native id, is another prompt, so the record is withdrawn and the answer a conflict; the owner settles its transcript entry only once the captured native answer handle takes it. One the CLI refused leaves the prompt waiting and its record withdrawn, saying so; one a crash cut off is unresolved as the canvas's messages load again, never answered again, its record saying so. Each decision is a `settled` record from corrallm to you, `by` the party that decided, its body what kind of answer it was (never the words, values, answers or feedback given; a session's prompt's in the core's words from its kind, what was chosen and the agent's name, as the owner's below, never its tool's input, a plan's mode or an MCP server's name), its told key `decided:<need>#<uuid>`, so the latest of an item (`decidedOf`) names who settled it to a second answer, across restarts too. A run hold's record and a native prompt's are kept with the association the router or the owner resolved as it decided (`about`, B19 C3: the agent the hold or prompt is of, its Needs item, and for a hold the choice picked, by key, and whether words went with it, never the words; `holdAbout` in `src/main/core/run-replies.ts`), beside the record and never in its words, which the agent's window reads (Settled records in the window, below); a workspace change's, a proposal's and a review's have none.
- **Prompts the core owns** (B13 C3: `src/main/core/prompts/owner.ts`; raised as [Sessions](sessions.md) says): each waits in Needs as yours, `prompt/<agent>/<generation>/<PromptId>`, with its choices (each marked where only you may pick it, every one of a prompt only you may answer, each with its hint, its effects where its adapter can tell them, whether it takes words and whether it ends the turn) and its own fields beside the generic ones (`prompt`: its PromptId, kind, when it was raised, its summary and reason, its subject, a plan's first lines, whether it was cut, why only you may answer it); a form's title is the core's for everyone (the MCP server that asks, by the name it is configured under where its adapter says which, else its agent's CLI, asks you to fill in a form, or to open a link), never the server's words, which may hold its link. What each reader sees of it is the one selector's (B13 C11, `src/shared/model/prompt-views.ts`): a token that reaches its agent (and a parent, its team's, through Needs alone) sees it without choices or form, a form without its summary or reason, an approval to use an MCP server's tool titled in the core's words ("MCP server “x” asks to use its tool “y”") without its summary, reason or detail (B13 C9: an MCP server's own words never reach a token, in a notice, a refusal or a settled entry either), a terminal's wait its report alone describes without its detail (what the terminal's screen shows), and every question whole but never an answer; a token's reply to it is refused in those words; the counts `agents` and the summaries give add the prompts the owner lists, once each. The reply router's prompt handler uses only the owner, which finds the PromptId in the canvas's live index (never by the id's text: the agent and generation must be the occurrence's) and answers as C3 sets out: it is yours alone (no token answers as you, R3; never its own agent, R6), the answer is checked against the prompt as raised (P4's `{ choice, feedback? }`, `{ answers }` keyed by question id with `{ picked }` or `{ text }`, or `{ form }`; never `text`, images, `permission` or `plan`, and nothing for a prompt answered in its terminal but Not waiting, below), then the prompt is reserved with nothing awaited (a second reply meanwhile is a conflict naming who answers); its `delivering` record is written and flushed (a failed flush gives nothing and reopens it); it is checked again (still reserved, its generation still the agent's: an end meanwhile wins, the record withdrawn, the reply a conflict saying how it ended); past `noReturn` it is handed synchronously to the session that raised it, never one looked up again; then it is settled and the record landed. A session's refusal withdraws the record and leaves the prompt open, unless the session ended it as it refused. An end after the handoff is ignored. A crash between the record and its landing leaves the record unresolved as the canvas's messages load, never given again: open prompts aren't persisted, so a core started again has none, and a reply to an old one is told what its record says. Answering never starts or resumes a session. The record's words are the core's, from the prompt's kind, its subject's type, the choice's hint and the agent's name ("You allowed Builder’s command once.", "You answered Builder’s questions (secret).": `decisionWords` in `src/main/core/decisions.ts`): never a title, label, command, path, plan, feedback, answer or value. Beside them it keeps what was decided, typed (`Message.settled`, `src/shared/model/settled.ts`, schema 7, B13 §9.2 C9): `{ v: 1, need, prompt: { id, kind, subject? }, outcome, secret? }`, the subject by its type alone and only where the protocol names it (an adapter's extension, none), the outcome a choice's value and hint, how many questions were answered, or a form's action, `secret` where an answer was; never a label (labels are untrusted and can quote a command), title, summary, reason, command, path, plan, feedback, answer or value. It is written with the record's row and never changed after, a crash's unresolved record keeping it; records of decisions are to you, so no token reads one. Withdrawn, answered in the terminal and dismissed are never records. A later reply to one that ended is told how: settled (by its record), withdrawn, answered in its terminal, or said not to be waiting. What no longer waits is in no token's reach, so a token's reply to it is not found; were one in reach, it would be told only who settled it, never how. Not waiting (B13 C7) is the core's own choice, offered only on a terminal's wait raised from its CLI's report alone (no subject, choice, question or plan: never one a hook described, the trust screen, or the core's stand-in for one it couldn't show), and only you may make it (it is marked so): `{ choice: 'not-waiting' }`, nothing more, before a terminal's answers are refused. It is settled dismissed by you at once, past `noReturn`, with no record (`outcome: 'dismissed'`), and its session is told to stop raising that observation until a distinct wait ([Sessions](sessions.md)); its CLI is told nothing, and nothing that holds a message for the agent changes. Each prompt the owner lists is an entry of its agent's transcript and session topic from its raise, settled there in place with how it ended (B13 C9: [Sessions](sessions.md)), with at most 100 ended prompt entries per agent (the oldest ended entry is dropped on settlement, every waiting prompt and other entry kept in place), and every change of the owner's is published at once: Needs, the agent's summary and its count, and what delivery holds. Its close barrier: once a canvas starts closing, what its sessions raise is declined and never kept, and an answer whose record was being written as it did is withdrawn and refused as a conflict, its session never told; once closed, what still waited on it ends withdrawn.
- **Settled records in the window** (B19 C3, Design §9: `src/shared/model/records.ts`): what the core settled for an agent reaches its window as typed display entries, read from the records alone. Its window holds a `record` entry for each record `shownRecord` shows: one kept with the core's association (`about`, above); a run hold's decision; an ask's end, in its recipient agent's window, however its asker is sent it; and a native prompt's decision that took effect or that a crash cut off (`unresolved`), unless its prompt's owner made it while this core runs (`owned`, a mark the store keeps in memory alone, never written): then B13's owner entry shows it, settled in place or open again after its CLI refused it, and once B13's cap or a /clear drops that entry nothing brings it back. Owner entries live only while the core runs, so after a restart, or its canvas opened again, each such decision shows in the window, once, with no owner entry beside it. At most `MAX_RECORD_ENTRIES` (100), the newest, per agent, within the store's own retention: an unresolved one counts though its row is never dropped, and B13's 100 ended owner entries and every live prompt are counted apart, unchanged. Each is under its record's id, namespaced (`record/<id>`), and names the record and the Needs item it settled, when, who decided, `settled` or `unresolved`, and what it settled, value-free: a hold's choice by key and whether words went with it, a native decision's kind, subject type and outcome, an ask's asker, question count and outcome; never a title, label, command, path, plan, feedback, answer, value or the record's words. `recordWords` words one as the core does: a hold's choice by its fixed key ("Approved by you.", "Stopped here by you.", "Changes asked for by you.", ", with words" where words went with a choice; never a label), a native decision by its hint or action, an ask by how it ended; never as applied where corrallm can't tell ("Allowed once by you, but corrallm stopped as it was answering, …"). Only a native decision can be `unresolved`: a hold's was decided in the write that kept it, and an ask ended whatever became of its asker's turn of it. One selector, `recordsFor`, gives `session.transcript` and the `session:<c>:<agent>` topic the window, ahead of the native entries, in the store's order: that is the core's position, so a reload, native history, a /clear or a restart moves none and makes none twice, and no native entry is shown under a record's id. It is yours alone: a token that reaches the agent reads none, in a page, the topic, a count or an error (a page `after` a record's id is not found, in the words any id never given gets). It is a projection, never an entry of the session's, so no turn's reply, rewind point, owner cap, native history or /clear reads or rewrites it, and no adapter emits one. The topic reads an agent's window again only as it changes (`watchRecords`), saying its new records and, where its records came or went, the whole order; another agent's turn, or a streamed word, reads none.
- **Withdrawal after receipt:** `withdraw` returns `{ reached, interrupted }`, based on the session's receipt at the take-back request, or its end if it already arrived, rather than a delivering record (which may still be on disk or in the session's queue). It waits for any immediate withdrawal's durable flush, never for a native turn's end; a received message is withdrawn with its note when that end arrives. A second preempt or queued drain therefore cannot hold the canvas's lanes on a hung turn. The CLI's history keeps a message it received, and work already done stays. Every interrupt stops the commands its turn started where its connection supports it, before another message is delivered (see the Codex connection's command cleanup and its bounded failures). A take-back, Kill of the run's sends or of a native turn with no stored message, and an ordinary session interrupt all use that same scope. With the next message delivered to that agent, from any party or the user, corrallm includes a note inside the same `[corrallm]` frame: the message's id and sender, that its sender withdrew it after it reached the agent and its turn was interrupted, not to carry out what it asked unless someone asks again, and that anything already done is left as it is. A kill (`run.kill`, of an agent or a group) leaves the same note for each message it takes back after its recipient received it, whichever end was killed: in place of its sender's withdrawal, whom the kill killed (the recipient, or else its sender) and who killed it, named as `core/parties.ts`' `quotedParty` names a party (the user, or anyone else's name in quotes; "at your own request" where the agent killed itself). Every name in a note, frame, refusal or notice is capped before escaping quotes, backslashes, newlines and other control characters (`core/parties.ts`, `quotedName`), so a name cannot close its quotes or start a new frame line. A note quotes nothing of the canvas but parties' names, capped as notices cap them: never a body, a group's name or a queue's text. The run's own sends (queue steps and messages) leave none: they are no messages of the store, the run holds each task a kill interrupted in Needs you, cancelled, for the user to inspect, resolve or retry, and a note could name such a task only by its canvas text. Untold notes are kept with the withdrawn messages, across restarts and log pruning, until the CLI echoes the message carrying them. Several withdrawals are named together; one taken off the queue before receipt adds no note. A note never starts a turn by itself, except before an unframed slash command (typed by the user or sent by a queue step) or a user message that starts with any catalog shell prefix: then a separate framed note goes first, its turn ends, and the command goes alone unchanged. The command's turn includes its note's: a Stop, a Kill, a take-back or a stalled turn's Interrupt of it (an interrupt of the agent's session, in the app or the core, after the command was sent and before the note's turn ended) interrupts the note's turn, and the command is then never sent, its turn ending `cancelled`, `taken-back` (a take-back's withdrawal `reached: false`, adding no note), while the note counts as told only if the CLI echoed it; a stalled note's Interrupt and resend lets the command go as the note's turn ends. The transcript shows the text echoed by the CLI, including these notes; a separate note appears before the command, and resumed history keeps what the agent was told. The note asks the agent not to act; it cannot force it or undo work. Taking back a live native turn returns once interruption is requested, without waiting for that turn to end; `interrupted` then says interruption was requested, not that the native end arrived. Its final withdrawn state and receipt-based note are recorded together when the turn ends. A repeated take-back shares that request. Waiting and unreached messages still acknowledge only after their immediate withdrawal is durable, including T4’s WAL-flush failure handling.

you: all), `needs` (yours with their choices; a token sees yours on the agents it reaches as B13 C11's selector says, without them or their forms, an MCP server's link among them, and an agent its team's prompts too; each item's id is unique on its canvas: `hold/<agent>/<generation>/<item>`, `start/<agent>` for a session that won't start, `unasking/<agent>` for one that would act without asking (its mode never asks, its CLI's default never does, or corrallm can't tell), `limited/<agent>` for an exhausted usage backend, `stalled/<agent>` for a silent turn, `prompt/<agent>/<generation>/<prompt>`, `setup/<workspace>/<generation>` for a worktree's setup, `rebind/<owner>/<generation>` for a workspace change, the agent's id escaped; a hold's generation fingerprints what it is, a prompt's is its session's, so an answer to one asked before never answers the one asked now), `agents`, `status`, `session.get`, `session.transcript` (paged by entry; a delivered turn is withdrawn when its end arrives, without holding the kill; one that can't be fails `unavailable`, saying the change is in place but may not survive a restart), each pause stamped with the party that set it: a token releases only its own (rule `sticky`, R9: one whose release would let go of no pause that holds its target is refused, naming who set those), you any; ## Asks and messages to you

B21 C4 (Design §9.2 C5, C6) builds them on the message store alone, with no second inbox and no ask table: `src/main/core/delivery/asks.ts` (`Asks`, each canvas's, owned by its `Delivery` as `delivery.asks`) keeps an index of the open asks and of the parties' messages waiting on you, rebuilt from the store as the canvas opens and kept by `MessageStore.watch`.

- **A party's message to you.** `message { to: { party: 'you' } }` (from an agent or an outside writer; `Target` in `src/shared/api/ids.ts`: a string is always an agent's id, the parties are objects) is a record to you (kind `text`, `delivered`, never a turn) and a Needs item `message/<id>` (kind `message`, for and by you alone, titled "Message from Planner", its body as `detail`, Dismiss and a Reply text). `{ party: 'manager' }` is the nearest lead granted questions, which is you until B24 grants one: kept resolved, `display.via: 'manager'`, so B24 can route it again. You name neither party (`invalid`: you message agents); an outside orchestrator has no manager (`invalid`). A sender keeps at most `MAX_WAITING` open (then `refused`). Dismiss settles it (`answered`, by you) with no record to its sender; Reply sends yours, to an agent as yours (unframed, a turn, `replyTo` the message), to an outside party as a record for `wait` (at most 16 KiB). It answers nothing and approves nothing. While it waits on you it is never pruned.
- **An ask** (`ask`, MCP alone: agents and outside writers ask, you answer) is a message of kind `prompt` from its asker to its recipient (a reached agent, never itself; or you, directly or as its manager), its `ask` column holding its one to four questions (B13's, no preview, never secret), its deadline (60 to 86,400 seconds from now, a day by default) and `via`. It is on disk, the log flushed, before `ask` returns `{ id }`; one that can't be kept is `unavailable`, never open. One open per asker and recipient (`conflict`, naming it), `MAX_OPEN_ASKS` a canvas (`refused`), and one to an agent counts against `MAX_WAITING`. A request id is kept on the row as its told key (`ask:<party>:<request>`), so a repeat finds the first ask across a restart while that row is kept, and another ask under the same request is a `conflict`. An open ask is never pruned; a settled ask and its request deduplication last until normal message retention prunes its row. An ask can't be taken back (`withdraw` refuses it, its answer and its end).
- **Delivered to an agent** as messages are (every hold; never carrying a handoff, which the agent's next message carries), behind corrallm's frame: `[corrallm] Question from agent "Planner" (an agent, not the user; question <id>). Answer with the reply tool: reply { to: "ask/<id>", answer: { answers: { "<question id>": { picked: [...] } | { text } } } }, or in your reply text. Its questions, in the asker’s words:`, then each question's id and header (quoted), how it is answered, its words and its options. **To you** it is `delivered` and a Needs item `ask/<id>` (kind `prompt`, for and by you, until its deadline, its questions, and Dismiss, yours alone). An ask to an agent has a Needs item too, by its recipient and you, which only they see: it names no agent, so no other token reaches it, and `NeedId` reach admits it to a party its `by` names.
- **Answering.** `reply { to: 'ask/<id>', answer: { answers } }` from its recipient or you, every question by its exact id (`checkQuestionAnswers`), at most 16 KiB. Its rendered body, including the question headings, must also fit the message’s 16 KiB budget; an answer beyond it is refused before settlement, leaving the ask open for a shorter reply. Structured answers are never cut. The first valid answer wins, a later one a `conflict` naming who answered. In one write the ask's row becomes `answered`, `by` the answerer, with a value-free settlement in `settled` (`{ v: 1, ask: { questions }, outcome }`: how many were answered, never what), and the asker is sent an answer row: a `text` from the answerer, `replyTo` the ask, its `ask` column the answers, its body corrallm's rendering of each question with its answer. A token's own words that would reach an agent asker's connection meet R1 and the file-mention rule there. An ask's turn that ends completed with no structured answer is answered by its reply text (`{ text }`, capped as replies are); a failed, cancelled or empty turn leaves it open (`replied`, its Needs item still there) and tells its asker once. A structured answer during the turn means its text is never a second answer. An ask's turn, an answer's and an ask's end make no ordinary reply.
- **Ends.** Its deadline expires it (by wall clock: a deadline passed while corrallm was down expires it as its canvas opens), you may dismiss one to you, and its recipient leaving the canvas withdraws it (`recipient`): each sends its asker a `settled` record from corrallm carrying the settlement, kept with its recipient's association where that is an agent (`about`, B19 C3: the agent and `ask/<id>`), which that agent's window reads. Its asker leaving withdraws it (`asker`), and its canvas's close for good withdraws it (`closed`), nothing sent. Admission and settlement recheck the wall clock even before the deadline timer runs; a late structured or turn-end answer cannot win. A late answer is a `conflict` saying how it ended. A core that stops while an ask's turn goes on leaves that turn unresolved, never resent, and the ask open.
- **To its asker.** Every row an asker is sent goes to an agent as an ordinary turn, framed (an answer as `[corrallm] Answer from agent "Builder" (an agent, not the user; message <id>, answering your question <ask id>):`, yours as the user's answer, never raw input), under every hold, making no reply; and to an outside party as a record for `messages` and `wait`.
- **A task's asks** (B21 C5, Design §9.2 C7). An ask an agent makes during one of its task's attempt's own turns belongs to that task: its `ask` column keeps `task` (owner, item, attempt). An attempt's own turn is the turn its session is on now (`SessionStore.turnOf`) whose message is its step's send or a continuation of it, of the agent's current tool step's attempt, running (`ownTurn`, `src/main/core/attempts.ts`, the AttemptId's resolver too); an ask made in any other turn (a party's message, yours, a reply, a slash command, a message item, a condition's question, no run) is taskless, as C4 built. Its answer, or the record of how it ended, carries the task (`Message.task`): a **continuation** (`isContinuation`), which is no run's send (`sentByRun` excludes a row with an `ask` column) and which delivery sends first in line for its agent, after corrallm's handoff request and ahead of every party's message, as the attempt's own turn. What holds a party's message holds it (admission, an exhausted backend, a pause or a kill, a held workspace, a session that won't start, the shutdown barrier, a mode that never asks, the agent busy), but never a usage rule (rules act between tasks); and while the run doesn't go (a restart's pause) it waits, as the run's own work does, until you resume it. Its frame is the answer's (or the record's) first line and body, then `Your question, asked during your current task:` with each question's header and words (its asker's own, quoted back, so a fresh conversation after a switch can carry on), then `Carry on with that task now, and end it as its step asked.` Its turn's end is told the run (`RunStore.continued`) in the same tick as its row is settled `replied`, so one write holds both: the run judges the attempt, or waits again (see [Engine](engine.md)). Meanwhile the agent is at a delivery point: others' messages reach it as turns the run never judges. The attempt stopped (Stop, Kill, Run again, its turn failing natively, a restart holding it uncertain), its open asks are withdrawn (`stopped`) with nothing sent its asker, and its continuations still to come with them, as delivery next looks (`Asks.sweep`: an attempt no longer running); one in flight is taken back, its turn interrupted, telling no one (`Delivery.interruptTask`, the run's `RunTasks.interrupt`), as the run's own sends are. An ask that had reached its agent recipient isn't interrupted there: the recipient's next message carries a note (`Question <id> from "Planner" was withdrawn after it reached you: its task was stopped. Do not answer it. ...`); your late answer is a `conflict` saying how it ended, a token's not found (an ended item is out of every token's reach). A continuation in a stalled turn you Interrupt and resend retries its attempt, as the run's own sends' do, and is never copied as a party's message.
- **A task's result** (B21 C5, §9.2 C8). `complete { canvas?, task, outcome, summary, request? }` writes a `result` record, from the agent to corrallm, `replyTo` the turn it was reported in, `task` the attempt, its `verdict` (`{ v: 1, outcome, summary }`, migration 10) and a body of `Succeeded:` or `Failed:` and the summary, kept with the told key `result:<attempt>` (one per attempt), on disk before `{ revs }` returns; in the same step it withdraws the attempt's open asks and its continuations to come (`completed`), so no later turn joins the task. A second report is a `conflict` (`This step was already reported succeeded.`), the same request its first result. Its readers are its agent and you, as for any message; the summary is the agent's words, never a condition's evidence, a Needs title, a notification or a log line. A report that can't be saved is `unavailable`, standing in memory. A step that has reported with `complete` cannot ask another question before its native turn ends (`conflict`): no later continuation joins that task. Its result record stays outside settled-message pruning while the turn it reports is unsettled, including a turn cut off by a restart; once that turn settles and its attempt is judged, normal retention applies. This dependency is indexed by turn id, so a turn settling reconsiders only its own result records.
- **The loop breaker** (B21 C6, Design §9.2 C9). Ten delivered turns between the same two agents of a canvas without you, then the eleventh waits for you. A turn is counted when its message is journaled `delivering` (`Delivery.#deliver`): a party's message, an ask, an answer, a reply delivered as a turn, a task's continuation, or the record of how an ask ended (counted for the pair that asked), each from one agent of the canvas to another, both directions together and each other pair apart. Nothing from you or an outside party (Q4) is a turn between agents, nor the run's own sends, its queue hand-offs (B19 C1), corrallm's handoff requests, notices or any record no turn is made of (a hand-off's evidence among them). The count (`LoopStore` in `src/main/core/delivery/loops.ts`, table `loop_pair`, migration 11) is written in the same write as the `delivering` record that it counts (the message store's `writeAlso` companion), so they reach the disk together or not at all; a turn never sent (its journal refused, taken back while it was journaled, its session refusing to start) is counted back, so a retry never counts twice, and only from the run of turns it was counted in: once you spoke to either agent since, the pair counts what was delivered after, and a turn counted before takes none of it back. An unsent withdrawal releases its reservation in the same write that keeps the withdrawal, even while session readiness is pending. A held message stays `pending`, with every later turn of its pair behind it, and the pair's one Needs item `loop/<a>/<b>` (kind `hold`, no agent, `for` and `by` you; the two ids escaped with `encodeURIComponent`, ordered by their UTF-8 bytes; none if the id would pass `MAX_NEED_ID`, the hold standing all the same) offers Go on, marked human-only. The oldest held party send across both directions selects the sender told once (a notice keyed by the oldest held message a party sent, so a restart tells nothing twice and a later hold tells again; corrallm's record of how an ask ended is told to no one and takes no one's notice). Go on (`reply`, yours alone; `Delivery.goOn`) starts the pair again from zero, on disk before it returns, and the held turns go in order. Input from you starts every pair holding an agent again from zero: your message to it (`Delivery.send` from you), your answer to an ask of it or one it asked, your dismissal of an ask or of a message of its to you, your reply to a message of its to you (`Asks`), your answer to its run hold or session prompt (`ReplyRouter`) and your `run.goOn` naming it. A retried request, a token's call, an outside party's message, a restart or a task's continuation (`RunStore.continued`) is never input. A pair's row goes with either agent leaving the canvas; there is at most one row for each pair of its agents, so nothing is ever evicted to make room and no held pair is forgotten. Headless, the hold waits for the app.

  The window shows each of these (`message/`, `ask/` and `loop/` cards, B21 X3) as the renderer doc describes; every gesture is one `reply`, and Go on and Dismiss are yours alone, as the core already refuses them to a token.

Withdrawal durability includes the WAL flush, not just a SQL commit visible to another reader. A failed flush fails the store closed; the operation returns `unavailable` even though the in-memory withdrawal has already taken effect.

An explicit stalled-turn resend keeps the original and its cancelled reply. Its new message has the same sender, recipient and body, a new UUID, origin `resend` and `resendOf` naming the original (schema 4; before it, a `resend:` told key and `replyTo`, which migration 4 moved): never `replyTo`, so nothing that reads replies (a `wait` for a message, serve's log, a reply's framing, a reader of `messages`) takes it for one. The original receives a once-only corrallm notice naming the new id and the user who requested it (its `resent:` told key, its `replyTo` the original, as a record about it). A message is resent once (`MessageStore.resent`), across restarts too; its origin makes even your resend respect pauses, usage and asking holds, which only `manual` goes past. A withdrawn or no-longer-current message is not copied. On a core-owned canvas, manual native ids are linked through an original record’s `delivery.as` (the run journal's record of a submission, kept unresolved while its turn went on, is settled cancelled as that turn ends and becomes the original), rather than written as a non-UUID link. Every app and headless resend belongs to the core mailbox (see [Sessions](sessions.md)). New rows and the sender notice are queued together, and delivery still waits for their durable commit.

**Command text in a `message`** (B16 C2, the API Spec's §5.6) is routed by the recipient's current connection's descriptor, the same for every caller, on the body as given, through the one decision the composer shares (`routeOf` in `src/shared/routing.ts`): a command its view answers in a declared panel (/resume, /mcp, /rewind) is refused, naming the operations that answer it; a command only its `continueIn` connection runs, or text starting with that connection's own shell prefix and a command after it where it takes shell commands, is refused, saying it runs there once you switch the agent's connection (`session.continueIn`, yours alone). A command the session offers itself runs as typed, except a bare-only continuation command typed bare; anything else, a path included, is delivered once it passes R1. A refusal keeps nothing. The run's own sends, `reply` text and Continue's `then` are not `message` and are not routed here.

Connections declaring `fileMentions` admit native file mentions only in your typed input: a token's `message` is refused, and automated canvas or other-party text is checked at dispatch, session start and again after startup before send, including after a fallback. The text-only selector and its boundary are in `src/shared/model/catalog.ts`; no path is resolved. A correction of a task containing a mention sends only your correction. Agent SDK delivery marks only another party's messages `client_composed: true`; your typing and run canvas text keep native input processing.

**The run's own sends** (B11 Design §3): on a canvas the core runs, each send of a task's attempt is a message too (`core/engines.ts`' run mailbox, `RunIO.mailbox`): origin `run`, from corrallm (for a correction you typed with a Retry, yours, origin `manual`, what you typed its display beside the held task it corrects, a hand-off's too), its `task` the attempt's owner, item and id, delivering under its own id (`delivery.as`), its body capped as any message's (the session gets the whole of it). The first to an agent after B11a's switch (never a correction you typed) carries the agent's handoff: `RunMailbox.record` returns the text its session is sent, framed as [Usage](usage.md) says, and the write recording it clears the carry; one never sent (its record not kept, or taken back before its session had it, `RunSendEnd.unsent`) leaves it for the next. It is recorded in the write that journals the run, the attempt linked to it (`TaskAttempt.messageId`), so its session gets it only once both are on disk; one whose record can't be kept is unresolved and never sent. Its turn's end settles it `replied`, with the turn's result, in the same write as what that end changed in the run; one taken back or never sent (a Stop, a refused shell-prefixed text) is withdrawn by corrallm. Delivery never delivers it, takes it back or kills it as a party's (`withdraw` refuses it: stop the run, or pause or kill its agent), makes no reply of it and tells no one of it (neither a wait nor a stall nor a cut-off notice); a restart leaves one out unresolved, its attempt restored uncertain. Delivery starting on a canvas (`Engines.deliver`, a cold start's `initialize`) cuts off only what the core last left out: a send the live run made while its canvas was held or passive, its attempt still running, stays the run's to settle as its turn ends. An OK's requested changes and a repeat's next try are no attempts: they stay submissions, which the journal keeps as your messages. The renderer's run sends as before until B11's cutover.

**Queue hand-offs** (B19 C1, Design §9): a queue's Message item for another agent is a queue hand-off, the run's work that delivery delivers. A message's purpose says which messages are hand-offs and their evidence (`Message.purpose`, `{ v: 1, type: 'handoff' | 'evidence' }`, `src/shared/model/purpose.ts`, migration 12): typed, versioned and minted by the core alone, never given by a caller (no operation takes one) and never inferred from a message's task, parties, origin or state; a message without one keeps its earlier meaning. The classifiers read it: `sentByRun` (the run's direct sends) excludes every message with a purpose; `runOwned` (`src/main/core/delivery/messages.ts`) is the run's direct sends and its hand-offs; `isQueueHandoff`, `isHandoffEvidence` and `isTurn` (`src/shared/model/messages.ts`) make a hand-off a turn and its evidence a record, never a turn and never active, whether or not the hand-off's row is still kept.

- **Recorded.** On a canvas the core runs, the run hands each one to delivery (`RunIO.handOffs`, `Delivery.handOff`): a message from the queue's agent to the item's recipient, kind `text`, origin `run`, purpose `handoff`, its body the item's words as written, its `task` a fresh attempt of the item, `pending`, linked to that attempt (`TaskAttempt.messageId`) in the run that the same write journals. Recording it claims no native turn, takes no carry and isn't `RunStore.sending`. Its owner's usage rule never holds it. As for any task's attempt, the run's gate admits it before it is recorded, against its recipient, as run work (`RunIO.admit`, so a switch it starts ends if the run stops), and reads its recipient's backend's usage rule then: warn tells the recipient's session, ask holds the item for you (`asking`, `AgentRun.usage`, its Needs hold with Go on and Wait for the reset), wait holds it until the window resets; delivery reads neither again (rules act between tasks). One longer than a message holds is never cut: its item is held for you (`too-long`). While its owner has `MAX_WAITING` messages waiting for its recipient none is recorded and the item waits unsent, no attempt made, until one goes (`RunStore.admissionChanged`). Room is checked against that exact sender and recipient, for every valid agent id. Each check tallies senders once per recipient’s waiting line, however many owners are waiting for room. A correction you type with a Retry of a hand-off is yours, sent by the run directly as before.
- **Delivered** once its record is on disk, as a party's message is: in its recipient's line, in the order it came, under every other hold of its recipient's (its pause or kill, a session that won't start, a held workspace, a mode that never asks, an exhausted backend; never the loop breaker, which counts no hand-off), and, as its run's work, while the run doesn't go (a restart's pause) or its owner is paused. It is journaled `delivering` under its own `delivery.as` (the first party send after a switch carries the recipient's handoff, taken then, never as it was recorded), flushed, rechecked and handed to the session behind corrallm's frame, `[corrallm] Task from agent "Lead" (from its queue: an agent, not the user; message <id>):`, its owner's name quoted as every party's is. Its words as written are checked against its recipient's connection as it is journaled and again before it is sent: a shell prefix or a file mention there declines it, withdrawn unsent, its item failed (`declined`) and held for you. Nor does it go while its run can't be kept on disk (a checkpoint too large or complex, `DeliveryDeps.unsaved`), as the run's own sends don't: it is unresolved, never sent, its item failed and held for you.
- **Its evidence.** Its turn's end settles it `replied`, with the turn's `TurnResult`, keeps the reply as its evidence (a record from the recipient to the queue's agent, kind `text`, origin `run`, purpose `evidence`, `replyTo` the hand-off, its `task`, the turn's result, `delivered`, its body capped as any reply's), and tells the run (`RunStore.handedOff`), all in one tick, so one write holds them: the item is judged as a message item's turn is, its whole reply what the queue's Ifs and waits read, never the capped body. No ordinary reply is made and the queue's agent is sent no turn of it; a `FAILED` line in it is data, and a native failure or cancellation holds the item for you whatever its text says. Only the attempt the run hands off now hears its end: a late end of an earlier one, or another's, finishes nothing.
- **The run's own.** No party takes a hand-off or its evidence back (`withdraw` refuses either as the run's); no sender is told of it (no hold, wait, stall or cut-off notice: the run holds its item); no loop counts it; and a stalled turn's Interrupt and resend retries its owner's attempt, as the run's direct sends' do. Stop and Run again take it back (`RunHandOffs.withdraw`, `Delivery.withdrawHandOff`): one still waiting is withdrawn by corrallm, nothing sent; one delivered is taken back, its turn interrupted, and its recipient's next message carries the note of it ("… was withdrawn after it reached you, …, when the run its queue is in was stopped."). Deleting its queue owner retires the attempt first and takes back its exact hand-off, including one still waiting for its recipient’s session to start. A Kill of either agent leaves the run's hold of the item and withdraws the hand-off as it withdraws a party's message between them, with the kill's note once it had reached its recipient. A hand-off whose attempt the run no longer runs is withdrawn as delivery next looks, or unresolved where the run holds no such attempt at all (its checkpoint and its rows disagree): it is never made again from its text.
- **Recovery.** Restoring a database snapshot leaves a pending hand-off unresolved and its run’s item uncertain, with no sender notice; a purpose this core cannot read leaves its row untouched. A pending hand-off stays pending across a quit, a close and a restart, still its attempt's: the run held or restored keeps the attempt running (`RunTasks.pending`), paused, and delivery sends it once the run resumes, under the same id. One `delivering` or delivered when the core stopped is cut off unresolved, never sent again, telling no one, its attempt restored uncertain (see [Run recovery](run-recovery.md)).

**Delivery points** (B19 C2, Design §9): while an agent's queue runs, a party's message to it (text, an ask, a taskless answer, a reply delivered as a turn, a queue hand-off) waits for the agent's next delivery point, which the run's interpreter owns (`RunStore.point`, a `DeliveryPoint`, read from the run as it is and never kept): **open** with no run going for it (none, a stopped one, a restart's pause), its queue done or stopped, at an authored wait (one inside a repeat too), or at a step deferred on its asks (B21 C7); a **gap** before each of its queue's items but an If (and a wait, which is a point of its own), and between a repeat's rounds once the round's condition is decided; **protected** within an item, an If's condition and steps, between a round's tasks and before its condition is decided (a message waits silently, no sender told: there is a point after it); and **held** at a delay, an OK, a task held for you or a condition waiting on you (`QueueHold`), which tells each sender once, in corrallm's words and with the hold's Needs item where you answer it (`hold/<agent>/<generation>/<item>`), never what the hold holds; leaving the hold and reaching another tells again. Your messages, corrallm's handoff requests and a task's continuations keep their lanes, past points: yours past the run's holds as ever, the request first in line, continuations after it (B21's frozen place). The run's interpreter and delivery share each agent's one slot, its next native turn (`RunStore.reserve` and `release`, synchronous, the core's alone, never persisted): delivery takes it as a party's message is journaled `delivering` and holds it until that turn ends (or the message never goes), and no task of the run's goes to the agent meanwhile, wherever its queue moved (it waits, `waiting`, at the item it would start); the run's own task holds it by being the agent's (`protected`). At each gap the run offers delivery the slot first, synchronously, before it starts the next item (`RunPoints.offer`, `Delivery.offer`): delivery takes it where something that waited for the agent as the gap opened is held by nothing but a check still to finish, and the queue waits there; once the turn ends (its reply or evidence kept first) the run offers the same gap again, and goes on once delivery declines it, or past it for good where the gap delivery took held nothing it could deliver after all. What a gap delivers is a finite prefix: only what was in the store's order as it opened (`MessageStore.end`), in the order it came; what arrives later waits for a later point, however much keeps arriving. A message that took its agent's slot keeps it through its delivering record's flush and its session's readiness: the run yields to it wherever its queue moves meanwhile (a Run started, a wait ended), its next task waiting for that turn (`RunStore.holds`); what hasn't taken the slot reads the point as delivery next looks, so the rest of a gap's prefix waits for a later point once the queue has moved into a protected stretch or a hold, never sent through an If or a hold. The barrier lifted, delivery is thawed before the run, so a gap the run opens as it goes on is offered to it. Nothing here sleeps or polls: the run's transitions offer the points, and delivery's checks read them as they look. An offer reads only its agent's line (`MessageStore.activeTo`, the active messages indexed by recipient as they change), never every message delivery acts on; a released slot moves the run only where its queue waited for it; and a point is read from the run's agents by id, never a walk of the canvas's nodes. An agent whose queue waits on its own outgoing hand-off is no delivery point (`RunStore.handingTo`): what is sent it waits until that item ends, a question its recipient asks it during the hand-off's turn too (taskless, as B21 C5 has it, the task being the queue's agent's, not the recipient's attempt; it stays open and reaches the agent at its next point, never as a continuation). So queues handing off to each other in a cycle wait for good: delivery finds each cycle as it looks, from the hand-offs it holds back alone (each pending hand-off whose recipient runs its own), and raises one Needs item for you, `cycle/<agent>` (the cycle's first agent by its UTF-8 bytes), kind `hold`, no agent named so no token reaches it, titled in corrallm's words with the agents' names, its one choice Stop, yours alone (`reply`, which stops the run as `run.stop` does, its hand-offs taken back); it goes as the cycle breaks.

**What the window shows of a hand-off, and what B24 builds on** (B19 X2 to X4; the window's half is in [the renderer](renderer.md)). The window reads hand-offs and records from the topics above, never from another path: a hand-off is a read-only row in its recipient's queue while it waits, is received or is withdrawn, from its sender, and a record is a line in its agent's window. Both are projections of rows the core keeps, so a closed window changes no delivery, and `serve` runs the same rules with no window (`src/main/core/b19-journey.test.ts` drives a hand-off, its evidence and your OK's record through the core alone, with `src/shared/model/test-b19.ts` building the rows that test checks the window's fixtures against). The seam B24 builds on is what B19 left ready, and nothing of B24's is here: (1) _The stored resolved recipient and `via`._ A message or ask to a manager is stored with the party it resolved to (you, until B24) and `display.via` or `ask.via` set to `manager`; B24 owns resolution from grants and ancestry, keeping one authoritative row and Needs item per ask (its id stable, first answer wins). B24 resolves the nearest eligible lead at admission and moves open manager-routed rows away from a lead that loses authority; rows already addressed to you stay with you, and a newly eligible lead does not take an open row from a still-eligible recipient. An ask already delivered leaves its old recipient a withdrawal notice, not a second answer path. Nothing in B19 reads `via` to decide delivery. (2) _A current-row router._ B24 must route an answer by the row as it is when the answer comes (`Asks` and the reply router read the row by id), so a row resolved again between its Need being drawn and answered is answered at its new destination, not the old one: no answer path may cache a recipient. (3) _A core-only traffic category._ Delivery's pump keeps its lanes apart (yours, corrallm's handoff request, a task's continuation, a party's text, a queue hand-off: `Delivery`'s `holds` and `#theirs`), and none is chosen by a caller's field, `kind: prompt` or a body that says it comes from a manager. B24's core-authored copies of routed native prompts and their withdrawal notices use typed `lead-copy` and `lead-notice` purposes in their own lane, after a handoff request and before continuations and ordinary traffic. They pass queue-only delay, OK and wait holds at a native turn boundary, while admission, usage, pause, kill and native waits still hold them. Ordinary messages and asks addressed through a manager keep the party lane; `via` grants no control priority. A hand-off remains outside the pair count. Withdrawal uses the authoritative message or attempt identity; B24 checks a prompt copy's current route again before sending it. (4) _No grant, privilege or automatic user action._ Leads, grants, fingerprints, escalation, deadlines and takeover are B24's; B19 persists none, and no token's `from` or task link makes it a lead.

**Images a connection takes** (B16 C3) are checked by one pure function (`imageRefusal` in `src/shared/images.ts`): the connection's declared kinds, per-image bytes and count, intersected with the platform's own ceilings (its kinds, 5 MiB an image, 20 images, 20 MiB in all), which a descriptor can narrow but never widen; null takes none. Bytes are decoded bytes, never base64 length; an image exactly at a limit passes, one byte or one image past refuses, naming the limit that applies. The core checks every route of yours that carries image bytes against the recipient's connection now: `message`, a hold's words (`reply` with `{ text, images }`, against the agent its answer goes to) and Continue (`session.continueIn`, against its destination, before anything switches or closes, its input kept for you to correct). At the send itself the connected driver checks the connection it runs (a message queued, or switched, since it was admitted): one that can't take its images is never sent, not as text alone either, but goes back, whole, to the head of its queue, with one notice. Delivery keeps its images with it and holds its agent's messages behind it, in order (its senders told, as for a session that won't start, `start/<agent>` in Needs), until the agent runs where they go or it is taken back: no retry sends it there again, however long the session runs. Once the agent runs where they go it is delivered once, whole. The manager refuses the same before a session's `send`. Tokens remain text-only (`human-text`). A native model's own refusal stays its adapter's.

A pending resend that needs images says so in its `display` (`requiresImages`, with how many). The bytes are live-only; if a restart lost them, delivery marks any message that requires them unresolved and tells its sender to paste the images again, never sending it as a text-only turn.

Terminal delivery does not wait for a fabricated startup hook. Claude Code's SessionStart omits permissions, and Codex's is lazy until a first turn. The shared Terminal `started` carries the trusted pre-launch default (read at launch, including for a session opened by a window), or the explicit start mode; native hook mode reports take precedence. If a Terminal still reports neither, hooks on give it a silent 30-second startup hold, with no unasking notice or Need until the scheduled bound expires. Hooks off or a bound passed produce unknown-running; the notice and Need say to check the terminal, switch to an asking mode or enable its hooks. New sessions get a new bound, and real unasking modes remain held. Yours still go.

A Terminal message queued behind startup, a folder-trust dialog or a user's draft has not reached the CLI. Its `user` receipt is emitted only after the text has been typed and Enter sent. Taking it back before submission returns `reached: false`, adds no withdrawal note, and leaves any notes it would have carried untold for the next message. The existing receipt handlers in delivery and `WithdrawalNotes` use that event for both delivery state and durable note acknowledgement.

The registered typed reply routes run holds, refusal Switch and native prompts through ReplyRouter and run-replies.ts, as well as proposals, file reviews and workspace cards. It checks current generation, caller reach, self, by and human-only choices before effects. message, withdraw and reply publish any changed messages, run, session summaries and Needs before returning their revision receipts; an accepted send still waits only for its durable pending row, never for the whole turn.

Directory readiness also holds delivery before any delivering record or native start. Delivery asks SessionManager for the agent's availability, tells each sender why a held workspace waits using the existing durable hold notice, and reschedules when provisioning, setup or Switch changes availability. The CLI default reader uses that agent's verified workspace, not the picked base; a base/user options read never establishes its native permissions. No hold releases pauses, usage limits or asking-mode checks.

Workspace readiness is a separate delivery hold, not a failed or missing session: provisioning, setup and a pending Switch keep the original message pending and tell its sender why once. A still-live old session does not clear that hold. Only a fresh readiness check releases it; availability changes wake it to check again. No message is marked delivered until its agent's verified active directory is ready.

A carrying run send keeps only its original task in the message record, so the queue owner cannot read the recipient’s handoff through its own sent-message history. The complete framed carry is live send data; the existing value-free carry marker still drives recovery.

The handoff store durably keeps the 64 newest accepted request turn ids per agent (`handoff.accepted_turns`, ids only), independently of message retention and the latest handoff; the shared session summary selector withholds those turns’ replies for every reader, including when an older native conversation is resumed after its request was pruned.

B13 X8 registers the owner's replies unchanged: `{ choice, feedback? }`, `{ answers: { [questionId]: { picked: string[] } | { text: string } } }` and `{ form: { action, values? } }`. A question reply is nonempty, bounded to sixteen ids and checked against every question as raised; picks and own words never mix. Prompt feedback and a hold's correction text are disjoint, and each handler refuses the other's shape. Not waiting returns the ordinary receipt with `outcome: 'dismissed'`, without a decision record or a native answer. All routes retain the owner's value-free decision records and the selector's reader-specific refusals.

The agent window and settings show a handoff tile with metadata only. Opening it reads `session.handoff` once and renders the exact text as plain text, with its recorded source, timestamp and byte count; no Markdown link or file action is inferred from it. The gear's independent save is one `agent.setHandoff`. Switch notices retain the core's words in structured transcripts and in Terminal's informational-notice bar. Unknown-action refusals retain the core's sentence and existing Skip/Stop choices through `reply`; the window offers no retry or go-on override.

Built-app coverage of the image hold (`e2e/connection-features.e2e.ts`, fakes only): a queued message with an image, its agent then switched to a connection that takes none, stays whole and unsent with one notice, and goes once, with its image, when the agent runs where images go; and the exact text of a continuation reaches the destination once. Token calls stay text-only, are refused the continuation and view-command operations (`src/main/core/session-control.test.ts`), and a token's message carrying panel or continuation text is refused by the core.
