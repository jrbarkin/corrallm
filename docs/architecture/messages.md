# Messages and delivery

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## Messages

What parties send a canvas's agents (API Spec §5, Core Server §5.9), served by the core from B6 (headless; the app from B11, whose composer's submissions its run journal keeps as your messages until then: [Run recovery](run-recovery.md)), each with how it came to be (`MessageOrigin`, `src/shared/model/messages.ts`: `manual`, typed by you; `party`, a party's or corrallm's; `run`, the run's own; `resend`, one you asked to send again), which the core records and no caller gives. A party is you, `corrallm`, `agent:<id>` or `outside:<name>` (`PartyId`, `src/shared/model/messages.ts`); no token is ever you. An agent's id is its node's: any text (line breaks too) of at most `MAX_NODE_ID` characters (`model/canvas.ts`), which a canvas file, the API's ids and a party id all hold to.

- **The store** (`core/delivery/messages.ts`): each canvas's messages in order, in memory and in the core's database, a row of `message` each (with how it came to be, `origin`, kept beside the message, never changed; what a view shows of it beside its body, `display`: the task it followed, the held task it corrected, the whole text of one whose body holds it cut (a submission longer than a message holds), its image count and whether it requires them, never their bytes; the message it resends, `resendOf`; the key of what a notice told, `told`; and the note its recipient must still be told of a withdrawal, `withdrawal`, in the same row), written with the database's next commit, and on disk once `durable()` resolves. The order is one every canvas's messages share (`MessageTable`): the core gives each place past the last the table's AUTOINCREMENT sequence gave, which every open raises past every place given before (from the clock: `store/open.ts`), so a cursor survives pruning, restarts and restores, and one naming a place whose row a crash cut off never skips the message given that place next (`end()` is the last place given, in any canvas). It keeps the newest `STORE_SETTLED_PER_PARTY` settled messages of each party within `STORE_BYTES`, and every pending and unresolved one (a party may have at most `MAX_WAITING` messages waiting for an agent: `message` refuses another), deleting the rows of those it drops. Beside them it keeps, in order and as each changes, those delivery still acts on (`active()`, `isActive`: waiting, being delivered, or a text to an agent whose turn goes on), which delivery and every needs pass read instead of every message kept. `watch` hears, by id, each message kept, changed or no longer kept (a staged one once revealed or undone): what `messages:<c>` publishes from.Each row is written as the message is in memory when its write runs, each column by name (so a newer corrallm's stay), and marked on disk only if it hasn't changed since; a write that fails leaves its rows to the next. It never throws: what it can't write it says on the console, but `durable` rejects then. Rows it doesn't read (a newer corrallm's kind or origin, a display it doesn't know) are left as they are. A store whose rows can't be read (the database couldn't be opened) starts empty, says why, and journals nothing (`durable` rejects once anything has changed), so nothing is sent without its record. What waited in a snapshot a damaged database was restored from may have gone since: the restore makes it unresolved and tells its sender (`store/restored.ts`).
- **Delivery** (`core/delivery/delivery.ts`): a message to an agent is delivered once the agent is idle (no turn, nothing asked, nothing queued in its session, nor on its way there from the run: `RunStore.sending`, a message whose record is on its way to disk first) and nothing holds it: its own or its group's pause (a kill too), a session that won't start (it stays first in line), a session that would act on a party's text unchecked (`#asking`: yours still go; you see it in Needs, `unasking/<agent>`, and its sender is told why): one that runs in a mode its adapter says never asks (`EngineCatalog.neverAsks`), or, on settings of its user's that are none of its modes (Codex's App Server on a custom policy), whose `started` event says they never ask (`asks: false`; `asksOf` reads Codex's: approvals `never`, or no sandbox with `on-failure`; `on-request` still asks about dangerous commands); an unreported non-Terminal holds messages until permissions are reported; one yet to start starts in its saved start mode if its connection starts in it (each asks), else in its CLI's own default: a session given no mode starts in the user's own default, which may never ask, so delivery reads it (`defaultAsks`: `session:options`' reader, in the canvas's project folder, its `defaults.asks`) once a session, again once that session ends, or with the next message sent RETRY_AFTER or more after a read that held its messages, and holds a party's message while it reads, while that default never asks, and while corrallm can't tell (a custom Codex policy it doesn't know, settings it couldn't read). A mode switched in either CLI’s terminal is seen only once the next hook fires. Codex’s permission_mode tells whether it asks, without distinguishing every sandbox preset; until that hook its last report stays in force. Claude Code’s managed (policy) settings are not read by `session:options`. Other holds are an exhausted usage backend (a turn hit its hard limit, held until its reset even without a rule), or its backend's usage rule (headless, a rule that asks waits for the reset, and one whose window's reset isn't known only warns, since nothing would read its usage again while messages waited; a usage hold the run set, `AgentRun.usage`, is that rule read now, so one a stopped run left, or whose window has reset, holds nothing), whether or not a run is going. A whole-run Stop, and the paused state a run restores in, hold only the run's own sends. A session that refused to start is tried again by the next message sent to its agent a minute or more after the refusal (`RETRY_AFTER`), which delivers the first in line; the sender's notice and the Needs item say so. A message goes only once its own record is on disk; one whose record can't reach it fails its `message` call and is unresolved, never sent; one whose delivering record can't reach it was never sent either, so it waits again, first in line, and nothing on its canvas is delivered until delivery tries again (`RECORD_RETRY`, a second on). Each is journaled delivering, with the id its session is sent it under (`delivery.as`), committed and flushed, then sent; the session's echo marks it delivered. A message may come with pasted images, live-only (its display says how many and that it requires them, so a restart that lost them leaves it unresolved, never sent without them), and a told key what admitted it finds it again by (`MessageStore.toldAs`: Continue in Terminal's `continued:<request>`, so a repeat of its request never sends it twice). Yours go past the run's holds into the session's queue, as typed; everything else is framed. A message's turn ending makes the agent's reply a message to its sender with the turn's `TurnResult`: a turn for an agent (its frame saying how the turn ended, when it didn't complete), a record for you or an outside party, and never answered by another reply. Each sender is told once (a `notice` from corrallm, keeping the key of what it told, so once across restarts too) when its message waits on a pause (naming who set it, and that only they or you can release it), a session that won't start, a mode that never asks, an exhausted backend or a usage window (every party whose messages wait, not only the first; told again once the agent holds again after it was released: a pause let go, a session that started, after a restart too, a mode that asks), when its turn waits for you (on its session's own prompt, or what its CLI asks in its terminal: never a hold of the run's, which holds no party's message), and when it ends withdrawn by someone else or cut off. A notice quotes a prompt's title (as a token may read it: B13 C11's selector) and an agent's name on one line, cut after 120 characters, and a reason after 1000: never a whole command. Closing the core, or a crash, leaves what was delivering, or delivered with no turn end, unresolved, never sent again. What waits for an agent no longer on the canvas (or from one) is withdrawn by corrallm, its sender told. Before its first party message, delivery starts the session without sending and rechecks the native started mode or asks; an unasking or unknown report holds the message, while yours still go. A Terminal carries its explicit start mode or trusted pre-launch default until a recognized native hook reports otherwise; one still unreported waits silently within its startup bound. While the core's shutdown barrier is prepared (`Delivery.freeze`, a quit or an update's restart), nothing starts being delivered, though what is delivering goes on and its reply comes back; a cancelled quit delivers what waited. Codex on-request can still ask about dangerous commands without a sandbox; on-failure without a sandbox and never remain unasking. Counting a session that can still ask as asking is the user's decision (Oct 24, the second review's G3), consistent with Claude Code's Auto mode, which also acts on most things unasked: delivery holds a party's text only for modes that never ask (Claude Code's Bypass permissions; Codex with approvals `never`, or no sandbox with `on-failure`).
- **Fallback** (B11a C3, C5: `src/main/core/fallback.ts`, see [Usage](usage.md)): before a party's message is handed over, delivery asks admission (never for yours, never while the agent is paused): where corrallm switches the agent's backend, the message waits, silently, and goes to the new endpoint under its own id and sender once the switch is committed, through every hold as any other's does; a fallback rule over its share that can't switch the agent holds it as ask does, and one a simulated reading only previews lets it go. No message is sent again: a sender whose message's turn failed on the limit gets that failed reply, as before, and, once the agent switches, one notice (`carries-on:<message>`): "‹agent› carries on with ‹target›; your message wasn't sent again."
- **Handoff requests** (B11a C7: `src/main/core/handoff.ts`, see [Usage](usage.md)): corrallm's request for an agent's handoff is a message from corrallm to the agent (`Delivery.ask`, kept with a told key starting `handoff:`, origin `party`), recorded before it is sent and first in line for its agent, ahead of every party's message waiting. What holds the agent holds it (its pause, a held workspace, a session that won't start, the barrier, an exhausted backend, a rule that asks or waits over its share, corrallm switching the agent), but never its asking mode (`unasking` doesn't list an agent for it), and it is never admitted as work; delivery withdraws it, by corrallm, as the handoff service says it is stale (not the agent's current request, its handoff off, its connection changed, its backend exhausted), so one left from before a restart is withdrawn as the canvas opens, never sent. Its turn's whole reply goes to the handoff service (`DeliveryDeps.handoff.replied`) in the same tick as the reply's record, which holds it capped as any reply. No notice is ever told of it (corrallm is its sender). The first party's message delivered to an agent after a switch carries the agent's handoff (`DeliveryDeps.handoff.carry`): taken as its delivering record is written, so that write clears the carry and keeps the message with a told key saying it carried one (`HANDOFF_CARRIED`, `carried:` and the switch, never the text: a party's message has no told key of its own), sent as corrallm's switch line, then the message as delivery frames it, then the handoff; one that never went (its record not written, taken back while journaled, held on its recheck, a session that won't start) leaves it for the next, its told key dropped. A message cut off unresolved (closing, or as delivery starts after a crash) keeps that key only where its session never had it (it was delivering, not delivered); as delivery starts, the handoff service gives each such carry back and drops the key, in the write that cuts them off (`DeliveryDeps.handoff.recover`). Yours never carry it.
- **Answers and who decided** (B11 C7: `src/main/core/run-replies.ts`, `src/main/core/decisions.ts`): the typed reply answers a run's hold with one of its choices, or words where it takes them (an OK's changes, a problem's or a repeat's next try: `{ text, images? }`, or `{ choice: 'retry' | 'more', text }`), decided at once (RunStore.decide) and recorded in the same write as the run; a refusal's Switch runs `session.continueIn` as the same caller and the run then sends the held attempt there, once. A hold a pause holds is refused, naming whose pause (no answer releases one, R9); one of a run not going is unavailable. The old session cards still send `{ permission, feedback? }`, string/array `{ answers }`, `{ plan }` or `{ form: { action, values? } }` through the temporary owner bridge; X10 converts those consumers and X11 removes their variants. Owner prompts use the registered C1 shapes below. A Terminal's described ask is answered in its terminal. A prompt's answer is recorded as being made, on disk, before its CLI is told, and told only if the session that asked it (the generation its id names) still runs: one started since, though it asks by the same native id, is another prompt, so the record is withdrawn and the answer a conflict; the CLI's answer awaited; shown answered (`SessionStore.answered`) only once the CLI took it. One the CLI refused leaves the prompt waiting and its record withdrawn, saying so; one a crash cut off is unresolved as the canvas's messages load again, never answered again, its record saying so. Each decision is a `settled` record from corrallm to you, `by` the party that decided, its body what kind of answer it was (never the words, values, answers or feedback given; a session's prompt's in the core's words from its kind, what was chosen and the agent's name, as the owner's below, never its tool's input, a plan's mode or an MCP server's name), its told key `decided:<need>#<uuid>`, so the latest of an item (`decidedOf`) names who settled it to a second answer, across restarts too.
- **Prompts the core owns** (B13 C3: `src/main/core/prompts/owner.ts`; raised as [Sessions](sessions.md) says): each waits in Needs as yours, `prompt/<agent>/<generation>/<PromptId>`, with its choices (each marked where only you may pick it, every one of a prompt only you may answer, each with its hint, its effects where its adapter can tell them, whether it takes words and whether it ends the turn) and its own fields beside the generic ones (`prompt`: its PromptId, kind, when it was raised, its summary and reason, its subject, a plan's first lines, whether it was cut, why only you may answer it); a form's title is the core's for everyone (the MCP server that asks, by the name it is configured under where its adapter says which, else its agent's CLI, asks you to fill in a form, or to open a link), never the server's words, which may hold its link. What each reader sees of it is the one selector's (B13 C11, `src/shared/model/prompt-views.ts`): a token that reaches its agent (and a parent, its team's, through Needs alone) sees it without choices or form, a form without its summary or reason, a terminal's wait its report alone describes without its detail (what the terminal's screen shows), and every question whole but never an answer; a token's reply to it is refused in those words; the counts `agents` and the summaries give add the prompts the owner lists, once each. So is the title of an MCP server's request among the events B13 replaces, for everyone (`mcpRequestTitle` in `src/shared/model/words.ts`), and a token's transcript gives that request only those words: its message, form and link left out. A prompt its session also shows as one of the events B13 replaces (until X10: [Sessions](sessions.md)) isn't listed: the old event's item stands for it, and an answer to that item is translated by its session and answered through the owner, as below. The reply router's prompt handler asks the owner first, which finds the PromptId in the canvas's live index (never by the id's text: the agent and generation must be the occurrence's) and answers as C3 sets out: it is yours alone (no token answers as you, R3; never its own agent, R6), the answer is checked against the prompt as raised (P4's `{ choice, feedback? }`, `{ answers }` keyed by question id with `{ picked }` or `{ text }`, or `{ form }`; never `text`, images, `permission` or `plan`, and nothing for a prompt answered in its terminal but Not waiting, below), then the prompt is reserved with nothing awaited (a second reply meanwhile is a conflict naming who answers); its `delivering` record is written and flushed (a failed flush gives nothing and reopens it); it is checked again (still reserved, its generation still the agent's: an end meanwhile wins, the record withdrawn, the reply a conflict saying how it ended); past `noReturn` it is handed synchronously to the session that raised it, never one looked up again; then it is settled and the record landed. A session's refusal withdraws the record and leaves the prompt open, unless the session ended it as it refused. An end after the handoff is ignored. A crash between the record and its landing leaves the record unresolved as the canvas's messages load, never given again: open prompts aren't persisted, so a core started again has none, and a reply to an old one is told what its record says. Answering never starts or resumes a session. The record's words are the core's, from the prompt's kind, its subject's type, the choice's hint and the agent's name ("You allowed Builder’s command once.", "You answered Builder’s questions (secret).": `decisionWords` in `src/main/core/decisions.ts`): never a title, label, command, path, plan, feedback, answer or value. Beside them it keeps what was decided, typed (`Message.settled`, `src/shared/model/settled.ts`, schema 7, B13 §9.2 C9): `{ v: 1, need, prompt: { id, kind, subject? }, outcome, secret? }`, the subject by its type alone and only where the protocol names it (an adapter's extension, none), the outcome a choice's value and hint, how many questions were answered, or a form's action, `secret` where an answer was; never a label (labels are untrusted and can quote a command), title, summary, reason, command, path, plan, feedback, answer or value. It is written with the record's row and never changed after, a crash's unresolved record keeping it; records of decisions are to you, so no token reads one. Withdrawn, answered in the terminal and dismissed are never records. A later reply to one that ended is told how: settled (by its record), withdrawn, answered in its terminal, or said not to be waiting. What no longer waits is in no token's reach, so a token's reply to it is not found; were one in reach, it would be told only who settled it, never how. Not waiting (B13 C7) is the core's own choice, offered only on a terminal's wait raised from its CLI's report alone (no subject, choice, question or plan: never one a hook described, the trust screen, or the core's stand-in for one it couldn't show), and only you may make it (it is marked so): `{ choice: 'not-waiting' }`, nothing more, before a terminal's answers are refused. It is settled dismissed by you at once, past `noReturn`, with no record (`outcome: 'dismissed'`), and its session is told to stop raising that observation until a distinct wait ([Sessions](sessions.md)); its CLI is told nothing, and nothing that holds a message for the agent changes.
- **Withdrawal after receipt:** `withdraw` returns `{ reached, interrupted }`, based on the session's receipt at the take-back request, or its end if it already arrived, rather than a delivering record (which may still be on disk or in the session's queue). It waits for any immediate withdrawal's durable flush, never for a native turn's end; a received message is withdrawn with its note when that end arrives. A second preempt or queued drain therefore cannot hold the canvas's lanes on a hung turn. The CLI's history keeps a message it received, and work already done stays. Every interrupt stops the commands its turn started where its connection supports it, before another message is delivered (see the Codex connection's command cleanup and its bounded failures). A take-back, Kill of the run's sends or of a native turn with no stored message, and an ordinary session interrupt all use that same scope. With the next message delivered to that agent, from any party or the user, corrallm includes a note inside the same `[corrallm]` frame: the message's id and sender, that its sender withdrew it after it reached the agent and its turn was interrupted, not to carry out what it asked unless someone asks again, and that anything already done is left as it is. A kill (`run.kill`, of an agent or a group) leaves the same note for each message it takes back after its recipient received it, whichever end was killed: in place of its sender's withdrawal, whom the kill killed (the recipient, or else its sender) and who killed it, named as `core/parties.ts`' `quotedParty` names a party (the user, or anyone else's name in quotes; "at your own request" where the agent killed itself). Every name in a note, frame, refusal or notice is capped before escaping quotes, backslashes, newlines and other control characters (`core/parties.ts`, `quotedName`), so a name cannot close its quotes or start a new frame line. A note quotes nothing of the canvas but parties' names, capped as notices cap them: never a body, a group's name or a queue's text. The run's own sends (queue steps and messages) leave none: they are no messages of the store, the run holds each task a kill interrupted in Needs you, cancelled, for the user to inspect, resolve or retry, and a note could name such a task only by its canvas text. Untold notes are kept with the withdrawn messages, across restarts and log pruning, until the CLI echoes the message carrying them. Several withdrawals are named together; one taken off the queue before receipt adds no note. A note never starts a turn by itself, except before an unframed slash command (typed by the user or sent by a queue step) or a user message that starts with any catalog shell prefix: then a separate framed note goes first, its turn ends, and the command goes alone unchanged. The command's turn includes its note's: a Stop, a Kill, a take-back or a stalled turn's Interrupt of it (an interrupt of the agent's session, in the app or the core, after the command was sent and before the note's turn ended) interrupts the note's turn, and the command is then never sent, its turn ending `cancelled`, `taken-back` (a take-back's withdrawal `reached: false`, adding no note), while the note counts as told only if the CLI echoed it; a stalled note's Interrupt and resend lets the command go as the note's turn ends. The transcript shows the text echoed by the CLI, including these notes; a separate note appears before the command, and resumed history keeps what the agent was told. The note asks the agent not to act; it cannot force it or undo work. Taking back a live native turn returns once interruption is requested, without waiting for that turn to end; `interrupted` then says interruption was requested, not that the native end arrived. Its final withdrawn state and receipt-based note are recorded together when the turn ends. A repeated take-back shares that request. Waiting and unreached messages still acknowledge only after their immediate withdrawal is durable, including T4’s WAL-flush failure handling.
- **Operations** (`core/ops/conversation.ts`, `session.ts`, `run.ts`, `wait.ts`, `reply.ts`): `wait` (outside tokens only: see Headless), `message` (to an agent: a token's at most `MAX_MESSAGE_BYTES` of UTF-8 and text only, rule `human-text`; yours, your composer's, up to `MAX_MESSAGE_LENGTH` characters with live images the recipient's connection takes, admitted `manual`), `reply` (`{ to: NeedId, answer: { choice } }`: a proposal, file review, stalled turn, worktree setup card or workspace change, yours alone, R3, through the one reply router, `src/main/core/replies.ts`; returns how it was settled, with the proposer's record's id for a proposal and a new review's id as `raised` if the file changed again; a second answer to a settled item is a conflict naming who settled it; B11 C7's registered typed reply answers a run's holds and a session's prompts too: see below), `withdraw` (your own message: off the queue, or its turn interrupted; you may take back anyone's still waiting; no canvas needed, the message says which; it returns once take-back is requested and any immediate withdrawal is on disk, so a restart never delivers what it reported withdrawn; a received turn ends separately, and an immediate withdrawal that can't be written fails `unavailable`, saying the message is taken back now but may not survive a restart, as `run.kill` does), `messages` (the caller's own, after a cursor; you: all), `needs` (yours with their choices; a token sees yours on the agents it reaches as B13 C11's selector says, without them or their forms, an MCP server's link among them, and an agent its team's prompts too; each item's id is unique on its canvas: `hold/<agent>/<generation>/<item>`, `start/<agent>` for a session that won't start, `unasking/<agent>` for one that would act without asking (its mode never asks, its CLI's default never does, or corrallm can't tell), `limited/<agent>` for an exhausted usage backend, `stalled/<agent>` for a silent turn, `prompt/<agent>/<generation>/<prompt>`, `setup/<workspace>/<generation>` for a worktree's setup, `rebind/<owner>/<generation>` for a workspace change, the agent's id escaped; a hold's generation fingerprints what it is, a prompt's is its session's, so an answer to one asked before never answers the one asked now), `agents`, `status`, `session.get`, `session.transcript` (paged by entry; through B13 C11's selector, as its topic: an MCP server's request given a token only in the core's words, as `needs` titles it, never its link, form or message, and a token's prompt entry without its answer (a question's, a permission's, a plan's or a form's action), feedback or an "always" choice's label, whether it was withdrawn kept; it and `messages` end a page early rather than pass `MAX_PAGE_BYTES` of JSON; a transcript's first entry, of whatever kind, is cut to fit and marked `cut` when it alone wouldn't (a diff's last lines first, then its texts, then its lists), while `messages` gives whole messages, each at most `MAX_MESSAGE_BYTES` of text), `session.interrupt`, the whole run's `run.start`, `run.stop` (which holds only the run's own sends, never a party's message: delivery holds those only for an agent's or a group's pause), `run.resume` and `run.goOn` (see [Core](core.md)), and `run.pause`, `run.kill` (which takes back what was sent to or from the agent, its recipient told of what had reached it: see Withdrawal after receipt) and `run.unpause`, on an agent or a group, each taking effect at once and returning once it is on disk (the canvas's run committed, and for a kill, in the same commit, what it took back at once; a delivered turn is withdrawn when its end arrives, without holding the kill; one that can't be fails `unavailable`, saying the change is in place but may not survive a restart), each pause stamped with the party that set it: a token releases only its own (rule `sticky`, R9: one whose release would let go of no pause that holds its target is refused, naming who set those), you any; `run.unpause` returns the pauses that still hold its target (another party's on it, or any on a group it is in: `RunStore.holding`), worded by `core/parties.ts`.

Withdrawal durability includes the WAL flush, not just a SQL commit visible to another reader. A failed flush fails the store closed; the operation returns `unavailable` even though the in-memory withdrawal has already taken effect.

An explicit stalled-turn resend keeps the original and its cancelled reply. Its new message has the same sender, recipient and body, a new UUID, origin `resend` and `resendOf` naming the original (schema 4; before it, a `resend:` told key and `replyTo`, which migration 4 moved): never `replyTo`, so nothing that reads replies (a `wait` for a message, serve's log, a reply's framing, a reader of `messages`) takes it for one. The original receives a once-only corrallm notice naming the new id and the user who requested it (its `resent:` told key, its `replyTo` the original, as a record about it). A message is resent once (`MessageStore.resent`), across restarts too; its origin makes even your resend respect pauses, usage and asking holds, which only `manual` goes past. A withdrawn or no-longer-current message is not copied. On a core-owned canvas, manual native ids are linked through an original record’s `delivery.as` (the run journal's record of a submission, kept unresolved while its turn went on, is settled cancelled as that turn ends and becomes the original), rather than written as a non-UUID link. Every app and headless resend belongs to the core mailbox (see [Sessions](sessions.md)). New rows and the sender notice are queued together, and delivery still waits for their durable commit.

Connections declaring `fileMentions` admit native file mentions only in your typed input: a token's `message` is refused, and automated canvas or other-party text is checked at dispatch, session start and again after startup before send, including after a fallback. The text-only selector and its boundary are in `src/shared/model/catalog.ts`; no path is resolved. A correction of a task containing a mention sends only your correction. Agent SDK delivery marks only another party's messages `client_composed: true`; your typing and run canvas text keep native input processing.

**The run's own sends** (B11 Design §3): on a canvas the core runs, each send of a task's attempt is a message too (`core/engines.ts`' run mailbox, `RunIO.mailbox`): origin `run`, from corrallm (from the queue's agent for a hand-off to another agent; for a correction you typed with a Retry, yours, origin `manual`, what you typed its display beside the held task it corrects), its `task` the attempt's owner, item and id, delivering under its own id (`delivery.as`), its body capped as any message's (the session gets the whole of it). The first to an agent after B11a's switch (never a correction you typed) carries the agent's handoff: `RunMailbox.record` returns the text its session is sent, framed as [Usage](usage.md) says, and the write recording it clears the carry; one never sent (its record not kept, or taken back before its session had it, `RunSendEnd.unsent`) leaves it for the next. It is recorded in the write that journals the run, the attempt linked to it (`TaskAttempt.messageId`), so its session gets it only once both are on disk; one whose record can't be kept is unresolved and never sent. Its turn's end settles it `replied`, with the turn's result, in the same write as what that end changed in the run; one taken back or never sent (a Stop, a refused shell-prefixed text) is withdrawn by corrallm. Delivery never delivers it, takes it back or kills it as a party's (`withdraw` refuses it: stop the run, or pause or kill its agent), makes no reply of it and tells no one of it (neither a wait nor a stall nor a cut-off notice); a restart leaves one out unresolved, its attempt restored uncertain. Delivery starting on a canvas (`Engines.deliver`, a cold start's `initialize`) cuts off only what the core last left out: a send the live run made while its canvas was held or passive, its attempt still running, stays the run's to settle as its turn ends. An OK's requested changes and a repeat's next try are no attempts: they stay submissions, which the journal keeps as your messages. The renderer's run sends as before until B11's cutover.

A pending resend that needs images says so in its `display` (`requiresImages`, with how many). The bytes are live-only; if a restart lost them, delivery marks any message that requires them unresolved and tells its sender to paste the images again, never sending it as a text-only turn.

Terminal delivery does not wait for a fabricated startup hook. Claude Code's SessionStart omits permissions, and Codex's is lazy until a first turn. The shared Terminal `started` carries the trusted pre-launch default (read at launch, including for a session opened by a window), or the explicit start mode; native hook mode reports take precedence. If a Terminal still reports neither, hooks on give it a silent 30-second startup hold, with no unasking notice or Need until the scheduled bound expires. Hooks off or a bound passed produce unknown-running; the notice and Need say to check the terminal, switch to an asking mode or enable its hooks. New sessions get a new bound, and real unasking modes remain held. Yours still go.

A Terminal message queued behind startup, a folder-trust dialog or a user's draft has not reached the CLI. Its `user` receipt is emitted only after the text has been typed and Enter sent. Taking it back before submission returns `reached: false`, adds no withdrawal note, and leaves any notes it would have carried untold for the next message. The existing receipt handlers in delivery and `WithdrawalNotes` use that event for both delivery state and durable note acknowledgement.

The registered typed reply routes run holds, refusal Switch and native prompts through ReplyRouter and run-replies.ts, as well as proposals, file reviews and workspace cards. It checks current generation, caller reach, self, by and human-only choices before effects. message, withdraw and reply publish any changed messages, run, session summaries and Needs before returning their revision receipts; an accepted send still waits only for its durable pending row, never for the whole turn.

Directory readiness also holds delivery before any delivering record or native start. Delivery asks SessionManager for the agent's availability, tells each sender why a held workspace waits using the existing durable hold notice, and reschedules when provisioning, setup or Switch changes availability. The CLI default reader uses that agent's verified workspace, not the picked base; a base/user options read never establishes its native permissions. No hold releases pauses, usage limits or asking-mode checks.

Workspace readiness is a separate delivery hold, not a failed or missing session: provisioning, setup and a pending Switch keep the original message pending and tell its sender why once. A still-live old session does not clear that hold. Only a fresh readiness check releases it; availability changes wake it to check again. No message is marked delivered until its agent's verified active directory is ready.

A carrying run send keeps only its original task in the message record, so the queue owner cannot read the recipient’s handoff through its own sent-message history. The complete framed carry is live send data; the existing value-free carry marker still drives recovery.

The handoff store durably keeps the 64 newest accepted request turn ids per agent (`handoff.accepted_turns`, ids only), independently of message retention and the latest handoff; the shared session summary selector withholds those turns’ replies for every reader, including when an older native conversation is resumed after its request was pruned.

B13 X8 registers the owner's replies unchanged: `{ choice, feedback? }`, `{ answers: { [questionId]: { picked: string[] } | { text: string } } }` and `{ form: { action, values? } }`. A question reply is nonempty, bounded to sixteen ids and checked against every question as raised; picks and own words never mix. Prompt feedback and a hold's correction text are disjoint, and each handler refuses the other's shape. Not waiting returns the ordinary receipt with `outcome: 'dismissed'`, without a decision record or a native answer. All routes retain the owner's value-free decision records and the selector's reader-specific refusals.
