# Messages and delivery

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## Messages

What parties send a canvas's agents (API Spec §5, Core Server §5.9), served by the core from B6 (headless; the app from B11, whose composer's submissions its run journal keeps as your messages until then: [Run recovery](run-recovery.md)), each with how it came to be (`MessageOrigin`, `src/shared/model/messages.ts`: `manual`, typed by you; `party`, a party's or corrallm's; `run`, the run's own; `resend`, one you asked to send again), which the core records and no caller gives. A party is you, `corrallm`, `agent:<id>` or `outside:<name>` (`PartyId`, `src/shared/model/messages.ts`); no token is ever you. An agent's id is its node's: any text (line breaks too) of at most `MAX_NODE_ID` characters (`model/canvas.ts`), which a canvas file, the API's ids and a party id all hold to.

- **The store** (`core/delivery/messages.ts`): each canvas's messages in order, in memory and in the core's database, a row of `message` each (with how it came to be, `origin`, kept beside the message, never changed; what a view shows of it beside its body, `display`: the task it followed, the held task it corrected, the whole text of one whose body holds it cut (a submission longer than a message holds), its image count and whether it requires them, never their bytes; the message it resends, `resendOf`; the key of what a notice told, `told`; and the note its recipient must still be told of a withdrawal, `withdrawal`, in the same row), written with the database's next commit, and on disk once `durable()` resolves. The order is one every canvas's messages share (`MessageTable`): the core gives each place past the last the table's AUTOINCREMENT sequence gave, which every open raises past every place given before (from the clock: `store/open.ts`), so a cursor survives pruning, restarts and restores, and one naming a place whose row a crash cut off never skips the message given that place next (`end()` is the last place given, in any canvas). It keeps the newest `STORE_SETTLED_PER_PARTY` settled messages of each party within `STORE_BYTES`, and every pending and unresolved one (a party may have at most `MAX_WAITING` messages waiting for an agent: `message` refuses another), deleting the rows of those it drops. Beside them it keeps, in order and as each changes, those delivery still acts on (`active()`, `isActive`: waiting, being delivered, or a text to an agent whose turn goes on), which delivery and every needs pass read instead of every message kept. Each row is written as the message is in memory when its write runs, each column by name (so a newer corrallm's stay), and marked on disk only if it hasn't changed since; a write that fails leaves its rows to the next. It never throws: what it can't write it says on the console, but `durable` rejects then. Rows it doesn't read (a newer corrallm's kind or origin, a display it doesn't know) are left as they are. A store whose rows can't be read (the database couldn't be opened) starts empty, says why, and journals nothing (`durable` rejects once anything has changed), so nothing is sent without its record. What waited in a snapshot a damaged database was restored from may have gone since: the restore makes it unresolved and tells its sender (`store/restored.ts`).
- **Delivery** (`core/delivery/delivery.ts`): a message to an agent is delivered once the agent is idle (no turn, nothing asked, nothing queued in its session, nor on its way there from the run: `RunStore.sending`, a message whose record is on its way to disk first) and nothing holds it: its own or its group's pause (a kill too), a session that won't start (it stays first in line), a session that would act on a party's text unchecked (`#asking`: yours still go; you see it in Needs, `unasking/<agent>`, and its sender is told why): one that runs in a mode its adapter says never asks (`EngineCatalog.neverAsks`), or, on settings of its user's that are none of its modes (Codex's App Server on a custom policy), whose `started` event says they never ask (`asks: false`; `asksOf` reads Codex's: approvals `never`, or no sandbox with `on-failure`; `on-request` still asks about dangerous commands); one that says neither holds messages until permissions are reported, even if a startup mode was requested; one yet to start starts in its saved start mode if its connection starts in it (each asks), else in its CLI's own default: a session given no mode starts in the user's own default, which may never ask, so delivery reads it (`defaultAsks`: `session:options`' reader, in the canvas's project folder, its `defaults.asks`) once a session, again once that session ends, or with the next message sent RETRY_AFTER or more after a read that held its messages, and holds a party's message while it reads, while that default never asks, and while corrallm can't tell (a custom Codex policy it doesn't know, settings it couldn't read). A mode switched in either CLI’s terminal is seen only once the next hook fires. Codex’s permission_mode tells whether it asks, without distinguishing every sandbox preset; until that hook its last report stays in force. Claude Code’s managed (policy) settings are not read by `session:options`. Other holds are an exhausted usage backend (a turn hit its hard limit, held until its reset even without a rule), or its backend's usage rule (headless, a rule that asks waits for the reset, and one whose window's reset isn't known only warns, since nothing would read its usage again while messages waited; a usage hold the run set, `AgentRun.usage`, is that rule read now, so one a stopped run left, or whose window has reset, holds nothing), whether or not a run is going. A whole-run Stop, and the paused state a run restores in, hold only the run's own sends. A session that refused to start is tried again by the next message sent to its agent a minute or more after the refusal (`RETRY_AFTER`), which delivers the first in line; the sender's notice and the Needs item say so. A message goes only once its own record is on disk; one whose record can't reach it fails its `message` call and is unresolved, never sent; one whose delivering record can't reach it was never sent either, so it waits again, first in line, and nothing on its canvas is delivered until delivery tries again (`RECORD_RETRY`, a second on). Each is journaled delivering, with the id its session is sent it under (`delivery.as`), committed and flushed, then sent; the session's echo marks it delivered. Yours go past the run's holds into the session's queue, as typed; everything else is framed. A message's turn ending makes the agent's reply a message to its sender with the turn's `TurnResult`: a turn for an agent (its frame saying how the turn ended, when it didn't complete), a record for you or an outside party, and never answered by another reply. Each sender is told once (a `notice` from corrallm, keeping the key of what it told, so once across restarts too) when its message waits on a pause (naming who set it, and that only they or you can release it), a session that won't start, a mode that never asks, an exhausted backend or a usage window (every party whose messages wait, not only the first; told again once the agent holds again after it was released: a pause let go, a session that started, after a restart too, a mode that asks), when its turn waits for you (on its session's own prompt, or what its CLI asks in its terminal: never a hold of the run's, which holds no party's message), and when it ends withdrawn by someone else or cut off. A notice quotes a prompt's title and an agent's name on one line, cut after 120 characters, and a reason after 1000: never a whole command. Closing the core, or a crash, leaves what was delivering, or delivered with no turn end, unresolved, never sent again. What waits for an agent no longer on the canvas (or from one) is withdrawn by corrallm, its sender told. Before its first party message, delivery starts the session without sending and rechecks the native started mode or asks; an unasking or unknown report holds the message, while yours still go. A session that has not reported permissions waits for a report, even if an asking startup mode was requested. Codex on-request can still ask about dangerous commands without a sandbox; on-failure without a sandbox and never remain unasking.
- **Withdrawal after receipt:** `withdraw` returns `{ reached, interrupted }`, based on the session's receipt and how the turn ended, rather than a delivering record (which may still be on disk or in the session's queue). While a withdrawal awaits that native turn's end, other agents' lanes on its canvas remain free for messages, pauses and kills. The CLI's history keeps a message it received, and work already done stays. Every interrupt stops the commands its turn started where its connection supports it, before another message is delivered (see the Codex connection's command cleanup and its bounded failures). A take-back, Kill of the run's sends or of a native turn with no stored message, and an ordinary session interrupt all use that same scope. With the next message delivered to that agent, from any party or the user, corrallm includes a note inside the same `[corrallm]` frame: the message's id and sender, that its sender withdrew it after it reached the agent and its turn was interrupted, not to carry out what it asked unless someone asks again, and that anything already done is left as it is. A kill (`run.kill`, of an agent or a group) leaves the same note for each message it takes back after its recipient received it, whichever end was killed: in place of its sender's withdrawal, whom the kill killed (the recipient, or else its sender) and who killed it, named as `core/parties.ts`' `quotedParty` names a party (the user, or anyone else's name in quotes; "at your own request" where the agent killed itself). Every name in a note, frame, refusal or notice is capped before escaping quotes, backslashes, newlines and other control characters (`core/parties.ts`, `quotedName`), so a name cannot close its quotes or start a new frame line. A note quotes nothing of the canvas but parties' names, capped as notices cap them: never a body, a group's name or a queue's text. The run's own sends (queue steps and messages) leave none: they are no messages of the store, the run holds each task a kill interrupted in Needs you, cancelled, for the user to inspect, resolve or retry, and a note could name such a task only by its canvas text. Untold notes are kept with the withdrawn messages, across restarts and log pruning, until the CLI echoes the message carrying them. Several withdrawals are named together; one taken off the queue before receipt adds no note. A note never starts a turn by itself, except before an unframed slash command (typed by the user or sent by a queue step) or a user message that starts with any catalog shell prefix: then a separate framed note goes first, its turn ends, and the command goes alone unchanged. The transcript shows the text echoed by the CLI, including these notes; a separate note appears before the command, and resumed history keeps what the agent was told. The note asks the agent not to act; it cannot force it or undo work.
- **Operations** (`core/ops/conversation.ts`, `session.ts`, `run.ts`, `wait.ts`, `reply.ts`): `wait` (outside tokens only: see Headless), `message` (to an agent, at most `MAX_MESSAGE_BYTES` of UTF-8), `reply` (`{ to: NeedId, answer: { choice } }`: a proposal, file review or stalled turn, yours alone, R3; returns how it was settled, with the proposer's record's id for a proposal and a new review's id as `raised` if the file changed again; a second answer to a settled proposal is a conflict), `withdraw` (your own message: off the queue, or its turn interrupted; you may take back anyone's still waiting; no canvas needed, the message says which), `messages` (the caller's own, after a cursor; you: all), `needs` (yours with their choices; a token sees yours on the agents it reaches without them or their forms, an MCP server's link among them, and an agent its team's prompts too; each item's id is unique on its canvas: `hold/<agent>/<item>`, `start/<agent>` for a session that won't start, `unasking/<agent>` for one that would act without asking (its mode never asks, its CLI's default never does, or corrallm can't tell), `limited/<agent>` for an exhausted usage backend, `stalled/<agent>` for a silent turn, `prompt/<agent>/<prompt>`, the agent's id escaped), `agents`, `status`, `session.get`, `session.transcript` (paged by entry; an MCP server's link left out for a token, as in `needs`; it and `messages` end a page early rather than pass `MAX_PAGE_BYTES` of JSON; a transcript's first entry, of whatever kind, is cut to fit and marked `cut` when it alone wouldn't (a diff's last lines first, then its texts, then its lists), while `messages` gives whole messages, each at most `MAX_MESSAGE_BYTES` of text), `session.interrupt`, and `run.pause`, `run.kill` (which takes back what was sent to or from the agent, its recipient told of what had reached it: see Withdrawal after receipt) and `run.unpause`, on an agent or a group, each taking effect at once and returning once it is on disk (the canvas's run committed, and for a kill, in the same commit, what it took back at once, one being delivered once its interrupted turn ends; one that can't be fails `unavailable`, saying the change is in place but may not survive a restart), each pause stamped with the party that set it: a token releases only its own (rule `sticky`, R9: one whose release would let go of no pause that holds its target is refused, naming who set those), you any; `run.unpause` returns the pauses that still hold its target (another party's on it, or any on a group it is in: `RunStore.holding`), worded by `core/parties.ts`.

An explicit stalled-turn resend keeps the original and its cancelled reply. Its new message has the same sender, recipient and body, a new UUID, origin `resend` and `resendOf` naming the original (schema 4; before it, a `resend:` told key and `replyTo`, which migration 4 moved): never `replyTo`, so nothing that reads replies (a `wait` for a message, serve's log, a reply's framing, a reader of `messages`) takes it for one. The original receives a once-only corrallm notice naming the new id and the user who requested it (its `resent:` told key, its `replyTo` the original, as a record about it). A message is resent once (`MessageStore.resent`), across restarts too; its origin makes even your resend respect pauses, usage and asking holds, which only `manual` goes past. A withdrawn or no-longer-current message is not copied. On a core-owned canvas, manual native ids are linked through an original record’s `delivery.as` (the run journal's record of a submission, kept unresolved while its turn went on, is settled cancelled as that turn ends and becomes the original), rather than written as a non-UUID link. Window-owned manual resends stay with the renderer’s engine and use submission-checkpoint `retryOf` links instead; they do not open a core run or create message-store copies (see [Sessions](sessions.md)). New rows and the sender notice are queued together, and delivery still waits for their durable commit.

**The run's own sends** (B11 Design §3): on a canvas the core runs, each send of a task's attempt is a message too (`core/engines.ts`' run mailbox, `RunIO.mailbox`): origin `run`, from corrallm (from the queue's agent for a hand-off to another agent; for a correction you typed with a Retry, yours, origin `manual`, what you typed its display beside the held task it corrects), its `task` the attempt's owner, item and id, delivering under its own id (`delivery.as`), its body capped as any message's (the session gets the whole of it). It is recorded in the write that journals the run, the attempt linked to it (`TaskAttempt.messageId`), so its session gets it only once both are on disk; one whose record can't be kept is unresolved and never sent. Its turn's end settles it `replied`, with the turn's result, in the same write as what that end changed in the run; one taken back or never sent (a Stop, a refused shell-prefixed text) is withdrawn by corrallm. Delivery never delivers it, takes it back or kills it as a party's (`withdraw` refuses it: stop the run, or pause or kill its agent), makes no reply of it and tells no one of it (neither a wait nor a stall nor a cut-off notice); a restart leaves one out unresolved, its attempt restored uncertain. Delivery starting on a canvas (`Engines.deliver`, a cold start's `initialize`) cuts off only what the core last left out: a send the live run made while its canvas was held or passive, its attempt still running, stays the run's to settle as its turn ends. An OK's requested changes and a repeat's next try are no attempts: they stay submissions, which the journal keeps as your messages. The renderer's run sends as before until B11's cutover.

A pending resend that needs images says so in its `display` (`requiresImages`, with how many). The bytes are live-only; if a restart lost them, delivery marks any message that requires them unresolved and tells its sender to paste the images again, never sending it as a text-only turn.

Terminal sessions report permissions from their native SessionStart hooks, without a human prompt. Delivery still rechecks the actual running session and never carries an earlier default read forward as its permission report. Until a recognized report arrives, the message remains held; bypass mode stays held. For an already-running session whose permissions remain unknown, the Need and sender notice say to switch its mode or restart it, rather than suggesting only a startup setting for a session not yet started.

A Terminal message queued behind startup, a folder-trust dialog or a user's draft has not reached the CLI. Its `user` receipt is emitted only after the text has been typed and Enter sent. Taking it back before submission returns `reached: false`, adds no withdrawal note, and leaves any notes it would have carried untold for the next message. The existing receipt handlers in delivery and `WithdrawalNotes` use that event for both delivery state and durable note acknowledgement.
