# Operations and topics

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/api/`

mcp.ts, the agents' server: MCP over streamable HTTP on 127.0.0.1, generated from the registry (one tool per op, listed by the caller's party; every call through core.call), the caller named by its bearer token: an agent's session or an outside token, never you; authentication is rechecked after the request body arrives, so a token replaced, revoked or expired meanwhile dispatches nothing; a token it doesn't take is answered 401, and one its store made that no longer works (renewed, revoked or expired: `TokenStore.stale`) 401 with `TOKEN_REPLACED`'s sentence. `corrallm serve` starts it, for outside tokens; the app doesn't yet (B11). No operation makes, renews or revokes a token: `corrallm token` asks the profile's owner over its token socket instead (see [Security](security.md)).

## `src/shared/api/`

The registry: every operation, defined once (see The registry). surface.ts holds each op's audience, kind, scope, rules, self, destructive, preempt, waits, varies and reads as plain data (the preload may import it); ops/*.ts each op's zod input and output and summary, through define.ts (the envelope: a write's `request`, an R4 or R5 op's `{ proposed }`); registry.ts lists them and how MCP names and lists each; ids.ts brands the ids ops take and finds them in parsed arguments for reach (failing closed where a pipe hides which id an op gets), and the kinds of id a schema takes; errors.ts is OpError, a code and a sentence (and TOKEN_REPLACED, the refusal a call gets when its token is replaced or expires meanwhile); limits.ts the API's numbers (MAX_REQUEST_BYTES, the image limits, TOKEN_WAITS…); deviations.ts, rules.ts and unhosted.ts the lists below. surface.snap.json is every party's surface, checked in (`pnpm api:surface`).

## The registry

`canvas.insertTemplate` inserts the shipped template's own top-level nodes with no wrapper. Its bounded output is `{ roots: NodeId[], agents: AgentId[], revs }`, with roots in template order; every inserted node id is core-minted and internal references follow. An explicit parent receives the roots; a lead defaults to its own agent. This preserves independent workspaces at top level and shares the parent's workspace when nested. The gallery's Insert remains one operation. `canvas.create` from a template retains its node ids and frames.

B11 schemas live beside each area's operations (`b11RunOps`, `b11SessionOps` and `b11ConversationOps`). The registered C6 operations are session.open, setMode (yours alone), setModel, setEffort, stopTask, restart, newConversation, rewindPreview, rewind and continueIn (yours alone); run.get is the runtime reader. The whole run's controls are registered over the core's run services (`src/main/core/run-control.ts`): run.start (W, Run and Run again, destructive: it takes back what the run has in flight) and run.resume (W), each with R9 (`sticky`: a token resumes or starts afresh only what no other party stopped, decided in or holds for you to decide), run.stop (W, preempt, destructive) and run.goOn (L, agent scope, self allowed, with R3, `human-choice`: a usage rule's hold is yours to end; its optional `until` is the hold's time as run.get shows it, a stale one a conflict). The typed reply is registered over the one reply router and the runtime's handlers (`src/main/core/run-replies.ts`), with R3 on every token's answer. Conversation/options/MCP controls and manual message schemas remain prepared: their registration awaits the C services and refusal contracts. `define(envelope, definition)` prepares the same request/revs/proposal envelope without registering a name; the registered path remains `define(name, definition)`. Native EntryId and TaskId meet R42a and resolve only in the named agent's current session, within caller reach.

`src/main/core/ops/session-control.ts` delegates the registered session operations to SessionControl and supplies R5's restore-code check. SURFACE, DEVIATIONS and RULES hold the C6 rows. Continue drains through its inner agent.setConnection call; an agent-scoped op never declares drains itself. Code rewind takes the workspace mutation gate and rechecks the proposal guard before its effect. B9a's worktree.remove is registered over C7's WorkspaceCleanup.removeKept (`src/main/core/ops/worktree.ts`): human-only (Y, trust-gate), a canvas command, destructive, with `discard`'s proposal envelope. Its strict input brands WorktreeId as a UUID. C7 resolves it only among that canvas's retained/removing records, refusing foreign, absent and active trees before assessment; no token is granted WorktreeId reach. No active binding is removed, so this prepared C7 contract declares no drains. Safe cleanup returns its result; a tree holding work asks the human too, using C7's fingerprint-bound proposal and typed reply's Discard/Cancel. The normal core composes it, with request deduplication and Needs receipts through the common publisher; no test-only registration flag remains.

B9a X12 gaps remain unregistered: `worktree.list` needs C's authorized projection of active bindings and retained trees, filtering shared membership to reached agents and withholding human-only location/setup/log/cleanup fields. WorkspaceCleanup.kept is only a raw retained/removing-record selector; the directory resolver verifies paths, not caller visibility. Without that projection there is no safe `worktrees:<c>` replacement source or read operation to authorize it, so neither the operation nor topic is registered. They must share C's selector and B11's common publisher (GUI-only, revisions allocated without subscribers, receipts through core.call). Provisioner.retry takes a raw workspace id; `worktree.retry` still needs C's canvas/agent service to resolve its binding and coordinate verified retry/setup. C has not supplied the named workspace-safety rule for structural/batch changes or its T9 security contract. Existing C workspace planning, gates and cleanup remain in place; X does not substitute a permission decision. B9a X14 supplies the Remove gesture (`NO_GESTURE`); list/retry gestures await those C contracts.

`src/shared/api/topics.ts` exports the runtime topic contracts accepted by the window subscription schema: `run:<c>`, `sessions:<c>`, `messages:<c>` and `session:<c>:<encoded agent>`. Requests are strict objects with branded canvas/agent IDs. Agent keys use canonical encodeURIComponent and are decoded exactly once; malformed Unicode or escapes are refused. Changes carry keyed agents and groups, keyed messages, or transcript upserts/appends and authoritative order. Run views keep pause causes in each agent’s `pauses` and each group’s `pauses`, never top-level arrays. Run snapshot entries use disjoint `agent/<encoded id>` and `group/<encoded id>` keys, so a parent agent can have both entries without collision. Every session summary caps `reply` at 4 KiB of UTF-8 at a character boundary, with `replyCut: true` only when cut; entries and transcript pages retain the full reply (B11 §16.3b). An oversized keyed snapshot uses begin `{ summary, count }`, indexed chunks `{ index, entries: [{ key, value }] }` and end `{ rev }`; count is the number of chunks, whose indices run consecutively from zero; their sequence supplies entry order, without an unbounded order header. A summary must fit in its begin frame or the publisher refuses the snapshot, never clipping or splitting it (B11 §16.3a). MAX_TOPIC_FRAME is 1 MiB including the frame envelope. The sole exception is one entry alone in a chunk, one that no frame holds with its chunk's envelope. The publisher sends append deltas after end, and the mirror installs only at end after every chunk arrives once in order. The live GUI schema, event, preload and GuiApi carry these topics. Components switch to them in X12/X13; their production subscriptions have not moved yet.

Every operation of corrallm's one API is defined once (`src/shared/api/`, Core Server §3), and both surfaces are generated from it: MCP for agents and outside orchestrators (`api/mcp.ts`), and a window's port for the GUI (`core/gui.ts`), which serves `GUI_OPS` (`surface.ts`: every op you may call that isn't in `UNHOSTED`, the message, run and session ops the app hosts from B11, while its run and sessions are the renderer's and reach the core over the few hand-written channels left: see Adding an IPC channel). An op's audience (`access` in `surface.ts`: `you` for the GUI, any other party for MCP) is the only thing that decides where it appears, and `core.call` checks it on every call. Results are always objects; every write's carries `revs` (the topic revisions it reached, `canvas:<id>` for a document it committed: core.call adds them, so an implementation returns its result without them, `ProducedOf`), and a doc op takes `expect` (the revisions it expects of up to `MAX_EXPECT` entities, by their keys, `EntityKey`, each in the caller's reach). Failures are values (`OpError`: `invalid`, `forbidden`, `human-only`, `not-found`, `conflict`, `refused`, `unavailable`, with one sentence; a conflict over entities a doc op expected at other revisions has `current`, what each is now), on MCP `isError` with the sentence first and `{ error }` as JSON second, never in `structuredContent`.

- By default an op is on both surfaces. One on a surface alone needs a `DEVIATIONS` row (`deviations.ts`) of one of the closed `REASONS`, or, until B11, an op the app doesn't host yet a line in `UNHOSTED` (`unhosted.ts`) naming the phase that will. A rule an op carries needs its row in `RULES` (`rules.ts`) and its check in the core.
- The GUI’s topics (`core/topics.ts`, `shared/api/topics.ts`) are `usage`, `settings` (`settings.get`: with `api`, whether the profile's MCP server listens and where, or why not, as its owner says, `Core.served`: B11 Design §16.6) and `canvases`, and each canvas’s `canvas:<c>` and `needs:<c>` (B9 Design §7): `topics.subscribe` (`{ topic, canvas? }`; a global topic ignores a canvas, which core.call fills in as for any op) returns `{ epoch, rev, state }`, then the port’s `topic(changes)` carries them in 16 ms batches, with topic revisions, a sequence (a canvas’s for its two topics, one shared by the global ones), actor and time. `usage`, `settings`, `canvases` (`canvas.list`) and `needs:<c>` (`needs`; in the app, a canvas the core keeps but doesn’t run has its proposals, its file's review and stalled-session prompts, which only you see; with the worktrees' setup composed, its workspaces' setup cards, kind `worktree`, on no agent, so they are yours alone) are replaced whole: read again through their op when their source says so (canvas memory, the journal, windows, a commit, the engines), once per caller who sees them alike, and sent only if different. `canvas:<c>` is keyed: its state is the canvas’s entities (`shared/model/state.ts`; a window builds the canvas from them with `canvasStateOf`, as `canvas.get` does), each change is a commit’s diff from the commit path at its revision (`set` written and renumbered rows, `remove` those gone), never a re-read; whoever doesn’t see the whole canvas (a lead) gets what it changed of its view (`canvas/view.ts`), so a topic is never a second way to reach anything. `topics.unsubscribe` stops them; a port going forgets its subscriptions. Each read is dispatched through the op whose surface declares `reads` for that topic, so its audience and reach remain the one authorization path. Tokens get neither subscription op (D5, `transport`); `Topics.follow` gives any caller what its subscription would carry, for T3c. All window topics use the same bounded whole snapshot or begin/chunk/end answer, including a large canvas or replacement topic. Large live replacements use that transfer too. The mirror keeps the previous complete state until end.
- `core/topics.ts` is the one publisher both B11's runtime topics and B9a's `worktrees:<c>` (a replaced topic read through its `reads` op, one row in TOPICS/CANVAS_TOPICS and a `changed` call) use. Every subscription, snapshot, re-read and publication takes its turn in one queue, so no change falls between a snapshot and its subscription. A port's 16 ms batches each fit `MAX_TOPIC_FRAME` less a 4 KiB envelope (`TOPIC_BUDGET`); only an entry alone in a snapshot chunk, one no frame holds with that chunk's envelope, may exceed it. A canvas's runtime topics (`core/runtime-topics.ts`) each keep one canonical state, yours, as last published: its revision moves at each change taken from the canvas's engine (its run and session stores, a session's actions as reduced, its message store's changed messages, its document's commits), whether or not anyone subscribes, and never on a no-op. You are sent that change; a copy that sees less (a token's, only through `follow`) is read again through its projection and sent what changed of it at the same revision, empty if nothing did, and ended once its projection refuses it, without sending the reason. Projections check audience, reach, caller party and their immutable document version again after an awaited read. Before flushing a runtime copy, the publisher synchronously checks its authority stamp (document identity and current lead status); changed authority discards older queued frames and re-reads a fresh replacement, or ends the refused copy. This prevents the 16 ms batching delay from leaking an earlier view. A change too big for a frame goes as several bounded deltas at consecutive revisions. If a keyed entry or authoritative order cannot fit a delta, it goes as a live replacement transfer using the same begin/indexed-chunks/end protocol; the mirror keeps its previous complete state until end. A text or thinking append is said as an `append`, from the reducer's action, never by comparing transcripts, and publishes no summary, including for partial copies. Canonical and URL-redacted per-session wire views cache immutable entries and update only the entries named by an action; unchanged subtrees skip deep projection visits. Partial subscriptions whose topic and authority did not change are not re-read. Many followers reuse the authorized append bodies rather than rescanning or resending full transcript entries; any other change republishes the agent's whole summary, so `reply` in a summary waits for the next such change (at the latest the turn's end), where `session.get` reads it live. A snapshot is whole if it fits a frame, else a transfer whose `begin` (with its summary) answers the subscription and whose chunks and `end` follow on the port; a summary too big for its frame refuses the subscription before anything is sent. An entry that no frame holds with its chunk's envelope, whether past 1 MiB itself or just under it, goes alone in its chunk, which alone may pass the frame (`snapshotFrameFits`), so no entry makes a topic unsubscribable. A replacement transfer queued for a subscriber whose earlier transfer's `begin` it was sent (its subscription's answer, or a batch) waits for that transfer's rest to go first, never cutting it off mid-transfer; a copy whose authority changed meanwhile, whose rest was read under the old, is ended instead. Each runtime topic is read through a projection (`Dispatcher.project`, `core/call.ts`): checked as a call of the op that `reads` it would be (session.get's for `sessions:<c>`, session.transcript's for a session, `messages`', and run.get's SURFACE reader), with the ops' own selectors (`core/ops/views.ts`), which the ops page and the projections read whole. A message's view on `messages:<c>` carries its `origin` and `display` as the message store keeps them (schema 4), never inferred from its sender or task link: the run's own sends are origin `run` with their `task` (the attempt), a correction you typed with a Retry is yours (`manual`) though linked to the run's task, and a run row's settling is taken in the same publication as the run change its turn's end made. A write's receipts: an op says `ctx.published(topic)` (a canvas's run, sessions, messages or Needs; never a per-agent session, whose wait would open a view), and once it is done core.call has the publisher publish what that topic has waiting and adds its revision (yours, for a replaced one) to `revs` if it moved while the op ran. The registered session writes, message, withdraw, reply, run.start/stop/resume/goOn and run.pause/kill/unpause declare their possible runtime effects through ops/publication.ts; only topics that actually changed receive receipts. A new core has a new epoch, its runtime revisions new; T3c for them is `core/runtime-topics.test.ts`. The core announces its own UUID `epoch` on each port; `renderer/api/topics.ts` mirrors the latest immutable state for `useSyncExternalStore`, shares one subscription per observed topic, re-subscribes on a new epoch or a revision gap, and keeps changes that arrive ahead of a snapshot’s reply; the client resolves a write once its mirror reached every `revs` it returned. T3c (`core/topics.test.ts`) checks the global topics against their reads, subscribed windows, unsubscribe and token refusal, and, after each doc op’s fixtures, every party’s copy of `canvas:<c>` rebuilt with `canvasStateOf` against its `canvas.get`, and of `canvases` and `needs:<c>` against `canvas.list` and `needs`.
- The renderer's B9 mirror also accepts `canvases`, `canvas:<id>` and `needs:<id>` (subscribed as `{ topic: 'canvas' | 'needs', canvas }`). Keyed `set`/`remove` changes preserve unchanged entities' objects; `replace` takes a whole topic's state. `whenAt(topic, rev)` holds a subscription until that revision arrives, even without a view listening. A GUI write resolves only after all its returned `revs` reach the mirror. Waiting writes fail on a core restart, rather than mistaking a new epoch's revisions for the old one's. The mirror's transport bypasses the client’s draft and revision barriers so subscriptions cannot deadlock a commit waiting for its change.

To add an operation:

1. Add its surface to `SURFACE` in `src/shared/api/surface.ts`: its audience (who may call it, and how far each reaches), kind, scope, and any rules, `self` (required when a token may call it naming an agent), `destructive`, `preempt` (it aborts what runs beneath it in its scope first), `drains` (`'canvas'` or `'agents'`: it removes or replaces what owns scopes beneath its own, so it holds them from when it comes until it ends, aborting what runs there, then queues as usual; only in the app's scope, where it drains the canvas its `replace` names, if it names one, or a canvas's, which T1 checks), `waits` (a long poll: only a read on MCP alone, the transport deviation, which T1 checks; it counts against a token's `TOKEN_WAITS` waits in flight, not its calls), `varies` and `reads`.
2. Define it in `src/shared/api/ops/<area>.ts` with `define(name, { summary, input, output })`: the summary is its MCP description; the input a `z.strictObject`, every string and list bounded, every id a branded one (`ids.ts`), never put through a pipe (a transform after it, a preprocess before it) nor in a union with a transform, which T1 refuses: core.call reads the id the op gets for reach, and finds nothing in reach where it can't; the output an object. Add a new area's ops to `OPS` in `registry.ts`.
3. Implement it in `src/main/core/ops/<area>.ts` (the `Implementations` type refuses a missing one), over the services `createCore` composes.
4. List it in `UNHOSTED` until the app serves it, or give it a deviation; give it fixtures in `REAL_FIXTURES` (`core/test-world.ts`): valid arguments (naming between them every kind of id it takes; `by`, those only some parties may pass, as a message they sent; `fresh`, the result's fields each call mints anew), invalid ones and arguments meeting each of its rules; for a kind of id no op took before, say in `REAL_OUT_OF_REACH` which ids of it each token party doesn't reach, as far as each reach goes. A write's fixtures carry a `request` id, so a call repeated through another transport dedupes.
5. Run `pnpm api:surface` and review the snapshot's diff.
