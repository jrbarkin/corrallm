# Operations and topics

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/api/`

mcp.ts, the agents' server: MCP over streamable HTTP on 127.0.0.1, generated from the registry (one tool per op, listed by the caller's party; every call through core.call), the caller named by its bearer token: an agent's session or an outside token, never you; authentication is rechecked after the request body arrives, so a token replaced, revoked or expired meanwhile dispatches nothing; a token it doesn't take is answered 401, and one its store made that no longer works (renewed, revoked or expired: `TokenStore.stale`) 401 with `TOKEN_REPLACED`'s sentence. `corrallm serve` starts it, for outside tokens; the app doesn't yet (B11). No operation makes, renews or revokes a token: `corrallm token` asks the profile's owner over its token socket instead (see [Security](security.md)).

## `src/shared/api/`

The registry: every operation, defined once (see The registry). surface.ts holds each op's audience, kind, scope, rules, self, destructive, preempt, waits, varies and reads as plain data (the preload may import it); ops/*.ts each op's zod input and output and summary, through define.ts (the envelope: a write's `request`, an R4 or R5 op's `{ proposed }`); registry.ts lists them and how MCP names and lists each; ids.ts brands the ids ops take and finds them in parsed arguments for reach (failing closed where a pipe hides which id an op gets), and the kinds of id a schema takes; errors.ts is OpError, a code and a sentence (and TOKEN_REPLACED, the refusal a call gets when its token is replaced or expires meanwhile); limits.ts the API's numbers (MAX_REQUEST_BYTES, the image limits, TOKEN_WAITS…); deviations.ts and rules.ts the lists below. surface.snap.json is every party's surface, checked in (`pnpm api:surface`).

## The registry

B9b's branch contracts are prepared in `src/shared/api/branch.ts`, outside the operation registry. `BranchDiffInput`/`BranchDiffOutput` describe a bounded review page; `BranchMergeInput`/`BranchMergeOutput` describe required source and destination review pins, an optional uncommitted-work choice and a settled merge result with receipts. Only canvas and agent are branded inputs; refs, OIDs, digests and cursors are comparison values. The merge's request UUID is required. These schemas register no operation or audience. The core's diff service (`src/main/core/workspaces/diff.ts`, see [Workspaces](workspaces.md)) is composed as `WorktreeServices.diff` for `branch.diff` to answer from: the op passes the canvas, agent, `after`, `limit` and a viewer built as `worktree.list` builds its own (with a token's open document), and turns an error result into its `OpFailure`. `worktree.list`'s output carries B9b's merge state as additive fields (C6, B9b Design §9 C12): `into` at the top (`BranchInto`, nullable) and `merge` on each item with a tree (`WorktreeMerge`), read from the core's observation service (`src/main/core/workspaces/observe.ts`), never from Git by the selector; a held merge's `sentence` is yours alone, under the op's existing `varies: ['items', ...]`, and `into` is the same for every caller. No audience or surface row changed. The merge service (`WorktreeServices.merge`) reads its cards' state again before it answers, so `branch.merge` (X2), naming `worktrees:<c>` (`ctx.published`), receipts a revision holding what it settled.

`canvas.insertTemplate` inserts the shipped template's own top-level nodes with no wrapper. Its bounded output is `{ roots: NodeId[], agents: AgentId[], revs }`, with roots in template order; every inserted node id is core-minted and internal references follow. An explicit parent receives the roots; a lead defaults to its own agent. This preserves independent workspaces at top level and shares the parent's workspace when nested. The gallery's Insert remains one operation. `canvas.create` from a template retains its node ids and frames.

Native EntryId and TaskId meet R42a and resolve only in the named agent's current session, within caller reach.

B9a's worktree operations (`src/main/core/ops/worktree.ts`, schemas in `b9aWorktreeOps`) are registered over C's services:

- `worktree.list` (A, a read, `reads: 'worktrees'`, `self: 'allowed'`, `varies: ['items', 'kept']`): `{ canvas, agent? }` → `{ items, kept, into }` (each item with a tree carrying its `merge` state: B9b C12, above), from C's authorized selector (`src/main/core/workspaces/list.ts`' `listWorktrees`), which never allocates, asks Git or verifies anything. You get every agent of the canvas (kept or open; its document now) with where its checkout is (`location`), its setup (command, source, state, exit code), the card waiting on it (`need`: its setup's, or its workspace change's) and why it failed (`error`), and the canvas's kept trees (`kept`). A token gets only the agents it reaches now, as `agentsReached` reads its open canvas at that call, with none of those fields and no kept tree: one item per agent, so a shared tree's workspace id names no member it doesn't reach, and its group's node only where canvas.get shows it the node (an agent it reaches, or a frame around one). `sharing(listing, agent)` is that shared-member rule as a function of a listing, for any later reader of an agent's workspace (X13's workspace context) to reuse rather than read bindings.
- `worktree.retry` (Y, trust-gate, a canvas command, no drains, not destructive): `{ canvas, agent }` → `{ state, need? }` over the directory resolver's `retry` (`src/main/core/workspaces/directories.ts`): its bound tree's recorded creation or recovery through Provisioner's `startRetry` (answered once recorded, its Git work going on after), a tree in setup offered its card again (never run), an agent with no tree yet has its failure forgotten and its project found again, then is made one as a start would. It never forces, deletes or switches; a busy queue is unavailable.
- `worktree.remove` over C7's WorkspaceCleanup.removeKept: human-only (Y, trust-gate), a canvas command, destructive, carrying `workspace-safety` (the proposal envelope: a tree holding work asks you, as a deletion's does). Its strict input brands WorktreeId as a UUID. C7 resolves it only among that canvas's retained/removing records, refusing foreign, absent and active trees before assessment; no token is granted WorktreeId reach. No active binding is removed, so it declares no drains. Safe cleanup returns its result; a tree holding work asks the human too, using C7's fingerprint-bound proposal and typed reply's Discard/Cancel for a tree read whole, or Keep alone when assessment cannot fingerprint it whole. Discard is refused against an unread tree even if offered earlier.

`workspace-safety` is a RULES row of kind `change` and a proposing rule (PROPOSING_RULES), carried by `canvas.delete`, `canvas.batch` and `worktree.remove`, the ops one call of which can meet it. Unlike a token's change rules it is checked on everyone's change: canvas/commit.ts' `workspaceSafety` after a token's rules (a tree a change leaves with no agent that holds work, or can't be read, makes the change a proposal for you, yours too; an op that can't propose is refused it), and workspaces/planner.ts' `unsafeStep` in every commit's preflight and write, whatever built it (an op, a batch, a file's Apply, a revert): no step binds an agent working in a tree (one past `creating`) to another, makes it a new one or unbinds it while it stays, failing closed. `ChangeChecks` excludes it from the token-only checks. The window reads worktrees through their topic; its Retry and kept-tree Remove gestures call `worktree.retry` and `worktree.remove`, with confirmations answered through `reply`.

`merge-permits` (B9b Design §9 C1, Q30) is a RULES row of kind `argument`: a token made with `--no-merge` (`OutsideCaller.merge` false; its party stays `outside-write`) is refused an agent's merge. Its check (`mergePermits` in `src/main/core/rules.ts`) reads only who calls, never the arguments, so `onEveryCarrier` puts it on every op whose surface carries the rule; core.call runs it as for every argument rule, for an op run as part of another too. It lets only an outside token made to merge through: a read-only token, and any agent, is refused by it as well as by the audience (whether a lead merges is B24's). `tools/list` stays per party. No op carries it until `branch.merge` is registered (B9b X2): T1's real registry names it `awaiting` that op, and fails once the op is registered until it carries the rule and the wait is dropped.

B13's read fields (C7, C11) sit inside outputs already named in `varies`, so no reader's result differs beyond them: `needs` and `status` items (`items`, `waitingForYou`; the `needs:<c>` topic) carry a prompt the core's owner holds with its own fields (`prompt`: the prepared `PromptNeedView`, whose tool input is any bounded JSON) and its choices' hint, effects, feedback and whether each ends the turn, its questions' `secret` and options' `preview`; `messages`, `wait` and `messages:<c>` carry a record's typed decision (`Message.settled`). Each is projected per reader by `src/shared/model/prompt-views.ts` (you, or a token: a token's has no choices, no form's own words and no terminal's screen); `src/main/core/prompt-views.test.ts` reads every boundary as you, a reached outside token, a reached lead, a parent of the prompting agent and an unreached agent, the topics' copies against their reads.

`src/shared/api/topics.ts` exports the runtime topic contracts accepted by the window subscription schema: `run:<c>`, `sessions:<c>`, `messages:<c>` and `session:<c>:<encoded agent>`. Requests are strict objects with branded canvas/agent IDs. Agent keys use canonical encodeURIComponent and are decoded exactly once; malformed Unicode or escapes are refused. Changes carry keyed agents and groups, keyed messages, or transcript upserts/appends and authoritative order. Run views keep pause causes in each agent’s `pauses` and each group’s `pauses`, never top-level arrays. Run snapshot entries use disjoint `agent/<encoded id>` and `group/<encoded id>` keys, so a parent agent can have both entries without collision. Every session summary caps `reply` at 4 KiB of UTF-8 at a character boundary, with `replyCut: true` only when cut; entries and transcript pages retain the full reply (B11 §16.3b). It carries the CLI's `suggestion` (whole, within `MAX_SUGGESTION_BYTES`, else left out) and its terminal's `asking` (bounded by `askingView` within `MAX_ASKING_BYTES`, each cut one marked `cut`) for you alone: `session.get` `varies` by both, and every token's copy or read leaves them out (`summaryFor`). An oversized keyed snapshot uses begin `{ summary, count }`, indexed chunks `{ index, entries: [{ key, value }] }` and end `{ rev }`; count is the number of chunks, whose indices run consecutively from zero; their sequence supplies entry order, without an unbounded order header. A summary must fit in its begin frame or the publisher refuses the snapshot, never clipping or splitting it (B11 §16.3a). MAX_TOPIC_FRAME is 1 MiB including the frame envelope. The sole exception is one entry alone in a chunk, one that no frame holds with its chunk's envelope. The publisher sends append deltas after end, and the mirror installs only at end after every chunk arrives once in order. The live GUI schema, event, preload and GuiApi carry these topics. GraphEditor reads the run, summaries, Needs and messages through these subscriptions; X13 finishes the session panels.

Every operation of corrallm's one API is defined once (`src/shared/api/`, Core Server §3), and both surfaces are generated from it: MCP for agents and outside orchestrators (`api/mcp.ts`), and a window's port for the GUI (`core/gui.ts`), which serves `GUI_OPS` (`surface.ts`: every op whose audience includes you, with no hosting exemptions; windows normally read runtime state from topics, with explicit NO_GESTURE reasons for the agents and status reads). An op's audience (`access` in `surface.ts`: `you` for the GUI, any other party for MCP) is the only thing that decides where it appears, and `core.call` checks it on every call. Reads validate the caller’s current audience and named-id reach again before returning; direct native effects validate them at their first noReturn boundary, then finish under that accepted operation. Results are always objects; every write's carries `revs` (the topic revisions it reached, `canvas:<id>` for a document it committed: core.call adds them, so an implementation returns its result without them, `ProducedOf`), and a doc op takes `expect` (the revisions it expects of up to `MAX_EXPECT` entities, by their keys, `EntityKey`, each in the caller's reach). Failures are values (`OpError`: `invalid`, `forbidden`, `human-only`, `not-found`, `conflict`, `refused`, `unavailable`, with one sentence; a conflict over entities a doc op expected at other revisions has `current`, what each is now), on MCP `isError` with the sentence first and `{ error }` as JSON second, never in `structuredContent`.

- By default an op is on both surfaces. One on a surface alone needs a `DEVIATIONS` row (`deviations.ts`) of one of the closed `REASONS`. A rule an op carries needs its row in `RULES` (`rules.ts`) and its check in the core.
- The GUI’s topics (`core/topics.ts`, `shared/api/topics.ts`) are `usage`, `settings` (`settings.get`: with `api`, whether the profile's MCP server listens and where, or why not, as its owner says, `Core.served`: B11 Design §16.6) and `canvases`, and each canvas’s `canvas:<c>`, `needs:<c>` (B9 Design §7) and `worktrees:<c>` (B9a §7: `worktree.list` as you, who works where, replaced whole): `topics.subscribe` (`{ topic, canvas? }`; a global topic ignores a canvas, which core.call fills in as for any op) returns `{ epoch, rev, state }`, then the port’s `topic(changes)` carries them in 16 ms batches, with topic revisions, a sequence (a canvas’s for its two topics, one shared by the global ones), actor and time. `usage`, `settings`, `canvases` (`canvas.list`) and `needs:<c>` (`needs`; in the app, a canvas the core keeps but doesn’t run has its proposals, its file's review and stalled-session prompts, which only you see; with the worktrees' setup composed, its workspaces' setup cards, kind `worktree`, on no agent, so they are yours alone) are replaced whole: read again through their op when their source says so (canvas memory, the journal, windows, a commit, the engines), once per caller who sees them alike, and sent only if different. `canvas:<c>` is keyed: its state is the canvas’s entities (`shared/model/state.ts`; a window builds the canvas from them with `canvasStateOf`, as `canvas.get` does), each change is a commit’s diff from the commit path at its revision (`set` written and renumbered rows, `remove` those gone), never a re-read; whoever doesn’t see the whole canvas (a lead) gets what it changed of its view (`canvas/view.ts`), so a topic is never a second way to reach anything. `topics.unsubscribe` stops them; a port going forgets its subscriptions. Each read is dispatched through the op whose surface declares `reads` for that topic, so its audience and reach remain the one authorization path. Tokens get neither subscription op (D5, `transport`); `Topics.follow` gives any caller what its subscription would carry, for T3c. All window topics use the same bounded whole snapshot or begin/chunk/end answer, including a large canvas or replacement topic. Large live replacements use that transfer too. The mirror keeps the previous complete state until end.
- `core/topics.ts` is the one publisher both B11's runtime topics and B9a's `worktrees:<c>` use. `worktrees:<c>` is a replaced topic read through its `reads` op (worktree.list), one row in TOPICS/CANVAS_TOPICS, and canonical (`TopicsDeps.canonical`), as is `needs:<c>` (§7 requires both revisions without subscribers): yours is read again straight from the selector at each change of its source, whether or not a window subscribes (the resolver's `changed`, which provisioning, setup, workspace changes, discovery and every document commit call, cleanup's, the merge service's as a merge is admitted, recorded, settled, held or ends, and the merge state's observation whenever a pass changes what a canvas shows), its revision moving at the change itself (its first state too) and never on a no-op; a write that names it (`ctx.published`) has it read again before its receipts, so a receipt is never only what a watching window happened to allocate. Every commit names both worktrees and Needs (who works where is written with the document, its items carry each agent's sharing, and a pending move changes its workspace cards), as do `reply`, `project.setSetupCommand`, `worktree.retry` and `worktree.remove`, `project.choose`, and a discard through `canvas.close` or a replacing `canvas.create`/`canvas.open` (for the old canvas); a receipt comes only if it moved. A worktrees first snapshot still has revision 1, but reading an unknown baseline, on subscribe or a receipt refresh, does not alone count as a write’s effect; its first source notification does, even without subscribers. Needs supplies its known empty baseline (`canonical.initial`), at revision 0, so a document change leaving it empty invents no receipt. Its first card and each later change move its canonical revision with or without a subscriber. Every document commit and project change notifies Needs directly, including on canvases without a core runtime, where no engine can announce a workspace card. Tokens follow it only as T3c does (`follow`, through worktree.list as themselves). Every subscription, snapshot, re-read and publication takes its turn in one queue, so no change falls between a snapshot and its subscription. A port's 16 ms batches each fit `MAX_TOPIC_FRAME` less a 4 KiB envelope (`TOPIC_BUDGET`); only an entry alone in a snapshot chunk, one no frame holds with that chunk's envelope, may exceed it. A canvas's runtime topics (`core/runtime-topics.ts`) each keep one canonical state, yours, as last published: its revision moves at each change taken from the canvas's engine (its run and session stores, a session's actions as reduced, its message store's changed messages, its document's commits), whether or not anyone subscribes, and never on a no-op. You are sent that change; a copy that sees less (a token's, only through `follow`) is read again through its projection and sent what changed of it at the same revision, empty if nothing did, and ended once its projection refuses it, without sending the reason. Projections check audience, reach, caller party and their immutable document version again after an awaited read. Before flushing a runtime copy, the publisher synchronously checks its authority stamp (document identity and current lead status); changed authority discards older queued frames and re-reads a fresh replacement, or ends the refused copy. This prevents the 16 ms batching delay from leaking an earlier view. A change too big for a frame goes as several bounded deltas at consecutive revisions. If a keyed entry or authoritative order cannot fit a delta, it goes as a live replacement transfer using the same begin/indexed-chunks/end protocol; the mirror keeps its previous complete state until end. A text or thinking append is said as an `append`, from the reducer's action, never by comparing transcripts, and publishes no summary, including for partial copies. Canonical and URL-redacted per-session wire views cache immutable entries and update only the entries named by an action; unchanged subtrees skip deep projection visits. Partial subscriptions whose topic and authority did not change are not re-read. Many followers reuse the authorized append bodies rather than rescanning or resending full transcript entries; any other change republishes the agent's whole summary, so `reply` in a summary waits for the next such change (at the latest the turn's end), where `session.get` reads it live. A snapshot is whole if it fits a frame, else a transfer whose `begin` (with its summary) answers the subscription and whose chunks and `end` follow on the port; a summary too big for its frame refuses the subscription before anything is sent. An entry that no frame holds with its chunk's envelope, whether past 1 MiB itself or just under it, goes alone in its chunk, which alone may pass the frame (`snapshotFrameFits`), so no entry makes a topic unsubscribable. A replacement transfer queued for a subscriber whose earlier transfer's `begin` it was sent (its subscription's answer, or a batch) waits for that transfer's rest to go first, never cutting it off mid-transfer; a copy whose authority changed meanwhile, whose rest was read under the old, is ended instead. Each runtime topic is read through a projection (`Dispatcher.project`, `core/call.ts`): checked as a call of the op that `reads` it would be (session.get's for `sessions:<c>`, session.transcript's for a session, `messages`', and run.get's SURFACE reader), with the ops' own selectors (`core/ops/views.ts`), which the ops page and the projections read whole. A message's view on `messages:<c>` carries its `origin` and `display` as the message store keeps them (schema 4), never inferred from its sender or task link: the run's own sends are origin `run` with their `task` (the attempt), a correction you typed with a Retry is yours (`manual`) though linked to the run's task, and a run row's settling is taken in the same publication as the run change its turn's end made. A write's receipts: an op says `ctx.published(topic)` (a canvas's run, sessions, messages or Needs; never a per-agent session, whose wait would open a view), and once it is done core.call has the publisher publish what that topic has waiting and adds its revision (yours, for a replaced one) to `revs` if it moved while the op ran. The registered session writes, message, withdraw, reply, run.start/stop/resume/goOn and run.pause/kill/unpause declare their possible runtime effects through ops/publication.ts; only topics that actually changed receive receipts. A new core has a new epoch, its runtime revisions new; T3c for them is `core/runtime-topics.test.ts`. The core announces its own UUID `epoch` on each port; `renderer/api/topics.ts` mirrors the latest immutable state for `useSyncExternalStore`, shares one subscription per observed topic, re-subscribes on a new epoch or a revision gap, and keeps changes that arrive ahead of a snapshot’s reply; the client resolves a write once its mirror reached every `revs` it returned. T3c (`core/topics.test.ts`) checks the global topics against their reads, subscribed windows, unsubscribe and token refusal, and, after each doc op’s fixtures, every party’s copy of `canvas:<c>` rebuilt with `canvasStateOf` against its `canvas.get`, and of `canvases`, `needs:<c>` and `worktrees:<c>` against `canvas.list`, `needs` and `worktree.list` (a tree kept as its agent goes, its receipt the revision your copy reaches).

To add an operation:

1. Add its surface to `SURFACE` in `src/shared/api/surface.ts`: its audience (who may call it, and how far each reaches), kind, scope, and any rules, `self` (required when a token may call it naming an agent), `destructive`, `preempt` (it aborts what runs beneath it in its scope first), `drains` (`'canvas'` or `'agents'`: it removes or replaces what owns scopes beneath its own, so it holds them from when it comes until it ends, aborting what runs there, then queues as usual; only in the app's scope, where it drains the canvas its `replace` names, if it names one, or a canvas's, which T1 checks), `waits` (a long poll: only a read on MCP alone, the transport deviation, which T1 checks; it counts against a token's `TOKEN_WAITS` waits in flight, not its calls), `varies` and `reads`.
2. Define it in `src/shared/api/ops/<area>.ts` with `define(name, { summary, input, output })`: the summary is its MCP description; the input a `z.strictObject`, every string and list bounded, every id a branded one (`ids.ts`), never put through a pipe (a transform after it, a preprocess before it) nor in a union with a transform, which T1 refuses: core.call reads the id the op gets for reach, and finds nothing in reach where it can't; the output an object. Add a new area's ops to `OPS` in `registry.ts`.
3. Implement it in `src/main/core/ops/<area>.ts` (the `Implementations` type refuses a missing one), over the services `createCore` composes.
4. Give it a deviation if needed, and fixtures in `REAL_FIXTURES` (`core/test-world.ts`): valid arguments (naming between them every kind of id it takes; `by`, those only some parties may pass, as a message they sent; `fresh`, the result's fields each call mints anew), invalid ones and arguments meeting each of its rules; for a kind of id no op took before, say in `REAL_OUT_OF_REACH` which ids of it each token party doesn't reach, as far as each reach goes. A write's fixtures carry a `request` id, so a call repeated through another transport dedupes.
5. Run `pnpm api:surface` and review the snapshot's diff.

Global window topic requests (`usage`, `settings`, `canvases`) do not infer a canvas from the caller's open canvases. They share the subscription envelope with scoped topics, but remain global whether zero, one or several canvases are open; subscribe and unsubscribe follow the same rule. Audience validation still precedes this routing, and canvas-scoped subscriptions retain the existing canvas/reach checks. In particular this does not admit token subscriptions.

Session conversation reach (`ConversationId`) resolves only through the exact caller's last admitted list for the reached agent and its current checkout. `session.conversations` filters a token's adapter results to native starts recorded for that agent by this core; `session.resumeConversation` cannot widen that admission. GUI listings retain all bounded adapter results (`items` is declared under `varies`). The `corral-mcp` argument RULES row on `session.changeMcpServer` refuses all token parties for corrallm's fixed server entries (`corrallm-server` and reserved `corrallm`); other servers keep L, agent scope and the self refusal. Conversation lists bound titles, branch labels and total bytes before granting admission; `session.options` refuses an overlarge result rather than clipping native setting identifiers.

B11a's inputs are `src/shared/api/fallback.ts`'s SetFallbackInput and SetHandoffInput, strict and bounded with branded canvas/agent selectors. `agent.setFallback` is registered (B11a C11): Y (the `permissions` deviation, D9), `kind: 'doc'` (so `canvas.batch` may hold it, yours alone there too), canvas scope, no drains (changing the chain restarts nothing), rule `connection`; `{ canvas?, agent, fallback: { to: StepInput[1..3], back?: 'return' } | null }` → `{ changed }`, a step's omitted connection its adapter's first as you save; an adapter or connection the catalog lacks, a connection of another adapter, a repeated step or the agent's own endpoint is `invalid`. Its gesture is the chain picker's Save (B11a X4): until then it has a NO_GESTURE reason. R8 (`connection`, `src/main/core/rules.ts`) refuses a token's commit that changes an existing agent's adapter, connection, fallback chain (the run's position in it included, compared as canonical JSON) or handoff settings, whatever op builds it; R11 (`new-agent`) lets a token's new agent carry a chain or handoff settings only as an exact copy of its source's. The session summary, `agents` and `status` carry `fallback` (`FallbackViewSchema`: the step the agent runs or null, how many steps, the endpoint it came from while on one, `stay` or `return`, and `switching` while corrallm switches it; no text, native id or path). The usage rule schema accepts the fallback action. corrallm's own switch is no operation: no op or caller reaches it (see [Usage](usage.md)). `agent.setHandoff` and `session.handoff`, and the views' `handoff` field, are C3's, unregistered.

T1 reads an object under an id's argument name by its own fields' names: a chain's `to` holds steps, not ids.
