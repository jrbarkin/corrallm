B21's session summary carries `api`, the current generation's observed tool listing, on `session.get`, `sessions:<c>` and `session:<c>:<agent>`. Listing and revocation publish only the affected agent's summary even when its status stays idle. A human-only loop Needs item carries `loop: { pair, held }`: the core's ordered pair and pending message ids in delivery order, including ask-settlement turns from corrallm. Its title contains names and the turn count only; message bodies remain in their authorized messages projection. These are additive read fields, with no new operation, audience or reply shape.

Runtime topics reuse session summaries across queue, label and position edits, invalidating only changed endpoints, fallback or handoff settings, and the sessions whose runtime state changed. Runtime publication stays in its microtask queue throughout a burst, retaining its ordering with reads and receipts, canonical revisions and append frames.

## `src/main/api/`

mcp.ts, the agents' server: MCP over streamable HTTP on 127.0.0.1, generated from the registry (one tool per op, listed by the caller's party; every call through core.call), the caller named by its bearer token: a generation of an agent's session (the session authority's credential, whose `tools/list` the server reports as that generation listed: `ApiServerOptions.listed`) or an outside token, never you; authentication is rechecked after the request body arrives, so a token replaced, revoked or expired meanwhile dispatches nothing; a token it doesn't take is answered 401, and one its store made that no longer works (renewed, revoked or expired: `TokenStore.stale`) 401 with `TOKEN_REPLACED`'s sentence. Each request gets a server of its own (stateless), all sharing one JSON Schema validator: the SDK's default compiled a fresh Ajv for every request, which only an elicitation (never made) uses. `corrallm serve` starts it, for outside tokens; the app doesn't yet (B11). No operation makes, renews or revokes a token: `corrallm token` asks the profile's owner over its token socket instead (see [Security](security.md)).

## `src/shared/api/`

The registry: every operation, defined once (see The registry). surface.ts holds each op's audience, kind, scope, rules, self, destructive, preempt, waits, varies and reads as plain data (the preload may import it); ops/*.ts each op's zod input and output and summary, through define.ts (the envelope: a write's `request`, an R4 or R5 op's `{ proposed }`); registry.ts lists them and how MCP names and lists each; ids.ts brands the ids ops take and finds them in parsed arguments for reach (failing closed where a pipe hides which id an op gets), and the kinds of id a schema takes; errors.ts is OpError, a code and a sentence (and TOKEN_REPLACED, the refusal a call gets when its token is replaced, revoked or expires meanwhile, at core.call's next audience check); limits.ts the API's numbers (MAX_REQUEST_BYTES, the image limits, TOKEN_WAITS…); deviations.ts and rules.ts the lists below. surface.snap.json is every party's surface, checked in (`pnpm api:surface`).

`src/shared/api/topics.ts` exports the runtime topic contracts accepted by the window subscription schema: `run:<c>`, `sessions:<c>`, `messages:<c>` and `session:<c>:<encoded agent>`. Every operation of corrallm's one API is defined once (`src/shared/api/`, Core Server §3), and both surfaces are generated from it: MCP for agents and outside orchestrators (`api/mcp.ts`), and a window's port for the GUI (`core/gui.ts`), which serves `GUI_OPS` (`surface.ts`: every op whose audience includes you, with no hosting exemptions; windows normally read runtime state from topics, with explicit NO_GESTURE reasons for the agents and status reads). Reads validate the caller’s current audience and named-id reach again before returning; direct native effects validate them at their first noReturn boundary, then finish under that accepted operation. Results are always objects; every write's carries `revs` (the topic revisions it reached, `canvas:<id>` for a document it committed: core.call adds them, so an implementation returns its result without them, `ProducedOf`), and a doc op takes `expect` (the revisions it expects of up to `MAX_EXPECT` entities, by their keys, `EntityKey`, each in the caller's reach).
