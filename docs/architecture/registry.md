# Operations and topics

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/api/`

mcp.ts, the agents' server: MCP over streamable HTTP on 127.0.0.1, generated from the registry (one tool per op, listed by the caller's party; every call through core.call), the caller named by its bearer token: an agent's session or an outside token, never you; authentication is rechecked after the request body arrives, so a token replaced, revoked or expired meanwhile dispatches nothing; a token it doesn't take is answered 401, and one its store made that no longer works (renewed, revoked or expired: `TokenStore.stale`) 401 with `TOKEN_REPLACED`'s sentence. `corrallm serve` starts it, for outside tokens; the app doesn't yet (B11). No operation makes, renews or revokes a token: `corrallm token` asks the profile's owner over its token socket instead (see [Security](security.md)).

## `src/shared/api/`

The registry: every operation, defined once (see The registry). surface.ts holds each op's audience, kind, scope, rules, self, destructive, preempt, waits, varies and reads as plain data (the preload may import it); ops/*.ts each op's zod input and output and summary, through define.ts (the envelope: a write's `request`, an R4 or R5 op's `{ proposed }`); registry.ts lists them and how MCP names and lists each; ids.ts brands the ids ops take and finds them in parsed arguments for reach (failing closed where a pipe hides which id an op gets), and the kinds of id a schema takes; errors.ts is OpError, a code and a sentence (and TOKEN_REPLACED, the refusal a call gets when its token is replaced or expires meanwhile); limits.ts the API's numbers (MAX_REQUEST_BYTES, the image limits, TOKEN_WAITS…); deviations.ts, rules.ts and unhosted.ts the lists below. surface.snap.json is every party's surface, checked in (`pnpm api:surface`).

## The registry

B11's prepared schemas are exported separately as `b11RunOps`, `b11SessionOps` and `b11ConversationOps` from their area's files in `src/shared/api/ops/`. They are absent from OPS and SURFACE, so they grant no calls, change no generated client or MCP surface, and do not replace the registered choice-only reply. They cover run controls, session lifecycle/settings/conversations/rewind/MCP/options, `session.continueIn`, manual messages with live images and typed reply answers. Continue is a command of its own; `agent.setConnection` stays a pure document operation. `define(envelope, definition)` prepares the same request/revs/proposal envelope using only kind and rules; `define(name, definition)` still reads registered surface metadata as before. SessionSummarySchema is the shared DTO schema for today's `session.get`. Native conversation, task and transcript-entry IDs retain R42a's bounded flag-safe shape; the new EntryId brand fails closed in reach until its resolver and operations are registered.

`src/shared/api/topics.ts` also exports the prepared runtime topic contracts independently of the live TOPICS and subscription schema: `run:<c>`, `sessions:<c>`, `messages:<c>` and `session:<c>:<encoded agent>`. Requests are strict objects with branded canvas/agent IDs. Agent keys use canonical encodeURIComponent and are decoded exactly once; malformed Unicode or escapes are refused. Changes carry keyed agents, keyed messages, or transcript upserts/appends and authoritative order. An oversized keyed snapshot uses begin `{ summary, count }`, ordered chunks `{ entries: [{ key, value }] }` and end `{ rev }`; the chunk sequence supplies order, without an unbounded order header. MAX_TOPIC_FRAME is 1 MiB including the frame envelope. The sole exception is one intrinsically oversized entry alone in a chunk. The later publisher sends append deltas after end, and the later mirror installs only at end; neither is wired by these contracts.

Every operation of corrallm's one API is defined once (`src/shared/api/`, Core Server §3), and both surfaces are generated from it: MCP for agents and outside orchestrators (`api/mcp.ts`), and a window's port for the GUI (`core/gui.ts`), which serves `GUI_OPS` (`surface.ts`: every op you may call that isn't in `UNHOSTED`, the message, run and session ops the app hosts from B11, while its run and sessions are the renderer's and reach the core over the few hand-written channels left: see Adding an IPC channel). An op's audience (`access` in `surface.ts`: `you` for the GUI, any other party for MCP) is the only thing that decides where it appears, and `core.call` checks it on every call. Results are always objects; every write's carries `revs` (the topic revisions it reached, `canvas:<id>` for a document it committed: core.call adds them, so an implementation returns its result without them, `ProducedOf`), and a doc op takes `expect` (the revisions it expects of up to `MAX_EXPECT` entities, by their keys, `EntityKey`, each in the caller's reach). Failures are values (`OpError`: `invalid`, `forbidden`, `human-only`, `not-found`, `conflict`, `refused`, `unavailable`, with one sentence; a conflict over entities a doc op expected at other revisions has `current`, what each is now), on MCP `isError` with the sentence first and `{ error }` as JSON second, never in `structuredContent`.

- By default an op is on both surfaces. One on a surface alone needs a `DEVIATIONS` row (`deviations.ts`) of one of the closed `REASONS`, or, until B11, an op the app doesn't host yet a line in `UNHOSTED` (`unhosted.ts`) naming the phase that will. A rule an op carries needs its row in `RULES` (`rules.ts`) and its check in the core.
- The GUI’s topics (`core/topics.ts`, `shared/api/topics.ts`) are `usage`, `settings` and `canvases`, and each canvas’s `canvas:<c>` and `needs:<c>` (B9 Design §7): `topics.subscribe` (`{ topic, canvas? }`; a global topic ignores a canvas, which core.call fills in as for any op) returns `{ epoch, rev, state }`, then the port’s `topic(changes)` carries them in 16 ms batches, with topic revisions, a sequence (a canvas’s for its two topics, one shared by the global ones), actor and time. `usage`, `settings`, `canvases` (`canvas.list`) and `needs:<c>` (`needs`; in the app, a canvas the core keeps but doesn’t run has its proposals, its file's review and stalled-session prompts, which only you see) are replaced whole: read again through their op when their source says so (canvas memory, the journal, windows, a commit, the engines), once per caller who sees them alike, and sent only if different. `canvas:<c>` is keyed: its state is the canvas’s entities (`shared/model/state.ts`; a window builds the canvas from them with `canvasStateOf`, as `canvas.get` does), each change is a commit’s diff from the commit path at its revision (`set` written and renumbered rows, `remove` those gone), never a re-read; whoever doesn’t see the whole canvas (a lead) gets what it changed of its view (`canvas/view.ts`), so a topic is never a second way to reach anything. `topics.unsubscribe` stops them; a port going forgets its subscriptions. Each read is dispatched through the op whose surface declares `reads` for that topic, so its audience and reach remain the one authorization path. Tokens get neither subscription op (D5, `transport`); `Topics.follow` gives any caller what its subscription would carry, for T3c. The core announces its own UUID `epoch` on each port; `renderer/api/topics.ts` mirrors the latest immutable state for `useSyncExternalStore`, shares one subscription per observed topic, re-subscribes on a new epoch or a revision gap, and keeps changes that arrive ahead of a snapshot’s reply; the client resolves a write once its mirror reached every `revs` it returned. T3c (`core/topics.test.ts`) checks the global topics against their reads, subscribed windows, unsubscribe and token refusal, and, after each doc op’s fixtures, every party’s copy of `canvas:<c>` rebuilt with `canvasStateOf` against its `canvas.get`, and of `canvases` and `needs:<c>` against `canvas.list` and `needs`.
- The renderer's B9 mirror also accepts `canvases`, `canvas:<id>` and `needs:<id>` (subscribed as `{ topic: 'canvas' | 'needs', canvas }`). Keyed `set`/`remove` changes preserve unchanged entities' objects; `replace` takes a whole topic's state. `whenAt(topic, rev)` holds a subscription until that revision arrives, even without a view listening. A GUI write resolves only after all its returned `revs` reach the mirror. Waiting writes fail on a core restart, rather than mistaking a new epoch's revisions for the old one's. The mirror's transport bypasses the client’s draft and revision barriers so subscriptions cannot deadlock a commit waiting for its change.
- T6 (`main/gestures.test.ts`) scans production renderer calls: every GUI op without `reads` needs a call site or a reason in `renderer/api/gestures.ts`'s `NO_GESTURE`, which holds only `canvas.batch` (several edits as one commit, for tokens: no gesture of the window's is one). The Canvases list calls `window.show` and `canvas.close`; proposal, file-review and stalled-session cards call `reply`. `renderer/test-api.ts` records operations separately from transport subscriptions, feeds snapshots and changes, and supplies `expectOneOp` for each gesture's intent. `renderer/test-canvas.ts`'s `fakeCanvas` answers a canvas's ops over it with the shared model's pure builds, and its file and folder ops as the core does, the dialogs' picks set by the test (`files`: what each save saved, what Open and the folder dialog pick); `test-graph.tsx` renders an editor on one (`onCanvas` hands it to the test), disposed only once unmounted, never by StrictMode's rehearsal.
- The tests that make 1:1 the default (Core Server §3.7): T1 and T2 (`shared/api/surface.test.ts`: the surface's rules, each also shown to catch a registry made wrong; `surface.snap.json` up to date), T3a (`core/transport.test.ts`: every op's fixtures through MCP's dispatch half and over HTTP answer byte for byte as `core.call` does, for the same caller, and every GUI op's through a window's port, for you), T3b (`core/callers.test.ts`: audience and tool lists agree, results alike but for `varies`, rules per party (R6 for agents alone, which have a node of their own; a world readied for a rule by its `meeting` hook, R11's cap while a call meets it), and reach generated per op and party: each id in an op's valid arguments swapped for each one its `OutOfReach` world says a token party doesn't reach, which must be not-found; it fails an op taking a kind of id no valid argument names, or that the world says nothing of for a party in its audience), T7 and T8 (`boundaries.test.ts`, ESLint). Each runs on the registry and on the core's test registry. T9 (`core/bypass.test.ts`) tries each change rule as an outside write token and a lead through every op, single, structural and in a `canvas.batch`, and on changes no single op makes, through the commit itself; R4's proposals (raised, allowed, refused, settled stale, kept across a restart, the proposer told), a batch holding a delete proposed whole and one mixing a refusal with a delete refused whole, and R3 on `reply`. T3b also generates reach from the arguments meeting each rule, and its world (`test-world.ts`) starts with two proposals waiting (`PROPOSED`, their ids from `CoreConfig.proposalIds`).

To add an operation:

1. Add its surface to `SURFACE` in `src/shared/api/surface.ts`: its audience (who may call it, and how far each reaches), kind, scope, and any rules, `self` (required when a token may call it naming an agent), `destructive`, `preempt` (it aborts what runs beneath it in its scope first), `drains` (`'canvas'` or `'agents'`: it removes or replaces what owns scopes beneath its own, so it holds them from when it comes until it ends, aborting what runs there, then queues as usual; only in the app's scope, where it drains the canvas its `replace` names, if it names one, or a canvas's, which T1 checks), `waits` (a long poll: only a read on MCP alone, the transport deviation, which T1 checks; it counts against a token's `TOKEN_WAITS` waits in flight, not its calls), `varies` and `reads`.
2. Define it in `src/shared/api/ops/<area>.ts` with `define(name, { summary, input, output })`: the summary is its MCP description; the input a `z.strictObject`, every string and list bounded, every id a branded one (`ids.ts`), never put through a pipe (a transform after it, a preprocess before it) nor in a union with a transform, which T1 refuses: core.call reads the id the op gets for reach, and finds nothing in reach where it can't; the output an object. Add a new area's ops to `OPS` in `registry.ts`.
3. Implement it in `src/main/core/ops/<area>.ts` (the `Implementations` type refuses a missing one), over the services `createCore` composes.
4. List it in `UNHOSTED` until the app serves it, or give it a deviation; give it fixtures in `REAL_FIXTURES` (`core/test-world.ts`): valid arguments (naming between them every kind of id it takes; `by`, those only some parties may pass, as a message they sent; `fresh`, the result's fields each call mints anew), invalid ones and arguments meeting each of its rules; for a kind of id no op took before, say in `REAL_OUT_OF_REACH` which ids of it each token party doesn't reach, as far as each reach goes. A write's fixtures carry a `request` id, so a call repeated through another transport dedupes.
5. Run `pnpm api:surface` and review the snapshot's diff.
