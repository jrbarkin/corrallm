# Run recovery and persistence

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/renderer/run/`

persistence.ts saves the engine's checkpoint to the core and restores it (run:save journals only the checkpoint, under the canvas's token: its run in the journal's envelope, its manual submissions your messages; run:get returns a RunRestore: the canvas's id, its token, its checkpoint and the core's notices), and runs a canvas switch around its one op (`switch`; see Run recovery and persistence); run.css marks where the run is on a queue's rows, wherever they are shown.

- Per-agent controls live in the right-click menu on canvas cards, All queues headings and session headers (also Context Menu / Shift+F10). `RunStore.pauseAgent` finishes current work then holds dispatch; `killAgent` cancels owned/received work immediately, holds the queue and leaves its native console open. `resumeAgent` releases only that hold. `AgentRun.paused` persists in the checkpoint, separately from whole-run pause; it is runtime state, never part of a saved `.corral` workflow. `RunIO.hold` keeps SessionStore's queued sends held too, while a fresh manual prompt can still intervene. Release drains in a microtask so same-stack canvas resets cannot send stale work.

- Group controls use the same menu on frames; an agent containing children keeps its individual controls and adds a Group section. `RunStore.pauseGroup/killGroup/resumeGroup` include every descendant agent and the parent agent itself, when present. Individual and group pause causes are kept separately, each stamped with the party that set it (`PauseCause`: you from the GUI, a token's party through the core): Resume releases only its own cause (a party's release only that party's, yours every party's), including across checkpoint restore, global Resume and Run again. New members inherit an active group hold; moving out, ungrouping or deleting a group releases that group's cause. Group Kill holds all members before withdrawing any work, so cancellation callbacks cannot start another member. Manual console correction remains available while held.

- Every session `end` carries its required `result` (`TurnResult`), live and in replayed history; there are no `end.interrupted` or `end.failed` flags or compatibility fallback. It keeps native completion, cancellation and failure reasons separate (a usage limit, a login, the API, the model declining, a start or connection that failed). A tool's task verdict is independent of that native result. Neither cancellation nor a native failure (a usage limit, a login, an API error, a start that failed) triggers an If failed branch, starts a repeat's next round or satisfies an expected failure: they hold for the user.

- `AgentRun.problem` holds the original queue item in Needs you. Retry, Mark resolved, Continue with failure/cancellation and Stop here are explicit decisions. Corrective composer messages include the original objective, keep the human note as a visible Message row, and create another attempt. A direct Terminal submission is correlated by its native message ID when exactly one held task owns that console; observation never sends it again. Slash commands stay commands. Attempt metadata stores timestamps, concise reasons and corrective notes.

- `engine/run/checkpoint.ts` validates the whole versioned runner snapshot before applying it. It includes cursor/outcomes, repeat rounds, held condition decisions, deadlines and minimal reply evidence for downstream conditions. `engine/delivery/submission-state.ts` stores manual Message metadata, never an executable queue of messages. Restored running/queued submissions are unresolved and are never automatically sent.

- `run/persistence.ts` serializes checkpoint writes and holds dispatch across a canvas switch. A switch (B9 Design §9: New, Open, a template's New, Show, closing the shown canvas) is one operation (`canvas.create`, `canvas.open`, `canvas.create { template }`, `window.show`, `canvas.close`), each through GraphEditor's `switchTo` and `RunPersistence.switch(action, open)`: drafts flushed and the old run saved under its token, the op called, then `open` (the run, session and view stores reset, All queues and agent windows closed, the window bound to the canvas the op names and its first `canvas:<c>` snapshot awaited), then `run:get`, restored paused under the new generation token. A flush asked for meanwhile, as main's RunShutdown asks as it quits, waits for the switch and saves under the new token, and only a disposed store refuses it. During a switch the editor stays inert until the new run is restored, with pointer input (portals included) and global shortcuts blocked, so no new manual message can be sent and erased by the late restore. The persistence barrier holds automated sends without pausing or interrupting the current run before the dialog answers. A cancelled op (Open's dialog: `{ canvas: null }`), one returning the canvas already shown, or a refused one (a file that isn't a canvas) keeps the canvas, its running turn, its stores and its token; a failed restore on every switch path (including Show, Close and a moving Allow) shows the recovery toolbar and its reason, keeping native work unavailable (Choose New or Open) until a switch shows another canvas (a cancelled one leaves it blocked). The canvas before stays open in the core with its changes, so nothing asks to discard them; the window says "<name> stays open with its changes. Find it in Canvases." when it had any. The canvas menu’s Canvases list (`graph/Canvases.tsx`) follows the `canvases` topic in core order, showing names, edits, running/open/shown state and project folders; Show and Close each call their one op, and Discard changes is separate and confirmed. `canvas.close` and an allowed `reply` return the replacement `canvas` only when they moved the calling window, so it restores that canvas without a second operation. Every reply flushes drafts and the run first; only a proposal's Allow can move the window and uses the switch barrier. File reviews, stalled-turn choices and Refuse run without making the editor inert or holding checkpoint writes for their duration, so an unresponsive CLI cannot block other agents' sends. A reply that keeps the same canvas keeps its stores and token. `NeedsSidebar.tsx` follows `needs:<c>`, showing core proposals, file reviews and stalled-session prompts beside the renderer engine’s holds and questions, with the core’s titles, loss/change details and choices. Each answer is one `reply`; its outcome stays on the card until dismissed (or in a notice when Allow switches canvases), or until the topic raises the same id again after removing it, which is a new item with live choices and a badge count. A failed reply stays at its card for retry only while its Needs item remains; once the topic removes it the card, error and badge count go, including if removal preceded the failure. A file that is not a canvas offers Keep alone. Save (`canvas.save`, or `canvas.saveAs` for a canvas never saved), Save As (`canvas.saveAs`) and Choose a project folder (`project.choose`) flush drafts and the run first, then call their one op, keeping the token. The agent chip and the settings sheet call `agent.setType` (with the connection chosen) or `agent.setConnection`, `agent.setSettings` and `agent.setRole`; Continue in Terminal also calls the renderer's `sendOnceIn` once `agent.setConnection` lands, and the composer's mode, model and effort also change the live session, until B11 (§8's exemptions, with Kill). The first restore, too, reads `run:get` only once the mirror holds the canvas shown (the owner's `ready`), whatever RunSource it has. Every automated dispatch waits for its in-flight checkpoint to reach the core.

- The core owns paths, the canvas's document and generation tokens. `RunContext` (`shared/run.ts`) is the canvas's id, its generation token and its checkpoint; `run:get` returns it as `RunRestore`, with the core's restore `notices` beside it (a file gone, a run discarded, a store set aside or restored), shown in the window's warning; `run:save` takes only `[token, checkpoint]` (anything else is refused before it is read), journals the run and never a document, so no run save can undo an operation's commit. The window's name, folder and edited state come from the mirror's `meta`, and its document from the `canvas:<c>` topic: GraphEditor keeps no copy, and no channel carries a document, a canvas's text or a file to open or save: those are operations' (`canvas.create`, `canvas.open`, `canvas.save`, `canvas.saveAs`, `project.choose` and the doc ops). `main/run-journal.ts` journals each canvas by its id in the core's database (Core Database §5: its run's state in `run`, in its own envelope, `{ format: 3, run, saveError? }` (B11 Design §4), never the document, nor the checkpoint's manual submissions, which it keeps, in the same write, as your messages in the canvas's message store, matched to a message that represents one already by the agent and the native id delivery handed it under (a longer one than a message holds made with its body cut, its whole text in its display, which it is given back and resent from), and gives back from there in the form the engine restores (`src/main/core/delivery/submissions.ts`; what still runs is kept as a restart would leave it, unresolved, and changed as it ends); a record no engine restores (a prompt longer than it keeps) is left out, said on the console, never failing the write, and submissions that aren't an engine's records at all refuse the checkpoint; which is the core's, `core/canvas/documents.ts`; each party's `wait` position in `read_position`), reading its file's text back, from the file canvas memory's row names, for the core's engines to check it still holds the canvas (one source of truth: memory keeps the file, and nothing keeps a copy), and keeps each canvas open until it is closed (`open_canvas`, a row each, with when it was used last: a window that shows none restores the one used last). Its writes go through the store's write lane, each on the drive once it resolves (its commit returned and the log flushed); the core journals a canvas's run within a write that holds its messages too (`core/engines.ts`' `#journalWithin`, and `MessageStore.writeWith`), so a canvas's run and its messages commit together. A run it can't restore (a state it can't parse, or one in no envelope it reads, as one migration 4 couldn't convert) is discarded, saying so in the restore's notices, as the store's own sentences are (set aside, restored from a snapshot) with the first canvas a window restores. Save As keeps the canvas's id, so its run, folder and conversations stay with it; a canvas a window opens or begins anew gets a new token, so stale generations cannot overwrite another canvas's run. Unsaved edits survive in the core's document. A canvas whose file went missing restores as the same canvas, unsaved, with a notice. Drafts, Save, Run and shutdown wait for every pending draft attempt, including its mirror acknowledgement.

- The core journals each headless canvas it runs from its engine's own state (`core/engines.ts`): at most one write per 250 ms, and one before every message the run sends, so a sent message's record is always on disk first (each of a task's attempts is a row in `message` too, origin `run`, linked to its attempt in that write; a party's message has its row as well: see Messages), and one before a `wait` that moved a party's read position returns (`read_position`, which every other save, as the app's, keeps as they were; the position moves only once its commit returned). A canvas's run and its messages are one record: each write of either holds every change to the other not yet on disk (the run's only if it changed since it last was), so what changes together lands together or not at all (a kill's hold and the withdrawals it makes, a turn's reply and what its end changed in the run), and a `wait` moves every position it moves in one write, or none. Each write is on the drive before it resolves (its commit returned and the log flushed, off the loop), so no crash loses a sent message's record or a position a `wait` returned past; closing the core holds each run where it is (what was going on is uncertain until inspected), journals it, then closes its sessions, writes out its stores and closes its database last, all of it even if a run can't be journaled (then `close` rejects, saying so, once everything has closed). A database that can't be opened (`unopened`) fails every read and write of the journal and canvas memory, saying why: no canvas restores or opens, so nothing is journaled and the run sends nothing.

- Run journal bounds hold automated run dispatch, not message delivery. If a checkpoint exceeds 32 MiB, 200,000 JSON values in either payload, or 64 nesting levels, `RunJournal.keep` retains the last good checkpoint and commits a `saveError` marker in the same write as any messages. The core publishes that marker only after the containing write is durable. Its canvas-wide Needs hold says why progress cannot be saved; before every run prompt, the engine checks the result of its journal write and refuses dispatch while a save error remains, leaving that attempt held for an explicit decision. It does not interrupt a turn already sent. Parties’ messages still commit and reach agents independently; malformed checkpoint data, wrong generation tokens and drive/SQL failures still reject their writes. A later checkpoint within bounds clears the marker and the canvas hold; explicit Run or Retry can then continue. A restart restores only the last good checkpoint, paused, with the saved explanation, and never replays a prompt sent without its record.

- Reopen/reload restores paused. Resume is explicit; an interrupted in-flight task stays uncertain until inspected/resolved or explicitly retried. Native session reconnection uses each connection's existing restart/resume and exact conversation ID. Main's `RunShutdown` asks the renderer to freeze/save and waits for acknowledgement. The core then flushes fallible saves while sessions and dispatch remain usable: a failed save surfaces the reason and Keep corrallm open cancels closing. Only an approved quit stops supervision and irreversibly closes the core and its sessions. A saved quit or Quit anyway awaits the entire core close before exiting or installing an update; only an explicit second quit, during a stuck save or a core close that hangs, uses a five-second escape: from that quit, the core has five more seconds to close before the app quits (or installs) anyway. Hidden unpackaged apps report save failures on stderr and exit without a native dialog. Once a quit has approved irreversible teardown, it owns every window: an earlier window-close save settling afterward cannot start a second failure dialog or change a normal quit to exit 1. An initial window load aborted by the approved quit (`ERR_ABORTED` or the destruction fallback `ERR_FAILED`) is expected; other load failures still log and exit 1. Repeated native before-quit and window-close events remain prevented until the complete core close settles (or the explicit second-quit escape expires); a window close is never the escape. A genuine core-close rejection is logged on stderr and exits 1 after cleanup, never treated as a successful quit or update installation.

The update dialog's Restart to update uses this same quit path, joining a save already in progress; only its approved completion calls Squirrel's quitAndInstall. Keep corrallm open clears the restart intent, including when the failure came from the core's flush. Later leaves the downloaded update staged for a normal quit/start. Updates never restart the app on their own; B14's run-aware quit question will apply to this path too. See [App updates](updates.md).

An early quit still saves: `window.get` can mark a canvas shown before React mounts the editor that owns its run. The preload listens for `run:stopping` immediately and retains that request until the run owner subscribes, including across an effect cleanup/remount. Main waits for its acknowledgement and then the complete core close as usual; an owner that never answers still fails the save timeout rather than silently dropping work.
