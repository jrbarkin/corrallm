# Run recovery and persistence

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/renderer/run/`

`e2e/core-continuity.e2e.ts` holds a native SDK or Terminal turn across reload and renderer death, then checks that its reply satisfies the following condition and the next task completes, with one native start and no repeated prompt. `e2e/window-closed.e2e.ts` closes the only window mid-turn, reads the live runtime through MCP, lets the run finish without a window, exchanges an outside message and reply, then reopens the same canvas through Canvases. Both distinguish the live core's identity from the new owner used by the existing core-crash and quit/relaunch recovery tests.

The core owns the run and journals it; the renderer’s run directory holds read-only display adapters, one-operation commands and run.css’s queue marks. There is no window run checkpoint, run token, run:get/run:save channel or RunPersistence. A canvas switch flushes drafts, sends one file/window operation and binds the returned canvas’s complete topic snapshots; it never freezes, saves or resets execution. A cancelled switch keeps the run exactly as it was.

- Per-agent controls live in the right-click menu on canvas cards, All queues headings and session headers (also Context Menu / Shift+F10). `RunStore.pauseAgent` finishes current work then holds dispatch; `killAgent` cancels owned/received work immediately, holds the queue and leaves its native console open. `resumeAgent` releases only that hold. `AgentRun.paused` persists in the checkpoint, separately from whole-run pause; it is runtime state, never part of a saved `.corral` workflow. `RunIO.hold` keeps SessionStore's queued sends held too, while a fresh manual prompt can still intervene. Release drains in a microtask so same-stack canvas resets cannot send stale work.

- Group controls use the same menu on frames; an agent containing children keeps its individual controls and adds a Group section. `RunStore.pauseGroup/killGroup/resumeGroup` include every descendant agent and the parent agent itself, when present. Individual and group pause causes are kept separately, each stamped with the party that set it (`PauseCause`: you from the GUI, a token's party through the core): Resume releases only its own cause (a party's release only that party's, yours every party's), including across checkpoint restore, global Resume and Run again. New members inherit an active group hold; moving out, ungrouping or deleting a group releases that group's cause. Group Kill holds all members before withdrawing any work, so cancellation callbacks cannot start another member. Manual console correction remains available while held.

- Every session `end` carries its required `result` (`TurnResult`), live and in replayed history; there are no `end.interrupted` or `end.failed` flags or compatibility fallback. It keeps native completion, cancellation and failure reasons separate (a usage limit, a login, the API, the model declining, a start or connection that failed). A tool's task verdict is independent of that native result. Neither cancellation nor a native failure (a usage limit, a login, an API error, a start that failed) triggers an If failed branch, starts a repeat's next round or satisfies an expected failure: they hold for the user.

- `AgentRun.problem` holds the original queue item in Needs you. Retry, Mark resolved, Continue with failure/cancellation and Stop here are explicit decisions. Corrective composer messages include the original objective, keep the human note as a visible Message row, and create another attempt. A direct Terminal submission is correlated by its native message ID when exactly one held task owns that console; observation never sends it again. Slash commands stay commands. Attempt metadata stores timestamps, concise reasons and corrective notes.

- `engine/run/checkpoint.ts` validates the whole versioned runner snapshot before applying it. It includes cursor/outcomes, repeat rounds, held condition decisions, deadlines and minimal reply evidence for downstream conditions. `engine/delivery/submission-state.ts` stores manual Message metadata, never an executable queue of messages. Restored running/queued submissions are unresolved and are never automatically sent.

- Windows are views of the core’s runtime. GraphEditor binds `canvas:<c>`, `run:<c>`, `needs:<c>`, `sessions:<c>` and `messages:<c>` through TopicMirror. A switch flushes local drafts, calls one file/window operation, binds the canvas its answer names and awaits all five snapshots before enabling commands. A cancelled, refused or same-canvas switch keeps the old binding and its live run untouched. A new epoch gates commands again while keeping the prior view and local drafts visible. (Main does not yet replace a window's port after a core crash: `CorePorts.reconnect` still reloads every window, so today the page starts over, its views closed, and restores its canvas from the new core, paused; the e2e that crash the core wait for that reload with `crashCoreAndReload` and open All queues again. The epoch path is what B11 Design §8 prefers the host to use instead.) No renderer run, checkpoint writer, generation token, pause/save on unload or run-ready handshake participates. New, Open and templates keep the previous canvas open with its changes; Canvases is the way back. Moving proposal Allow uses the same binding barrier; other replies leave unrelated input usable. Needs cards use the core’s ids, titles, choices and outcomes, and each answer is one typed `reply`. Save, Save As and Choose project flush drafts then call their one operation; the core already owns and journals the runtime.

- The core owns paths, documents, runtime allocation and durable checkpoints. Its journal is internal, never a renderer-writable document or checkpoint. The mirror carries the document and its name, folder and edited state. `main/run-journal.ts` journals each canvas by its id in the core's database (Core Database §5: its run's state in `run`, in its own envelope, `{ format: 3, run, saveError? }` (B11 Design §4), never the document, nor the checkpoint's manual submissions, which it keeps, in the same write, as your messages in the canvas's message store, matched to a message that represents one already by the agent and the native id delivery handed it under (a longer one than a message holds made with its body cut, its whole text in its display, which it is given back and resent from), and supplies them from there in the form the engine restores (`src/main/core/delivery/submissions.ts`; what still runs is kept as a restart would leave it, unresolved, and changed as it ends); a record no engine restores (a prompt longer than it keeps) is left out, said on the console, never failing the write, and submissions that aren't an engine's records at all refuse the checkpoint; which is the core's, `core/canvas/documents.ts`; each party's `wait` position in `read_position`), reading its file's text back, from the file canvas memory's row names, for the core's engines to check it still holds the canvas (one source of truth: memory keeps the file, and nothing keeps a copy), and keeps each canvas open until it is closed (`open_canvas`, a row each, with when it was used last: a window that shows none restores the one used last). Its writes go through the store's write lane, each on the drive once it resolves (its commit returned and the log flushed); the core journals a canvas's run within a write that holds its messages too (`core/engines.ts`' `#journalWithin`, and `MessageStore.writeWith`), so a canvas's run and its messages commit together. A run it can't restore (a state it can't parse, or one in no envelope it reads, as one migration 4 couldn't convert) is discarded, saying so in the restore's notices, as the store's own sentences are (set aside, restored from a snapshot) with the first canvas a window restores. Save As keeps the canvas's id, so its run, folder and conversations stay with it. Window switches change only the view binding; runtime writes stay in the core. Unsaved edits survive in the core's document. A canvas whose file went missing restores as the same canvas, unsaved, with a notice. Drafts, Save, Run and shutdown wait for every pending draft attempt, including its mirror acknowledgement.

- The core journals each headless canvas it runs from its engine's own state (`core/engines.ts`): at most one write per 250 ms, and one before every message the run sends, so a sent message's record is always on disk first (each of a task's attempts is a row in `message` too, origin `run`, linked to its attempt in that write; a party's message has its row as well: see Messages), and one before a `wait` that moved a party's read position returns (`read_position`, which every other save, as the app's, keeps as they were; the position moves only once its commit returned). A canvas's run and its messages are one record: each write of either holds every change to the other not yet on disk (the run's only if it changed since it last was), so what changes together lands together or not at all (a kill's hold and the withdrawals it makes, a turn's reply and what its end changed in the run), and a `wait` moves every position it moves in one write, or none. Each write is on the drive before it resolves (its commit returned and the log flushed, off the loop), so no crash loses a sent message's record or a position a `wait` returned past; closing the core holds each run where it is (what was going on is uncertain until inspected), journals it, then closes its sessions, writes out its stores and closes its database last, all of it even if a run can't be journaled (then `close` rejects, saying so, once everything has closed). A database that can't be opened (`unopened`) fails every read and write of the journal and canvas memory, saying why: no canvas restores or opens, so nothing is journaled and the run sends nothing.

- Run journal bounds hold automated run dispatch, not message delivery. If a checkpoint exceeds 32 MiB, 200,000 JSON values in either payload, or 64 nesting levels, `RunJournal.keep` retains the last good checkpoint and commits a `saveError` marker in the same write as any messages. The core publishes that marker only after the containing write is durable. Its canvas-wide Needs hold says why progress cannot be saved; before every run prompt, the engine checks the result of its journal write and refuses dispatch while a save error remains, leaving that attempt held for an explicit decision. It does not interrupt a turn already sent. Parties’ messages still commit and reach agents independently; malformed checkpoint data, wrong generation tokens and drive/SQL failures still reject their writes. A later checkpoint within bounds clears the marker and the canvas hold; explicit Run or Retry can then continue. A restart restores only the last good checkpoint, paused, with the saved explanation, and never replays a prompt sent without its record.

- A core restart restores paused (by corrallm, `Run.pausedBy`, unless a party had stopped the run: that stop stays its own, so a token resumes a restart's pause but never your stop). A window reload or reconnect keeps the live run and sessions going. After a core restart Resume is explicit; an interrupted in-flight task stays uncertain until inspected/resolved or explicitly retried. Native session reconnection uses each connection's existing restart/resume and exact conversation ID. Quitting while work goes on asks first (B14 C2: Quit and pause, Keep running or Cancel, a sheet on a window; see [Core](core.md)), freezing nothing while it asks; with nothing at work it quits unasked, the core holding its barrier only if still idle (`ifIdle`). Quit and pause first has each window finish the drafts it composes (`drafts.flush`, over its port, at most 5 s each; see [IPC](ipc.md)). The core then prepares its shutdown barrier (`prepareShutdown`, B11 Design §16.5: see [Core](core.md)): no new dispatch on a canvas it runs (no run task or delivery starts, turns going on go on), no write admitted from any transport, and every fallible save forced, while sessions remain usable: a failed save surfaces the reason and Keep corrallm open cancels closing, lifting the barrier (`cancelShutdown`) so the endpoint and every turn go on. Only an approved quit stops supervision and irreversibly closes the core and its sessions (`commitShutdown`: the endpoint first, then the sessions, children and database). Before any of that, a merge of an agent's branch past its point of no return (B9b: its install into your checkout begun) is waited for, never killed to quit, and one that hasn't reached it is refused at its next step, nothing changed; a restart reconciles a merge a crash interrupted by what your checkout shows, before new work in the agent's tree or another merge into its repository, never by running it again (see [Workspaces](workspaces.md), The merge). A saved quit or Quit anyway awaits the entire core close before exiting or installing an update; only an explicit second quit, during a stuck save or a core close that hangs, uses a five-second escape: from that quit, the core has five more seconds to close before the app quits (or installs) anyway. Hidden unpackaged apps report save failures on stderr and exit without a native dialog. Once a quit has approved irreversible teardown, it owns every window: an earlier window-close save settling afterward cannot start a second failure dialog or change a normal quit to exit 1. An initial window load aborted by the approved quit (`ERR_ABORTED` or the destruction fallback `ERR_FAILED`) is expected; other load failures still log and exit 1. Repeated native before-quit and window-close events remain prevented until the complete core close settles (or the explicit second-quit escape expires); a window close is never the escape. A genuine core-close rejection is logged on stderr and exits 1 after cleanup, never treated as a successful quit or update installation.

Keep running keeps everything: the same core, endpoint, sessions and run, with the windows closed on macOS and minimized elsewhere (Linux is never windowless), and reopening shows them again; nothing is restored, replayed or restarted. The system's shutdown or logout (B14 C4) uses the barrier's `system` reason, its refused writes saying so, with no question and no failed-save dialog: drafts get at most a second in all (`flushDrafts` for `system`), then the barrier is prepared and committed. Main does this on powerMonitor's `shutdown` (prevented, then it quits itself) and when its core closes itself: the core process does it on its own when it is signalled (SIGTERM, SIGHUP or SIGINT: a Linux logout signals main and the core at once, as `pnpm dev`'s Ctrl-C does), telling main `exiting` first and exiting 0 once closed, and main, hearing `exiting` or an exit 0 it didn't ask for, withdraws any question and takes the same path rather than sit with no core or restart it. Five seconds after the signal main exits regardless, 0 if the core closed, else 1; what the OS or that limit cut off restores as after a crash: paused, in-flight work unresolved, and the CLIs a dead core left ended as the next core starts. An idle check (`prepareShutdown` with `ifIdle`) holds the barrier only if nothing is at work, in the same step it counts presence, else answers `busy` and holds nothing, so main asks rather than cut off work that started since it last heard.

Quit and pause is this same path: it adds no durable cause, so each run restores paused by corrallm, as after any restart (Core Server §5.9: a party's messages still reach an idle agent of a run restored paused). Pause all (`run.pauseAll`, B14 C3, from main's native menus) is how you hold those too: a pause of yours, stamped `you`, on every agent of every canvas the core runs, with a run or without, each journaled in its run and so restored with it; it releases nothing and is released per agent like any pause.

The update dialog's Restart to update uses this same quit path, joining a save already in progress; only its approved completion calls Squirrel's quitAndInstall. Its barrier is prepared for `update` (the sentence a refused write gets says so). Keep corrallm open clears the restart intent, including when the failure came from the core's barrier. Later leaves the downloaded update staged for a normal quit/start. Updates never restart the app on their own. While work goes on, Restart to update asks first too: Restart and pause, or Cancel, which clears the restart intent; there is no Keep running for an update. See [App updates](updates.md).

An early quit still saves: open canvases are initialized in the core at startup, without waiting for React or a window to mount. The preload answers `drafts.flush`; the core’s preparation barrier forces the durable runtime state. A missing renderer is never an unacknowledged run owner.

Background runtime allocation and checkpoint writes keep a canvas open without changing `open_canvas.opened_at` when it is already open. Only explicit use (opening, showing or saving a canvas, including the retained legacy save entry) advances its last-used place. Startup initializes open canvases concurrently; whichever background initialization or journal finishes last must not replace the window's last shown canvas with an older draft. The journal's background `open(canvas, false)` and `keep` preserve that order; a new row still receives a place when first opened. Database recovery warnings from the run topic are announced as an alert in the canvas file float (above the Start window, with any open or save problem), with a Dismiss button: dismissing is the view's alone (it hides those notices for that canvas in that page, sends no operation and leaves the core's notices as they are).
