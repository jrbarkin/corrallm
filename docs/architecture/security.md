# Security mechanisms

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

## `src/main/loopback.ts`

What both local servers (MCP, hooks) check before the token: their own Host, no Origin (see Security rules).

## Security rules and mechanisms

- Never enable `nodeIntegration`, and never disable `contextIsolation`, `sandbox` or `webSecurity`. No `<webview>`.

- The preload exposes one typed function per IPC channel through `contextBridge`, and one per registry operation in `GUI_OPS`, generated from that fixed list in `src/shared/api/surface.ts`, each posting its own operation over the window's port to the core. Never expose `ipcRenderer`, the port, a generic `invoke`/`send` or a function that takes an operation or channel name, or Electron event objects to the renderer.

- Main registers only `core:connect` in `src/main/ipc.ts`, checking its sender frame (top-level frame of our own origin) and empty arguments. Keep `ipcMain.handle`/`ipcMain.on` there. This handshake is the preload's own, never exposed to the page: through it main hands a trusted window a `MessagePort` to the core (`host/ports.ts`), tagged with that window, which the preload keeps inside a CoreLink. The core makes every call on it yours, at that window (`core/gui.ts`), and validates it with the op's schema in `core.call`; identity comes from the port, never from a message. Remaining hand-written channels are declared in `src/shared/ipc.ts`, and parsed and handled in `core/channels.ts` for that same window.

- Production renderer is served from `app://main_window/` by `src/main/app-protocol.ts` (not `file://`, not `loadFile`). The CSP is a response header from `src/main/csp.ts`: never add `'unsafe-inline'` or `'unsafe-eval'` to `PROD_CSP`. Dev-only relaxations go in `DEV_CSP`. The only inline styles allowed are the two exact ones xterm.js writes for its scrollbar, by hash (`TERMINAL_STYLES`); xterm.js draws only with its WebGL renderer, loaded before the terminal opens (its DOM renderer's inline styles are blocked). Without WebGL2 (checked before it opens, and when a lost context cannot be replaced) the terminal is not drawn and the view says it needs WebGL2 (`src/renderer/terminal/screen.ts`): never fall back to the DOM renderer or relax `PROD_CSP` for one.

- Dev vs production is decided by `MAIN_WINDOW_VITE_DEV_SERVER_URL` (defined only under `pnpm dev`), not `app.isPackaged`. e2e runs the production build unpackaged.

- Navigation and redirects away from the app origin, and renderer-created windows, are blocked (`security.ts`; one to an allowlisted site, `allowedExternalUrl`, opens in the browser instead). Links the user clicks (Markdown links in a transcript, links Cmd-clicked in a terminal, OSC 8 or found by xterm.js's web-links addon) go to the core over `link.open` with only their URL (`OpenLinkContext` in the renderer), never through `window.open` or `target="_blank"`. The core decides, never on the renderer's say-so (`links.ts`): the URL is validated and length-capped (`MAX_LINK_LENGTH`) and normalized by `linkTarget` (`url-policy.ts`: https, or http to localhost or 127.0.0.1 only; no credentials); a site on `EXTERNAL_URL_ALLOWLIST` (https, default port) opens at once; any other asks in a native dialog ("Open docs.example.com in your browser?", with "Always for this site"), one question per window at a time, and a site allowed always is remembered by origin in user data (`links.json`). Always open the normalized URL, never the raw input. A file:// link Cmd-clicked in a terminal (Claude Code prints the files it names as OSC 8 links; xterm.js's `allowNonHttpProtocols` is on only for these, and the renderer drops every scheme but http, https and file, `linkAction` in `open-link.ts`) goes to the core over `link.reveal` with only its URL. The core (`reveal.ts`) asks main to show it in the OS file manager, selected in its folder (`shell.showItemInFolder`), only if the URL is length-capped, a file:// URL on this machine (no host; `localhost` counts as none) with no credentials, naming a file or folder that exists, whose real path (symlinks resolved, `fs.realpath`) is the real path of the canvas's project folder (`projectRoot` on the directory resolver, for the canvas the sender's window shows) or inside it. Anything else stays inert: no project folder, outside it (a symlink in it that leads out included), another host, missing. It never opens the file (no `shell.openPath`, no `openExternal` for file:// URLs), so no executable or document is ever run from a link.

- All permission requests and checks are denied (`ALLOWED_PERMISSIONS` in `security.ts`). Add entries deliberately.

- A canvas's text never acts as the user, nor does a token's. The run never sends canvas text (a queue's message or step, which a shared file may hold, or a hand-off) that starts with its recipient connection's `shellPrefix` (the catalog's: "!" for both Terminals), checked as the run sends it and again as its session starts it (`shellRefusal` in `src/shared/engine/catalog.ts`, worded from the catalog), each time against the connection the recipient runs then, since a message kept in a session's queue (behind a turn, or by a session that refused to start) may go after the agent switches: it holds in Needs you, unsent. A connection that declares no `shellPrefix` (the App Server, the Agent SDK) runs no text as a shell command, so the hold never applies to it. A token's `message` whose body starts with its recipient's prefix is refused at once (rule `shell-text`, R1). Only what the user typed may (an Agent SDK agent's bash mode, continued in Terminal); a correction you type that starts with any connection's prefix (`EngineCatalog.shellPrefixes`) is sent alone, never with the canvas's text, since its agent may run in a Terminal by the time it goes. Only your sends go past holds; every other party's waits on them (see Messages). Every message from another party (a token's, an agent's, a delivered reply) reaches its agent framed with who sent it (`core/delivery/delivery.ts`), and a CLI that takes who sent a message (the Agent SDK's `origin`) is told it too, so its CLI never takes it for its user's.

- No token is ever you. Only a window's port, made by main, or main's own native UI gives a human caller (`asHuman`, defined and called only in `core/gui.ts`, which only the core process's entry loads, for a port main posted on its parentPort). A token's lookup can't name you (`clientOf`'s type), and the MCP server refuses one that would. Operations only you may call are never listed on the agents' server, and are refused there if called (`human-only`). Deleting an agent is yours: a token's delete, alone or in a batch, applies nothing and comes to you as a proposal (R4), which only you answer (R3: a token's `reply` to one is refused), and Allow applies it only if nothing it touched changed since; a rule that refuses a change wins over a proposal, so Allow never applies what a rule refused. So is discarding work, and closing what a window shows: a token's `canvas.close` with `discard` of a canvas with edits not saved, or of one a window shows, its `canvas.create` replacing such a canvas, and its `canvas.save` that would remove agents the file on disk has, each come to you as a proposal (R4's argument half). A path comes only from a dialog you complete: `canvas.open`, `canvas.saveAs` and `project.choose` are yours alone (D1, `trust-gate`), and no argument names a path; so is `project.setSetupCommand`, what that folder's worktrees run to set themselves up.

- Restoring an agent's files is yours (R5, rule `restore-code`, prepared with B11 C6's session ops in `src/shared/api/prepared.ts` until X9 registers them): a token's code (or code and conversation) rewind applies nothing and comes to you as a proposal carrying its guard (`src/main/core/rewind-guard.ts`): the adapter, the native conversation, the message, the connection, the workspace generation its session runs at, and every file the rewind's preview names (at most 200; more is refused as too many to propose) by size, modification time and SHA-256, read without following a link or blocking on what isn't a regular file, never shown. Allow reads all of it again under the workspace mutation gate and restores only if it is the same; any difference settles it stale, restoring nothing. An agent's rewind of its own session is refused (R6, `self: refused`) before R5 could propose it. Restoring files changes them for every agent working in that tree, so it runs under the workspace mutation gate (`src/main/core/workspaces/gate.ts`): refused while any of them may be writing (a turn going on, background tasks, or a session whose bounded close didn't finish), on any canvas working in that folder, and holding their new work (a send, a launch; a send to the restoring agent too) until it is done. It never interrupts their work, releases their holds or waits for a person.

- Every answer to what waits on a canvas goes through one router (`src/main/core/replies.ts`, B11 C7): an item is answered only as it waits now, at the generation its id names (a run's hold asked again, a prompt of another session, a setup card or a workspace change planned anew is a conflict, never answered for the one waiting); never by an agent of what waits on itself (R6, which R3's argument check refuses first too); only by a party its `by` names, and a `humanOnly` choice only by you (R3); until B24 every run hold and session prompt is yours alone, and a setup, a workspace change and a cleanup for good. A reply never releases a pause (R9): a hold a pause holds is refused, naming whose. A refusal's Switch runs `session.continueIn` through ctx.call as the same caller, so D9 decides whoever may answer the hold. A prompt's answer goes to its CLI first, recorded as being made before it is told; one the CLI refuses still waits, and one a crash cut off is unresolved, never sent again. Who decided is recorded (`src/main/core/decisions.ts`: a `settled` record to you, `by` the party), never an answer's values: no words, form values, question answers or feedback are written anywhere, and a token's `needs` shows your items without their choices or forms.
- A proposal's Needs text is hidden from a token unless it reaches every removed agent and any agent proposer; reaching only the first agent never reveals the others' names, queues or conversations, including through a reply refusal. Pending proposals are capped per party and canvas (32), with identical calls at the same baseline reusing one, and token-created open canvases per party (16). These bounds survive token renewal and restart; only settlement or closure frees a slot.

- Which canvases and agents a caller reaches, and the rules that narrow what tokens may do, are enforced in `core.call` and, on a canvas's document, at commit on the change itself, whatever op made it, never left to an operation's implementation. Every transport calls `core.call`, which checks the caller's audience on every call, not only when listing tools.

- Both local servers (MCP, `api/mcp.ts`; hooks, `sessions/terminal/hooks.ts`) listen only on 127.0.0.1 and refuse a foreign Host or any Origin header before checking the token (`loopback.ts`). MCP takes only an `application/json` body, of at most `MAX_REQUEST_BYTES`, read before a body too large is answered 413.

- Only one app instance may use a profile (`requestSingleInstanceLock` in index.ts), and `<profile>/core.lock` (`core/lock.ts`) admits one owner, so the app and `corrallm serve` never own one profile at once (a lock left behind is taken over by one process at a time): the app's core process takes it as main asks it up (`init` in `core/entry.ts`, before it composes the core; let go once the core closes, and a crashed core's is taken over by the next) and, while `serve` holds it, answers who does, composing nothing, so main refuses to start, saying so in a native dialog; `serve` refuses while the app holds it. A window that crashes ends its canvas's sessions as one that reloads or is destroyed does (`core/windows.ts`). Linux locks identify their owner by boot ID and process start ticks, never wall-clock-derived `ps` times; macOS keeps `lstart`. An inspection failure, or a wall-clock-only Linux lock record whose pid is still alive, cannot authorize taking the profile.

- Paths the core opens, saves to or works in (canvases opened from and saved to, the folders agents run in) are `TrustedPath`s (`core/host.ts`): from a dialog you completed (`host/dialogs.ts` returns an unbranded path; `core/host/app.ts` brands its answer in the core process), or from canvas memory reading back a path it wrote, as the journal does with a canvas's run, or a workspace's checkout once `verifiedCheckout` (`src/main/core/workspaces/checkout.ts`) has checked, at that use, that it is the checkout the core made of the picked repository in the owned root there: the repository's real path and identity, the owned root, its folder, `.git` and registration agreeing, and Git finding it as its own top level (see [Workspaces](workspaces.md)). A workspace record's path alone is never trusted. No command line mints one, so `corrallm serve` runs a canvas only from the file and in the folder canvas memory keeps for it, picked in the app (`Core.keptCanvas`; it has no `--project`).

- Outside tokens are made by a person (`corrallm serve --new-token`, only with stderr on a terminal), named (the name is the party, `outside:<name>`; a new token of a live one's name replaces it at once), reach only the canvases named when made, by their stable ids, read-only or read-write, expire within 12 hours (1 by default), and are kept only as a SHA-256 hash (`tokens.json`, 0600), a new token forced to disk (`writeWhole`'s `durable`) before it is printed, so no power loss brings back the one it replaced. A new one is printed once, on that terminal, and no log, result, store or child process's arguments ever hold it; orchestrators register corrallm by the variable that holds it (`CORRALLM_OUTSIDE_TOKEN`, under the server name `corrallm-server`), and `corrallm wait` reads it only from its environment and sends it only to http on 127.0.0.1 or localhost, with no credentials, query or fragment (`loopbackUrl` in `url-policy.ts`). No operation a token can call creates or widens a token.

- Read-only Git commands share `SAFE_GIT_OPTIONS` (`src/main/git.ts`), the baseline disabling fsmonitor and implicit bare repositories. Patch-producing commands additionally use `safeGitDiffArgs` for diff/log/show: first read the configured driver keys with `git config --null --name-only --get-regexp '^filter\..*\.(clean|process)$'`, then pass them to the helper. Its command arguments disable external diff and textconv and blank each filter's clean/process commands and set its required flag to false; it throws for a driver whose name holds `=`, which `-c` (split at the first `=`) cannot name, so such a repository gets no patch rather than running its driver. The caller still prepends `SAFE_GIT_OPTIONS`. Codex's App Server `/diff` uses this shared helper for both tracked and untracked files.

- Workspace Git (making and checking worktrees, and B9b's diffs and merges) goes only through `GitRunner` (`src/main/core/workspaces/git.ts`; see [Workspaces](workspaces.md)): git by absolute path from the PATH's absolute folders, no shell; on every call `SAFE_GIT_OPTIONS`, an empty private hooks folder of the core's as `core.hooksPath`, no submodule recursion, `protocol.allow=never` (no fetch, lazy or otherwise, so no ssh or credential helper) and no auto-gc or maintenance; every filter driver configured where the call runs disabled by name (clean, smudge, process, required), and configuration it can't neutralize refused (a driver `-c` can't name, `core.worktree`, configured `hook.*`); patches add `safeGitDiffArgs`; every `GIT_` variable removed from the agents' environment; bounded time and output; each git a child the core owns. Discovery (`src/main/core/workspaces/discovery.ts`) refuses a folder inside a repository, a `.git` symlink, a `.git` file or registration that doesn't agree with the folder picked and a `core.worktree` redirect, and never takes a failure to read a repository for a folder that isn't one. The owned root (`src/main/core/workspaces/owned.ts`) is verified before anything is written in it: real folders the user owns from the checkout's real path down, no symlink, private, marked by the core (in the common Git directory, by path and inode, so `git clean -fdx` can't unmark it and a folder put in its place isn't taken for it); `info/exclude` is never written through a symlink.

- A worktree's setup (`src/main/core/workspaces/setup.ts`; see [Workspaces](workspaces.md)) runs only what the core fixes: the command you set for the picked repository (`project.setSetupCommand`, yours alone: D1, `trust-gate`; one line of at most 4 KiB with no control, format or separator character, so what the card shows is what runs, under the fixed POSIX shell), or the fixed table's for its base commit's lockfile (pnpm, npm: an argument list, no shell, the executable only from the PATH's absolute folders), never a token's, a canvas's, a file's or the repository's own (its scripts, its `packageManager`, its manifest). Each setup is one card for you alone: it names no agent, so no token's Needs holds it and no token's reach names it, R3 refuses a token's `reply`, and the service refuses any party but you again. It is answered only at the generation it shows: a changed command clears Always and raises a new card, so an older answer is stale, and Run checks again that what may run now hashes to what was shown. Your approval and the running attempt are on disk before anything runs; Always runs that exact command only, by itself only in the repository's later new workspaces, until you clear it (`project.clearSetupApproval`, yours alone: D9, `permissions`). It runs in the checkout verified at that moment as an owned process group (`spawnOwned`: never unowned, recorded until its output closes), which Stop, its timeout and the core closing end whole; a crash's group is ended as the next core starts and its setup is marked interrupted, never run again by itself. Its output, which may hold secrets, goes only to a private bounded log in the profile and, escaped, to your card. No setup runs on Windows: ending its process tree there is a release blocker. A worktree is removed only once that is safe, or as you decided (`src/main/core/workspaces/cleanup.ts`, B9a C7): what it holds is read in its verified checkout (its changed and untracked files, whether its HEAD and branch are reachable from the picked checkout's HEAD now, who may still write there, a setup running); clean, merged and with no writer, it goes with its last agent; otherwise the deletion applies nothing until you confirm it, yours too, through the same proposals as a token's R4 delete (Delete keeps its work, Discard removes it and its branch), each bound to what it held when asked, so work added meanwhile settles it stale. A file's Apply or a discard keeps what it would lose. Git removes only the checkout verified as the one made (never one a link stands in for, forced only for a discard you approved), and its branch only at the commit decided. A kept tree's removal (`worktree.remove`, prepared, yours alone) asks the same way. A workspace change's Switch is yours alone, under the workspace mutation gate, keeping the trees its agents leave. Local files (`src/main/core/workspaces/copy.ts`) are copied only as the base commit's `.worktreeinclude` selects among files Git ignores in the picked checkout: never through a symlink on either side, never over a file the workspace has or tracks, within limits, all or nothing, private, recorded by name and hash only.

- Packaged builds exit if launched with a switch in `FORBIDDEN_SWITCHES` (`src/main/index.ts`): remote debugging, or launcher prefixes such as `--gpu-launcher` that would make the app run an arbitrary executable. Unit tests cover every listed switch, before initialization and the native self-test. The local packaged gates (`scripts/check-macos.sh` and `scripts/check-linux.sh`) additionally require exit 1 for remote-debugging-port, gpu-launcher and renderer-cmd-prefix; the macOS gate first verifies the bundle with `codesign --verify --deep --strict`.

- Fuses (`forge.config.mts`) must stay as configured: RunAsNode, `NODE_OPTIONS` and Node inspect flags disabled; ASAR integrity and OnlyLoadAppFromAsar enabled (integrity is enforced on macOS and Windows only). Consequences: `child_process.fork` throws in packaged builds (use `utilityProcess.fork`, as the core process is forked, or `spawn`; the packaged self-test checks it throws), and Playwright cannot drive the packaged app. These fuses protect Electron, not the shipped command's separate plain Node runtime. Its launcher (`build/corrallm`) unsets `NODE_OPTIONS`, `NODE_PATH` and `NODE_REPL_EXTERNAL_MODULE` before invoking that runtime; the packaged self-test deliberately supplies a failing preload to prove the launcher removes it.

- Packaged app updates use only the fixed HTTPS update.electronjs.org feed for jrbarkin/corrallm, through Electron's native Squirrel updater. macOS needs a Developer ID-signed app; ad hoc builds skip it. Linux only checks the fixed GitHub latest-release API without authentication, with redirects refused and a short timeout; it opens a constructed release-page URL through the core's existing link.open policy, ignoring the response's html_url. No renderer, file or environment value can replace the feed or repository. Restart waits for the approved RunShutdown save/flush/close path; no download restarts the app automatically. `CORRALLM_NO_UPDATE_CHECK=1` disables checks. See [App updates](updates.md) for contacts and data sent.

- The companion command uses a separate pinned Node outside ASAR, never Electron's RunAsNode mode. Its official archive is checked against a committed SHA-256 on every package build, and macOS signs the executable with the app under hardened runtime with JIT alone. The command's readable resources do not weaken Electron's fuses. The launcher handles no token; the CLI's token and trust rules above apply unchanged.

- Credentials only come from environment variables (see `.env.example`). Never commit `.env` or key files; `pnpm dev` strips the signing variables before launching the app. Agents use the `claude` and `codex` CLIs' own logins; corrallm never reads, stores or passes credentials (the Agent SDK connection asks `claude auth status` only what kind of login it has, the App Server connection asks Codex's `account/read` the same).

- Agents run only in the project folder the user picked in main's folder dialog (`project.ts`, through `HostServices.pickFolder`): that choice is the trust gate (SDK sessions skip Claude Code's own trust dialog; Codex, on either connection, is told on its command line that the folder is trusted, for its session alone: `folderTrust`, never written to the user's config.toml). The renderer never passes a path, a command line or an environment, and names a session to resume only by picking one the core listed to that very window for the agent's working directory binding (`session:list`, then `session:resume`, within ten minutes, and never one another agent's session holds: `sessions/claims.ts`): the core resolves `claude` (`sessions/claude-code/claude.ts`) and `codex` (`sessions/codex/codex.ts`), the environment and the folder, and remembers session ids itself. The one path that crosses is a file dropped on a terminal: the page passes the dropped `File` objects, the preload reads their paths with `webUtils.getPathForFile` (a file the page made has none), and the core checks them (`terminal.drop`: absolute, length-capped, no control characters; then that they exist) before pasting them, quoted, into that terminal, never using them otherwise. Connectors use an agent's id only to route events, never in a path or a command line. What an agent is set to run with goes on its CLI's command line only as checked values, from the renderer and from `.corral` files alike: a model's name (`MODEL_PATTERN`: never with a dash first, which would read as a flag), an effort (`EFFORT_PATTERN`; Claude Code's only one of its levels) and a mode its connection starts in (the catalog's `startModes`, each one that asks: neither a file nor `session:start` sets one that never asks). Every session's process is closed before the app quits. A Terminal view sends only keystrokes, its size and dropped files; its CLI's hooks post to a server on 127.0.0.1 that needs the session's own token (from private files in its session folder, never from a child environment), and corrallm only listens to them (it never answers with a decision, and never answers what the CLI asks in its terminal). Every command hook, on POSIX and Windows, and Claude Code's status line read their Authorization header from a 0600 file only the user can read (`curl -H @<file>`, never a token on a command line). Only the header file's path is in the CLI and hook children's environments; the old token variable is stripped. Claude Code's native HTTP hooks keep their header in its 0600 settings file instead of interpolating an environment variable. Its `httpHookAllowedEnvVars` setting restricts interpolation only and does not disable these hooks; URL restrictions, hook disabling and managed-only locks still apply. Its status line posts to that server too, and never puts what Claude Code gives it into a command line; Codex's are read from its app server (a Codex · Terminal session asks a private one nothing but `account/rateLimits/read`). Usage readings keep only shares and times.
