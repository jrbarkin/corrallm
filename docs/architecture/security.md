## `src/main/loopback.ts`

What both local servers (MCP, hooks) check before the token: their own Host, no Origin (see Security rules).

## Security rules and mechanisms

- Never enable `nodeIntegration`, and never disable `contextIsolation`, `sandbox` or `webSecurity`. No `<webview>`.

- The preload exposes fixed typed functions for terminal events, topic updates and draft flushes through `contextBridge`, and one per registry operation in `GUI_OPS`, generated from that fixed list in `src/shared/api/surface.ts`, each posting its own operation over the window's port to the core. Never expose `ipcRenderer`, the port, a generic `invoke`/`send` or a function that takes an operation or channel name, or Electron event objects to the renderer.

- Main registers only `core:connect` in `src/main/ipc.ts`, checking its sender frame (top-level frame of our own origin) and empty arguments. Keep `ipcMain.handle`/`ipcMain.on` there. This handshake is the preload's own, never exposed to the page: through it main hands a trusted window a `MessagePort` to the core (`host/ports.ts`), tagged with that window, which the preload keeps inside a CoreLink. The core makes every call on it yours, at that window (`core/gui.ts`), and validates it with the op's schema in `core.call`; identity comes from the port, never from a message. There is no hand-written channel dispatcher; fixed terminal events, topic changes and draft flushes use the dedicated window-port protocol.

- Production renderer is served from `app://main_window/` by `src/main/app-protocol.ts` (not `file://`, not `loadFile`). The CSP is a response header from `src/main/csp.ts`: never add `'unsafe-inline'` or `'unsafe-eval'` to `PROD_CSP`. Dev-only relaxations go in `DEV_CSP`. The only inline styles allowed are the two exact ones xterm.js writes for its scrollbar, by hash (`TERMINAL_STYLES`); xterm.js draws only with its WebGL renderer, loaded before the terminal opens (its DOM renderer's inline styles are blocked). Without WebGL2 (checked before it opens, and when a lost context cannot be replaced) the terminal is not drawn and the view says it needs WebGL2 (`src/renderer/terminal/screen.ts`): never fall back to the DOM renderer or relax `PROD_CSP` for one.

- Dev vs production is decided by `MAIN_WINDOW_VITE_DEV_SERVER_URL` (defined only under `pnpm dev`), not `app.isPackaged`. e2e runs the production build unpackaged.

- Quitting is main's alone (B14 C2, C4: `src/main/host/closing.ts`): native events only (before-quit, a window's close, Restart to update, powerMonitor's `shutdown`, the core's `exiting`), never an operation, so no token or page can quit, keep running or answer for you. Its questions (the quit question and the failed-save one) are always sheets on a corrallm window with an AbortSignal, never parentless boxes (which on macOS run synchronously, holding main's loop), so the system's shutdown or logout withdraws them and nothing it shows can hold a logout; main's five-second budget then exits regardless. The system's path stops supervision before anything else, so a core that closed itself, or one that dies as the session ends, is never restarted against a profile being given up. A notification's click reaches the core only as an opaque handle main never resolves. The e2e answer to the question (`e2e/launch.ts`) is Playwright's, in the unpackaged hidden app: there is no production seam that answers it.

- Navigation and redirects away from the app origin, and renderer-created windows, are blocked (`security.ts`; one to an allowlisted site, `allowedExternalUrl`, opens in the browser instead). Links the user clicks (Markdown links in a transcript, links Cmd-clicked in a terminal, OSC 8 or found by xterm.js's web-links addon) go to the core over `link.open` with only their URL (`OpenLinkContext` in the renderer), never through `window.open` or `target="_blank"`. The core decides, never on the renderer's say-so (`links.ts`): the URL is validated and length-capped (`MAX_LINK_LENGTH`) and normalized by `linkTarget` (`url-policy.ts`: https, or http to localhost or 127.0.0.1 only; no credentials); a site on `EXTERNAL_URL_ALLOWLIST` (https, default port) opens at once; any other asks in a native dialog ("Open docs.example.com in your browser?", with "Always for this site"), one question per window at a time, and a site allowed always is remembered by origin in user data (`links.json`). Always open the normalized URL, never the raw input. A file:// link Cmd-clicked in a terminal (Claude Code prints the files it names as OSC 8 links; xterm.js's `allowNonHttpProtocols` is on only for these, and the renderer drops every scheme but http, https and file, `linkAction` in `open-link.ts`) goes to the core over `link.reveal` with only its URL. The core (`reveal.ts`) asks main to show it in the OS file manager, selected in its folder (`shell.showItemInFolder`), only if the URL is length-capped, a file:// URL on this machine (no host; `localhost` counts as none) with no credentials, naming a file or folder that exists, whose real path (symlinks resolved, `fs.realpath`) is the real path of the canvas's project folder (`projectRoot` on the directory resolver, for the canvas the sender's window shows) or inside it. Anything else stays inert: no project folder, outside it (a symlink in it that leads out included), another host, missing. It never opens the file (no `shell.openPath`, no `openExternal` for file:// URLs), so no executable or document is ever run from a link.

- All permission requests and checks are denied (`ALLOWED_PERMISSIONS` in `security.ts`). Add entries deliberately. OS notifications and the Dock badge are main's native capability (B14 C9), through Electron's `Notification` and the Dock API, made only for the current core's fixed, bounded notify/unnotify requests; no renderer permission is granted, and a page's Web Notifications stay denied by both handlers (`src/main/security.test.ts`, `e2e/security.e2e.ts`).

- A notification never carries what another party wrote beyond a name (B14 C8, `src/main/core/notification-text.ts`): the core words it from a fixed sentence chosen by the Needs item's kind and id, never its title, detail, choices or form, and carries at most an agent's or a canvas's name, cleaned to letters, marks, digits, spaces and `- _ , ' ( ) #` (no markup, which Linux notification servers render unescaped, no URL punctuation, control, bidi or invisible character) and capped at 32 bytes; the body at most 160. Nothing else reaches main: no subtitle, action, reply field, icon, sound, group or id but the opaque handle (`src/main/host/test-notification.ts` holds main's adapter to that). A click carries only that handle, which the core alone resolves, to a canvas it still runs and a Need it names (C10): the window then switches itself through its own operations, so a click answers, resumes or opens nothing. `notifications.enabled` (C11) stays out of `settings.get`, which tokens read. Native errors carry no values into logs. Authorization is asked only on C9's trusted cue: the core's `Presence.notify` (the `notifications.enabled` setting as the notifier reads it) with a positive working count, never application launch, a restore or a token-readable settings result, and once per main process.

- A canvas's text never acts as the user, nor does a token's. The run never sends canvas text (a queue's message or step, which a shared file may hold, or a hand-off) that starts with its recipient connection's `shellPrefix` (the catalog's: "!" for both Terminals), checked as the run sends it and again as its session starts it (`shellRefusal` in `src/shared/model/catalog.ts`, worded from the catalog), each time against the connection the recipient runs then, since a message kept in a session's queue (behind a turn, or by a session that refused to start) may go after the agent switches: it holds in Needs you, unsent. A connection that declares no `shellPrefix` (the App Server, the Agent SDK) runs no text as a shell command, so the hold never applies to it. A token's `message` whose body starts with its recipient's prefix is refused at once (rule `shell-text`, R1, its recipient's connection read through `agentEndpoint`; one that runs no connection yet, unchosen or naming what this build lacks, may come to run any, so every prefix the catalog declares is refused to it), as is one past 16 KiB of text or carrying images (rule `human-text`: only your composer's message is longer or pastes images, B11 §16.6). Only what the user typed may (an Agent SDK agent's bash mode, continued in Terminal); a correction you type that starts with any connection's prefix (`EngineCatalog.shellPrefixes`) is sent alone, never with the canvas's text, since its agent may run in a Terminal by the time it goes. Only your sends go past holds; every other party's waits on them (see Messages). Every message from another party (a token's, an agent's, a delivered reply) reaches its agent framed with who sent it (`core/delivery/delivery.ts`), and a CLI that takes who sent a message (the Agent SDK's `origin`) is told it too, so its CLI never takes it for its user's.

- No token is ever you. Only a window's port, made by main, or main's own native UI gives a human caller (`asHuman`, defined and called only in `core/gui.ts`, which only the core process's entry loads, for a port main posted on its parentPort). Main's native UI is `asHuman('host')` for one fixed request alone, Pause all (`WindowPorts.pauseAll`, the registered `run.pauseAll`), never an operation named by a message: that op is on neither generated surface (`host`, the native-menu deviation), so no window or token calls it. A token's lookup can't name you (`clientOf`'s type), and the MCP server refuses one that would. Operations only you may call are never listed on the agents' server, and are refused there if called (`human-only`). Deleting an agent is yours: a token's delete, alone or in a batch, applies nothing and comes to you as a proposal (R4), which only you answer (R3: a token's `reply` to one is refused), and Allow applies it only if nothing it touched changed since; a rule that refuses a change wins over a proposal, so Allow never applies what a rule refused. So is discarding work, and closing what a window shows: a token's `canvas.close` with `discard` of a canvas with edits not saved, or of one a window shows, its `canvas.create` replacing such a canvas, and its `canvas.save` that would remove agents the file on disk has, each come to you as a proposal (R4's argument half). A path comes only from a dialog you complete: `canvas.open`, `canvas.saveAs` and `project.choose` are yours alone (D1, `trust-gate`), and no argument names a path; so is `project.setSetupCommand`, what that folder's worktrees run to set themselves up.

- A prompt is read through one selector (B13 C11, `src/shared/model/prompt-views.ts`) at every boundary: Needs, `status`, transcripts and their topic, the counts, the router's refusals, notices and `wait`. A token that reaches its agent (or a parent, its team's prompts in Needs) never reads a choice, a form's schema, link or own words (its title is the core's), what a terminal's screen shows, or an answer, feedback or an "always" label; what no longer waits is out of its reach. Records of decisions are yours, typed and value-free (`Message.settled`). Prompt text is the agent's or a server's words, never instructions.

- A proposal's Needs text is hidden from a token unless it reaches every removed agent and any agent proposer; reaching only the first agent never reveals the others' names, queues or conversations, including through a reply refusal. Pending proposals are capped per party and canvas (32), with identical calls at the same baseline reusing one, and token-created open canvases per party (16), counting a canvas you Allow a token to make, which is the token's own. These bounds survive token renewal and restart; only settlement or closure frees a slot.
- Restoring an agent's files is yours (R5, rule `restore-code`, registered with B11 C6's session ops, checked by `src/main/core/ops/session-control.ts`): a token's code (or code and conversation) rewind applies nothing and comes to you as a proposal carrying its guard (`src/main/core/rewind-guard.ts`): the adapter, the native conversation, the message, the connection, the workspace generation its session runs at, and every file the rewind's preview names (at most 200; more is refused as too many to propose) by size, modification time and SHA-256, read without following a link or blocking on what isn't a regular file, never shown. Allow reads all of it again under the workspace mutation gate and restores only if it is the same; any difference settles it stale, restoring nothing. An agent's rewind of its own session is refused (R6, `self: refused`) before R5 could propose it. Restoring files changes them for every agent working in that tree, so it runs under the workspace mutation gate (`src/main/core/workspaces/gate.ts`): refused while any of them may be writing (a turn going on, background tasks, or a session whose bounded close didn't finish), on any canvas working in that folder, and holding their new work (a send, a launch; a send to the restoring agent too) until it is done. It never interrupts their work, releases their holds or waits for a person.

- Which canvases and agents a caller reaches, and the rules that narrow what tokens may do, are enforced in `core.call` and, on a canvas's document, at commit on the change itself, whatever op made it, never left to an operation's implementation. Every transport calls `core.call`, which checks the caller's audience on every call, not only when listing tools.

- No default chooses an agent for a token (B12 C2, C3). The token rules read an agent's identity through the one resolver alone (`agentEndpoint` in `src/shared/model/catalog.ts`): the adapter it names, else the owner of a connection it names that the catalog knows; with neither it is unchosen, and no preference, registry order or label chooses for it (`ChangeCheckDeps` has no default). R6 (`self`) and R8 (`connection`) compare endpoints as the resolver reads them, unchosen distinct from every endpoint, so a token's change giving an unchosen agent an adapter or a connection is refused, even the one a default would have named. R11 (`new-agent`) refuses a token's new agent whose endpoint isn't known (unchosen, or an adapter or connection this build lacks), copy or not. The default agent itself is yours alone: `settings.set` is human-only (the `consent` deviation), listed to no token; it implies no installation, login or consent, a failed write changes nothing, and the core never reads it to create or run an agent.

- Both local servers (MCP, `api/mcp.ts`; hooks, `sessions/terminal/hooks.ts`) listen only on 127.0.0.1 and refuse a foreign Host or any Origin header before checking the token (`loopback.ts`). MCP takes only an `application/json` body, of at most `MAX_REQUEST_BYTES`, read before a body too large is answered 413. It authenticates before reading and again after the body arrives: sending headers cannot reserve an old token’s authority across renewal, revocation or expiry. The MCP server is the profile owner's endpoint (`src/main/core/endpoint.ts`): the app's core always serves it (B11 Design §16.6), as `corrallm serve` does, in the core process beside its dispatcher, never main or a window, on the port the profile keeps and never another (one taken is a status, `settings.get`'s `api`, never a dialog); with no outside token made, nothing authenticates. Nothing of it but that status reaches HostServices or a topic, and no operation, flag or window path makes or widens a token. Its api.json (0600) names the owning process by pid and verified start, and is removed only by the owner that wrote that record, so an old core's late cleanup never removes a newer one's. While the core's shutdown barrier is prepared (a quit, Restart to update, the system's shutdown or logout, or the core signalled), every transport's writes are refused, `unavailable`; committing it closes the endpoint, ending every request going on, before any session ends.

- Only one app instance may use a profile (`requestSingleInstanceLock` in index.ts), and `<profile>/core.lock` (`core/lock.ts`) admits one owner, so the app and `corrallm serve` never own one profile at once, nor either while `corrallm token` writes its tokens with nothing else owning it (a lock left behind is taken over by one process at a time): the app's core process takes it as main asks it up (`init` in `core/entry.ts`, before it composes the core; let go once the core closes, and a crashed core's is taken over by the next) and, while `serve` holds it, answers who does, composing nothing, so main refuses to start, saying so in a native dialog; `serve` refuses while the app holds it. A window that reloads, crashes, closes or switches canvases ends no session: it only views the core runtime (`core/windows.ts`). Genuine canvas close, deletion, a project/workspace switch, explicit restart and app quit may still end sessions. Linux locks identify their owner by boot ID and process start ticks, never wall-clock-derived `ps` times; macOS keeps `lstart`. An inspection failure, or a wall-clock-only Linux lock record whose pid is still alive, cannot authorize taking the profile.

- Paths the core opens, saves to or works in (canvases opened from and saved to, the folders agents run in) are `TrustedPath`s (`core/host.ts`): from a dialog you completed (`host/dialogs.ts` returns an unbranded path; `core/host/app.ts` brands its answer in the core process), or from canvas memory reading back a path it wrote, as the journal does with a canvas's run, or a workspace's checkout once `verifiedCheckout` (`src/main/core/workspaces/checkout.ts`) has checked, at that use, that it is the checkout the core made of the picked repository in the owned root there: the repository's real path and identity, the owned root, its folder, `.git` and registration agreeing, and Git finding it as its own top level (see [Workspaces](workspaces.md)). A workspace record's path alone is never trusted. No command line mints one, so `corrallm serve` runs a canvas only from the file and in the folder canvas memory keeps for it, picked in the app (`Core.keptCanvas`; it has no `--project`).

- Outside tokens are made, renewed and revoked by a person (`corrallm serve --new-token`, or `corrallm token new|renew|revoke`, each only with stderr on a terminal), named (the name is the party, `outside:<name>`; a new or renewed token of a live one's name replaces it at once), reach only the canvases named when made, by their stable ids, read-only, read-write, or read-write with `--no-merge` (B9b Q30: a writer, `outside-write`, that merges no agent's branch; `merge-permits`, checked in core.call on every op that carries it, refuses it, whatever op runs the merge), expire within 12 hours (1 by default), and are kept only as a SHA-256 hash (`tokens.json`, 0600), a new token forced to disk (`writeWhole`'s `durable`) before it is printed, so no power loss brings back the one it replaced, as is a revoke. A token replaced, revoked or expired is refused at once: a call it has going ends with `TOKEN_REPLACED`, and its next request is answered 401 with that sentence (its hash known for that while the owner runs). A new one is printed once, on that terminal, or, with `--into <file>`, written only to that file, 0600 (the one store of a token's value, Build Plan B30), so that a client's headers helper (`corrallm token header --from <file>`, which opens a regular file without following a final symlink or blocking on a FIFO, checks the opened inode is the user's alone, reads at most 1,025 bytes (refusing more than 1,024), and prints the header only on its stdout, to the client that runs it) reads the current token each time it connects and a renewal into the file needs no restart; no log, result, store of corrallm's or child process's arguments ever hold it. Orchestrators register corrallm by the variable that holds it (`CORRALLM_OUTSIDE_TOKEN`, under the server name `corrallm-server`) or by that helper, which names the file, never the token; `corrallm wait` reads it only from its environment, or from the file `CORRALLM_OUTSIDE_TOKEN_FILE` names, checked as the helper checks it, and sends it only to http on 127.0.0.1 or localhost, with no credentials, query or fragment (`loopbackUrl` in `url-policy.ts`). No operation a token can call creates, renews or widens a token. The no-merge restriction is the token's access itself (`write-no-merge` in `tokens.json`, and in the token socket's strict request and answer), never a field beside `write`: a renewal makes the new token with the live one's access, so it keeps the restriction, and a corrallm that doesn't know the value (one from before it) reads that entry as no token and drops it as it writes the store, and its socket refuses a request for one, so a downgrade stops such a token working rather than making it a writer that may merge.

- `corrallm token` asks whichever corrallm owns the profile (the app's core or `serve`) over the profile's token socket, never MCP (`core/token-socket.ts`): `<profile>/token.sock`, a Unix domain socket that only the profile's user can open. Its owner, holding core.lock, binds it under umask 077 (`listen` binds before it returns, so it is never anyone else's to open), sets it 0600 and checks that it is a socket of the user's with no bit for anyone else, at a canonical profile path of the user's that no one else may write to. Every ancestor must belong to the user or root and prevent replacement by other users (a sticky shared ancestor such as /tmp protects its checked child entry too), so another user cannot swap the profile between check and bind/connect; otherwise it doesn't serve it, saying why, and runs on. A socket there is one an owner that died left behind, which it replaces; anything else there it leaves alone, and serves none. The OS checks write permission on the socket at every connect (Linux and macOS both do), which is the check: Node can't read a peer's credentials, so a local process of the same user can open it, as it can read the profile (the OS user is the boundary, Build Plan Q7). No token is asked for or accepted on it, so it is no token's path. Its client asks only a socket that is the user's alone, in such a folder, never a link, so another user can't stand in for the owner. One request a connection, one line of strictly validated JSON each way (at most 64 KiB in UTF-8 bytes, newline included; a client idle 10 seconds is dropped): canvases are named by absolute files, which the owner looks up in canvas memory as `serve --canvas` does, so no path is trusted for it, and closing waits only for a request being answered. An oversized successful answer omits only optional canvas file labels, preserving the token and every canvas id. With nothing owning the profile, `corrallm token` checks the same canonical profile and ancestors before taking core.lock and writing tokens.json. Token files on Windows are refused too until private ACLs can be checked. Windows, whose equivalent would be a named pipe only the user can open, is held with Windows: neither side tries one there, and both say so.

- Read-only Git commands share `SAFE_GIT_OPTIONS` (`src/main/git.ts`), the baseline disabling fsmonitor and implicit bare repositories. Patch-producing commands additionally use `safeGitDiffArgs` for diff/log/show: first read the configured driver keys with `git config --null --name-only --get-regexp '^filter\..*\.(clean|process)$'`, then pass them to the helper. Its command arguments disable external diff, textconv and, for log and show, signature verification (`--no-show-signature`: a repository's `log.showSignature` would run its `gpg.program`; diff never verifies, and refuses the option), show a submodule by its commit only and never ask whether it is dirty (`--submodule=short --ignore-submodules=dirty`: either starts a git in the submodule under its own configuration, whose external diff and filter drivers nothing here reaches; only the command-line flag outranks a committed `.gitmodules` `ignore`), and blank each filter's clean/process commands and set its required flag to false; it throws for a driver whose name holds `=`, which `-c` (split at the first `=`) cannot name, so such a repository gets no patch rather than running its driver. The caller still prepends `SAFE_GIT_OPTIONS`, and runs git with `SAFE_GIT_ENV` over its environment: `GIT_NO_LAZY_FETCH=1` and `GIT_ALLOW_PROTOCOL` set to the empty string, so a partial clone's patch of a blob it lacks fails rather than fetching it, since the fetch would run whatever its remote names (an `ext::` command its configuration allows, its upload-pack or ssh); Git before 2.45.1 (and its 2.39.4+ backports) ignores the first, and the second admits no transport or external helper (a literal `none` would allow a helper named `git-remote-none`). Codex's App Server `/diff` uses this shared helper and environment for both tracked and untracked files; the workspace runner's environment includes it. File suggestions (`src/main/files.ts`) use it too: expanding a sparse index during `ls-files` may fetch a promised tree, even though it reads no blob bodies.

- Workspace Git (making and checking worktrees, and B9b's diffs and merges) goes only through `GitRunner` (`src/main/core/workspaces/git.ts`; see [Workspaces](workspaces.md)): git by absolute path from the PATH's absolute folders, no shell; on every call `SAFE_GIT_OPTIONS`, an empty private hooks folder of the core's as `core.hooksPath`, no submodule recursion, `protocol.allow=never` and `GIT_ALLOW_PROTOCOL` naming no transport (no fetch, lazy or otherwise, so no ssh, `ext::` command or credential helper; the environment variable because a repository's `protocol.<name>.allow` outranks `protocol.allow`, and Git older than GIT_NO_LAZY_FETCH lazily fetches a partial clone's missing blobs while populating it) and no auto-gc or maintenance; every filter driver configured where the call runs disabled by name (clean, smudge, process, required), and configuration it can't neutralize refused (a driver `-c` can't name, `core.worktree`, configured `hook.*`); patches add `safeGitDiffArgs`; every `GIT_` variable removed from the agents' environment; bounded time and output; each git a child the core owns. Discovery (`src/main/core/workspaces/discovery.ts`) refuses a folder inside a repository, a `.git` symlink, a `.git` file or registration that doesn't agree with the folder picked and a `core.worktree` redirect, and never takes a failure to read a repository for a folder that isn't one. The owned root (`src/main/core/workspaces/owned.ts`) is verified before anything is written in it: real folders the user owns from the checkout's real path down, no symlink, private, marked by the core (in the common Git directory, by path, device, inode and nanosecond creation time, refusing missing creation times and incomplete older markers on nonempty roots, so `git clean -fdx` can't unmark it and a folder put in its place isn't taken for it); `info/exclude` is never written through a symlink. What a workspace's Git writes in the common Git directory (`src/main/core/workspaces/metadata.ts`: its branch's loose ref, reflog, `packed-refs` or `reftable/`, and `worktrees/` with its registration) is verified before a creation or removal writes anything, and again before and after each of Git's writes: the user's real folders and files, no link anywhere along them; worktrees are registered by absolute paths, so the configuration is never written. The checks stop a link that is present before or after a write, not one a process running as the user swaps in and out within it. Provisioning writes over no file it finds: it populates only a checkout holding nothing but its `.git`, by a merge Git refuses to write over a file with, and a population a crash left unmarked is adopted only when it is exactly what Git wrote, else held for you (`interrupted-population`), never populated again by a restart or a retry. B9b's merge calls add the runner's merge profile: replace refs ignored, `merge.renormalize=false`, every configured custom merge driver blanked by name (one `-c` can't name refused), so a path that needs one fails closed, and Git 2.39 or later. The install is only a fast-forward to a prepared commit named by its object id, with fixed flags (`--ff-only --no-overwrite-ignore --no-verify-signatures --no-autostash --no-stat --no-squash --no-edit`) that beat the repository's merge options, so it computes no merge and Git refuses an ignored or untracked file in its way, writing nothing then but ORIG_HEAD; a merge's commits are plumbing, by the identities given, never signed and never edited; a checkpoint's temporary index (GIT_INDEX_FILE) is only one the merge service made in a private folder of the profile's. What a merge's Git writes in the Git directory, loose objects included, is checked as a workspace's metadata is (`verifyMergeWrites`, ORIG_HEAD's log included). Before any of a merge's effects, its selectors and checks (`src/main/core/workspaces/merge-select.ts`, `merge-checks.ts`, `uncommitted.ts`; see [Workspaces](workspaces.md)) decide what it is between and whether it may go on: the destination is the branch HEAD names in the checkout discovered again from the canvas's picked TrustedPath, which must be the workspace's repository, never minted and never treated as an owned root, refused detached, symbolic, one of corrallm's own or checked out in another worktree; the source is only the agent's generated branch in its verified checkout, on that branch, ready, with no change waiting; a caller's pins are compared with what is read, never passed to Git. Your checkout must be clean as `status --no-optional-locks` reads it (no lock taken, nothing rewritten), its filters blanked, with full stat checks and no order file whatever the repository configures, with no operation in progress, no index or ref lock, no skip-worktree or assume-unchanged entry, no sparse or split index, not shallow and without grafts. A merge is refused before anything changes when it would write into `.corral/worktrees` (compared folded whatever `core.ignoreCase` says), change a submodule (whatever the repository's configuration says to ignore), write a file a configured filter applies to or change a `.gitattributes` while one is configured (naming the files and giving the `git merge --no-ff` to run yourself), or need an object the repository lacks (never fetched); ignored files where it writes are named first, best effort. An agent's uncommitted work is read without a lock and digested as `add -A` would store it, links by their text and nothing written, and offers no commit when it is partly staged, unmerged, a submodule or nested repository, a copied local file, filtered, named in a way that isn't UTF-8, hidden from status, a file with a second name (a hard link: untracked, or tracked whether changed or not, which Review changes then shows unreadable, without its patch) or too much to read. Review changes (`src/main/core/workspaces/diff.ts`) only reads: it makes or repairs no worktree, takes no lock, writes nothing and runs no repository program; its patches go through `GitRunner.patch` (safeGitDiffArgs, every path literal and after `--`, no optional lock, capped), with replace refs ignored and the committed pairing and order pinned; untracked files are read by the core, under real folders only, opened without following a link, a regular file with one name, at most 1 MiB, a link shown by its text; `shared` names only the members the caller's own worktree listing reaches; and paging retains nothing, its cursor a compared value (never a Git argument or a reach id) binding the tip, the digest and the review's state, so a page never mixes two states of the work. The merge (`src/main/core/workspaces/merge.ts`; see [Workspaces](workspaces.md)) runs in its repository's lane of the one provisioning queue, its admission, checks and every pin read again in the lane and again just before the install; it is prepared away from your checkout, writing only objects (`merge-tree` in your checkout so its attributes apply, its merge drivers blanked; `commit-tree` by your Git identity as Git resolves it there, none invented, with a `Corrallm-Requested-By:` trailer), then recorded on disk (`merge_job`) and installed only by that fast-forward. Past the install's start it is never cancelled, quitting waits for it, and anything but your branch at the merge, HEAD on it, ORIG_HEAD your commit, the index the merge's tree and the files clean is `held` for you, never called merged or unchanged; nothing is reset and no lock removed. Git refusing the fast-forward over a file in its way is the one "nothing changed" past that point, ORIG_HEAD put back. A restart reconciles a merge left going on by what your checkout shows, before any new work in the agent's tree or any merge into its repository, never by running it again. An agent's uncommitted work is committed only when the caller chose it, bound to the digest it reviewed, as corrallm, on the agent's own branch, through a temporary index (the agent's index untouched until its branch holds the commit, then reset to it without writing a file), and published only after your checkout was checked to be the merge.

- A worktree's setup (`src/main/core/workspaces/setup.ts`; see [Workspaces](workspaces.md)) runs only what the core fixes: the command you set for the picked repository (`project.setSetupCommand`, yours alone: D1, `trust-gate`; one line of at most 4 KiB with no control, format or separator character, so what the card shows is what runs, under the fixed POSIX shell), or the fixed table's for its base commit's lockfile (pnpm, npm: an argument list, no shell, the executable only from the PATH's absolute folders), never a token's, a canvas's, a file's or the repository's own (its scripts, its `packageManager`, its manifest). Each setup is one card for you alone: it names no agent, so no token's Needs holds it and no token's reach names it, R3 refuses a token's `reply`, and the service refuses any party but you again. It is answered only at the generation it shows: a changed command clears Always and raises a new card, so an older answer is stale, and Run checks again that what may run now hashes to what was shown. Your approval and the running attempt are on disk before anything runs; Always runs that exact command only, by itself only in the repository's later new workspaces, until you clear it (`project.clearSetupApproval`, yours alone: D9, `permissions`). It runs in the checkout verified at that moment as an owned process group (`spawnOwned`: never unowned, recorded until its output closes), which Stop, its timeout and the core closing end whole; a crash's group is ended as the next core starts and its setup is marked interrupted, never run again by itself. Its output, which may hold secrets, goes only to a private bounded log in the profile and, escaped, to your card. No setup runs on Windows: ending its process tree there is a release blocker. A worktree is removed only once that is safe, or as you decided (`src/main/core/workspaces/cleanup.ts`, B9a C7): what it holds is read in its verified checkout (its changed and untracked files, whether its HEAD and branch are reachable from the picked checkout's HEAD now, who may still write there, a setup running), running no repository program: a submodule is read by its commit only, never asked whether it is dirty (Git would ask a git run in it under its own configuration), and one checked out there may hold work, so the tree is unknown with one, whoever's change asked (a token's delete preflight included); clean, merged and with no writer, it goes with its last agent; otherwise the deletion applies nothing until you confirm it, yours too, through the same proposals as a token's R4 delete (Delete keeps its work, Discard removes it and its branch), each bound to what it held when asked, so work added meanwhile settles it stale. If assessment cannot fingerprint a tree whole (including a checked-out submodule, an unreadable tree or one past the entry cap), Discard is not offered and is refused on replay; it can only be kept, including when an older removal resumes. A file's Apply or a discard keeps what it would lose. Git removes only the checkout verified as the one made (never one a link stands in for, forced only for a discard you approved, with every filter its own configuration gives it disabled too), and its branch only at the commit decided. A kept tree's removal (`worktree.remove`, yours alone: D1, `trust-gate`) asks the same way. This is the `workspace-safety` rule (RULES; B9a §7), checked on everyone's change, yours too, not only a token's, and whatever builds it (an op, a batch, a file's Apply, a revert, a build no single op makes): besides that confirmation, every commit's plan is checked (`unsafeStep`, in the preflight and in the write, failing closed) so no change binds an agent working in a tree to another, makes it a new one or unbinds it while it stays (its move waits for your Switch), and no document change runs, approves or changes a setup. Retrying a worktree (`worktree.retry`) is yours alone (D1, `trust-gate`): it retries only the recorded creation or recovery, never forces, resets, deletes or switches anything, and a setup it reaches still asks you on its card. Who works where (`worktree.list`) is every caller's, as far as each reaches now: a token is told only the agents it reaches (one item each, so a shared tree names no member it doesn't reach, and its group's node only where canvas.get shows it), never a checkout's location, its setup command or log, the cards on it, why it failed, or the kept trees; its `worktrees:<c>` topic is a window's alone (D5). A workspace change's Switch is yours alone, under the workspace mutation gate, keeping the trees its agents leave. Local files (`src/main/core/workspaces/copy.ts`) are copied only as the base commit's `.worktreeinclude` selects among files Git ignores in the picked checkout: never through a symlink on either side, never over a file the workspace has or tracks, within limits, all or nothing, private, recorded by name and hash only.

- Setup copying also refuses multiply linked source files: an ignored pathname is not permission to read the same inode through a hard link from outside the checkout. A crash copy is adopted only when private and singly linked; tracked names are protected case-insensitively. Failed publication flushes remove the current copy as well as earlier files of that attempt. Setup completion cleans up its group even when descendants closed their output; cancellation during preparation is rechecked at spawn. The human setup preview preserves command whitespace. These are checks within checkout isolation, not an OS sandbox against a process already running as the user.
