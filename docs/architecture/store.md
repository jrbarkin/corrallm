# Core database

## `src/main/core/store/`

The core's database (B9.0, Core Database §5): <profile>/core.db, through Node's SQLite, which sqlite.ts alone reaches, lazily (`process.getBuiltinModule`, never a static import, which the bundler would hoist above the CLI's check of Node's version; a test keeps it so). open.ts is openStore, which never rejects: core.db made 0600 before SQLite opens it (so its -wal and -shm are too); one that was there checked read-only first (a transaction a crash left in its rollback journal, as while it is set up, rolled back first; corrallm's application id, meta.min_reader, quick_check: faults.ts); then incremental vacuuming on a new one, WAL, synchronous NORMAL (no sync as SQLite commits: the store flushes its log itself) and F_FULLFSYNC on macOS for each sync SQLite does make (checkpoints), foreign keys, an untrusted schema, a 4 MiB journal size limit, no automatic checkpoints, no busy timeout (the core is the only writer), and migrations.ts' forward-only migrations (each with its user_version and meta.min_reader in one transaction, run with foreign keys off, so one may rebuild a table others refer to, and refused if it leaves a reference to nothing; schema 1: canvas, conversation, run, run_workflow, message, read_position, open_canvas, meta; schema 2, B9's, min_reader 2, so a corrallm of schema 1 refuses it: a canvas's document as rows, document, node, link and queue_item (WITHOUT ROWID, foreign keys checked as each statement ends, never deferred), its revisions and what each changed (revision, change), proposal and file_review; schema 3, min_reader 3, below; every table STRICT, the side of every foreign key that refers indexed).

Schema 3 (migrations.ts' third) keeps workspaces: each canvas's agents work in checkouts of their own of the repository picked as its project folder (Git worktrees, a group's agents sharing one), so a corrallm of schema 2, which would start every agent in the project folder itself and resume there conversations of another checkout, refuses it. It touches no repository; workspaces are made once the store is open. Its tables: `repository` (a picked checkout on this profile: as picked and its real path, its common Git directory and identity, `root_kind` 'project' or 'profile' and the owned folder its checkouts go in, a generation; unique by real path and identity), `canvas_repository` (the repository a canvas's project folder is, none for a folder that isn't one, and the canvas's project generation), `worktree` (a canvas's workspace: path and `branch_ref`, each unique, the base it was made from, `forked_from`, its owner key `agent/<id>` or `group/<id>`, its state, `creating`, `setup`, `ready`, `missing`, `error`, `retained` or `removing`, its generation and error code; at most one active, neither `retained` nor `removing`, per canvas, repository and owner, by a partial unique index; ON DELETE RESTRICT to its canvas, so no canvas is forgotten while it owns one in any state), `agent_worktree` (each agent's binding to a workspace of its own canvas, a composite foreign key, with its active generation and, while a change waits, the desired owner and generation, which must be past it; no reference to the agent's node, so a binding outlives a deleted node until cleanup settles it, and a workspace stays while a binding refers to it), `worktree_job` (an intent recorded before its work: kind, phase, generation, the identity it expects, a JSON payload and an outcome, none while it goes on; one open job of a kind per workspace), `worktree_setup` (a workspace's setup, one generation at a time: the command as offered, its source, `configured`, `detected` or `none`, its spec and copy-manifest hashes, its state, `pending`, `running`, `done`, `skipped`, `failed` or `interrupted`, who allowed it and when, its log key and exit code; nothing past `pending` or `skipped` without an approval) and `project_setup` (per repository: the command you set, none for the detected one, and its shell kind, the spec hash allowed always, when it changed). `conversation` is rebuilt keyed by `(canvas_id, adapter, agent_id, workspace_key)`: every row schema 2 kept moves to `PROJECT_WORKSPACE` ('project', the picked project folder itself), its native id and role fingerprint as they were; a workspace's conversations are keyed by its id. The conversation rebuild precedes the new workspace tables, so its freed pages are reused. `meta.workspace_generation` keeps the high-water mark of binding and pending-plan generations, even after their rows are removed. A job’s immutable `intent_hash` fingerprints its original payload independently of its mutable progress payload.

One a newer corrallm made that this one can't read is refused, left untouched; a damaged one is set aside (core.rejected-<uuid>.db, its -wal first, then -shm and -journal) and the newest snapshot passing the same checks restored, else it starts empty, saying so; a profile with snapshots but no core.db (a restore cut short) is restored the same way, saying so.

Every open numbers each never-reused sequence (migrations.ts' SEQUENCES: message's seq) on from the clock in ms, past every place given before, those whose rows a crash cut off and those a database a restore replaced gave included, so a cursor from before reads what comes next; a restore raises each document's revision the same way (a token's `expect` holds them), and a restore, or an empty start in place of a database, then settles in the same transaction what waited in the snapshot (restored.ts: a message pending there may have gone since, so it is unresolved, never sent, and its sender told by a notice).

What opening wrote is checkpointed (TRUNCATE) before the store is used, so it is on the drive, and the log begun anew (checkpointer.ts' `beginLog`: a write that changes nothing, since SQLite syncs a new log's header on the connection that begins it). store.ts is the open Store: `prepare` (cached), `tx` (transaction.ts: BEGIN IMMEDIATE, a synchronous function, COMMIT, a savepoint within one, rolled back only if SQLite hasn't, as on a full disk; its log flushed on the loop: tests only), `write` (the lane: writes queued in one turn of the loop share one commit, each in a savepoint, each resolving only once that commit returned and its log was flushed to the drive, off the loop: Node's fsync on its thread pool, F_FULLFSYNC on macOS, one flush at a time for every commit made before it began: "on disk before it is sent").

A failed flush fails the store closed: every write and read refused from then on, saying why (once on stderr), until the core opens it again; what it committed since its last flush that worked taken back best effort (the log cut back to where those commits began, as `wal_checkpoint(NOOP)` said before each, and closed while a connection that only reads holds the database, so SQLite checkpoints none of it, and the next open recovers the log up to there alone; every snapshot published since removed, including one whose rename succeeded but publication rejected).

Limit: if cutting the log or syncing that cut itself fails, a write whose flush failed may come back after a restart, in doubt as in PostgreSQL and SQLite.

The store says so on stderr.

No recovery marker is written or checked at open.

Successful writes cost only their WAL flush; normal opens and writes create only core.db, -wal and -shm (snapshots are taken separately, as it closes or once due). `checkpoint` (checkpointer.ts: PASSIVE, once every commit made is flushed, on a worker thread with a connection of its own, whose code is a string run as CommonJS, since the bundles are one file each; sqlite.ts gives the expression it connects with; once it copied all of the log it begins it anew there, cutting it back to JOURNAL_SIZE_LIMIT, and the lane commits nothing meanwhile, so the two connections never write at once), run once idle a second (at most 30 s after the first unchecked commit).

An idle checkpoint with no queued write also runs incremental vacuum on that worker, at most 64 pages per pass, checkpointing its result; another pass waits a second of idle time, and a queued write takes priority.

No drive flush waits on the core's loop while it serves (only opening and closing sync on it).

A commit's own writes into the log do run on the loop, into the system's cache, which the system holds back while other programs write heavily to the drive: G2 holds on a quiet drive, and only the connection on a thread of its own (Core Database §4's fallback, not built) would hold it under such writing. `snapshot` (snapshots.ts: SQLite's backup into backups/core-<time>.db, read through a connection of its own in one step; the backup, conversion to a rollback journal and quick check run on the checkpointer's worker, never scanning the copy on the core's loop; idle checkpoints wait until that snapshot ends, leaving foreground writes free; quick-checked and forced to disk before it is named, never kept with a fault, the newest three kept, what one cut short left removed by the next; taken as it closes and every four hours) and `close` (writes, and transactions outside one, refused from its start; the lane drained and flushed, a TRUNCATE checkpoint, a snapshot, then the checkpointer's thread ended; once).

The worker captures its unused stdout and stderr instead of opening the parent's terminal streams, which may already have hung up when the closing snapshot starts it. `Database` is what the stores kept in it read and write through: the Store, or, when it couldn't be opened, `unopened` (every read and write fails, saying why). createCore opens it first (once core.lock is held: entry.ts, serve) and closes it last, after journaling; what opening it said is said with the first canvas restored, as the journal's warnings are.

Kept in it: canvas memory (memory.ts: canvas, conversation, its agents' conversations by the workspace each CLI ran in, then adapter and agent, `conversationsIn` and `withConversationsIn`; a change remembered as it is made, and written with every canvas changed whose row isn't on disk as it is yet, so one whose write failed is written with the next, and fails `flush` until it is; the 200 canvases used most recently with a file, folder or conversations, by used_at, and apart from them the 200 drafts used most recently (each New makes one, with its run), so drafts never push out a saved canvas; the rest forgotten with all the database keeps of them, their runs and documents included, but never one open, nor one with edits not saved, `Documents.unsaved` (a canvas displaced from its file by another's Save As counts as unsaved, even when its text still matches the saved hash), nor one that owns a workspace record in any state; `forget` drops one, a draft discarded, resolving with whether it did: a canvas that owns a workspace record is kept whole, and `Documents.forget` keeps its live document then), each canvas's document (canvas/documents.ts: document, node, link, queue_item, revision, change) and the run journal (run-journal.ts: run, read_position, open_canvas, each referring to its canvas's row, which it makes for a draft: `ensure`; `keep` and `moveRead` within a write another store makes too) and the message store (delivery/messages.ts: message, each message a row with what it told and its withdrawal note) and the workspace store (`src/main/core/workspaces/store.ts`, WorkspaceStore: repository, canvas_repository, worktree, agent_worktree, worktree_job, worktree_setup, project_setup). The workspace store writes only within a write, its own (`write`) or another store's (a document commit's `within`, the run journal's), keeping nothing in memory, so a failed write leaves nothing to undo; it checks every id, absolute path, ref, OID, hash, code and command it is given (`invalid`), and applies the same validation when reading them back, failing the read otherwise rather than guessing. Generated branches keep their narrow ASCII shape; a picked checkout’s captured base ref accepts Git’s full-ref shape, including Unicode and punctuation, without accepting a leading option or invalid ref syntax. Workspaces move only along fixed edges from the state the caller expects (`transition`: `stale` if elsewhere, `refused` for an edge it lacks; a ready or setup workspace cannot go directly back to `creating`, a `retained` one only goes `removing`, a `removing` one may stay so with its cleanup error or go back to `retained`; `error` and `missing` carry an error code; their retry may re-enter `creating`, so provisioning must reconcile the actual Git registration and checkout first, never recreate over existing work). A binding's generation is allocated in the same transaction as its binding, from the clock past the durable high-water mark in meta, so clearing a plan, deleting a binding or restarting with the clock set back never repeats a published generation; a plan waits beside it (`plan`, `clearPlan`) until `bind` installs it at the generation reviewed, and `advance` moves a workspace and its bindings on (a plan waiting moves past them). Jobs are idempotent by id and their original intent hash (object-key order ignored), even after their progress payload changes, one open of a kind per workspace, phases and outcomes compare-and-set (`advanceJob`, `finishJob`; `openJobs` is what a restart finishes). Setups are offered a generation at a time, run only once allowed with the approval on disk first (`startSetup`), and `interruptSetups` marks every running one interrupted as the core starts, never to run again by itself. `setProjectCommand` (a bounded one-line command and its shell kind) clears Always whenever either changes. A workspace record is forgotten (`forget`) only once `removing`, unbound and with no job going on. It does nothing to a repository or a file and mints no `TrustedPath`: a path it reads back is a record, to check again before use. test-store.ts seeds and reads a profile's database for tests, through the stores' API (keepCanvases, keepMessages, openedLast, forgetRun) or a connection of the test's own (onDisk, journaledRun, readPositions, refuseWrites: triggers that fail a table's writes; madeAtSchema: a new database made as a corrallm of an earlier schema made it, to seed what that one kept and test a migration), never by writing its files. schema-3.test.ts keeps a canvas through today's stores, copies its rows into a database made at schema 2, and checks migration 3 keeps every row, that today's stores read it, that a failed migration leaves schema 2 as it was, that a corrallm of schema 2 refuses the result, and that a schema-2 snapshot restores migrated.

An oversized run (over MAX_RUN_BYTES, 32 MiB) leaves its last good checkpoint in place and keeps a saveError in the run's JSON in the same commit as its messages.

Messages still reach the drive before delivery; size alone never fails them. run:get reports saveError (and a restore notice), and Needs shows a canvas-wide `unsaved/<canvas>` warning, with no answer.

A smaller checkpoint or forgetting the run clears it.

A renderer's oversized run:save records the warning then rejects, so it never claims to have saved progress; core journaling can continue.

Restart restores only the last checkpoint that fit, paused, with that warning. `dump` (store/dump.ts, cli/dump.ts) reads repositories (schema 3, with their setup), canvases (including their document's rows, conversations and, from schema 3, their workspace records: repository, worktrees with their setups and jobs, bindings), runs and messages as JSON lines in one read transaction, including committed WAL rows.

It uses SQLite READONLY and query_only, never the store's writer, migrations, recovery, checkpoints or core.lock.

It shares open.ts' application-id, min-reader and integrity checks, refusing before its first line; schemas 1 and 2 can be inspected without migration.

As with any SQLite WAL reader, it participates in -shm and may create an empty -wal/-shm on a closed database; it writes no database page or WAL frame.

A slow output pipe pins its read view (the owner's writes still continue) and is awaited, never accumulated in memory.
