## `src/main/core/store/`

The asynchronous write lane keeps FIFO order, appending no SQL while its log flush runs. Each commit stops between atomic writes after 32 changed rows or 16 writes (including writes changing no rows); one write stays intact even when larger. The next group runs in the lane’s next turn after the previous flush. This bounds queued aggregation and avoids competing with our own fsync; synchronous SQLite still cannot bound operating-system write latency.

An optional failure callback on `Store.write` restores in-memory staging synchronously when a savepoint, commit or flush fails, before another queued savepoint can consume it; it never marks a successful write durable before the log flush.

The core's database (B9.0, Core Database §5): <profile>/core.db, through Node's SQLite, which sqlite.ts alone reaches, lazily (`process.getBuiltinModule`, never a static import, which the bundler would hoist above the CLI's check of Node's version; a test keeps it so). open.ts is openStore, which never rejects: core.db made 0600 before SQLite opens it (so its -wal and -shm are too); one that was there checked read-only first (a transaction a crash left in its rollback journal, as while it is set up, rolled back first; corrallm's application id, meta.min_reader, quick_check: faults.ts); then incremental vacuuming on a new one, WAL, synchronous NORMAL (no sync as SQLite commits: the store flushes its log itself) and F_FULLFSYNC on macOS for each sync SQLite does make (checkpoints), foreign keys, an untrusted schema, a 4 MiB journal size limit, no automatic checkpoints, no busy timeout (the core is the only writer), and migrations.ts' forward-only migrations (each with its user_version and meta.min_reader in one transaction, run with foreign keys off, so one may rebuild a table others refer to, and refused if it leaves a reference to nothing; what a migration's SQL can't do, its `convert`, runs within that same transaction, through its connection, after its SQL and before what it leaves is checked: migration 4's alone, `src/main/core/store/conversion-4.ts`, which only migrations.ts imports and which refuses to run outside migration 4; schema 1: canvas, conversation, run, run_workflow, message, read_position, open_canvas, meta; schema 2, B9's, min_reader 2, so a corrallm of schema 1 refuses it: a canvas's document as rows, document, node, link and queue_item (WITHOUT ROWID, foreign keys checked as each statement ends, never deferred), its revisions and what each changed (revision, change), proposal and file_review; schema 3, min_reader 3, schema 4, min_reader 4, schema 5, min_reader 5, schema 6, min_reader 6, schema 7, min_reader 6, schema 8, min_reader 6, schema 9, min_reader 9, schema 10, min_reader 10, schema 11, min_reader 11, schema 12, min_reader 12, schema 13, min_reader 12, schema 14, min_reader 14, and schema 15, min_reader 15, below; every table STRICT, the side of every foreign key that refers indexed).

Schema 3 (migrations.ts' third) keeps workspaces: each canvas's agents work in checkouts of their own of the repository picked as its project folder (Git worktrees, a group's agents sharing one), so a corrallm of schema 2, which would start every agent in the project folder itself and resume there conversations of another checkout, refuses it. It touches no repository; workspaces are made once the store is open. Its tables: `repository` (a picked checkout on this profile: as picked and its real path, its common Git directory and identity, `root_kind` 'project' or 'profile' and the owned folder its checkouts go in, a generation; unique by real path and identity), `canvas_repository` (the repository a canvas's project folder is, none for a folder that isn't one, and the canvas's project generation), `worktree` (a canvas's workspace: path and `branch_ref`, each unique, the base it was made from, `forked_from`, its owner key `agent/<id>` or `group/<id>`, its state, `creating`, `setup`, `ready`, `missing`, `error`, `retained` or `removing`, its generation and error code; at most one active, neither `retained` nor `removing`, per canvas, repository and owner, by a partial unique index; ON DELETE RESTRICT to its canvas, so no canvas is forgotten while it owns one in any state), `agent_worktree` (each agent's binding to a workspace of its own canvas, a composite foreign key, with its active generation and, while a change waits, the desired owner and generation, which must be past it; no reference to the agent's node, so a binding outlives a deleted node until cleanup settles it, and a workspace stays while a binding refers to it), `worktree_job` (an intent recorded before its work: kind, phase, generation, the identity it expects, a JSON payload and an outcome, none while it goes on; one open job of a kind per workspace), `worktree_setup` (a workspace's setup, one generation at a time: the command as offered, its source, `configured`, `detected` or `none`, its spec and copy-manifest hashes, its state, `pending`, `running`, `done`, `skipped`, `failed` or `interrupted`, who allowed it and when, its log key and exit code; nothing past `pending` or `skipped` without an approval) and `project_setup` (per repository: the command you set, none for the detected one, and its shell kind, the spec hash allowed always, when it changed). `conversation` is rebuilt keyed by `(canvas_id, adapter, agent_id, workspace_key)`: every row schema 2 kept moves to `PROJECT_WORKSPACE` ('project', the picked project folder itself), its native id and role fingerprint as they were; a workspace's conversations are keyed by its id. The conversation rebuild precedes the new workspace tables, so its freed pages are reused. `meta.workspace_generation` keeps the high-water mark of binding and pending-plan generations, even after their rows are removed. A job’s immutable `intent_hash` fingerprints its original payload independently of its mutable progress payload.

Schema 4 (migrations.ts' fourth, B11 Design §4, §16 item 2) keeps your manual messages in the mailbox, never in a run checkpoint, and each run in an envelope of its own, so a corrallm of schema 3, which would journal a window's checkpoint over it, write messages with no origin and take a resend for a reply, refuses it. `message` is rebuilt (its rows set aside in a temporary table first, so the new table takes the old one's pages; every place given stays given, the newest deleted ones' too) with `origin` (`manual`: typed by you, which goes past the run's holds; `party`: a party's or corrallm's message, reply or record; `run`: the run's own, none yet; `resend`: one you asked to send again, which waits on the holds as any other's does), NOT NULL with no default, so every row written names it; `display` (JSON: the task row it follows, `after`, the held task it corrected, `task`, the text shown if not its body, how many images it carried and whether it can't be sent without them, `requiresImages`; never an image's bytes); and `resend_of` (the message it sends again, only a resend's: never its `reply_to`, which is only a reply's, or a record's about another message). Each existing row is classified by what made it: Interrupt and resend's (PR #31: its `told` key `resend:<reply_to>`, or `resend:<reply_to>:images`, which made it one) becomes `resend`, its `reply_to` moved to `resend_of` and its `told` cleared, one that needed images it no longer has requiring them; any other of yours `manual`; everything else `party`. Then its conversion converts every canvas's run, opened since or not, in the same transaction: a run journaled as schema 3 did (`{ version: 2, state, messages, saveError? }`, or `{ saveError }` alone) becomes `{ format: 3, run, saveError? }` (`run` its state as kept, `updated_at` as it was), and each manual submission its `messages` held your message to its agent, after every message the canvas has, unless a message already represents it (matched by the agent it went to and the native id delivery handed it under, `delivery.as`, or by its own id: never by an equal body), which keeps its own record, gaining only the `display` its submission showed; a new one is `manual` (or `resend`, linked by `resend_of` to the message its `retryOf` named, where one is kept), its body the submission's text (cut, marked so, to the most a message's body holds, `MAX_MESSAGE_BYTES`, where it is longer: its `display` then holds the whole), `replied` with its result (one that kept no result its status, with that status's plainest reason) or `unresolved` (one queued or running as the profile closed, never sent again), `delivery.as` its native id, and the time the run holding it was journaled its `sent_at` (a submission kept no time of its own). It reads what schema 3 kept as the code of schema 3 read it, its own frozen copy of those checks and limits: a run it can't read so (a part that isn't JSON, beyond the journal's bounds, a submission record no engine wrote) is left as it was, and the journal, which reads only its own envelope, discards it as it next restores the canvas, saying so.

Schema 5 (migrations.ts' fifth, B9b Design §9 C8) adds the merge journal, `merge_job`: a merge of an agent's branch into your picked checkout's branch, recorded once its commits are prepared and before anything of your checkout changes, so that a restart finds what it did by what your checkout shows and never runs it again. A corrallm of schema 4, which would neither reconcile an install a crash interrupted nor hold the agent's worktree until it is, refuses it. A row holds its canvas (ON DELETE CASCADE), agent and workspace (`workspace_id`, no reference: the row outlives the workspace's cleanup), its repository (RESTRICT), who asked (`caller_key` and `request_id`, unique together, so a caller's repeated request is answered from the row, across a restart too), its `intent` (JSON, immutable: the destination checkout's real top level, Git directories and repository identity, its branch and the commit pinned, the prepared merge commit and its tree, the agent's branch, tip and checkpoint commit with its digest, ORIG_HEAD as it was, the requester and a digest of the request's arguments) and `intent_hash`, its `phase` (`installing`, `installed`, `published`, `done`), its `outcome` (`merged`, `refused`, `interrupted`, `held`, `superseded`; none while it goes on) and `sentence`. At most one goes on per repository (a partial unique index); settled ones are kept. It is not `worktree_job`: those rows go with their workspace, one open job of a kind is kept per workspace, and an older reader would fail on a kind it doesn't know. `src/main/core/store/schema-5.test.ts` keeps a profile as a corrallm of schema 4 kept it and checks migration 5 keeps every row, that today's stores read it, that a failed migration leaves schema 4 as it was, and that a corrallm of schema 4 refuses the result.

Schema 6 (migrations.ts' sixth, after B9b's merge journal; B11a Design §12 C1, C2) keeps an agent's fallback chain, with where corrallm switched it in that chain, and its handoff settings in its `node` row (`fallback`, `handoff`: JSON as the document has them, an agent's only, null for none), read and written with the rest of the row (canvas/documents.ts), so a restart finds the chain and whether the agent was switched. A corrallm of schema 5, which would read agents without their chain and change how they run with a stale place in it, refuses it, as it refuses a version-3 canvas file.

Schema 7 (migrations.ts' seventh, B13 Design §9.2 C9) adds one nullable JSON column, `message.settled`: what a record of a native prompt's decision decided, typed and value-free (see [Messages](messages.md)). A column only, so it keeps min_reader 6: a corrallm of schema 6 still opens the database, reading and writing its own columns by name and leaving this one as it is. The message store writes it with the record's row and never changes it after (an update by either schema leaves it); a value it can't read (another version's, or one holding a field it doesn't know) leaves its row unread, as an unreadable `display` does. `dump` decodes it with the other JSON columns.

Schema 8 (migrations.ts' eighth; B11a Design §12 C7, §12.4) adds `handoff`, one row per agent while it is on the canvas (`canvas_id`, `agent_id`, ON DELETE CASCADE with its canvas): the exact text of the agent's latest accepted handoff (`text`, at most 16 KiB of UTF-8, none until one is accepted), with when (`at`), which CLI wrote it (`source`: adapter, connection, model, JSON), the task it was on (`during`: owner and item, JSON, nullable) and its size (`bytes`, its text's length in UTF-8), all four present or none; the switch it waits to be carried for (`carry`, nullable), and why there was no handoff to carry as that switch was made (`carry_why`: `reached`, its context never reached its ask point; `unaccepted`, it did but no handoff was accepted; `off`; or `unreported`, its connection reported no context; kept once carried); and the Markdown copy last exported and how its latest export went (`exported`: path and SHA-256, and `done`, `refused` or `failed`, JSON, nullable). Only a table is added, so min_reader stays 6: a corrallm of schema 6 or 7 reads what it knows as it was and never writes this table. The handoff store (`src/main/core/delivery/handoffs.ts`: HandoffTable, and HandoffStore per canvas) keeps each canvas's rows in memory and writes them only within a write: with every write of the canvas's messages and run (an accepted handoff in the write recording its reply; a carry cleared in the write recording the send that took it), within a switch's document commit (its `carry` column alone, `stageCarry`, undone if that write fails), or in a write of its own (`durable`: what was exported, and the rows of agents no longer on the canvas, deleted as it opens). A row it can't read (a newer corrallm's) is left as it is.

Schema 9 (migrations.ts' ninth, B21 Design §9.2 C6) adds one nullable JSON column, `message.ask`: on an ask's row (a message of kind `prompt` from its asker to its recipient) its questions, deadline, whether it was sent to the asker's manager and, from C5, its task; on an answer's row the ask it answers and the answers by question id, or the reply text that answered it (`src/shared/model/asks.ts`). It requires reader 9, which preserves open asks and their answer framing. The message store writes it with the row and never changes it after. An ask's settlement goes in the existing `settled` column, written once as the ask ends (`coalesce`: a row that has one keeps it, so neither a native decision's nor an ask's is ever written over). A value it can't read leaves its row unread, as an unreadable `settled` does; `dump` decodes it with the other JSON columns. There is no ask table: the open asks are an index each canvas's delivery rebuilds from its messages as it opens (see [Messages](messages.md)).

Schema 10 (migrations.ts' tenth, B21 Design §9.2 C8) adds one nullable JSON column, `message.verdict`: on a `result` record (a message from an agent to corrallm, its `task` the attempt it reports, its `replyTo` the turn it reported in) the outcome its agent reported with `complete`, `succeeded` or `failed`, and its summary, in the agent's own words, at most 4 KiB of UTF-8 (`src/shared/model/results.ts`). It requires reader 10, which preserves the fixed report when judging or recovering its attempt. The message store writes it with the row and never changes it after; a value it can't read leaves its row unread, as an unreadable `ask` or `settled` does; `dump` decodes it with the other JSON columns.

Schema 11 (migrations.ts' eleventh, B21 Design §9.2 C9) adds `loop_pair`, the loop breaker's counts: one row per pair of agents of a canvas while the turns delivered between them since you last gave either input are above zero (`canvas_id`, ON DELETE CASCADE with its canvas; `a` and `b`, the two agents' ids ordered by their UTF-8 bytes, as SQLite's BINARY collation orders them; `turns`, at least 1; `a` and `b` differ). Counts only: no text and no message id. It requires min_reader 11: a corrallm without the breaker would send a turn it holds, so none older may open the database once this ran. The loop store (`src/main/core/delivery/loops.ts`: LoopTable, and LoopStore per canvas) keeps each canvas's rows in memory and writes them within every write that holds the canvas's message changes (`MessageStore.writeAlso`: a turn's count is on disk with the `delivering` record it counts), or in a write of its own (`durable`: a reset, and the rows of agents no longer on the canvas, deleted as it opens). A count past the limit, or one too large to read, is read as the limit (held), never as zero.

Schema 12 (migrations.ts' twelfth, B19 Design §9 C1) adds one nullable JSON column, `message.purpose`: what the core made a message for, typed and versioned (`src/shared/model/purpose.ts`: `{ v: 1, type: 'handoff' | 'evidence' }`), on a queue hand-off (a queue's Message item for another agent, a pending message from the queue's agent) and on its evidence (the recipient's reply, kept as a record for the queue's item); none on every other message, which keeps the meaning it had before. It requires reader 12: a corrallm without it would take a pending hand-off for the run's own send, which no delivery path of its own owns, and its evidence for a turn to deliver. The message store writes it with the row and never changes it after; a value it can't read leaves its row unread, as an unreadable `verdict` does; `dump` decodes it with the other JSON columns. No caller gives it: only the core's delivery mints it (see [Messages](messages.md)).

Snapshot recovery reads a pending message’s purpose before settling it: queue hand-offs become unresolved without a sender notice, while an unreadable purpose leaves the row intact.

Schema 13 (migrations.ts' thirteenth, B19 Design §9 C3) adds one nullable JSON column, `message.about`: on a record the core settled (a run hold's decision, a native prompt's, an ask's end), the agent whose window shows it and the Needs item it settled, and for a hold's decision the choice it picked, by key, and whether words went with it (`RecordAbout`, `src/shared/model/records.ts`); never a title, a label, words, an answer or a value, and none for any other message or a record kept before it. It only says where a record is shown, so it keeps min_reader 12: a corrallm of schema 12 still opens the database, reading and writing its own columns by name and leaving this one as it is, and misreads nothing. The message store writes it with the row and never after (no upsert's `SET` names it); a value it can't read (another version's) shows the record in no window but leaves the row read and the column as it is. `dump` decodes it with the other JSON columns.

Schema 14 (migrations.ts' fourteenth, B24 Design §3, C1, C2) adds who leads and the outside orchestrators you let answer approvals, kept on this machine and never in a canvas file. `lead` is one row per agent you made a lead of the agents nested in it (`canvas_id`, ON DELETE CASCADE with its canvas, and `agent_id`): what it may answer for them (`grants`, JSON: `{ v: 1, questions, plans, approvals }`), what it was when you did (`fingerprint`, JSON: `{ v: 1, role, adapter, connection }`, its role's SHA-256 or `none` as `roleFingerprint` gives it, never the role's text, and its endpoint as `agentEndpoint` resolves it), what of that changed since, holding it until you confirm it (`held`: `adapter`, `connection` or `role`, the first a commit found changed; none while it leads), and when you last changed it (`changed_at`). `outside_grant` is one row per outside token's name (`canvas_id`, ON DELETE CASCADE, and `name`, the party's) you let answer ordinary approvals on that canvas once each (Q3), with when (`changed_at`); it is kept when its token expires or is revoked, until you remove it. It requires min_reader 14: a corrallm without them would remove a lead's agent, or change its role and back again, with its row none the wiser, so none older may open the database once this ran. `dump` adds each canvas's `leads` (their JSON decoded) and `outsideGrants` to its line.

One a newer corrallm made that this one can't read is refused, left untouched; a damaged one is set aside (core.rejected-<uuid>.db, its -wal first, then -shm and -journal) and the newest snapshot passing the same checks restored, else it starts empty, saying so; a profile with snapshots but no core.db (a restore cut short) is restored the same way, saying so.

Every open numbers each never-reused sequence (migrations.ts' SEQUENCES: message's seq) on from the clock in ms, past every place given before, those whose rows a crash cut off and those a database a restore replaced gave included, so a cursor from before reads what comes next; a restore raises each document's revision the same way (a token's `expect` holds them), and a restore, or an empty start in place of a database, then settles in the same transaction what waited in the snapshot (restored.ts: a message pending there may have gone since, so it is unresolved, never sent, and its sender told by a notice).

What opening wrote is checkpointed (TRUNCATE) before the store is used, so it is on the drive, and the log begun anew (checkpointer.ts' `beginLog`: a write that changes nothing, since SQLite syncs a new log's header on the connection that begins it). store.ts is the open Store: `prepare` (cached), `tx` (transaction.ts: BEGIN IMMEDIATE, a synchronous function, COMMIT, a savepoint within one, rolled back only if SQLite hasn't, as on a full disk; its log flushed on the loop: tests only), `write` (the lane: queued writes share bounded commits in FIFO order, each in a savepoint, each resolving only once that commit returned and its log was flushed to the drive, off the loop: Node's fsync on its thread pool, F_FULLFSYNC on macOS, one flush at a time before the lane appends again: "on disk before it is sent").

A failed flush fails the store closed: every write and read refused from then on, saying why (once on stderr), until the core opens it again; what it committed since its last flush that worked taken back best effort (the log cut back to where those commits began, as `wal_checkpoint(NOOP)` said before each, and closed while a connection that only reads holds the database, so SQLite checkpoints none of it, and the next open recovers the log up to there alone; every snapshot published since removed, including one whose rename succeeded but publication rejected).

Limit: if cutting the log or syncing that cut itself fails, a write whose flush failed may come back after a restart, in doubt as in PostgreSQL and SQLite.

The store says so on stderr.

No recovery marker is written or checked at open.

Successful writes cost only their WAL flush; normal opens and writes create only core.db, -wal and -shm (snapshots are taken separately, as it closes or once due). `checkpoint` (checkpointer.ts: PASSIVE, once every commit made is flushed, on a worker thread with a connection of its own, whose code is a string run as CommonJS, since the bundles are one file each; sqlite.ts gives the expression it connects with; once it copied all of the log it begins it anew there, cutting it back to JOURNAL_SIZE_LIMIT, and the lane commits nothing meanwhile, so the two connections never write at once), run once idle a second (at most 30 s after the first unchecked commit).

An idle checkpoint with no queued write also runs incremental vacuum on that worker, at most 64 pages per pass, checkpointing its result; another pass waits a second of idle time, and a queued write takes priority.

No drive flush waits on the core's loop while it serves (only opening and closing sync on it).

A commit's own writes into the log do run on the loop, into the system's cache, which the system holds back while other programs write heavily to the drive: G2 holds on a quiet drive, and only the connection on a thread of its own (Core Database §4's fallback, not built) would hold it under such writing. `snapshot` (snapshots.ts: SQLite's backup into backups/core-<time>.db, read through a connection of its own in one step; the backup, conversion to a rollback journal and quick check run on the checkpointer's worker, never scanning the copy on the core's loop; idle checkpoints wait until that snapshot ends, leaving foreground writes free; quick-checked and forced to disk before it is named, never kept with a fault, the newest three kept, what one cut short left removed by the next; taken as it closes and every four hours) and `close` (writes, and transactions outside one, refused from its start; the lane drained and flushed, a TRUNCATE checkpoint, a snapshot, then the checkpointer's thread ended; once).

The worker captures its unused stdout and stderr instead of opening the parent's terminal streams, which may already have hung up when the closing snapshot starts it. `Database` is what the stores kept in it read and write through: the Store, or, when it couldn't be opened, `unopened` (every read and write fails, saying why). createCore opens it first (once core.lock is held: entry.ts, serve) and closes it last, after journaling; what opening it said is said with the first canvas restored, as the journal's warnings are.

Kept in it: canvas memory (memory.ts: canvas, conversation, its agents' conversations by the workspace each CLI ran in, then adapter and agent, `conversationsIn` and `withConversationsIn`; a change remembered as it is made, and written with every canvas changed whose row isn't on disk as it is yet, so one whose write failed is written with the next, and fails `flush` until it is; the 200 canvases used most recently with a file, folder or conversations, by used_at, and apart from them the 200 drafts used most recently (each New makes one, with its run), so drafts never push out a saved canvas; the rest forgotten with all the database keeps of them, their runs and documents included, but never one open, nor one with edits not saved, `Documents.unsaved` (a canvas displaced from its file by another's Save As counts as unsaved, even when its text still matches the saved hash), nor one that owns a workspace record in any state; `forget` drops one, a draft discarded, resolving with whether it did: a canvas that owns a workspace record is kept whole, and `Documents.forget` keeps its live document then), each canvas's document (canvas/documents.ts: document, node, link, queue_item, revision, change) and the run journal (run-journal.ts: run, in its envelope, read_position, open_canvas, each referring to its canvas's row, which it makes for a draft: `ensure`; `keep` and `moveRead` within a write another store makes too; a checkpoint's manual submissions your messages in the canvas's message store, in the same write, given back from there in the form an engine restores as its run is: `src/main/core/delivery/submissions.ts`, until B11's view rows replace submissions) and the message store (delivery/messages.ts: message, each message a row with how it came to be, what a view shows of it, what it told and its withdrawal note) and the workspace store (`src/main/core/workspaces/store.ts`, WorkspaceStore: repository, canvas_repository, worktree, agent_worktree, worktree_job, worktree_setup, project_setup) and the merge journal (`src/main/core/workspaces/merge-journal.ts`, MergeJournal: merge_job; each merge recorded within a write of its own before it is installed, on disk before the install begins, its intent checked whole and never changed, its phase and outcome compare-and-set, a caller's request found again by its key and id, and what it reads back read only as it wrote it, else failing the read) and the lead store (`src/main/core/leads.ts`, LeadStore: lead, outside_grant; read whole once as the core opens, never throwing, so a database it can't read leads to no lead and no grant; each `agent.setLead` and `outside.setGrant` written in a write of its own, on disk before it resolves, then taken in memory; within every document commit's write, the rows of agents it removes deleted and those of agents whose adapter, connection or role it changes held, taken in memory once that write is on disk, nothing of it if it fails; as a canvas's document loads, the rows of agents it lacks deleted and those changed since held, in a write of its own; a row it can't read, another version's, is no lead and is kept as it is until its agent goes or you set it again). The workspace store writes only within a write, its own (`write`) or another store's (a document commit's `within`, the run journal's), keeping nothing in memory, so a failed write leaves nothing to undo; it checks every id, absolute path, ref, OID, hash, code and command it is given (`invalid`), and applies the same validation when reading them back, failing the read otherwise rather than guessing. Generated branches keep their narrow ASCII shape; a picked checkout’s captured base ref accepts Git’s full-ref shape, including Unicode and punctuation, without accepting a leading option or invalid ref syntax. Workspaces move only along fixed edges from the state the caller expects (`transition`: `stale` if elsewhere, `refused` for an edge it lacks; a ready or setup workspace cannot go directly back to `creating`, a `retained` one only goes `removing`, a `removing` one may stay so with its cleanup error or go back to `retained`; `error` and `missing` carry an error code; their retry may re-enter `creating`, so provisioning must reconcile the actual Git registration and checkout first, never recreate over existing work). A binding's generation is allocated in the same transaction as its binding, from the clock past the durable high-water mark in meta, so clearing a plan, deleting a binding or restarting with the clock set back never repeats a published generation; a plan waits beside it (`plan`, `clearPlan`) until `bind` installs it at the generation reviewed, and `advance` moves a workspace and its bindings on (a plan waiting moves past them). Jobs are idempotent by id and their original intent hash (object-key order ignored), even after their progress payload changes, one open of a kind per workspace, phases and outcomes compare-and-set (`advanceJob`, `finishJob`; `openJobs` is what a restart finishes; `worktreesIn` lists every canvas's workspaces in given states, what a restart checks). Provisioning's create jobs (`src/main/core/workspaces/provision.ts`) go `recorded`, `branch`, `registered`, `populated`, then `done` as their workspace moves to `setup`; each job's id is made from its workspace and attempt, its payload the intent. A `remove` job (`src/main/core/workspaces/cleanup.ts`) records what was decided of a tree being removed (its branch too, forced or not, the fingerprint approved, the tip decided), recorded in the deciding write as its workspace goes `removing`, superseded when it is decided again or kept after all, and finished in the write that forgets the workspace. Setups are offered a generation at a time, run only once allowed with the approval on disk first (`startSetup`), and `interruptSetups` marks every running one interrupted as the core starts, `interruptSetup` the one the core ended as it closed, never to run again by itself. `setProjectCommand` (a one-line command of at most 4 KiB with no control, format or line-separator character, and its shell kind) clears Always whenever either changes. A setup's output and what was copied into a workspace are kept beside the database, not in it, in private files of the profile's (`<profile>/workspaces/setup/`: see [Workspaces](workspaces.md)); a row names its log only by key. A workspace record is forgotten (`forget`) only once `removing`, unbound and with no job going on. It does nothing to a repository or a file and mints no `TrustedPath`: a path it reads back is a record, to check again before use. Repositories are kept by discovery's `recordRepository` (`src/main/core/workspaces/discovery.ts`), by the real path and identity Git and the file system gave, never a path a caller names; a repository found again keeps its `owned_root`. test-store.ts seeds and reads a profile's database for tests, through the stores' API (keepCanvases, keepMessages, openedLast, forgetRun, messagesIn: each canvas's one message store, which a test's run journal keeps submissions in) or a connection of the test's own (onDisk, journaledRun, readPositions, refuseWrites: triggers that fail a table's writes; madeAtSchema: a new database made as a corrallm of an earlier schema made it, to seed what that one kept and test a migration), never by writing its files. schema-3.test.ts keeps a canvas through today's stores, copies its rows into a database made at schema 2, and checks migration 3 keeps every row, that today's stores read it, that a failed migration leaves schema 2 as it was, that a corrallm of schema 2 refuses the result, and that a schema-2 snapshot restores migrated. `src/main/core/store/test-schema-3.json` is every row a corrallm of schema 3 kept through its own stores and core (a canvas the core ran, with a party's and a manual resend, a canvas a window ran, with its submissions, runs beside a size refusal), made once by a generator not kept; `src/main/core/store/schema-4.test.ts` seeds it into a database made at schema 3 (or 2) and checks migration 4 keeps every row and its meaning, that today's stores read it, that a failed migration leaves schema 3 as it was, that a corrallm of schema 3 refuses the result, that a schema-3 snapshot restores migrated, and that only migrations.ts reaches its conversion.

An oversized run (over MAX_RUN_BYTES, 32 MiB) leaves its last good checkpoint in place and keeps a saveError in the run's JSON in the same commit as its messages.

Messages still reach the drive before delivery; size alone never fails them. run:get reports saveError (and a restore notice), and Needs shows a canvas-wide `unsaved/<canvas>` warning, with no answer.

A smaller checkpoint or forgetting the run clears it.

A renderer's oversized run:save records the warning then rejects, so it never claims to have saved progress; core journaling can continue.

Restart restores only the last checkpoint that fit, paused, with that warning. `dump` (store/dump.ts, cli/dump.ts) reads repositories (schema 3, with their setup), canvases (including their document's rows, conversations and, from schema 3, their workspace records: repository, worktrees with their setups and jobs, bindings), runs (from schema 4, in their envelope) and messages (from schema 4, with their origin, decoded display and resend_of; from schema 7, a record's decoded settled decision; from schema 13, its decoded association) as JSON lines in one read transaction, including committed WAL rows.

It uses SQLite READONLY and query_only, never the store's writer, migrations, recovery, checkpoints or core.lock.

It shares open.ts' application-id, min-reader and integrity checks, refusing before its first line; schemas 1 to 3 can be inspected without migration, each as it kept its rows.

As with any SQLite WAL reader, it participates in -shm and may create an empty -wal/-shm on a closed database; it writes no database page or WAL frame.

A slow output pipe pins its read view (the owner's writes still continue) and is awaited, never accumulated in memory.

A successful export of a superseded handoff still updates the last-copy path and hash, retaining the newer handoff and leaving its export status alone. The per-agent export lane records that proof durably before attempting the newer copy.

C3’s additive `handoff.accepted_turns` column keeps the 64 newest accepted request turn ids per agent as JSON (ids only), written with the reply and retained across handoff replacement and message pruning so resumed conversations cannot preview those replies in summaries.

Migration 15 (B24 C3) changes no table: it raises `meta.min_reader` to 15, because a lead's copy and notice are messages whose `purpose` (`lead-copy`, `lead-notice`, each with its Need item) an older reader would take for none, leaving a pending copy of a prompt no core holds any more to be delivered and never withdrawn.
