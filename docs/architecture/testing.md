## `e2e/`

Playwright Electron tests (*.e2e.ts) and their global setup.

B11's continuity specs share `e2e/continuity-world.ts`: a temporary profile with a seeded token hash, endpoint discovery through api.json, and SDK/Terminal fakes whose first turn waits on an observed file gate. `e2e/core-continuity.e2e.ts` checks reload and renderer-crash continuity through a dependent output condition (Playwright keeps a crashed page dead even after its window reloads, so the crash case recovers the view as a user does, closing the dead window and opening a new one); `e2e/window-closed.e2e.ts` checks last-window close, no-window MCP and reopen. Neither restarts the utility core. `e2e/mcp-parity.e2e.ts` exercises queue edits in both directions, canonical saves (equal apart from the expected author: yours is the unmarked one, so a person's edit clears an outside author instead of naming `you`), manual and outside messages, shared session reads, human-only refusals, a held OK and a visible deletion proposal. The core-only counterpart in `src/main/core/app.test.ts` removes every window and subscription mid-turn and checks that the same native session completes the condition and next task.

Global setup builds through Forge once. Its child gets `CORRALLM_E2E_BUILD=1` and `CORRALLM_UNSIGNED=1`: only together do they skip staging the shipped Node/command, since the specs launch the unpackaged production bundles. Forge still copies the app's native modules and builds the headless CLI bundle once in `prePackage`. Normal package/native gates keep full staging. `src/main/e2e-build.test.ts` checks that setup and the complete-build requirement for `E2E_SKIP_BUILD`; `src/main/shipped-cli-config.test.ts` checks the unsigned-only bypass, signing and Node-based Vite invocation without running Forge or native modules.

After building (or validating a reused build), global setup runs `e2e/webgl.ts`: it launches the app with the same sandbox and production CSP as the specs, requests xterm's WebGL2 context kind, clears a pixel and checks its readback. It prints the renderer and GL version, closes the probe app, and stops the suite with one diagnostic if WebGL2 is absent, lost or unable to draw. The check runs before any specs, including with `E2E_SKIP_BUILD=1`; a failed graphics environment must not become dozens of terminal/CSP failures. `src/main/e2e-webgl.test.ts` drives the browser callback with a fake context, and `src/main/e2e-build.test.ts` checks the ordering and failure propagation without launching Electron.

Linux Docker e2e uses Mesa llvmpipe, Xvfb's GLX extension and Chromium's ANGLE OpenGL backend (see [toolchain](toolchain.md)). Only `e2e/launch.ts` reads the script's `CORRALLM_E2E_GL=mesa` opt-in, and only on Linux; it adds fixed graphics switches to the unpackaged test launch. No sandbox is disabled, no CSP is relaxed, and no switch is added to a product or packaged smoke-test launch. `src/main/e2e-launch.test.ts` checks the opt-in and other platforms; `src/main/linux-scripts.test.ts` checks the actual CI command's environment and display arguments through stand-ins.

Launch the app with launchApp() (launch.ts): a throwaway profile, so the real app's saved state never leaks in, and no `claude` or `codex` unless the test points the app at a fake. Its main's `dialog.showMessageBox` answers the quit question (B14 C2) Quit and pause, so `close()` quits while agents work, and leaves every other message box to the app; a test that wants another answer replaces it again. On Linux and Windows the last window's close asks the same question, and Keep running minimizes the windows instead of closing them (macOS closes them); specs that close the last window use `closeLastWindow` and `reopenWindow` from `e2e/last-window.ts`, which answer Keep running once and assert that every window is kept (the harness hides windows and Xvfb has no window manager, so the minimize call is observed, not `isMinimized`). A dead renderer's window is destroyed instead (`destroy`), and the question comes on a new window.

Failed SDK/control/recovery/settings, graph and terminal specs opt into `launchApp`’s `diagnoseFailure` callback. Before closing, it prints bounded app stdout/stderr and window text (including session startup refusals) to the test log. The SDK and App Server fakes also write opt-in startup facts into the throwaway profile: executable, Node version, cwd and booleans for supplied fake configuration, never credentials, instructions or prompt bodies. The failed spec prints those files too, before deleting the profile. This distinguishes a missing runtime/spawn from an auth refusal or environment loss without needing the Docker trace volume. Successful specs stay quiet.

Specs that assert restore-as-paused kill the actual core with `e2e/core-crash.ts`: `crashCore` returns once a new core has a new pid, and `crashCoreAndReload` also waits for the window's reload into it (main's `CorePorts.reconnect` still reloads every window after a crash, so the page starts over with its views closed: a spec opens All queues again). A window reload alone is not a restore case: it leaves the run going.

The Codex Terminal specs wait for a typed turn to be over (`turnOver` in `e2e/codex-terminal.e2e.ts`: its message row `completed`, then Idle), not for the fake's logged prompt or an Idle that is true until corrallm hears the turn begin: the fake logs a prompt before any hook runs, drops a prompt it gets while working, and corrallm learns the session id (what a restart resumes) from the prompt's hook. Its hooks and the app server's turns take seconds on a loaded machine, so waits for a whole turn's end give 15 s.

Holds are operations to the core now (Pause, Kill and Resume from a menu), and nothing orders a window's operations: a menu closes before its operation lands, so a spec that pauses then clicks Run first waits for the visible hold (`Paused`), or Run can start the queue it meant to hold.

Terminal link e2e uses `e2e/terminal-link.ts`: wait for the agent view’s open animation to end (it grows out of its card, and until it ends the screen’s box is the card’s, so every cell computed from it is wrong), re-read the screen’s geometry, come onto the link’s row from the next row, and wait briefly for the link pointer on `.xterm-screen` (xterm 6 decorates that element, not its outer `.xterm`) before Ctrl-click (Cmd on macOS). xterm asks its link providers for a row’s links as the pointer comes onto the row and keeps that answer while the pointer stays there, so a pointer that reached the row before the CLI’s reply did (the view lags the CLI under software rendering) never finds the link from the same row. Where no pointer shows in time the helper clicks nothing and says so; the spec’s poll hovers again, and the out-of-project file is Cmd-clicked three times only once each click lands on its shown link. `src/main/e2e-terminal-link.test.ts` checks that exact target, that nothing is measured before the animation ends, the approach from another row, asynchronous discovery, the unclicked miss, each platform’s modifier and its release on a failed click. `src/renderer/terminal/screen.test.ts` checks the product side: a link opens with Cmd on macOS and Ctrl on Linux and Windows, never plainly or with the other key. Plain-click and out-of-project file assertions remain. The Linux queue-drag failure kept the original order; it did not demonstrate a one-slot reorder error. The corresponding sortable tests move the task directly above the wait, in one event and through intermediate positions, on the unchanged main implementation. Queue drag e2e scrolls the handle into view before measuring it, checks that the press starts its drag, and waits for the complete expected order from the core’s mirror. The old failure does not establish whether the original press missed because of clipping or another pointer/layout condition; the strengthened e2e must be rerun with real rendering. Long graph stories keep the existing 60-second deadline and their assertions in smaller tests: link/work versus deletion, each nested drag direction and return, and three batches covering all nine gallery templates. Each gallery batch still switches consecutively between canvases and checks their reset project folder.

- Test-driven by default. For a bug, first write a test that reproduces it and fails, then fix it, then confirm the test passes. For new behaviour, write the tests with (or before) the code.

- The test suite is the regression guard, not ad-hoc review. Keep tests robust and meaningful: assert behaviour users or callers rely on, not incidental details. Prefer unit tests for logic, and add Playwright e2e only for what needs the real app (pointer interactions, CSP, packaging).

- A guard that something did not happen never sleeps a few milliseconds and then asserts. It waits for the state that shows the hold (a sender's hold notice, a pending record, a Needs item), moves fake timers past every re-check that could still act, flushes the core, and asserts what was decided as well as what was sent: a send that goes anyway is decided at once but reaches the fake CLI only after a journal fsync. `src/main/core/stall-resend.test.ts`'s resend holds are the model.

- Tests never run the real Claude or Codex. `launchApp` (e2e/launch.ts) sets `CORRALLM_AGENT_PATHS` to `{}` unless the test gives a JSON map of fakes, so the app finds neither CLI (nor offers them as installed, `catalog.installed`) by accident. Main's session tests use the fake connector (`src/main/sessions/fake.ts`, one per CLI), and so do the core's engine and message tests (`core/engines.test.ts`, `core/messages.test.ts`); the engine's tests use a fake backend (`src/main/core/engine/test-backend.ts`), while renderer tests use `src/renderer/test-api.ts` operations and immutable topic snapshots (`src/renderer/test-canvas-runtime.ts` scripts widget data without running queues or constructing an engine), and e2e runs the app with `CORRALLM_FAKE_SESSIONS=1` (`launchApp({ env })`; honoured only by unpackaged builds), which gives each CLI's connections a fake connector. A connector's own tests drive a fake CLI that prints the real one's formats.

- Renderer and engine tests read the catalog the core builds (see The catalog) from `src/shared/test-catalog.json`: `src/renderer/test-setup.ts` loads it as the app does before it mounts, and the engine's tests read it, with the lookups the app gives the engine, from `src/main/core/engine/test-engine.ts`; shared model tests use the pure catalog fixture `src/shared/test-model.ts` (neither imports the renderer). It is a copy, never edited by hand: `src/main/sessions/adapters.test.ts` keeps it equal to main's catalog (a vitest file snapshot), and rewrites it with `pnpm exec vitest run --project main src/main/sessions/adapters.test.ts -u` when a descriptor changes (prettier leaves it alone). What reads the catalog it is given (the engine: the run, the sessions, the words they share) is also tested over `src/shared/test-made-up.ts`, a catalog of an adapter no build has, which the loaded one lacks.

- Every test file that makes a run makes it with `liveRun` (an Engine's run, `engine.run`, kept with `liveRunOf` before it is given its nodes) and checks, after each test, that it restores from its checkpoint as it was (`afterEach(expectRestorable)`, `src/main/core/engine/run/test-restore.ts`): whatever a run holds, its checkpoint keeps, since the core journals it. The run's tests share a harness (`run/test-run.ts`: a run with its clock and its agents' turns under the test's control), and so do the built-in templates' run tests, which live with the core runner (`src/main/core/engine/run/templates-run.test.ts`).

- jsdom cannot draw xterm.js: renderer tests that show a Terminal agent mock `src/renderer/terminal/screen.ts` with `fakeScreens` (`src/renderer/terminal/test-screen.ts`), which also fakes main's terminals (`fakeTerminals`). `src/renderer/terminal/screen.test.ts` makes real xterm.js terminals without drawing them: it fakes the canvas's WebGL2 context and the WebGL addon's context loss, to check what the view shows without WebGL2.

- The Pause e2e (`e2e/agent-controls.e2e.ts`) runs the real SDK connector against its protocol fake, not `CORRALLM_FAKE_SESSIONS`. Its first native turn waits on an explicit test-only file gate: the test sees Pausing, independent success and the dependent wait, then releases the turn and checks the same completion and resume assertions. The group controls e2e (`e2e/group-controls.e2e.ts`) gates the same way: group Pause meets its nested members' first turns held, sees Pausing and independent success, then releases them; group Kill interrupts its held turns while the outsider's stays held until the test has seen it still running. Forty serial timers in the fake's "slow" stream accumulate scheduling delays under load and cannot provide a reliable UI interaction window. Unit tests check nested completion immediately before and after Pause after a long clock jump on the unchanged main implementation: already-completed turns say Paused, active ones say Pausing until they finish. The missing-Pausing log is consistent with the finite stream completing before the UI gesture; the gated e2e verifies the intended active-turn case without relying on that timing window.

- The 512 MiB snapshot loop measurement (`src/main/core/store/snapshots-loop.test.ts`) runs in the serial `store-performance` project after the other projects finish (`sequence.groupOrder: 1`). Its 30-second timeout and maximum 50 ms loop interval stay unchanged; the parallel test pool's disk and scheduling contention must not decide a loop-responsiveness assertion. Ordinary snapshot tests stay in `main`.

- The vacuum/write test (`src/main/core/store/vacuum.test.ts`) gates the write's flush and checks ordering: the current bounded vacuum pass finishes, the queued write runs and becomes durable, and no second pass gets ahead of it. It does not time the drive's real fsync; the separate reclamation test still checks the 64-page bound.

- Command-shipping unit tests use an injected download, fixture tarballs and fake native runtime files: they check all four targets, cached and downloaded checksum failures, only the required files staged outside ASAR, Forge hooks and signing, Linux command/desktop targets, and symlinked launchers with an empty PATH. They never load a native addon. The packaged app's native self-test additionally runs the actual shipped launcher with an empty PATH, including its pty round trip; `scripts/check-macos.sh` and `scripts/check-linux.sh` exercise the signed or ad hoc packaged resources rather than a checkout's Node or node_modules.

- Electron-cache unit tests also intercept `createRequire`'s executable lookup: Vitest's module mocks do not intercept that require. They read the installed package's version but return a stand-in executable, so a fresh Electron patch never downloads or loads the real binary in a unit test.

- `src/main/shipped-command.test.ts` runs the launcher against the test's Node with a tiny stand-in bundle and hostile preload/module-search settings, checking they never reach the runtime. The packaged self-test also supplies a failing preload rather than clearing `NODE_OPTIONS` itself; neither test can hide a launcher that forgets to sanitize it.

- Dump tests keep the owner's maintenance timers under test control, with real WAL flushes: an idle checkpoint legitimately rewrites the database and WAL, so a read-only dump's byte-hash assertion must compare a quiet owner. Usage-reset delivery tests control Date and timers, checking the hold just before reset and delivery after it; setup and fsync time never consume their usage window.

- CLI integration tests own every child from spawn (`src/main/cli/test-children.ts`), before any startup or address wait. POSIX children have private process groups. Teardown signals every live child, allows five seconds to close, then kills surviving groups (the child directly on Windows) and allows two seconds to observe exit and pipe closure; a folder is removed only after all children are gone. A private launch line reports a terminal server’s pid before startup, so teardown tracks it separately from its script wrapper even before api.json; that line is stripped from captured output. Teardown refuses later spawns, and process tests have explicit 15–30 second budgets (30 seconds for terminal startup’s 20-second readiness wait; the CLI wait batch keeps its 20-second budget).

The serve test helper waits for both readable api.json and the complete “corrallm serve: serving” line, rejecting with its diagnostic if the child exits first. Discovery is published before delivery and the serving announcement, so the file alone is not full startup. `src/main/cli/test-serve-startup.test.ts` controls those events independently, including split output chunks and early exits. Refused starts bypass this helper; the publication-order test reads api.json directly on the announcement's data event, keeping its stronger ordering assertion.

- Each real `TestChildren` scope also owns an independent detached guardian (`src/main/cli/test-lifetime.ts`). Vitest's main global setup builds its Node-only bundle through `vite.test-lifetime.config.mts`, outside shipping outputs; it also exports `TestChildren` for the process-regression fixture. Node test commands preload it before the CLI loads: they wait for the guardian's ready marker, record their OS start identity and private group, and refuse startup if the scope has ended (including a race during registration). Worker threads inherit the preload but skip registration: they share the process's pid and must not overwrite its profile record, particularly the SQLite checkpointer. Terminal commands preload it inside `script(1)` too, so ownership does not depend on the wrapper surviving or its pid header arriving. The scope's pipe is an OS lease: normal teardown closes it, and worker exit or SIGKILL closes it without JavaScript hooks. The guardian marks the scope closed, stops only its recorded groups, then reads their profiles' native-CLI registries after the servers are gone and stops those groups too. Intentional server SIGKILLs during G3 leave this lease open, preserving the test's recovery scenario. No other tests' folders or process-table command searches are used. Primary teardown still runs first; the guardian also runs if it fails. A failed guardian keeps its scope records under node_modules/.cache/probes/test-lifetimes and reports the location.

- Crash-test and guardian group cleanup (`src/main/cli/test-process-groups.ts`) verifies the shared OS process identity, allows five seconds after SIGTERM and five after SIGKILL, polling every 50 ms against a monotonic deadline rather than checking once after the core's 250 ms startup probe. A reused or unverifiable leader is never signalled; a group still alive at the bound fails cleanup and keeps the folder. An EPERM from kill(0) is inconclusive: a bounded, headerless ps read checks for living members of that exact group, including descendants without a leader and excluding zombies. That membership read never authorizes a signal by itself. Failed or timed-out probes are retried within the existing polling bound, never treated as an empty group. If an identity read or signal fails, cleanup independently checks whether the group has exited, allowing five seconds for reaping: a gone group is cleaned successfully, while a surviving or still unverifiable group keeps its record and the guardian reports its pid and the reason on stderr. Serve and crash teardown hooks have a 30-second budget for primary shutdown plus the independent server/native-group cleanup; their normal test assertions are unchanged. `src/main/cli/test-crash-cleanup.test.ts` covers delayed reaping and real survivors, and `src/main/cli/test-lifetime.test.ts` covers pipe loss, registration races, failed identity reads and identity refusal with a fake OS. `src/main/cli/test-lifetime-process.test.ts` kills a stand-in worker, including after its terminal wrapper died, and checks the server and its descendants end while another scope's process stays alive.

- `src/main/cli/serve.test.ts` runs the CLI bundle (`corrallm serve` and `corrallm wait`), which the vitest `main` project's global setup builds first (`src/main/cli/global-setup.ts`), in child processes on a profile of its own: its database keeps a canvas and its project folder, as the app would (seeded through the store's API, `keepCanvases`), its tokens.json known tokens' hashes, and its agents run `fake-codex.mjs` (which reads what it is asked after corrallm's frame line); an MCP client (the SDK's `Client`) calls as an outside orchestrator, and `--new-token` runs under `script(1)`, a terminal. `src/main/cli/wait.test.ts` checks how `corrallm wait` exits on each refusal, against a stand-in server, and that it reads a token file afresh at each wait. `src/main/cli/token.test.ts` runs `corrallm token new|renew|revoke` the same way, under `script(1)`, against a running `serve` and with nothing owning the profile (`src/main/core/entry.test.ts` runs it against the app's core process, composed in the test): each takes effect at once with no restart, is refused without a terminal, keeps only the hash, never shows a token it writes `--into` a 0600 file whose headers helper reads the current one across a renewal, and no token is in any process's arguments (`ps`), serve's log or a tool's result. `src/main/core/token-socket.test.ts` checks the socket's owner-only mode and folder, that the OS refuses a connect without write permission on it, a socket left behind replaced and anything else refused, the client's refusal of a socket or folder that isn't the user's alone, the request bounds, and Windows' refusal. The core database's gates (Core Database §8): `src/main/cli/crash.test.ts` (G3) kills `corrallm serve` with SIGKILL seven times while two outside orchestrators send three agents messages (every third a turn that goes on until interrupted) and wait for replies, and checks across every crash that no message reaches an agent twice (the fake codex logs each turn it starts), none acknowledged is lost, no read position goes back, and each in flight as it was killed is unresolved; `e2e/load.e2e.ts` (G2, B11's load test built in B9.0) runs `corrallm serve` (the app's core process serves no messages, waits or pauses until B11) with `e2e/loop-delay.mjs` loaded into it (`node --import`), which measures its event loop from inside from its first SIGUSR2, over the whole and each span between two, while four orchestrators send six agents about 2,600 messages over 35 s, wait for every reply and pause and release an agent ten times a second, and, 10 s in, a fifth sends the canvas 200 doc ops (Core Server §7.4's burst: six lanes of work, one op from each every 250 ms, so six in flight and 24 writes a second, under its token's limit; each lane makes an agent, three with `canvas.addAgent` and three spawned linked from those, names and moves it, adds, changes, moves and removes its queue's items and adds to an agent already there, and one turns Arrange on and off: nothing a rule refuses or proposes), each checked to succeed, timed (p50, p99 and max) and the canvas checked as they left it, and holds the loop to p99 under 25 ms and max under 100 ms over the whole, the doc ops included (it also reports the spans before, during and after them), on a quiet drive (while another program writes heavily to the same drive, a commit's own writes into the log can stall the loop past 100 ms, as 2 of 8 runs did with `dd` writing alongside: only the core's connection on a thread of its own would hold G2 then); `e2e/damaged-store.e2e.ts` (G4) gives the built app a `core.db` that isn't a database, and it runs on, restored or empty, saying so in its window (serve.test.ts checks `serve` does the same). e2e specs may import the store's test helpers (`src/main/core/store/test-store.ts`). `e2e/lock.e2e.ts` checks `core.lock` with the built app (whose core process holds it, found through `app.getAppMetrics()`), and `e2e/core-crash.e2e.ts` kills that process: the window reconnects to the new core, the canvas restored paused, and a core that keeps stopping is given up on.

- Local tier: `pnpm test:fast` (no `cli/crash.test.ts`, no store-performance) and `pnpm test:e2e:smoke` (the `smoke`, `security`, `files` and `lock` specs) stand in for the full suites on a laptop; CI runs `pnpm test` and `pnpm test:e2e` whole, so no test is dropped, only run later. The macOS packaged gate verifies the strict deep bundle signature, node-pty's executable spawn-helper, the app's native self-test, three refused launch switches (exit 1), and the shipped command's self-test and help with an empty PATH. GitHub CI is disabled on GitHub until it is re-enabled before launch; the local gates are CI meanwhile. Linux CI is local in Docker: `scripts/ci-linux.sh`, `scripts/check-linux.sh` and `scripts/check-linux-packages.sh` for both arm64 and x64; see [the local CI commands](toolchain.md#local-ci). The crash gate tracks each `serve` from spawn with `TestChildren` too. Its intentional mid-run SIGKILLs remain unchanged. Teardown waits for every owner to exit and close its pipes, then reads the profile's `sessions/pids.json` with `recordedTestGroups` and polls its verified groups through `stopTestGroups` before removing the folder. A failed owner shutdown, unreadable registry, failed group cleanup or surviving group keeps the folder and fails teardown. `src/main/cli/test-crash-cleanup.test.ts` exercises ordering, late CLI writes and failures with a fake OS.

Linux script tests (`src/main/linux-scripts.test.ts`) inject stand-in docker, git, pnpm and xvfb-run executables. They run both architecture paths without Docker, check that the image build has one Dockerfile source (a two-file stdin archive containing the default `Dockerfile`, with no `--file` flag), verify clean runtime images and artifact cleanup on failure, and exercise gate order and fail-fast reporting. The package configuration test requires Electron's audio library and the core's process inspection tools even with optional dependencies disabled. Shell syntax and upstream maker paths can be checked without Docker; the real container builds, Linux Electron/e2e runs and deb/rpm installations remain separate local gates.

The crash gate synchronizes each SIGKILL with six acknowledged messages, two or three native turn receipts and a recorded slow turn still in flight. Further sends race the crash; the final restart waits for a native receipt on every recipient with pending work. Its coverage counts and invariant assertions are unchanged, and its 240-second test deadline and 30-second startup/readiness bounds only fail a stuck run, never decide how much traffic ran.

The startup-shutdown CLI test holds only its login environment read (`-ilc`) behind a file gate until the CLI acknowledges repeated SIGTERM with “stopping already”; releasing the gate then proves it stops before making a token or delivering anything. The shell passes other invocations through to /bin/sh: Linux script first uses `$SHELL -c` to launch Node, and gating that earlier invocation would report script’s pid and stop the wrapper before serve ever starts. `src/main/cli/test-startup-shell.test.ts` checks both invocations without a pty or signals. It does not assume a two-second shell is still reading when the test is scheduled. The 30-second test deadline remains.

The two exhausted-usage reset/restart tests use FakeConnector's injected `step` to run native turns through microtasks, independently of their fake usage clock. They await actual reply/notice events and let the normal core shutdown persist them across a restart; they do not spend a real polling budget advancing fake CLI timers. Their five-second test deadline remains a failure guard. The terminal restart e2e waits for the agent panel's Web Animations to end before taking its reference screen size, matching the 380 ms grow in AgentView rather than assuming a live CLI implies settled geometry.

T3a’s transport cases (`src/main/core/test-transport.ts`) preserve each generated reach check’s caller. Every ordinary valid, invalid and rule fixture still runs for every caller; each caller-specific unreachable variant runs only for that token, and windows run the ordinary fixtures as you. Replaying a token’s foreign ids as you would turn negative reach probes into successful structural mutations, repeatedly laying out and growing the shared test canvas. `src/main/core/test-transport.test.ts` pins this matrix for MCP dispatch, HTTP’s token subset and the window.

T3b's OpFixture can declare `proposesForYou` for a proposing rule the operation carries: a C-owned confirmation that asks the human too, as workspace-safety does for C7's kept-tree removal and for a delete or batch leaving a tree that holds work (the world's `kept-work` agents). The world's workspace records are each made once and lost since, so the core's startup check of `setup`/`ready` checkouts changes none of them in the background, and a retry of one finds it still gone without Git work going on after. The generated rule case asserts the human receives a proposal for that fixture; other human rule cases still assert direct application. Worktree removal's focused core test replaces only Git assessment/removal, exercising C7's real canvas/retention checks, proposal and fingerprint logic through the normal registry; its service integration tests retain real Git coverage.

macOS script tests (`src/main/macos-scripts.test.ts`) use fake codesign, app and shipped-command executables for both architectures, including paths with spaces. They check fail-fast signature and helper checks, reject each accepted launch switch, and require an empty PATH for the shipped command. Real signature verification and native execution remain packaged gates.

Token-control security tests additionally cover writable ancestors of a private profile, canonical profile aliases, foreign owners, sticky shared ancestors and the unowned writer’s checks before core.lock. Socket bounds are checked in UTF-8 bytes with a newline arriving after an oversized prefix and non-ASCII answers; presentation labels may be omitted to keep an already minted token and its complete grant deliverable. Token-file tests check no-follow/nonblocking open flags, the opened inode’s owner, closure on refusal, growth after stat, multiple tokens and Windows’ refusal until ACL checks exist.

Withdrawal-note Stop/Kill probes in `src/main/core/messages.test.ts` hold the original turn and its separate note behind explicit gates released by their interrupts, rather than relying on a slow native turn. They check the note was received, then stop or take back the command it carries, await the command’s cancellation, and assert it never reached the CLI.

The seeded message-store sequences keep their 30-second deadlines and fixed seeds. They check Vitest’s abort signal at I/O boundaries and teardown awaits their outstanding callback before closing/removing the fixture; a timed-out restart cannot open the next test’s profile or install a second allocator there. The active-index sequence, like its pruning neighbours, skips unrelated snapshot publication while retaining real SQLite commits, flushes, restarts and restore settlement. Snapshot publication has separate store tests.

Owned-root tests pin inode reuse by reporting the old device/inode with a new creation time on a real replacement directory, independent of the filesystem’s allocator. They also refuse missing creation times and inode-only older markers on nonempty roots. The actual delete/recreate fixture remains, so Linux exercises its native allocation behaviour too.
