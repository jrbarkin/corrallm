## `e2e/`

Playwright Electron tests (*.e2e.ts) and their global setup.

Launch the app with launchApp() (launch.ts): a throwaway profile, so the real app's saved state never leaks in, and no `claude` or `codex` unless the test points the app at a fake.

- Test-driven by default. For a bug, first write a test that reproduces it and fails, then fix it, then confirm the test passes. For new behaviour, write the tests with (or before) the code.

- The test suite is the regression guard, not ad-hoc review. Keep tests robust and meaningful: assert behaviour users or callers rely on, not incidental details. Prefer unit tests for logic, and add Playwright e2e only for what needs the real app (pointer interactions, CSP, packaging).

- Tests never run the real Claude or Codex. `launchApp` (e2e/launch.ts) sets `CORRALLM_AGENT_PATHS` to `{}` unless the test gives a JSON map of fakes, so the app finds neither CLI (nor offers them as installed, `catalog.installed`) by accident. Main's session tests use the fake connector (`src/main/sessions/fake.ts`, one per CLI), and so do the core's engine and message tests (`core/engines.test.ts`, `core/messages.test.ts`); the engine's and the renderer's tests a fake backend (`src/shared/engine/test-backend.ts`), and e2e runs the app with `CORRALLM_FAKE_SESSIONS=1` (`launchApp({ env })`; honoured only by unpackaged builds), which gives each CLI's connections a fake connector. A connector's own tests drive a fake CLI that prints the real one's formats.

- Renderer and engine tests read the catalog the core builds (see The catalog) from `src/shared/test-catalog.json`: `src/renderer/test-setup.ts` loads it as the app does before it mounts, and the engine's tests read it, with the lookups the app gives the engine, from `src/shared/engine/test-engine.ts` (shared code, tests included, never imports the renderer). It is a copy, never edited by hand: `src/main/sessions/adapters.test.ts` keeps it equal to main's catalog (a vitest file snapshot), and rewrites it with `pnpm exec vitest run --project main -u src/main/sessions/adapters.test.ts` when a descriptor changes (prettier leaves it alone). What reads the catalog it is given (the engine: the run, the sessions, the words they share) is also tested over `src/shared/test-made-up.ts`, a catalog of an adapter no build has, which the loaded one lacks.

- Every test file that makes a run makes it with `liveRun` and checks, after each test, that it restores from its checkpoint as it was (`afterEach(expectRestorable)`, `src/shared/engine/run/test-restore.ts`): whatever a run holds, its checkpoint keeps, since the core journals it. The run's tests share a harness (`run/test-run.ts`: a run with its clock and its agents' turns under the test's control), and so do the built-in templates' run tests, which stay with the templates (`src/renderer/graph/templates-run.test.ts`).

- jsdom cannot draw xterm.js: renderer tests that show a Terminal agent mock `src/renderer/terminal/screen.ts` with `fakeScreens` (`src/renderer/terminal/test-screen.ts`), which also fakes main's terminals (`fakeTerminals`).

- The Pause e2e (`e2e/agent-controls.e2e.ts`) runs the real SDK connector against its protocol fake, not `CORRALLM_FAKE_SESSIONS`. Its first native turn waits on an explicit test-only file gate: the test sees Pausing, independent success and the dependent wait, then releases the turn and checks the same completion and resume assertions. Forty serial timers in the fake's "slow" stream accumulate scheduling delays under load and cannot provide a reliable UI interaction window. Unit tests separately check completion immediately before and after Pause after a long clock jump, without changing run code.

- The 512 MiB snapshot loop measurement (`src/main/core/store/snapshots-loop.test.ts`) runs in the serial `store-performance` project after the other projects finish (`sequence.groupOrder: 1`). Its 30-second timeout and maximum 50 ms loop interval stay unchanged; the parallel test pool's disk and scheduling contention must not decide a loop-responsiveness assertion. Ordinary snapshot tests stay in `main`.

- The vacuum/write test (`src/main/core/store/vacuum.test.ts`) gates the write's flush and checks ordering: the current bounded vacuum pass finishes, the queued write runs and becomes durable, and no second pass gets ahead of it. It does not time the drive's real fsync; the separate reclamation test still checks the 64-page bound.

- Command-shipping unit tests use an injected download, fixture tarballs and fake native runtime files: they check all four targets, cached and downloaded checksum failures, only the required files staged outside ASAR, Forge hooks and signing, Linux command/desktop targets, and symlinked launchers with an empty PATH. They never load a native addon. The packaged app's native self-test additionally runs the actual shipped launcher with an empty PATH, including its pty round trip; `scripts/check-macos.sh` and `scripts/check-linux.sh` exercise the signed or ad hoc packaged resources rather than a checkout's Node or node_modules.

- Dump tests keep the owner's maintenance timers under test control, with real WAL flushes: an idle checkpoint legitimately rewrites the database and WAL, so a read-only dump's byte-hash assertion must compare a quiet owner. Usage-reset delivery tests control Date and timers, checking the hold just before reset and delivery after it; setup and fsync time never consume their usage window.

- CLI integration tests own every child from spawn (`src/main/cli/test-children.ts`), before any startup or address wait. POSIX children have private process groups. Teardown signals every live child, allows five seconds to close, then kills surviving groups (the child directly on Windows) and allows two seconds to observe exit and pipe closure; a folder is removed only after all children are gone. A private launch line reports a terminal server’s pid before startup, so teardown tracks it separately from its script wrapper even before api.json; that line is stripped from captured output. Teardown refuses later spawns, and process tests have explicit 15–30 second budgets (30 seconds for terminal startup’s 20-second readiness wait; the CLI wait batch keeps its 20-second budget).

- `src/main/cli/serve.test.ts` runs the CLI bundle (`corrallm serve` and `corrallm wait`), which the vitest `main` project's global setup builds first (`src/main/cli/global-setup.ts`), in child processes on a profile of its own: its database keeps a canvas and its project folder, as the app would (seeded through the store's API, `keepCanvases`), its tokens.json known tokens' hashes, and its agents run `fake-codex.mjs` (which reads what it is asked after corrallm's frame line); an MCP client (the SDK's `Client`) calls as an outside orchestrator, and `--new-token` runs under `script(1)`, a terminal. `src/main/cli/wait.test.ts` checks how `corrallm wait` exits on each refusal, against a stand-in server. The core database's gates (Core Database §8): `src/main/cli/crash.test.ts` (G3) kills `corrallm serve` with SIGKILL seven times while two outside orchestrators send three agents messages (every third a turn that goes on until interrupted) and wait for replies, and checks across every crash that no message reaches an agent twice (the fake codex logs each turn it starts), none acknowledged is lost, no read position goes back, and each in flight as it was killed is unresolved; `e2e/load.e2e.ts` (G2, B11's load test built in B9.0) runs `corrallm serve` (the app's core process serves no messages, waits or pauses until B11) with `e2e/loop-delay.mjs` loaded into it (`node --import`), which measures its event loop from inside from its first SIGUSR2, over the whole and each span between two, while four orchestrators send six agents about 2,600 messages over 35 s, wait for every reply and pause and release an agent ten times a second, and, 10 s in, a fifth sends the canvas 200 doc ops (Core Server §7.4's burst: six lanes of work, one op from each every 250 ms, so six in flight and 24 writes a second, under its token's limit; each lane makes an agent, three with `canvas.addAgent` and three spawned linked from those, names and moves it, adds, changes, moves and removes its queue's items and adds to an agent already there, and one turns Arrange on and off: nothing a rule refuses or proposes), each checked to succeed, timed (p50, p99 and max) and the canvas checked as they left it, and holds the loop to p99 under 25 ms and max under 100 ms over the whole, the doc ops included (it also reports the spans before, during and after them), on a quiet drive (while another program writes heavily to the same drive, a commit's own writes into the log can stall the loop past 100 ms, as 2 of 8 runs did with `dd` writing alongside: only the core's connection on a thread of its own would hold G2 then); `e2e/damaged-store.e2e.ts` (G4) gives the built app a `core.db` that isn't a database, and it runs on, restored or empty, saying so in its window (serve.test.ts checks `serve` does the same). e2e specs may import the store's test helpers (`src/main/core/store/test-store.ts`). `e2e/lock.e2e.ts` checks `core.lock` with the built app (whose core process holds it, found through `app.getAppMetrics()`), and `e2e/core-crash.e2e.ts` kills that process: the window reconnects to the new core, the canvas restored paused, and a core that keeps stopping is given up on.

- Before calling a change done on macOS: `pnpm typecheck && pnpm lint && pnpm format:check && pnpm test && pnpm test:e2e`, then `pnpm package` and `scripts/check-macos.sh`. The macOS packaged gate verifies the strict deep bundle signature, node-pty's executable spawn-helper, the app's native self-test, three refused launch switches (exit 1), and the shipped command's self-test and help with an empty PATH. GitHub CI is disabled until the repository is public. Linux CI is local in Docker: `scripts/ci-linux.sh`, `scripts/check-linux.sh` and `scripts/check-linux-packages.sh` for both arm64 and x64; see [the local CI commands](toolchain.md#local-ci-while-the-repository-is-private). The full Linux suite runs under xvfb with the usual production-build global setup; the launch helper explicitly enables chromiumSandbox so Playwright never injects --no-sandbox on Linux; no spec is silently omitted. The Linux gate passes `--retries=0` explicitly, so `CI=1` cannot hide a failing spec with a successful retry. Package installation checks use clean Debian/Fedora containers to catch missing declared dependencies, run as non-root, test the shipped command with no system Node, and verify uninstall.

The crash gate tracks each `serve` from spawn with `TestChildren` too. Its intentional mid-run SIGKILLs remain unchanged. Teardown waits for every owner to exit and close its pipes, then reuses `Children.recover` on the profile’s `sessions/pids.json` (verified start times and private groups, SIGTERM then SIGKILL), and confirms every recorded group is gone before removing the folder. A failed owner shutdown, unreadable registry, failed group cleanup or surviving group keeps the folder and fails teardown. `src/main/cli/test-crash-cleanup.test.ts` exercises ordering, late CLI writes and failures with a fake OS.

Linux script tests (`src/main/linux-scripts.test.ts`) inject stand-in docker, git, pnpm and xvfb-run executables. They run both architecture paths without Docker, verify clean runtime images and artifact cleanup on failure, and exercise gate order and fail-fast reporting. The package configuration test requires Electron's audio library and the core's process inspection tools even with optional dependencies disabled. Shell syntax and upstream maker paths can be checked without Docker; the real container builds, Linux Electron/e2e runs and deb/rpm installations remain separate local gates.

The crash gate synchronizes each SIGKILL with six acknowledged messages, two or three native turn receipts and a recorded slow turn still in flight. Further sends race the crash; the final restart waits for a native receipt on every recipient with pending work. Its coverage counts and invariant assertions are unchanged, and its 240-second test deadline and 30-second startup/readiness bounds only fail a stuck run, never decide how much traffic ran.

The startup-shutdown CLI test holds only its login environment read (`-ilc`) behind a file gate until the CLI acknowledges repeated SIGTERM with “stopping already”; releasing the gate then proves it stops before making a token or delivering anything. The shell passes other invocations through to /bin/sh: Linux script first uses `$SHELL -c` to launch Node, and gating that earlier invocation would report script’s pid and stop the wrapper before serve ever starts. `src/main/cli/test-startup-shell.test.ts` checks both invocations without a pty or signals. It does not assume a two-second shell is still reading when the test is scheduled. The 30-second test deadline remains.

The two exhausted-usage reset/restart tests use FakeConnector's injected `step` to run native turns through microtasks, independently of their fake usage clock. They await actual reply/notice events and let the normal core shutdown persist them across a restart; they do not spend a real polling budget advancing fake CLI timers. Their five-second test deadline remains a failure guard. The terminal restart e2e waits for the agent panel's Web Animations to end before taking its reference screen size, matching the 380 ms grow in AgentView rather than assuming a live CLI implies settled geometry.

T3a’s transport cases (`src/main/core/test-transport.ts`) preserve each generated reach check’s caller. Every ordinary valid, invalid and rule fixture still runs for every caller; each caller-specific unreachable variant runs only for that token, and windows run the ordinary fixtures as you. Replaying a token’s foreign ids as you would turn negative reach probes into successful structural mutations, repeatedly laying out and growing the shared test canvas. `src/main/core/test-transport.test.ts` pins this matrix for MCP dispatch, HTTP’s token subset and the window.

macOS script tests (`src/main/macos-scripts.test.ts`) use fake codesign, app and shipped-command executables for both architectures, including paths with spaces. They check fail-fast signature and helper checks, reject each accepted launch switch, and require an empty PATH for the shipped command. Real signature verification and native execution remain packaged gates.
