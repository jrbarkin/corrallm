# Usage readings and rules

## `src/renderer/usage/`

Usage readings and rules in the renderer (see Usage readings and rules): store.ts keeps main's (useSyncExternalStore), usage.ts says which backends a canvas's adapters spend and words readings and rules (a hold's words are the engine's: model/words.ts), UsageGauge.tsx is a gauge per backend (on the canvas beside the project folder, and in All queues' header) whose panel sets the backend's rule and simulates usage.

## Usage readings and rules

A backend's usage limits belong to its account, so the core keeps one reading per backend (`src/main/usage.ts`, types and checks in `src/shared/usage.ts`): how much of each window (`fiveHour`, `weekly`) is used and when it resets, with when it was read, remembered across restarts in the app's user data (`usage.json`, version 2), and nothing else the CLI said. The backends are the catalog's (each adapter declares those its connections spend, and each connection's `usage` names one: `claude-code` for Claude Code's Terminal, `codex` for both of Codex's, none for the Agent SDK); the core keeps no reading of another, and a `.corral` file or checkpoint naming a backend this build lacks keeps it, unread. The renderer’s usage store follows the `usage` topic through its mirror (`renderer/api/topics.ts`), and calls the generated `usage.setRule` and `usage.simulate` operations for edits. `usage:changed`, its preload listener and the hand-written usage channels are gone; `usage.get`, `usage.setRule` and `usage.simulate` are the only window calls for usage. Rules are the user's, one per backend, kept by the core with the readings, not in `.corral` files.

- **Persistence.** Ordinary changes still coalesce for two seconds, and flush writes any pending change before shutdown. Every replacement of usage.json, including readings, simulations, rule changes and hard-limit releases, forces its temporary file to disk before rename and syncs its folder after (except on Windows, which opens no folder to sync). A later reading cannot replace a durably saved hard limit with an unforced file. A hard-limit write remains immediate and rejects on failure before publishing; ordinary write failures are logged as before.
- **A hit hard limit.** A turn that fails with `usage-limit` marks its usage backend exhausted until the limit lifts, independently of any rule (`core/engines.ts`): at the turn's `resetsAt` where its connection says it, else at the latest reset of the windows the backend's latest reading shows used up (at 100%, with a reset to come: `usedUpUntil` in `src/shared/usage.ts`), the turn's end then carrying that reset on to the run, its reply and the windows. Each connection that spends a backend reports a limit: the App Server's turn by `usageLimitExceeded`, with the used-up window's reset from its limits (else the soonest); Claude Code · Terminal's by its StopFailure hook's `rate_limit`, which says no reset, so it holds only where a status line has read a window full (whether Claude Code's status line reads one full at a limit, and when beside the hook, is not recorded); Codex · Terminal's by a turn ended without its Stop hook while its usage, read before the turn ends, shows its plan used up (see Codex), with that reset. Where nothing says when the limit lifts, nothing holds: a hold ends at a reset corrallm knows, one with no end would wait for a reading that a backend read only through its sessions (Claude Code's) never gets while it holds them, and a turn sent meanwhile fails at once, spending nothing, its sender told why. So a turn that failed on a rate limit with no window full (a transient one) holds nothing. The core forces this fact to disk in `usage.json` (`exhausted`, with the window when known) before publishing the hold or the failed turn, across restarts, for every agent spending that backend on every canvas. A hold it can't force to disk is never published (`UsageReadings.exhaust` rejects): it holds all the same until the core stops, the core says so on stderr, and the failed turn still ends; the next turn to hit the limit writes it again. `UsageReadings.durably` says a hold only once a write holding it is on disk (or it was read from the file): the one fact that switches an agent to the next backend of its chain. Parties’ messages wait, with one notice to each sender naming the agent, backend and reset in the host’s locale; delivery’s own clock wakes them at the reset. A fresh reading showing room in the exhausted window, including a simulated reading, releases them too; an omitted window says nothing, and forgetting a reading or removing a rule releases no hard limit. Since nothing is delivered to a held backend's agents, no session of it starts to report a limit that ends early (the user resetting their plan's usage), so the core reads a held backend itself (`core/usage-probe.ts`): by its adapter's `readUsage`, which spends nothing (Codex's: a private `codex app-server` asked only `account/rateLimits/read`, run as a CLI the core owns, with the agents' environment, in the home folder, since the limits are the account's), as the core starts and then every 10 minutes (`PROBE_MS`) while the backend is held, one read at a time; a reading goes to `UsageReadings.take`, and one that fails or says nothing changes nothing. A backend whose adapter has no reader (Claude Code's) holds until its reset. Tests give the core their own readers (`CoreConfig.sessions.readUsage`); fake sessions read none. The user’s own messages still go as typed, past the hold. `status` and `agents` show an otherwise idle agent as `limited`; Needs lists its exhausted usage until the reset, without choices, even when no message waits. The state and Need disappear at the reset. Rules still act before the hard limit.
- **Where readings come from.** `UsageReadings.take(backend, windows)` is the one way in; each connection gets it from `createConnectors({ usage })` and adapts what its CLI reports. Claude's Terminal connection: `sessions/claude-code/statusline.ts` (below), heard through its TerminalCli's `statusLine` (a Terminal session passes what its CLI says of usage to `TerminalSessionDeps.usage`). The Agent SDK connection runs on an API key (decided Oct 12, 2026), which has no usage windows: it reads nothing, and its agents are not held by rules (`usageBackendOf` in the engine's catalog, `src/shared/model/catalog.ts`).
- **Codex's readings.** `codex app-server` reports the plan's limits as a RateLimitSnapshot (`account/rateLimits/read`'s `rateLimits`, and each `account/rateLimits/updated`): `sessions/codex/limits.ts` reads Codex's own (`limitId` codex; a model's are not the plan's) once, for both the App Server's composer and the readings, naming each window by its length (300 minutes → `fiveHour`, 10080 → `weekly`; where Codex says no length, `primary` → `fiveHour`, `secondary` → `weekly`), `usedPercent` kept from 0 to 100, `resetsAt` (epoch seconds) × 1000 if within a week and a day. The App Server connection reads them as it connects and hears each update (its Translator's `usage`). Codex · Terminal's TUI tells corrallm nothing of them, so its TerminalCli's `readUsage` asks a private `codex app-server` (`codex/terminal/usage.ts`: the user's own `codex`, in the project folder, asked only `account/rateLimits/read`, then closed, through `askAppServer` as for its hooks' trust) when the session starts and after each turn ends (before it ends a turn Codex ended without its Stop hook: see Codex); one read at a time for every Codex Terminal session, and one more after it for whatever asked meanwhile. Reading them asks no model, so it spends no usage and needs no consent on a ChatGPT plan, in any build (the App Server connection still refuses a ChatGPT login in a commercial or hosted build, before it reads anything). On an API key Codex has no plan limits: no reading.
- **The status-line wrapper.** Claude Code gives its status line command a JSON input with `rate_limits.five_hour`/`.seven_day` (`used_percentage`, `resets_at` in epoch seconds), after the first API response of a subscription login. A Claude Code Terminal session's `--settings` (written by its TerminalCli's `prepare`, `claude-code.ts`) add corrallm's status line (they win over user, project and local settings): `/bin/sh <session dir>/statusline.sh`. The script reads its input with the shell's own commands, posts it in the background (curl, at most 2 s, headers from a 0600 file holding the session's token) to the hook server's `/status` path, then runs the user's own status line as Claude Code would (`/bin/sh -c '<their command>'`, the same input on stdin, in the same folder and environment) and exits as it does; with none, it prints nothing (Claude Code's footer is then as it was). The user's own is found when the session starts, as Claude Code finds it: `.claude/settings.local.json`, then `.claude/settings.json` in the project folder, then `settings.json` in `CLAUDE_CONFIG_DIR` (or `~/.claude`); its padding, refresh interval and vim indicator setting are kept. Since a refresh interval (like a limit's reset or the prompt cache expiring) reposts the input on a timer, a post counts as the turn's activity only when its progress fields (`statusLineProgress`: cost, API time, lines changed, tokens) change; see the stall watchdog in [Sessions](sessions.md). Claude Code runs status lines only in a trusted folder, the same gate as the user's own. Not covered: a status line changed during a session (it shows from the next one), managed (policy) status lines and `disableAllHooks` (they turn corrallm's off too: no readings; the session says so as it starts, see Terminal), `CLAUDE_CODE_SHELL_PREFIX` (applied to corrallm's command, not again to the user's), a local settings file in a worktree's main checkout, and Windows, where Claude Code runs status lines through Git Bash or PowerShell: there corrallm adds no status line (the user's shows as it is) and reads no usage. Without curl, the user's line still shows and nothing is read.
- **Rules** (`UsageRule`: a window, a share 1–99, an action) act between tasks: before a step or message would start (`RunStore.#gate`), an agent on the backend whose latest reading is over the share of the window (and the window not reset since) is warned about once a window (a notice in its session; it goes on), asked (status `asking`, `AgentRun.usage`, in the four places: row, All queues' lane head, the Needs you sidebar, the bar above the composer or under the terminal: Go on, Wait for the reset, Stop here; it asks no longer than its window lasts), or held until the window resets (status `waiting`; Go on now). Go on and Wait for the reset apply to every agent on that backend until the window resets; Stop here stops the queue at the top-level item holding the task. A new reading (`RunStore.usageChanged`) re-checks them. A rule may also say `fallback` (Carry on with the next backend: see Fallback below), read against the backend of the agent the task goes to (warn, ask and wait keep the queue owner's); with no chain, or no step left, it asks as ask does, with the same Go on and Wait memory. The picker keeps its existing three choices until the chain picker comes (B11a X4).
- **In queues.** An If may check `{ kind: 'usageAbove', backend, window, percent }` against the latest reading when the run reaches it (never by chance). A time may be `{ resets, backend }`: a delay (or a wait's limit) until the window resets, taken from the reading when the queue reaches it and kept (the next window's reset, read meanwhile, does not hold it again); with no reading of that window it goes on at once and says so. Each names its backend, and reads that backend's reading whichever agent's queue holds it. An agent's pickers offer both (an If's condition, a delay's time) for the backend its connection spends (the catalog's `usage`, the engine's `usageBackendOf`), and neither to an agent spending none (an Agent SDK agent, on an API key). One its queue already holds (from a shared file, or written before it switched connection) reads and runs as it says, and editing it offers that backend still.
- **Trying it.** "Simulate usage…" in a gauge's panel sets a simulated reading (marked so; a real reading replaces it), so rules, Ifs and waits can be tried with explicit sample usage readings.

## Fallback: carrying on with the next backend

B11a's fallback service (`src/main/core/fallback.ts`, `FallbackService`, composed once by createCore) switches an agent to the next step of the chain you set (`agent.setFallback`, yours alone: see [Canvas](canvas.md)) when its usage runs out, or a usage rule says to, from a fresh conversation, and its work carries on there.

- **Admission.** One check runs before automated work starts for an agent (`FallbackService.admit`): in the run's gate, before a task's attempt goes to its recipient (`RunIO.admit`); for a task held because its attempt failed on its recipient's usage limit, as the run moves; and in delivery, before a party's message is handed over (`DeliveryDeps.admit`). Never for your own messages, never while the agent or a group holding it is paused or killed, never under the shutdown barrier, and for run work never while the run is stopped. Run admission marks its work, including a task already held on its limit, so the lane keeps checking that the run is going; party delivery remains independent of Run/Stop. It says `go` (the work goes, or is held, as it would have been), `switching` (the work waits, shown as switching) or `ask` (a fallback rule that can't switch asks).
- **Triggers.** The agent's current backend held exhausted on disk (`durably`, above), whoever's turn hit the limit; or a real reading over a `fallback` rule's share of the recipient's backend. A `usage-limit` with no known reset holds nothing and switches nothing: the task is held for you as before, saying the chain didn't act because corrallm can't tell when the limit ends (`RunIO.limitNote`). A simulated reading over a `fallback` rule switches nothing: the agent's session is told once a window, "Simulated: ‹agent› would carry on with ‹next›", and the work goes. An agent spending no backend (the Agent SDK) is never switched away on its own.
- **The walk.** From the step after the one the agent is on, then its own endpoint (`on.from`), never past it (`next` in `src/shared/model/fallback.ts`), passing by a step this build can't run, one the agent runs already, and a backend held exhausted or held by its rule (any action but warn) over its share on a real reading. The first step left wins; each passed by is named in the switch's notice. With none left, the work is held for you as before, its sentence naming each step and when it can take work (a task held on the limit), or the rule asks, told once a window. An agent whose own endpoint you made one of its steps, on none of them yet, says its chain didn't act, and that removing that step from its chain lets it act again (`agent.setFallback` refuses a chain naming the agent's own endpoint).
- **The switch** (C4): one lane per agent, nothing journaled. It waits until the agent's session has nothing going, asked, queued or on its way from the run, and from that moment holds whatever would start a turn or a session (`SessionStore.switching`); checks the agent's workspace; closes its session, waiting for a close that hasn't finished (`SessionManager.closed`), never forcing it; forgets the target adapter's remembered conversation (`fresh`); and commits the step to the agent's document as corrallm (`fallback.switch`, or `fallback.return`), through Documents.change, checked against the agent's revision as admission captured it and workspace-safety, with C3's handoff carry staged in the same write. After each await, and in the document commit check after its queue and workspace preflight, it checks again that the agent is there and unchanged, not paused or killed, the run still going for run work, the barrier not held, and its target able to take work; any change abandons the switch (a closed session and a forgotten conversation are harmless), and admission decides again. A held workspace, a failed `fresh`, a commit that can't be written or anything unforeseen abandons it and says why in the agent's transcript; admission tries a blocked switch or return again once the agent changes or its availability does, never in a loop. Once the commit is on disk the engine follows the document, the transcript says where it went, why and what it passed by, a task held on the limit goes once more as a new attempt there (`RunStore.continueAfterSwitch`), senders whose messages failed on the limit are told once, and what waited goes, on the new endpoint. A target that won't start then holds as any session that won't start does.
- **Switching back** (C8): a chain with `back: 'return'` switches the agent back to its own endpoint at its next admitted work once that endpoint's backend can take work: not held exhausted, no rule (but warn) over its share on a real reading, and, for a rule's switch, a reading of it at all. It puts back what corrallm wrote, never retries a held task, and never interrupts a turn. Stay, the default, never returns on its own.
- **A restart** decides again: the document has switched or it hasn't. A switch committed before a crash leaves a task held on the limit for your Retry; one not committed is made again once the run is resumed, while the hold is on disk.

## Prepared handoff threshold

`src/shared/model/fallback.ts` validates nullable session context in whole tokens on the connection's own reported basis, with a positive window and a nullable compaction point. Handoff settings default to 95% and allow integer percentages from 10 through 95. `askPoint` takes the smaller of that share of the window and the reported compaction point minus `HANDOFF_RESERVE` (20,000 tokens); an unknown compaction point uses the share alone, and a small window floors the ask point at zero. It gives 947,000 for a 1M window compacting at 967,000, and 430,000 for a reported 475,000 window compacting at 450,000. The connections prepare reports through their own adapters (see [Claude Code](claude-code.md) and [Codex](codex.md)), with the catalog context capability true for Claude Code's two connections and Codex's App Server (each proven by a recording of a real automatic compaction) and false for Codex's Terminal. Arming, request delivery and acceptance remain unwired. A compaction can come before the reading reaches `compactAt` (the tool output a turn has yet to add is counted by the CLI; a user's lowered compaction setting is invisible to Claude's Terminal): the reserve of the ask point is what covers that.

A compaction can still precede the handoff: a lowered native compaction setting, idle compaction, or large tool output in the middle of a turn may cross first. The later service must rearm below the threshold and retain the previous handoff until another is accepted; this calculation cannot prevent native compaction.
