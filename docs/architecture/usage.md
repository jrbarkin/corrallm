## `src/renderer/usage/`

Usage readings and rules in the renderer (see Usage readings and rules): store.ts keeps main's (useSyncExternalStore), usage.ts says which backends a canvas's adapters spend and words readings and rules (a hold's words are the engine's: model/words.ts), UsageGauge.tsx is a gauge per backend (on the canvas beside the project folder, and in All queues' header) whose panel sets the backend's rule and simulates usage.

## Usage readings and rules

A backend's usage limits belong to its account, so the core keeps one reading per backend (`src/main/usage.ts`, types and checks in `src/shared/usage.ts`): how much of each window (`fiveHour`, `weekly`) is used and when it resets, with when it was read, remembered across restarts in the app's user data (`usage.json`, version 2), and nothing else the CLI said. The backends are the catalog's (each adapter declares those its connections spend, and each connection's `usage` names one: `claude-code` for Claude Code's Terminal, `codex` for both of Codex's, none for the Agent SDK); the core keeps no reading of another, and a `.corral` file or checkpoint naming a backend this build lacks keeps it, unread. The renderer’s usage store follows the `usage` topic through its mirror (`renderer/api/topics.ts`), and calls the generated `usage.setRule` and `usage.simulate` operations for edits. `usage:changed`, its preload listener and the hand-written usage channels are gone; `usage.get`, `usage.setRule` and `usage.simulate` are the only window calls for usage. Rules are the user's, one per backend, kept by the core with the readings, not in `.corral` files.

- **Persistence.** Ordinary changes still coalesce for two seconds, and flush writes any pending change before shutdown. Every replacement of usage.json, including readings, simulations, rule changes and hard-limit releases, forces its temporary file to disk before rename and syncs its folder after (except on Windows, which opens no folder to sync). A later reading cannot replace a durably saved hard limit with an unforced file. A hard-limit write remains immediate and rejects on failure before publishing; ordinary write failures are logged as before.
- **A hit hard limit.** A turn that fails with `usage-limit` marks its usage backend exhausted until the limit lifts, independently of any rule (`core/engines.ts`): at the turn's `resetsAt` where its connection says it, else at the latest reset of the windows the backend's latest reading shows used up (at 100%, with a reset to come: `usedUpUntil` in `src/shared/usage.ts`), the turn's end then carrying that reset on to the run, its reply and the windows. Each connection that spends a backend reports a limit: the App Server's turn by `usageLimitExceeded`, with the used-up window's reset from its limits (else the soonest); Claude Code · Terminal's by its StopFailure hook's `rate_limit`, which says no reset, so it holds only where a status line has read a window full (whether Claude Code's status line reads one full at a limit, and when beside the hook, is not recorded); Codex · Terminal's by a turn ended without its Stop hook while its usage, read before the turn ends, shows its plan used up (see Codex), with that reset. Where nothing says when the limit lifts, nothing holds: a hold ends at a reset corrallm knows, one with no end would wait for a reading that a backend read only through its sessions (Claude Code's) never gets while it holds them, and a turn sent meanwhile fails at once, spending nothing, its sender told why. So a turn that failed on a rate limit with no window full (a transient one) holds nothing. The core forces this fact to disk in `usage.json` (`exhausted`, with the window when known) before publishing the hold or the failed turn, across restarts, for every agent spending that backend on every canvas. A hold it can't force to disk is never published (`UsageReadings.exhaust` rejects): it holds all the same until the core stops, the core says so on stderr, and the failed turn still ends; the next turn to hit the limit writes it again. Parties’ messages wait, with one notice to each sender naming the agent, backend and reset in the host’s locale; delivery’s own clock wakes them at the reset. A fresh reading showing room in the exhausted window, including a simulated reading, releases them too; an omitted window says nothing, and forgetting a reading or removing a rule releases no hard limit. Since nothing is delivered to a held backend's agents, no session of it starts to report a limit that ends early (the user resetting their plan's usage), so the core reads a held backend itself (`core/usage-probe.ts`): by its adapter's `readUsage`, which spends nothing (Codex's: a private `codex app-server` asked only `account/rateLimits/read`, run as a CLI the core owns, with the agents' environment, in the home folder, since the limits are the account's), as the core starts and then every 10 minutes (`PROBE_MS`) while the backend is held, one read at a time; a reading goes to `UsageReadings.take`, and one that fails or says nothing changes nothing. A backend whose adapter has no reader (Claude Code's) holds until its reset. Tests give the core their own readers (`CoreConfig.sessions.readUsage`); fake sessions read none. The user’s own messages still go as typed, past the hold. `status` and `agents` show an otherwise idle agent as `limited`; Needs lists its exhausted usage until the reset, without choices, even when no message waits. The state and Need disappear at the reset. Rules still act before the hard limit.
- **Where readings come from.** `UsageReadings.take(backend, windows)` is the one way in; each connection gets it from `createConnectors({ usage })` and adapts what its CLI reports. Claude's Terminal connection: `sessions/claude-code/statusline.ts` (below), heard through its TerminalCli's `statusLine` (a Terminal session passes what its CLI says of usage to `TerminalSessionDeps.usage`). The Agent SDK connection runs on an API key (decided Oct 12, 2026), which has no usage windows: it reads nothing, and its agents are not held by rules (`usageBackendOf` in the engine's catalog, `src/shared/engine/catalog.ts`).
- **Codex's readings.** `codex app-server` reports the plan's limits as a RateLimitSnapshot (`account/rateLimits/read`'s `rateLimits`, and each `account/rateLimits/updated`): `sessions/codex/limits.ts` reads Codex's own (`limitId` codex; a model's are not the plan's) once, for both the App Server's composer and the readings, naming each window by its length (300 minutes → `fiveHour`, 10080 → `weekly`; where Codex says no length, `primary` → `fiveHour`, `secondary` → `weekly`), `usedPercent` kept from 0 to 100, `resetsAt` (epoch seconds) × 1000 if within a week and a day. The App Server connection reads them as it connects and hears each update (its Translator's `usage`). Codex · Terminal's TUI tells corrallm nothing of them, so its TerminalCli's `readUsage` asks a private `codex app-server` (`codex/terminal/usage.ts`: the user's own `codex`, in the project folder, asked only `account/rateLimits/read`, then closed, through `askAppServer` as for its hooks' trust) when the session starts and after each turn ends (before it ends a turn Codex ended without its Stop hook: see Codex); one read at a time for every Codex Terminal session, and one more after it for whatever asked meanwhile. Reading them asks no model, so it spends no usage and needs no consent on a ChatGPT plan, in any build (the App Server connection still refuses a ChatGPT login in a commercial or hosted build, before it reads anything). On an API key Codex has no plan limits: no reading.
- **The status-line wrapper.** Claude Code gives its status line command a JSON input with `rate_limits.five_hour`/`.seven_day` (`used_percentage`, `resets_at` in epoch seconds), after the first API response of a subscription login. A Claude Code Terminal session's `--settings` (written by its TerminalCli's `prepare`, `claude-code.ts`) add corrallm's status line (they win over user, project and local settings): `/bin/sh <session dir>/statusline.sh`. The script reads its input with the shell's own commands, posts it in the background (curl, at most 2 s, headers from a 0600 file holding the session's token) to the hook server's `/status` path, then runs the user's own status line as Claude Code would (`/bin/sh -c '<their command>'`, the same input on stdin, in the same folder and environment) and exits as it does; with none, it prints nothing (Claude Code's footer is then as it was). The user's own is found when the session starts, as Claude Code finds it: `.claude/settings.local.json`, then `.claude/settings.json` in the project folder, then `settings.json` in `CLAUDE_CONFIG_DIR` (or `~/.claude`); its padding, refresh interval and vim indicator setting are kept. Claude Code runs status lines only in a trusted folder, the same gate as the user's own. Not covered: a status line changed during a session (it shows from the next one), managed (policy) status lines and `disableAllHooks` (they turn corrallm's off too: no readings; the session says so as it starts, see Terminal), `CLAUDE_CODE_SHELL_PREFIX` (applied to corrallm's command, not again to the user's), a local settings file in a worktree's main checkout, and Windows, where Claude Code runs status lines through Git Bash or PowerShell: there corrallm adds no status line (the user's shows as it is) and reads no usage. Without curl, the user's line still shows and nothing is read.
- **Rules** (`UsageRule`: a window, a share 1–99, an action) act between tasks: before a step or message would start (`RunStore.#gate`), an agent on the backend whose latest reading is over the share of the window (and the window not reset since) is warned about once a window (a notice in its session; it goes on), asked (status `asking`, `AgentRun.usage`, in the four places: row, All queues' lane head, the Needs you sidebar, the bar above the composer or under the terminal: Go on, Wait for the reset, Stop here; it asks no longer than its window lasts), or held until the window resets (status `waiting`; Go on now). Go on and Wait for the reset apply to every agent on that backend until the window resets; Stop here stops the queue at the top-level item holding the task. A new reading (`RunStore.usageChanged`) re-checks them. "Carry on with the next backend" comes with the fallback chain: it will be one more `UsageAction`.
- **In queues.** An If may check `{ kind: 'usageAbove', backend, window, percent }` against the latest reading when the run reaches it (never by chance). A time may be `{ resets, backend }`: a delay (or a wait's limit) until the window resets, taken from the reading when the queue reaches it and kept (the next window's reset, read meanwhile, does not hold it again); with no reading of that window it goes on at once and says so. Each names its backend, and reads that backend's reading whichever agent's queue holds it. An agent's pickers offer both (an If's condition, a delay's time) for the backend its connection spends (the catalog's `usage`, the engine's `usageBackendOf`), and neither to an agent spending none (an Agent SDK agent, on an API key). One its queue already holds (from a shared file, or written before it switched connection) reads and runs as it says, and editing it offers that backend still.
- **Trying it.** "Simulate usage…" in a gauge's panel sets a simulated reading (marked so; a real reading replaces it), so rules, Ifs and waits can be tried with explicit sample usage readings.
