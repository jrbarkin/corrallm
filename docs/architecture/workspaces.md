# Workspaces

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

B9a gives independent work independent checkouts: each canvas's outermost group, or lone agent, works in a Git worktree of its own of the repository picked as the canvas's project folder. The records are schema 3's (see [Store](store.md)); this page is the Git and filesystem side, in `src/main/core/workspaces/`. Q32 is answered yes (Claude Code trusts a worktree inside a trusted folder), so new checkouts live inside the picked checkout.

## The Git runner

`src/main/core/workspaces/git.ts` is the one runner every workspace Git call goes through (`GitRunner`); no other file of the folder starts a process (`git.test.ts` scans it). B9b's diffs and merges are to reuse it.

- No shell. Git is run by absolute path, found only in the PATH's absolute folders: a relative entry such as `.` could otherwise find a `git` a repository planted in the folder it runs in. Arguments are the core's own, refs and OIDs of core shapes, paths after `--end-of-options`.
- Fixed options on every call: `SAFE_GIT_OPTIONS` (no fsmonitor, no implicit bare repository), `core.hooksPath` set to an empty folder of the core's own (no repository hook runs, whichever hooks folder the repository's configuration names; the folder is checked to be a real, private, empty folder before every call, and nothing runs otherwise), `submodule.recurse=false`, `protocol.allow=never` (no transport at all: no fetch, so no lazy fetch of a partial clone and no ssh, `ext::` command or credential helper; held by `GIT_ALLOW_PROTOCOL` below, since a repository's `protocol.<name>.allow` outranks it), `gc.auto=0` and `maintenance.auto=false` (no automatic prune, and no gc detaching from the core's process group).
- Filter drivers: each driver configured where a call runs (`inspect`, `git config --list -z --name-only`, so includes and conditional includes are read as Git reads them in that folder) has its clean, smudge and process commands blanked and its required flag cleared, so no filter runs, Git LFS's included (its pointers are checked out as they are). A driver whose name holds `=` can't be named by `-c`, so it is refused, as are `core.worktree` (it would redirect the checkout) and configured hooks (`hook.*`, which `core.hooksPath` doesn't reach). Configuration Git can't read fails the call: nothing runs on what couldn't be inspected.
- Patches (`patch`) add `safeGitDiffArgs` from `src/main/git.ts`: no external diff, textconv or filter driver, no signature program for log and show (`log.showSignature` would run `gpg.program`), and a submodule shown by its commit only, never asked whether it is dirty (either starts a git in the submodule under its own configuration, which the inspection here never read; a committed `.gitmodules` `ignore` is outranked only by the command-line flag).
- The environment is the agents' (their PATH and home), every `GIT_` variable removed (none can redirect a call, as GIT_DIR, GIT_WORK_TREE or GIT_INDEX_FILE would, or configure one, as GIT_CONFIG_PARAMETERS or GIT_CONFIG_COUNT would), then `GIT_TERMINAL_PROMPT=0`, `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL=none` (the one transport policy above every configuration, naming no transport Git has: Git older than GIT_NO_LAZY_FETCH, 2.45.1 and its 2.39.4+ backports, still lazily fetches a partial clone's missing blobs while populating it) and `LC_ALL=C`.
- Bounded: each call has a timeout (15 s unless it says otherwise) and an output bound (1 MiB; a configuration listing 4 MiB); what a failed git said is kept to 2,000 characters, for diagnostics only. Its exit codes that answer (Git's 1 for "there is none") are answers; any other fails it (`GitError`, with a fault: git-missing, git-unsupported, hooks, config, refused, timeout, output or failed).
- Owned: with the core's process owner (`core/children.ts`), every git, its version check included, is a recorded child in a private process group, ended whole when it takes too long or prints too much, and refused once the core is closing.
- Git older than 2.36 is refused (`worktree list --porcelain -z` reads paths of any shape).

What this protects is corrallm running a repository's programs itself. A worktree is checkout isolation, not a sandbox: agents run their own commands in it, and a process already running as the user can change a repository's configuration whenever it likes.

## Repository discovery

`src/main/core/workspaces/discovery.ts` (`discoverRepository`) takes the picked folder, a TrustedPath, and finds the checkout it is: its real top level, its own and common Git directories, the repository's identity (its common directory's inode, so one deleted and cloned again at the same path is another), its HEAD (branch ref, or none when detached, and commit) and the filter drivers configured in it. It refuses, saying why in a sentence for the person:

- a folder inside a repository (`subdirectory`, naming the top level to choose instead): never widened to the whole repository;
- a checkout that is really somewhere else (`redirected`): a `.git` symlink, a `.git` file naming another repository, a linked worktree whose registration's back-pointer doesn't name it, `core.worktree`, a top level elsewhere, or a folder Git hasn't registered as a checkout;
- configuration the runner can't neutralize (`config`), a `.git` Git can't read or a path with control characters (`unsupported`), a repository with no commit (`no-commit`: "Make the repository's first commit, then retry."), a missing or unreadable folder, and Git missing, too old or failing.

Only Git's own "not a git repository", with no `.git` there at all, is a folder that isn't one (`not-git`), whose agents share it as before. A picked linked worktree is supported: it, not the main checkout, is the base. `recordRepository` keeps what was found in the `repository` table, within a write, by real path and identity: one kept already is found again (its picked path and common directory as they are now), its workspaces' folder never moved; a new one gets this profile's folder inside its checkout.

## The owned root

`src/main/core/workspaces/owned.ts`. A repository's checkouts go in `<checkout>/.corral/worktrees/<profile-id>/`, each named by its workspace's id. `ensureOwnedRoot` makes it if it is missing and verifies it before anything is written in it; `verifyOwnedRoot` only verifies. Every folder from the checkout's real path down must be a real folder (a symlink anywhere, which a repository could commit, is refused, and nothing is written where it leads), the user's, and the last one private (0700), marked by the core. The marker is kept in the repository's common Git directory (`corrallm/owned-root-<hash of the root's path>.json`, 0600, never through a symlink), not in the checkout, where a `git clean -fdx` would take it while Git spares the checkouts themselves; it names the repository record, the root's path and the root folder's inode, so another folder put in its place isn't taken for it. One the core didn't mark is refused, never adopted, unless it is empty (just made, or a crash between making it and marking it). A root outside the checkout is refused.

`excludeOwnedRoot` adds `/.corral/worktrees/` to the repository's local `info/exclude`, in its common directory, once, keeping what it holds: never the tracked `.gitignore`, never through a symlink, never a file it can't read whole (over 1 MiB). The checkout's status, `git add -A` and its agents then never take the workspaces for its files, nor add them as embedded repositories. The non-Git walk of `src/main/files.ts` skips `.corral` too.

## Provisioning

`src/main/core/workspaces/provision.ts` (`Provisioner`, B9a Design §3's protocol). Nothing composes it yet: binding agents to workspaces at the document seam is C6's, the resolver's use of it X11b's.

- **Intent first.** `intend`, synchronous and within a write (its own, or a document commit's), returns the owner's workspace in use if there is one; otherwise it records the workspace `creating`, its generated checkout path (`<owned root>/<workspace id>`) and branch (`refs/heads/corrallm/<profile id>/<workspace id>`), the base captured from the picked checkout's HEAD (its commit, and branch or none; never its uncommitted edits), and a `create` job at phase `recorded`. The job's payload is its immutable intent (canvas, repository, path, branch, base, fork, attempt) and its id is made from the workspace and attempt, so recording the same intent again is the same job (`WorkspaceStore.recordJob`'s intent hash), never a second one. No Git runs and no file is touched in that write.
- **Phases outside SQL.** `run` takes the job to its repository's lane of the queue (below). Its phases, each marked on disk once done (`CREATE_PHASES`): `branch`, the ref made at the base commit with `update-ref`'s empty old value, so only if it doesn't exist; `registered`, `git worktree add --no-checkout` of that branch at the path; `populated`, the files read from the base commit's tree (`read-tree --reset -u --no-recurse-submodules`). Before any of it the repository is discovered again and must be the one recorded (real path, common directory, the identity the job expects), and the owned root is made or verified and excluded; before a phase runs, what Git and the file system have is read again, so a phase done but not recorded is adopted rather than done twice. Before population, Git's configuration is inspected again in the new checkout (conditional includes on its branch and folder apply only there) and the checkout must verify as below, on its branch, at its base.
- **Ready for setup.** Verified again, the job ends `done` and the workspace moves to `setup` in one write: copying local files and the setup command are C9 and C10's, and agents wait until the workspace is `ready`. A failure the job can name (Git's, the owned root's, a check's) ends it `failed` and the workspace `error` with a code (`config`, `branch-moved`, `unregistered-checkout`, `interrupted-registration`, `checkout-changed`, `repository-changed`, `owned-root-<fault>`, `git-<fault>`, ...); one it can't (the core closing, the store failing) leaves the job open for the next start.
- **Never over what it didn't make.** A branch already at another commit, a folder with files at the path, a registration on another branch, or one Git left locked part way through adding it fails the job, its contents untouched. Nothing here forces, resets, removes or prunes a checkout or branch: removal is cleanup's (C7).
- **Reuse.** `provision` returns the owner's workspace in use, or makes one; concurrent asks for an owner share one allocation (ten simultaneous starts run one set of Git commands), and runs and retries are shared the same way.
- **The queue.** `src/main/core/workspaces/queue.ts` (`ProvisioningQueue`): one lane per repository, keyed by its common Git directory and shared by every canvas (B9b's merges are to share it), at most 2 repositories at work at once, at most 64 jobs waiting or running. Past that, `provision` refuses (`busy`) before recording anything. Its work never waits for a person or an agent's turn.
- **Restart.** `reconcile`, after child recovery: every open create job runs again from what is on disk (a crash before or after the branch, after registration, part way through population or after it is recorded all finish to one checkout, no step done twice), then every `setup` or `ready` workspace's checkout is checked, so one removed while the core was stopped is `missing` before it is asked for. Population is redone only while a workspace is still `creating`, before any agent could have run in it.
- **Lost and found.** `checkout` checks a `setup` or `ready` workspace each time its path is asked for: a folder gone is `missing` (`checkout-missing`, or `repository-missing`), one changed is `error`; a check Git couldn't make holds without recording anything (unknown, not safe). `retry` runs a failed creation again as a new attempt of the same intent, from what Git has; a workspace made once, then lost and found again as it was made, goes back to `setup` (or `ready` once its setup was done or skipped) at a new generation, so what ran in it before is stale. One gone for good stays `missing`: retry never makes a checkout over its branch.

## The verified checkout

`src/main/core/workspaces/checkout.ts` is the workspaces' one `TrustedPath` mint site (`src/main/boundaries.test.ts` pins it, and that only `verifiedCheckout` mints, after `checkCheckout`). A path read back from the store is a record; each use checks, as Git and the file system say now, that the repository is the one recorded (its checkout at its real path, its common directory with the identity recorded), that the owned root verifies and the checkout is its folder named by the workspace's id (a real folder, not a symlink, the user's), that its `.git` names a registration in the common directory whose back-pointer names it back, that Git finds it as its own top level with that common directory, and that Git lists it as registered. Only then is its path minted. The trust gate is still the project folder picked: this checkout is that repository's, made by the core in the folder it owns there. The branch checked out there now is reported, not required: an agent may switch branches in its own checkout.

## The profile id

`src/main/core/workspaces/profile.ts` (`profileId`): a UUID naming this profile's branches and its folder in each checkout, so two profiles' workspaces of one repository never meet. Kept in `<profile>/workspaces/profile-id` (0600), beside the database rather than in it, so a restored database keeps it; made once, and one that can't be read is refused, never replaced. The runner's empty hooks folder is meant to be `<profile>/workspaces/hooks`.
