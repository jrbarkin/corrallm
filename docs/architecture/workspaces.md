# Workspaces

[Architecture index](overview.md) · [Canonical instructions](../../AGENTS.md)

B9a gives independent work independent checkouts: each canvas's outermost group, or lone agent, works in a Git worktree of its own of the repository picked as the canvas's project folder. The records are schema 3's (see [Store](store.md)); this page is the Git and filesystem side, in `src/main/core/workspaces/`. Q32 is answered yes (Claude Code trusts a worktree inside a trusted folder), so new checkouts live inside the picked checkout.

## Prepared branch review contracts

B9b's pure helpers are in `src/shared/model/branch-review.ts` and `src/shared/model/branch-patch.ts`, with wire schemas in `src/shared/api/branch.ts`. They run no Git, read no files and grant no authority. Neither branch operation is registered yet.

The review cursor is canonical unpadded base64url of a strict version-1 object containing the tip, nullable uncommitted digest and inventory position (0–20,000). Decoding refuses malformed or noncanonical encodings; continuation compares only those observations, returning conflict on change. The manifest sorts valid UTF-8 path bytes without normalization, prefixes the tip with the versioned domain, and records mode, blob OID and NUL-terminated path for each entry. Deletions use mode 000000 and a zero OID of the repository's length. SHA-256 uses Web Crypto over those canonical bytes. Duplicate, lossy, unsupported or oversized entries are refused. Inventory completeness, blob computation, the 1 GiB hashing bound and checkpoint eligibility remain the core service's responsibility.

Pages include at most 200 entries (50 by default) and 60 KiB of serialized JSON, including metadata and continuation. A cut patch ends at a complete line and UTF-8 boundary; its file is still consumed by the continuation. Metadata that cannot fit even with an empty patch fails rather than returning a nonadvancing page. The service supplies committed entries first, then uncommitted entries in path-byte order, each inventory capped at 10,000. Untracked patches render already-read bytes, using at most 1 MiB and detecting binary data by a NUL in the first 8,000 bytes; the core remains responsible for opening safely and checking file type and links. Lossy displayed names stay within 4,096 UTF-8 bytes and must never be used as Git inputs. Refusal path lists quote at most five names, shorten each quoted name to 256 UTF-8 bytes, and count the rest; a reason of at most 512 bytes keeps the sentence within 2 KiB.

## The Git runner

`src/main/core/workspaces/git.ts` is the one runner every workspace Git call goes through (`GitRunner`); no other file of the folder starts a process (`git.test.ts` scans it). B9b's diffs and merges reuse it, with the merge profile below.

- No shell. Git is run by absolute path, found only in the PATH's absolute folders: a relative entry such as `.` could otherwise find a `git` a repository planted in the folder it runs in. Arguments are the core's own, refs and OIDs of core shapes, paths after `--end-of-options`.
- Fixed options on every call: `SAFE_GIT_OPTIONS` (no fsmonitor, no implicit bare repository), `core.hooksPath` set to an empty folder of the core's own (no repository hook runs, whichever hooks folder the repository's configuration names; the folder is checked to be a real, private, empty folder before every call, and nothing runs otherwise), `submodule.recurse=false`, `protocol.allow=never` (no transport at all: no fetch, so no lazy fetch of a partial clone and no ssh, `ext::` command or credential helper; held by `GIT_ALLOW_PROTOCOL` below, since a repository's `protocol.<name>.allow` outranks it), `gc.auto=0` and `maintenance.auto=false` (no automatic prune, and no gc detaching from the core's process group), and `worktree.useRelativePaths=false` (a worktree is registered by absolute paths, so `worktree add` never writes the repository's configuration to record relative ones). A call's own configuration (`config`) comes before them, so they win over it.
- Filter drivers: each driver configured where a call runs (`inspect`, `git config --list -z --name-only`, so includes and conditional includes are read as Git reads them in that folder) has its clean, smudge and process commands blanked and its required flag cleared, so no filter runs, Git LFS's included (its pointers are checked out as they are). A driver whose name holds `=` can't be named by `-c`, so it is refused, as are `core.worktree` (it would redirect the checkout) and configured hooks (`hook.*`, which `core.hooksPath` doesn't reach). Configuration Git can't read fails the call: nothing runs on what couldn't be inspected.
- Patches (`patch`) add `safeGitDiffArgs` from `src/main/git.ts`: no external diff, textconv or filter driver, no signature program for log and show (`log.showSignature` would run `gpg.program`), and a submodule shown by its commit only, never asked whether it is dirty (either starts a git in the submodule under its own configuration, which the inspection here never read; a committed `.gitmodules` `ignore` is outranked only by the command-line flag).
- The environment is the agents' (their PATH and home), every `GIT_` variable removed (none can redirect a call, as GIT_DIR, GIT_WORK_TREE or GIT_INDEX_FILE would, or configure one, as GIT_CONFIG_PARAMETERS or GIT_CONFIG_COUNT would), then `GIT_TERMINAL_PROMPT=0`, `SAFE_GIT_ENV` from `src/main/git.ts` (`GIT_NO_LAZY_FETCH=1` and `GIT_ALLOW_PROTOCOL` set to the empty string, the one transport policy above every configuration, admitting no transport or remote helper, since Git older than GIT_NO_LAZY_FETCH, 2.45.1 and its 2.39.4+ backports, still lazily fetches a partial clone's missing blobs while populating it) and `LC_ALL=C`.
- Bounded: each call has a timeout (15 s unless it says otherwise) and an output bound (1 MiB; a configuration listing 4 MiB); what a failed git said is kept to 2,000 characters, for diagnostics only. Its exit codes that answer (Git's 1 for "there is none") are answers; any other fails it (`GitError`, with a fault: git-missing, git-unsupported, hooks, config, refused, timeout, output or failed).
- Owned: with the core's process owner (`core/children.ts`), every git, its version check included, is a recorded child in a private process group, ended whole when it takes too long or prints too much, and refused once the core is closing.
- Git older than 2.36 is refused (`worktree list --porcelain -z` reads paths of any shape). A call may ask for a newer floor of its own (`needs`): an older Git refuses it (`git-unsupported`, naming both versions) before anything runs, and runs every other call.
- **The merge profile** (B9b Design §9 C7, C9; a call's `merge`): replace refs ignored (`git --no-replace-objects`, which Review changes' reads take alone as `noReplaceObjects`), so an object id means the object itself; `merge.renormalize=false`, since renormalizing runs clean and smudge filters inside a merge; and every custom merge driver configured where the call runs (`inspect`'s `mergeDrivers`, includes and conditional includes as Git reads them there) blanked by name (`merge.<name>.driver=`), after the call's own configuration, so none runs, whether a committed attribute, one only in the checkout's working tree or `merge.default` names it, and a path that needs one fails closed: a conflict on Git 2.50, Git stopping on 2.39, never merged some other way. A driver whose name holds `=` can't be named by `-c`, so a merge's call refuses it (other calls never run a merge driver, so discovery doesn't). Built-in drivers (`text`, `binary`, `union`) apply as the repository asks. Merging needs Git 2.39 (`MERGE_GIT_VERSION`: `merge-tree --write-tree` came in 2.38, and bookworm's 2.39.5 is the oldest tested), every call of the profile refused on an older one while worktrees and the rest keep 2.36; and its calls are bounded by 5 minutes (`MERGE_TIMEOUT_MS`) unless they say otherwise.
- **The install** (`install`) is only a fast-forward to a prepared merge commit, named by its object id: `merge --ff-only --no-overwrite-ignore --no-verify-signatures --no-autostash --no-stat --no-squash --no-edit -q`, under the merge profile, bounded by 30 minutes (`INSTALL_TIMEOUT_MS`). It computes no merge, and its flags beat whatever the repository sets (`branch.<name>.mergeOptions`, `merge.ff`, `merge.verifySignatures`, `merge.autoStash`, `merge.stat`). Git refuses an untracked or ignored file in its way, naming it (an ignored file where the merge brings a file or a folder, an ignored link where a folder comes, ignored files inside a folder that becomes a file, a name differing only in case where the filesystem doesn't tell them apart), where the two-tree `read-tree -m -u` writes over ignored files; a new file into an ignored folder is allowed, its other files kept. A refusal, another git's `index.lock` included, writes nothing but ORIG_HEAD.
- **Commits** (`commitTree`): `commit-tree` of a tree on one or two parents, by object id, by the author and committer given (`-c author.*` and `-c committer.*`, which beat the repository's), with `commit.gpgSign=false` and `--no-gpg-sign` (never signed, so no `gpg.program`), `-m` (never an editor), and, as plumbing, no commit hook; what it answers is checked to be an object id. A name, email or message Git would read some other way (`<`, `>`, a control character, a NUL, too long) is refused.
- **Capped reads** (`capped`, for Review changes' pages): what a call prints is read up to a byte cap; past it the git's whole process group is ended, as the core's child, and the read answers what it had, `cut`, ending at a whole character (never a larger buffer read whole and then cut). A git that fails, times out or floods stderr fails as any call does, never answered as a short page.
- **A temporary index** (`index`): GIT_INDEX_FILE is set only to a `TemporaryIndex`, which only `src/main/core/workspaces/merge-index.ts` makes, for one merge job: `<profile>/workspaces/merge/<job>/index`, its folder made fresh for that job (refused if it is there already) in a folder of the profile's that must be a real one of the user's no one else may write to, and removed as the job ends. No caller's path, environment or argument sets it (`boundaries.test.ts`).

What this protects is corrallm running a repository's programs itself. A worktree is checkout isolation, not a sandbox: agents run their own commands in it, and a process already running as the user can change a repository's configuration whenever it likes.

## Repository discovery

`src/main/core/workspaces/discovery.ts` (`discoverRepository`) takes the picked folder, a TrustedPath, and finds the checkout it is: its real top level, its own and common Git directories, the repository's identity (its common directory's inode, so one deleted and cloned again at the same path is another), its HEAD (branch ref, or none when detached, and commit) and the filter drivers configured in it. It refuses, saying why in a sentence for the person:

- a folder inside a repository (`subdirectory`, naming the top level to choose instead): never widened to the whole repository;
- a checkout that is really somewhere else (`redirected`): a `.git` symlink, a `.git` file naming another repository, a linked worktree whose registration's back-pointer doesn't name it, `core.worktree`, a top level elsewhere, or a folder Git hasn't registered as a checkout;
- configuration the runner can't neutralize (`config`), a `.git` Git can't read or a path with control characters (`unsupported`), a repository with no commit (`no-commit`: "Make the repository's first commit, then retry."), a missing or unreadable folder, and Git missing, too old or failing.

Only Git's own "not a git repository", with no `.git` there at all, is a folder that isn't one (`not-git`), whose agents share it as before. A picked linked worktree is supported: it, not the main checkout, is the base. `recordRepository` keeps what was found in the `repository` table, within a write, by real path and identity: one kept already is found again (its picked path and common directory as they are now), its workspaces' folder never moved; a new one gets this profile's folder inside its checkout.

## The owned root

`src/main/core/workspaces/owned.ts`. A repository's checkouts go in `<checkout>/.corral/worktrees/<profile-id>/`, each named by its workspace's id. `ensureOwnedRoot` makes it if it is missing and verifies it before anything is written in it; `verifyOwnedRoot` only verifies. Every folder from the checkout's real path down must be a real folder (a symlink anywhere, which a repository could commit, is refused, and nothing is written where it leads), the user's, and the last one private (0700), marked by the core. The marker is kept in the repository's common Git directory (`corrallm/owned-root-<hash of the root's path>.json`, 0600, never through a symlink), not in the checkout, where a `git clean -fdx` would take it while Git spares the checkouts themselves; it names the repository record, the root's path, device, inode and nanosecond creation time, so a replacement with a reused inode isn't taken for it. A filesystem without a positive creation time cannot establish ownership. An older marker that records only the inode cannot verify a nonempty root and is refused rather than upgraded from an unverified folder. One the core didn't mark is refused, never adopted, unless it is empty (just made, or a crash between making it and marking it). A root outside the checkout is refused.

`excludeOwnedRoot` adds `/.corral/worktrees/` to the repository's local `info/exclude`, in its common directory, once, keeping what it holds: never the tracked `.gitignore`, never through a symlink, never a file it can't read whole (over 1 MiB). The checkout's status, `git add -A` and its agents then never take the workspaces for its files, nor add them as embedded repositories. The non-Git walk of `src/main/files.ts` skips `.corral` too.

## Git's metadata

`src/main/core/workspaces/metadata.ts` (`verifyGitMetadata`). What a workspace's Git writes in the repository's common Git directory is verified as the owned root is: the common directory at its real path, every folder Git writes in (or makes a folder in) a real folder of the user's, every file it writes a real file of the user's, and no link anywhere along them. A creation checks it before anything is written (before the owned root is made, so a refused one writes nothing at all), a removal before anything is removed, and both again just before and just after each of Git's writes. A link present at either check fails the job; these checks do not contain a process running as the user that swaps a link in and out within the write. What is checked is everything Git writes there for a workspace, as traced with the files and reftable ref backends, packed refs and relative worktree paths:

- its branch, made or deleted (`update-ref`): its loose ref below `refs/` (`refs/heads/corrallm/<profile-id>/<workspace-id>`, each folder of it), its reflog by the same path below `logs/` (appended in place, so it must have no other name either), `packed-refs` (rewritten when a packed branch is deleted, through a link if it is one) and, in a repository keeping its refs in reftable, `reftable/`, where its tables are written;
- its registration (`worktree add`, population's index, `worktree remove`): `worktrees/`, and the registration's folder in it.

No object is written for a workspace (no fetch, gc or maintenance; no filter, so no LFS), and no configuration (worktree paths are absolute). B9b's merges write more: `verifyMergeWrites` (`MergeWrites`) checks it the same way, for the merge service to call before each of a merge's writes and after it, a failed one too. Preparing a merge writes objects only (its trees, a conflict's blobs, its commits, a checkpoint's blobs): loose ones, and a pack in `objects/pack/` for a file a checkpoint adds past `core.bigFileThreshold`, so `objects/`, every fan-out folder in it and `objects/pack/` must be real folders of the user's, with no link along them (a symlinked object store refuses with `symlinked`); alternates are stores Git only reads, never checked. The install writes the destination checkout's own `index` and `ORIG_HEAD` (each replaced whole) and `logs/HEAD` (appended, so one name only), in the common directory for a main checkout or in its registration's folder (`worktrees/<name>`, which must be one) for a linked one, whose main checkout it leaves alone, and its branch's loose ref and reflog in the common directory; in a reftable repository, the tables in `reftable/` instead. A checkpoint writes the generated branch's ref and log and the agent checkout's `logs/HEAD` and index. These were traced from what Git writes (`merge-writes.test.ts`), not inferred; a checkout's files are written by Git's own checkout, which writes through no link in a leading path. A file where Git would make a folder (a reftable repository's `refs/heads` stub) stops Git, so nothing past it is written. What fails the check fails a creation with `git-metadata-<fault>` (`symlinked`, `not-folder`, `not-file`, `linked`, `unowned`, `missing`, `unreadable`) and leaves a removal `removing` with `cleanup-git-metadata-<fault>`, stopping further writes. A Git write that fails is checked the same way before it is classified: Git may fail on a link before the check after the write runs, and the code then names the link (`git-metadata-<fault>`, `cleanup-git-metadata-<fault>`), else `git-failed` / `cleanup-failed`. The core's own writes there, the owned root's marker and `info/exclude`, are checked where they are made (above).

## Provisioning

`src/main/core/workspaces/provision.ts` (`Provisioner`, B9a Design §3's protocol). createCore composes it with one runner and provisioning queue for the app and serve; the directory resolver below allocates on demand.

- **Intent first.** `intend`, synchronous and within a write (its own, or a document commit's), returns the owner's workspace in use if there is one; otherwise it records the workspace `creating`, its generated checkout path (`<owned root>/<workspace id>`) and branch (`refs/heads/corrallm/<profile id>/<workspace id>`), its base, and a `create` job at phase `recorded`. The base is read before the write (`base`): the picked checkout's HEAD (its commit, and branch or none; never its uncommitted edits), or, for a fork, the committed HEAD of the workspace it forks (its verified checkout's commit and the branch checked out there, never its uncommitted files; one never made, still `creating` or whose creation failed, is at the base it was to be made from, with no Git run), recorded with `forked_from`. A fork whose source can't be read is refused (`fork`), recording nothing: an unknown HEAD is never taken for the project's. The job's payload is its immutable intent (canvas, repository, path, branch, base, fork, attempt) and its id is made from the workspace and attempt, so recording the same intent again is the same job (`WorkspaceStore.recordJob`'s intent hash), never a second one. No Git runs and no file is touched in that write.
- **Phases outside SQL.** `run` takes the job to its repository's lane of the queue (below). Its phases, each marked on disk once done (`CREATE_PHASES`): `branch`, the ref made at the base commit with `update-ref`'s empty old value, so only if it doesn't exist; `registered`, `git worktree add --no-checkout` of that branch at the path; `populated`, the files read from the base commit's tree into a checkout holding nothing but its `.git` (`read-tree -m -u --no-recurse-submodules`: a merge, not a reset, so Git writes over no file it finds there). Before any of it the repository is discovered again and must be the one recorded (real path, common directory, the identity the job expects), and the owned root is made or verified and excluded; before a phase runs, what Git and the file system have is read again, so a phase done but not recorded is adopted rather than done twice. Before population, Git's configuration is inspected again in the new checkout (conditional includes on its branch and folder apply only there) and the checkout must verify as below, on its branch, at its base.
- **Ready for setup.** Verified again, the job ends `done` and the workspace moves to `setup` in one write: its local files and setup follow (Setup, below), and agents wait until the workspace is `ready`. A failure the job can name (Git's, the owned root's, a check's) ends it `failed` and the workspace `error` with a code (`config`, `branch-moved`, `unregistered-checkout`, `interrupted-registration`, `checkout-changed`, `repository-changed`, `owned-root-<fault>`, `git-<fault>`, ...); one it can't (the core closing, the store failing) leaves the job open for the next start.
- **Never over what it didn't make.** A branch already at another commit, a folder with files at the path, a registration on another branch, or one Git left locked part way through adding it fails the job, its contents untouched. Nothing here forces, resets, removes or prunes a checkout or branch: removal is cleanup's (C7).
- **Reuse.** `provision` returns the owner's workspace in use, or makes one; concurrent asks for an owner share one allocation (ten simultaneous starts run one set of Git commands), and runs and retries are shared the same way.
- **The queue.** `src/main/core/workspaces/queue.ts` (`ProvisioningQueue`): one lane per repository, keyed by its common Git directory and shared by every canvas (B9b's merges are to share it), at most 2 repositories at work at once, at most 64 jobs waiting or running. Past that, `provision` refuses (`busy`) before recording anything. Its work never waits for a person or an agent's turn.
- **Restart.** `reconcile`, after child recovery: every open create job runs again from what is on disk (a crash before or after the branch, after registration or after population is recorded all finish to one checkout, no step done twice), then every `setup` or `ready` workspace's checkout is checked, so one removed while the core was stopped is `missing` before it is asked for.
- **A population not marked is never redone over.** A checkout found populated whose population the job didn't mark may have been changed while the core was stopped, by you or anything running as you. It is adopted, writing nothing, only if it is exactly what Git wrote: Git's index whole (no `index.lock` beside it) and the base commit's tree, no entry of it marked skip-worktree or assume-unchanged, every file as the index has it (compared by content wherever its stat differs, with `core.checkStat=default`, `core.trustctime=true` and `core.ignoreStat=false` whatever the repository says), nothing else there (`ls-files --others`, ignored files included), and each submodule's folder empty, as population leaves it. This proof trusts Git’s index as the user’s processes leave it. Anything else, or anything Git can't read there, is held for you: the job fails and the workspace is `error` with `interrupted-population`, its files as they are. A restart never populates it again, nor does your retry, which looks again (and adopts it once it is exactly what Git wrote). Population runs only into a checkout holding nothing but its `.git`.
- **Lost and found.** `checkout` checks a `setup` or `ready` workspace each time its path is asked for: a folder gone is `missing` (`checkout-missing`, or `repository-missing`), one changed is `error`; a folder that goes while Git is being asked about it is `missing` too, whatever Git said of it; a check Git couldn't make holds without recording anything (unknown, not safe). `retry` runs a failed creation again as a new attempt of the same intent, from what Git has; a workspace made once, then lost and found again as it was made, goes back to `setup` (or `ready` once its setup was done or skipped) at a new generation, so what ran in it before is stale. One gone for good stays `missing`: retry never makes a checkout over its branch. `startRetry` is the same retry answered once it is recorded (the workspace then, and `done`, what it ends with), for `worktree.retry`; asked again while it goes on, it is the same one.

## The document seam

`src/main/core/workspaces/planner.ts` (`WorkspacePlanner`, B9a Design §3's grouping, ungrouping and project changes) is composed in createCore as the Documents participant every commit goes through, whatever made it: an op's change (a doc op, `canvas.batch`), a file review's Apply and a discard's revert, so no path changes who works where without it. It is inert for a canvas with no workspace records; discovery records the picked repository before provisioning its first workspace.

- **Planning is pure** (`workspacePlan`, over shared/model/workspaces.ts' `bindingPlan`): each outermost group's or lone agent's tree chosen from the records as the commit's write finds them and the document before and after (with spawnAgent's copies).
- **A new member joins at once.** An agent with no workspace that joins a component with one is bound to it (`bind`), at a generation of its own; a component with none yet gets one on demand, by provisioning: from the project's HEAD (an independent add), or forked from where a member moving to it works when it is made (a split whose member waits for your Switch: the resolver's `forkSource`, so the new tree branches from the former group's commit then, the work that member did meanwhile included). No Git runs in a commit's write.
- **A fork only the commit knows is recorded in it.** A component whose plan forks a workspace (shared/model/workspaces.ts' `create.source`) and none of whose members works elsewhere (a spawn outside a shared group, copying an agent with a tree: spawnAgent's copies; members moved out of a tree still being made) gets its tree in the commit (`make`): its base read in the preflight (Provisioner's `base`: the source's committed HEAD), then, within the write, Provisioner's `intend` records the workspace `creating` at that base with `forked_from` and its job's intent, and binds its members to it, so a crash before the job runs loses nothing (the next core's `reconcile` makes it at the recorded base). Once the write is on disk it is made as a start's tree is (`made`, in the background: createCore composes the resolver's `provision`, which runs its job and then offers its setup); a refused or failed commit records none of it, and a retried one records it once. Without provisioning composed (a document's tests), such members get theirs on demand, as before.
- **A materialized agent's move waits for you.** One whose tree would change while that tree is made (any state past `creating`: an agent may have worked there) keeps its active binding, generation and session; its change is recorded (`plan`: the owner it is to move to, at a desired generation past its active one), so the resolver holds its new starts and sends (`pending-change`). Moving it back clears the change. One whose tree is still `creating` moves at once (nothing ran there). The Switch that installs a waiting change is the reply router's (Workspace changes, below).
- **Owners, not checkouts, follow membership.** A lone agent's tree becomes its group's as it gains members (`setOwner`), and back, keeping path, branch and every binding's generation.
- **Nothing is removed unseen.** A removed agent is unbound; a tree no agent is bound to any more (or whose owner left the document) is retained, its work and branch kept, unless what was decided of it removes it (Cleanup and retention, below): `within(commit, removals)` marks such a tree `removing` with its job in the same write instead, and `removed` runs its removal once the write is on disk.
- **The loss preflight** (`preflight`), before every commit's point of no return (before an op's checks, before Apply's and a revert's write): the plan over the records as they are, refused while a tree it changes is being restored (the mutation gate, below) or while the committed HEAD a tree it forks can't be read (`unavailable`), the base of each tree it forks (`forks`, which Documents carries into the write: a plan that changed since fails the write, keeping nothing), and what it keeps and holds (`Losses`: trees retained, moves pending, agents removed, and, with the cleanup composed, what each tree it leaves with no agent holds now, `trees`), which the commit's check decides on (Cleanup and retention, below).
- **One write.** Within the commit's write (`within`), after its rows, the plan is made again and applied, so the document and who works where are on disk together or not at all, across a crash too; a failure fails the commit (CommitFailed), keeping neither.
- **A project change** (`projectChosen`, from `project.choose` once the pick is another, before its sessions end): every tree in use retained, its agents unbound (their waiting changes with them), and the canvas's project generation moved on to the new pick's repository (none known yet: none). A missing old repository forgets nothing; cancel changes nothing.

## Cleanup and retention

`src/main/core/workspaces/cleanup.ts` (`WorkspaceCleanup`, B9a Design §3's "Deletion and retention", C7): what becomes of a tree no agent works in any more.

- **What it holds** (`assess`): read in its verified checkout, as Git says now (configuration inspected and its filter drivers disabled first): its HEAD and its generated branch's tip, its changed and untracked files (counted, the first 20 named), whether its HEAD and tip are both reachable from the picked checkout's HEAD now (merged: equal to its base commit alone is no proof), the agents whose sessions may still write there (the session manager's `writingIn`) and whether its setup runs. What Git couldn't read safely, including warnings from status or failed filesystem reads, or a checkout gone, is unknown: never safe and never eligible for Discard. For a tree read whole, its `fingerprint` changes whenever any of it does: its status is hashed with each file it names as the file system has it (inode, size, mode, modification and change times, read without following a link), so a changed file written again changes it though Git prints the same status.
- **No repository program runs to assess it.** A submodule is read by its commit only (`status --ignore-submodules=dirty`): whether one is dirty Git asks a git run in it, under the submodule's own configuration, whose filters nothing here reaches, so none is asked. A submodule checked out in the tree (a gitlink of its index whose folder isn't empty, or isn't a real folder below real folders) may hold work no status says: the tree is never safe with one (`unknown` names it, so its deletion offers keeping its work only), and its folder, with the Git directory its `.git` file names, is read entry by entry into the fingerprint, as is a repository nested in the tree, which status names whole. At most 20,000 entries are read in all; past that the tree is unknown too. An unknown tree cannot be checked for staleness, so its card says corrallm keeps it and asks you to remove it yourself if you mean to.
- **Safe** (`safe`) is clean, merged, with no writer and no setup running: such a tree goes with its last agent, its branch with it, without asking.
- **Otherwise you decide.** The planner's preflight assesses each tree a commit would leave with no agent; the committer (canvas/commit.ts) then decides: as you decided on a confirmation (`CleanupDecision`, Allow's, bound to each tree's fingerprint when you were asked: a conflict, settled stale, if any holds anything else now), else safe ones removed and, if any isn't safe, the change applies nothing and becomes a proposal for you, yours too (a delete of yours: "Delete Builder? Its worktree holds work."), a token's R4 proposal carrying the same words of what each tree holds. For trees read whole, its choices are Delete, keep its work (Allow: the tree retained, in Kept worktrees), Delete, and discard its worktree and branch, and Cancel (Refuse). If any tree is unknown, Discard is absent: Delete keeps its work, or you can Cancel. A Discard against a tree now unknown is refused, even if the question offered it earlier. A file's Apply and a discard's revert keep what they leave unless it is safe (`safeRemovals`): nothing more is asked of them.
- **Removing** (`intend`, within the deciding write: a commit's, a kept tree's Remove): the workspace `removing`, with a `remove` job recording the decision (its branch too, forced or not, the fingerprint approved, the tip decided). Then (`remove`, in its repository's lane of the provisioning queue): its writers waited for (at most 10 s, else left `removing` with `cleanup-writing`), assessed again, and kept (`retained`) unless still what was decided (safe, or what it held as you approved: `heldFingerprint`, its fingerprint without its writers and setup, which it has just waited to stop, so a discard you chose while the deleted agent's session ran there removes it once that session ends having written nothing): an unknown tree is retained even when an older Discard was recorded, and work added meanwhile is never destroyed. Git's metadata it writes through is verified first, and again before and after each of Git's writes (Git's metadata, above). Its checkout is verified as the one made (`checkCheckout`), then removed by `git worktree remove` (with `--force` only for a discard you approved), every filter driver the picked checkout's configuration and the checkout's own give it disabled (conditional includes on its branch or folder included) for the status Git runs there first, which a submodule checked out there makes Git refuse before running anything; one gone is skipped; one that isn't the checkout made is left, `cleanup-<fault>`. Its branch is deleted only at the tip decided (`update-ref -d` with that old value: one moved since is kept), and never while a checkout of the repository (the picked one, another worktree; not one whose folder is gone) has it checked out, which would be left on no branch. Its setup's log and copy record are removed (`forgetSetup`), then its job finished and its record forgotten, in one write. A failure leaves it `removing` with its error code, tried again as the core starts (`reconcile`, in the background) or when you remove it again; `close` lets what goes on finish before the process owner closes.
- **Kept trees** (`kept`): every retained or removing workspace (of a canvas, if given), with its owner, its owner's name (as the canvas names it now, else as it last did: a deleted agent's, from the canvas's kept changes), branch, base, state and error: the way back to work no agent reaches. `removeKept` is its Remove (`worktree.remove`, registered, yours alone): removed at once if safe; holding work that was read whole, a proposal for you (Remove it and its branch, or Cancel), whose Discard removes it as it was when asked. An unknown tree offers only Keep it (Refuse), with the reason it cannot be checked for staleness; no removal is recorded.
- **A canvas that owns a workspace record**, in any state, is never forgotten (canvas memory, `forget` and eviction): a draft discarded keeps its document and records until its last workspace record goes.

## Workspace changes

`src/main/core/workspaces/rebind.ts` (`WorkspaceChanges`, C7): the change the planner leaves waiting (a materialized agent moved into, or out of, a group) is one card in Needs per destination owner (`rebind/<owner>/<generation>`, kind `worktree`, the latest desired generation of its members), naming no agent, so no token's Needs holds it nor can a token name it, yours alone. Switch (`switch`, the reply router's) rechecks the plan (an earlier generation's card is a conflict), makes its destination if it has none yet (provisioning, given), then under the mutation gate (`drain`: refused while any agent of the old trees or the destination may be writing, new work for every one of them held meanwhile) checks the plan again, ends each member's session (`SessionStore.close`: its next turn starts where it works then), installs each member's binding to the destination at the generation the card showed, and retains each tree no agent works in any more. Who decided is recorded (`src/main/core/decisions.ts`). Not now is to leave it: moving the agents back drops the change.

## The mutation gate

`src/main/core/workspaces/gate.ts` (`WorkspaceGate`): what changes the files of a working tree under every agent working in it (a code rewind's restore; B9b's merge and a rebind's Switch are to use it) runs there, one at a time per tree (a workspace, or the shared project folder). Its members are the agents whose session runs in it or whose working directory is it, on every canvas the core runs (two canvases may pick one folder; a refusal names another canvas's agent only as "an agent on another canvas"). It refuses (unavailable, so an Allow stays open) while any member may be writing: a turn going on, background tasks, or a session whose bounded close didn't finish (the session manager's `closing`). While it runs, new work for its members waits (the manager's `send` and launch `pass` it; `availability` says `mutating`): a send to the agent whose own session restores waits too, and only that agent's launch goes past it (its composite reopens it, and awaits its session). It never interrupts work, releases a hold or waits for a person. `drain` does the same for whole trees (a workspace change's Switch): refused while any agent of them may be writing, every one of their agents' new work held while it runs, none exempt.

## Local files

`src/main/core/workspaces/copy.ts` (`copyLocalFiles`, B9a Design §4's copy rules) copies the picked checkout's local files into a new workspace's verified checkout, before its setup is offered and before any agent runs there. What it copies is what the repository-root `.worktreeinclude` committed at the workspace's base commit selects (Git's ignore rules; never the picked checkout's own uncommitted copy, never one a token could hand it), and only files Git ignores in the picked checkout: no file, nothing copied, and no `.env` taken by default.

- Selected by Git: `ls-files --others --ignored --exclude-from=<the manifest>` lists what it matches (NUL-separated, no shell glob), the checkout's own ignore rules are asked of the same files by literal name, and X8's `selectCopyFiles` takes the files both select, under `COPY_LIMITS` (the manifest 64 KiB, 256 files, 16 MiB each, 64 MiB in all). A manifest that is a symlink or not text, one over its size, or a listing past 4,096 files or Git's output bound refuses the copy. The workspaces' own folder (`.corral/worktrees/`), `.git` and the profile's folder are never copied from.
- Never through a symlink, on either side: every folder from the picked checkout to a file, and from the workspace's checkout to its copy, must be a real folder, the file a regular one with just one hard link (a folder that is a repository of its own is refused too), opened without following a link and checked to be the very file listed (device, inode, link count and size, nothing read past it). Both roots are checked again at use, since the asynchronous listing can outlive the checkout's verification. The excluded profile is compared by its real path, including when it was opened through an alias. Multiple links are refused because another name could be outside the picked checkout. Reads are nonblocking, so a file exchanged for a FIFO cannot hang the core before the descriptor is checked.
- Never over anything: a file the workspace tracks, including a name differing only by case, is never copied over (`tracked`), nor one that is there with other bytes (`exists`); one there already with the same bytes (a crash's copy) is adopted only if it too is private and has just one hard link. Its opened descriptor must still identify the file checked.
- All or nothing: the limits and every safety check are applied before anything is written, and a failure part way takes back what that attempt wrote, including the current partial or published file when its own flush or its directory's flush fails. Copies are private (0600, 0700 for one its owner may run), each written whole beside its place, synced, then linked there (a link fails if anything is there).

What was copied is recorded by name, size and SHA-256 only (`CopyRecord`; its hash is the setup's `copy_manifest_hash`), never what the files hold, in a private file of the profile's (`<profile>/workspaces/setup/copies/<workspace>.json`, written whole once everything is copied), so a restart never copies again over a workspace's modified files. A copy refused leaves the workspace in `error` with `copy-<fault>` (`symlink`, `tracked`, `exists`, `file-bytes`, `file-count`, `manifest`, ...); retrying it (Provisioner's `retry`) brings it back to `setup`, to copy again.

## Registry and wire state

The worktree operations (`src/main/core/ops/worktree.ts`; see [Operations and topics](registry.md)) read and act through these services, never a raw record or a caller's path: Both `worktrees:<c>` and `needs:<c>` keep canonical revisions without subscribers. Document commits and project changes publish workspace cards even without a core runtime; their writes name both topics for receipts, including a discard or replacement reverting the old canvas.

- **Who works where** (`src/main/core/workspaces/list.ts`, `listWorktrees`: `worktree.list` and its `worktrees:<c>` topic): one item per agent of the canvas's document now, from the bindings, trees, setup records and kept trees, and from what the resolver knows in memory of an owner with no tree yet (`provisioning`: its provisioning going on, its failure, and what discovery found of the picked folder). It never allocates, asks Git or verifies: a tree is said as its record is (`creating`, `setup`, `ready`, `missing`, `error`), a binding with a change waiting as `pending-change` (still its old tree, with the Switch card's id), an agent with no tree as `unmade` (or `creating`, or `error` with why, as the resolver has it), the shared project folder as `shared-folder`, and no folder as `no-project`. For your listing of a kept canvas not opened in this core, its picked folder comes from canvas memory, without restoring or checking it; an unrestored pick is not no project, and a listing never admits a session to that path. Its mode (`own`, `group`) and group are the active tree's owner's. You see every agent, where each checkout is, its setup (command, source, state, exit code), the card on it and why it failed, and the kept trees (`kept`, with where each is). A token sees only the agents it reaches now, without any of that, and no kept tree; each item is one agent's, so a shared tree names no member it doesn't reach, and its group node only where canvas.get shows the node to it. A binding whose agent has left the document isn't listed. `sharing(listing, agent)` is the shared-member rule over a listing (the agent, then those sharing its tree that the listing names): what an agent's workspace context (B9a X13) is to read its members and their branches through, with the same viewer, rather than read bindings.
- **Retry** (`WorkspaceDirectories.retry`: `worktree.retry`, yours alone): an agent's bound tree in `creating`, `error` or `missing` is retried through Provisioner's `startRetry` (`retry`, split: it resolves once the retry is recorded, a failed creation's new attempt `creating` on disk or a lost one found again as made, and runs its Git work on, so a canvas-scoped op never waits minutes for a checkout); once it is ready for setup, its setup is offered (its card; what runs is still yours to allow, unless you allowed that exact command always). A tree in `setup` is offered its card again if it has none, never run: a failed or interrupted setup keeps its card's Retry. A ready tree is left as it is. A change waiting for your Switch is never switched; its old tree may be recovered. An agent with no tree has its owner's recorded failure forgotten and its project found again (discovery is redone), then is made one in the background as its next start would be; a folder that isn't a repository makes none. The core closing waits for a retry's work, and offers no setup then.
- **Workspace-safety** (RULES' `workspace-safety`, B9a §7), on every change to a canvas's document whoever makes it and whatever builds it: the planner checks each commit's plan (`unsafeStep`, in the preflight and again in the write, failing closed) so no step binds an agent working in a tree (one past `creating`) to another, makes it a new one, or unbinds it while it stays on the canvas; its move waits for your Switch instead. The committer's `workspaceSafety` decides the trees a change leaves with no agent (removed if safe, else the change is a proposal for you, yours too, or refused by an op that can't ask); a file's Apply and a revert keep them instead. A plan has no setup step: no document change runs, approves or changes a setup, so a token's new member joins a tree waiting for setup still waiting.

## Setup

`src/main/core/workspaces/setup.ts` (`WorkspaceSetups`, B9a Design §4 and its frozen review, §14 items 2 and 3) offers each new workspace's setup once its local files are copied (`prepare`, shared while it goes on; `reconcile` for every workspace in `setup` not yet offered), as one card in Needs you for the workspace, not one per agent:

- **What may run** is fixed by the core: the command you set for the picked repository (`project.setSetupCommand`, kept in `project_setup`: one line, at most 4 KiB, no control or format character nor line separator, run as `/bin/sh -c <command>`, its shell kind posix or windows); else the fixed table's for the base commit's root lockfile (`SUGGESTED_COMMANDS`: `pnpm install --frozen-lockfile`, `npm ci`, an argument list run without a shell, the executable found only in the agents' PATH's absolute folders); else none, which only Skip answers. Lockfiles are read at the base commit, as regular blobs; nothing a repository holds (package.json's scripts, its `packageManager`, a manifest, another tool's setup file) becomes a command. What runs is hashed (`specHash`: the form, then the command or the executable and its arguments) into the offer.
- **The card** (`items`, kind `worktree`, `setup/<workspace>/<generation>`, `for` and `by` you, every choice `humanOnly`) shows the exact command, where it runs (the checkout and its branch), where it came from, the copied files' names, and that installing dependencies can run scripts and use the network; once it ran, the last 20 lines (at most 2,000 characters) of its output, with escape sequences, control and invisible characters removed. It names no agent, so no token's view of Needs holds it and no token can name it (reach); a token sees only that its agent waits (`worktree.list`'s state `setup`, without the command, the card or where it runs).
- **Answers** (`reply`): only yours (the service refuses any other party too), only at the generation the card names: an offer moves to the next generation whenever what it would run changes, so an answer to a card raised anew is a conflict. Run (and Retry, a new attempt after a failure or interruption) checks again that what may run now hashes to what the card showed, and that the checkout verifies, then writes your approval and the running attempt (`startSetup`) before anything runs, and returns `started`. Always also keeps that spec hash for the repository (`setAlways`): that exact command then runs by itself in the repository's later new workspaces, approved by you, never a re-offered one, until you clear it (`project.clearSetupApproval`, yours alone: D9, `permissions`; one running goes on, each new workspace asks again). Skip settles it and the workspace is `ready`. Stop ends the command's whole process group, then the card offers Retry or Skip.
- **A changed command** (`setCommand`): the store clears Always whenever the command or its shell kind changes, and every setup still waiting (pending, failed, interrupted) of that repository's workspaces, on any canvas, is offered again with it, raising a new card; one running, done or skipped is left as it is.

`src/main/core/workspaces/setup-run.ts` (`SetupProcess`) runs one: through `spawnOwned` (sessions/process.ts), refused without the core's process owner, so it is a child of `core/children.ts` (recorded before it runs, in a process group of its own), with the agents' environment, no input, in the verified checkout. Closing stdout and stderr does not prove its descendants ended: completion starts group cleanup before the owner's close listener releases the recovery record, and waits for that cleanup before reporting an exit. Stop and shutdown are checked again after preparing its environment and at the actual spawn boundary, including while its private log is being opened, so a cancelled preparation runs nothing. Its output goes to a private log (`<profile>/workspaces/setup/logs/<log key>.log`, 0600 in 0700 folders, made anew without following a link): its first 1 MiB, then a line saying how much was left out and its last 64 KiB, measured in bytes even for multibyte text; only the latest attempt's log of a workspace is kept. At most 2 run at once on a profile (others wait, approved and recorded); each is ended after 30 minutes. A descendant that leaves the group (`setsid`, a daemon detaching itself) is beyond it, as it is beyond the core's other children. Exit 0 is `done` and the workspace `ready`; anything else `failed`, with its exit code (none if it was stopped, timed out or couldn't start), held until Retry or Skip.

The core closing (`close`, before the process owner's) ends what runs and marks it `interrupted` (`interruptSetup`); a crash's is marked so as the next core starts (`recover`, after `Children.recover` has ended the groups the crashed core recorded). An interrupted setup never runs again by itself, Always or not: whether it did what it does is unknown, so its card asks Retry or Skip.

Run/Always/Retry and Skip pass the reply's no-return boundary into the store lane: a cancelled call cannot write approval or settle a card while waiting for verification or another write. Once that write begins, cancellation cannot turn it into an apparently refused approval. The checkout is verified after the environment read, and its directory identity and canonical path are checked across opening the log, immediately before spawn; a directory exchanged during either preparation is refused.

**Windows** can't yet end a setup command's whole process tree (`Children` ends only its leader there), so no setup runs on Windows: its card offers only Skip and says why, Run and Always are refused (`unavailable`), and Always never starts one. This stays a release blocker under the held Windows work.

Switch reads the old committed tips before making a destination and again under the mutation gate, before closing any session or replacing a binding. A fork that no longer starts at its source's committed tip (including one left by a refused, retried Switch), a changed membership, project generation or destination supersedes the old card: the unused destination is retained, the desired plan gets a new generation, and nothing switches. Answering the replacement card forks the current source. A lost source is never replaced by the project's HEAD: Switch refuses, its card says the previous worktree is missing, and Not now leaves new work held.

**Composition.** createCore constructs WorkspaceStore, WorkspaceGit, ProvisioningQueue, Provisioner, WorkspaceDirectories, WorkspaceSetups and WorkspaceCleanup once, for both the app and serve. The profile id is kept by `profileId`; Git uses the agents' environment and the core's process owner, with the private hooks folder under the profile. The document participant and mutation gate share these stores and services. The gate includes all native sessions, protecting their received turn and background-task activity before their asynchronous events reach the core engine. A native binding whose close has not finished remains a member until its process actually ends. Rebind cards are published for these canvases as well as canvases whose runtime the core has opened. `CoreConfig.setups`, `cleanup` and `directoryResolver` remain test overrides only: no production host supplies them. Non-workspace core fixtures use `test-directories.ts` to fake the directory seam; the composition tests use real throwaway Git repositories and fake connectors.

`src/main/core/workspaces/directories.ts` resolves the picked root's repository, keeps its canvas/repository link and allocates one workspace per owner on demand. Initial bindings are written with the provisioning intent (`provision`'s `within` callback), before Git runs, so membership changes and restart see the creating workspace. A tree it makes forks its plan's source (planner.ts' `forkSource`: where a member moving to it works now, as at a split's Switch), else the project's HEAD. An agent bound to a tree still `creating` (a commit's fork) has that tree's open job run, or joined, as it is asked for, in case nothing runs it yet; a refused run says nothing, so no listener loops on it. Concurrent starts share that work. Setup preparation follows population; only a verified ready checkout becomes a working directory. A pending rebind returns held with the existing Switch card's generation, never the desired binding as ready. A verification crossing an active or desired generation change is refused; the old running session and its events remain intact until Switch. A folder Git identifies as non-Git uses the legacy picked directory; a failed discovery never falls back to it.

Recovery starts after owned-child recovery and setup interruption recovery: unfinished provisioning is reconciled before setup offers are reconciled. It runs in the background, so startup need not wait for a large checkout; new dispatch remains held meanwhile. Closing stops admission of workspace Git phases, closes sessions and setups, ends owned children, waits for outstanding directory work (including resumed creating jobs), and only then closes the database. A refused busy run still publishes no availability event. Interrupted creation keeps its job for the next start. Cleanup reconciles removals in the background too. Setup logs and copy records remain private until cleanup calls `forget` after removing their workspace.

The manager, options, history and file picker consume this one resolver. Contextual reads re-verify the agent's checkout each time; options without an agent still read base/user defaults. Reveal admits the picked root but excludes its `.corral/worktrees` subtree unless the target belongs to a checkout this canvas keeps and Provisioner verifies now. No caller chooses a containment root or mints a path.

## The verified checkout

`src/main/core/workspaces/checkout.ts` is the workspaces' one `TrustedPath` mint site (`src/main/boundaries.test.ts` pins it, and that only `verifiedCheckout` mints, after `checkCheckout`). A path read back from the store is a record; each use checks, as Git and the file system say now, that the repository is the one recorded (its checkout at its real path, its common directory with the identity recorded), that the owned root verifies and the checkout is its folder named by the workspace's id (a real folder, not a symlink, the user's), that its `.git` names a registration in the common directory whose back-pointer names it back, that Git finds it as its own top level with that common directory, and that Git lists it as registered. Only then is its path minted. The trust gate is still the project folder picked: this checkout is that repository's, made by the core in the folder it owns there. The branch checked out there now is reported, not required: an agent may switch branches in its own checkout.

## The profile id

`src/main/core/workspaces/profile.ts` (`profileId`): a UUID naming this profile's branches and its folder in each checkout, so two profiles' workspaces of one repository never meet. Kept in `<profile>/workspaces/profile-id` (0600), beside the database rather than in it, so a restored database keeps it; made once, and one that can't be read is refused, never replaced. The runner's empty hooks folder is meant to be `<profile>/workspaces/hooks`.
